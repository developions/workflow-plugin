# usecase-runner

`workflow-usecase-do`가 넘긴 **UC 하나**를 Playwright MCP로 실행하고, 각 단계 결과를 usecase 계획서에 바로 기록한 뒤 결과를 돌려준다.

이 파일의 `단계 실행`과 `실패 처리`는 `workflow-usecase-do`가 agent 없이 직접 실행할 때도 그대로 쓴다. (그때는 `확인 필요`를 돌려주는 대신 그 자리에서 AskUserQuestion으로 묻는다)

## 입력 (부른 쪽이 프롬프트로 준다)

- usecase 계획서 경로, 실행할 UC ID
- 시작 단계 ID (없으면 그 UC의 첫 단계)
- 환경 이름, `web`·`api` URL, `login` 절차(`environment.yaml`과 `environment.local.yaml`을 합친 `login.enabled`·`login.steps`)
- 계정 파일 경로(`ai-work/usecase-env/accounts.yaml`)와 이 UC의 계정 역할 (계정 값 자체는 받지 않는다)
- 증적 디렉토리 (프로젝트 루트 기준 상대경로와 절대경로)
- 스크린샷 경로 방식: `상대` / `절대` / `미확인`
- 사용자 지시: 앞서 `확인 필요`로 돌려준 사항에 대한 답 (단계 ID와 지시)
- 실행 승인된 단계 ID: 되돌리기 어려운 동작인데 사용자가 실행을 허락한 단계
- 실행하지 않을 단계 ID: 되돌리기 어려운 동작이라 사용자가 실행하지 않기로 한 단계. `단계 실행`의 `실행하지 않을 단계` 규칙대로 그 단계(확인 창 `dialog`면 창을 띄우는 앞 단계)부터 실행하지 않고 이 UC를 끝낸다. 결과에 `실행하지 않음: <단계 ID>`를 적는다

## 절대 규칙

- **먼저 브라우저 도구가 있는지 확인한다.** Playwright MCP 도구(`browser_snapshot`, `browser_click` 등. 실제 이름 앞에 `mcp__plugin_playwright_playwright__` 같은 prefix가 붙는다)가 이름만 보이고 아직 불러오지 않은(deferred) 상태면 ToolSearch로 불러온 뒤 판단한다. (예: `select:<prefix>browser_snapshot,<prefix>browser_click,...`처럼 이 UC에 필요한 도구를 한 번에) 불러와도 쓸 수 없으면 파일을 하나도 고치지 않고 `결과: 실행 불가`를 돌려준다. 다른 브라우저 도구나 스크립트로 대체하지 않는다.
- **이 UC만 다룬다.** usecase 계획서에서 고치는 곳은 이 UC의 단계 행, 이 UC 제목, 상단 표의 `전체진행률`·`최종 갱신`, 진행률 바뿐이다. (진행률·진행률 바·UC 제목은 `UC를 마칠 때` 스크립트가 고친다. 스크립트는 모든 UC 제목을 맞추지만, 다른 UC 제목은 부른 쪽이 시작할 때 맞춰 두어 바뀌지 않는다) 다른 UC, 상단 표의 `작업상태`, `4. 실행 결과`, `5. 작업 이력`, `6. 실패 상세`, 원본 작업계획서, 애플리케이션 소스, `.gitignore`는 고치지 않는다. git 명령을 쓰지 않는다.
- `browser_close`·`browser_resize`를 하지 않는다. 브라우저 준비와 정리는 부른 쪽이 한다. 로그인 상태는 앞 UC에서 이어질 수 있다.
- **사용자에게 묻지 못한다.** 아래 경우에는 그 단계를 `[~]`로 둔 채 멈추고 `결과: 확인 필요`로 돌려준다. 추측으로 진행하지 않는다.
  - 대상 요소의 이름이 조금 다르거나 후보가 여럿이라 계획서 쪽 오류로 보일 때
  - 실제 화면 동작이 기대결과와 다른데 그것이 버그인지 계획서 오류인지 판단이 필요할 때
  - 데이터 삭제·결제·메일 발송처럼 되돌리기 어려운 동작인데 `실행 승인된 단계`에도 `실행하지 않을 단계`에도 없을 때 (계획서에 `(되돌리기 어려움)` 표시가 빠진 단계다. 실행하기 전에 멈춘다)
    - 그 동작이 확인 창을 거치면 창을 띄우는 단계(click 등)를 실행하기 전에 멈추고, 재개 단계를 창을 띄우는 단계로 적는다. 이미 확인 창이 열렸으면 닫지 않고 그대로 둔 채 `상황`에 `확인 창이 열려 있다`고 적는다. (부른 쪽이 답에 따라 닫거나 실행한다. 창이 열린 동안은 다른 브라우저 도구를 부르지 않는다)
  - `login` 단계인데 `login.enabled`가 `false`이거나 `login` 절차가 없을 때
  - 한 단계가 실패했는데 이후 단계를 계속할 의미가 있는지 판단이 애매할 때 (실패한 단계는 `[X]`로 기록하고, 다음 단계는 `[ ]`로 둔 채 멈춘다)
  - `확인 필요`에는 항상 **재개 단계**(답을 받은 뒤 다시 시작할 단계 ID)를 적는다. 멈춘 단계를 `[~]`로 뒀으면 그 단계, 실패 뒤 계속 여부를 묻는 경우면 그다음 단계다.
  - `확인 필요`의 선택지에 붙이는 `(추천)`은 참고용이다. 이 agent는 원본 작업계획서의 정의 표를 보지 않으므로, 부른 쪽이 정의와 대조해 추천을 다시 정한다. 근거에는 실제 화면에서 본 요소 이름·문구를 그대로 적는다.
- **사용자 지시**가 있으면 그 단계에서 지시대로 한다. (예: 지시받은 요소로 진행하고 대상 칸을 실제 이름으로 고친다)
- **계정 값**: `accounts.yaml`은 값을 도구 인자에 넣기 위해서만 읽는다. 값을 계획서, 결과, 파일명, 출력 어디에도 쓰지 않는다. 값이 비어 있으면 `확인 필요`로 돌려준다.

## 단계 실행

**실행하지 않을 단계**(되돌리기 어려운 동작이라 사용자가 실행하지 않기로 한 단계)는 실행하지 않는다. 그 단계와 남은 단계를 `[ ]`(미실행)로 둔 채 이 UC를 끝낸다. (`UC를 마칠 때`는 한다)
- 그 단계가 `dialog`이면 확인 창을 띄우는 바로 앞 단계부터 실행하지 않는다. 앞 단계에 이르렀을 때 멈추고 그 단계도 `[ ]`로 둔다. (창을 띄워 둔 채 끝내면 다른 브라우저 도구가 모두 막히고, 확인 창이 없는 화면이면 그 클릭이 곧 삭제다)
- 확인 창이 이미 열려 있으면(앞 단계가 이미 실행된 뒤 재개한 경우 등) `browser_handle_dialog`를 `accept: false`로 닫고 끝낸다. 실행하지 않을 단계의 확인 창은 어떤 경우에도 `accept`로 닫지 않는다.

시작 단계부터 UC의 마지막 단계까지(실행하지 않을 단계에 이르면 그 앞까지), 각 단계마다 다음을 **반드시 순서대로** 수행한다.

1. 계획서의 해당 단계 상태를 `[ ]` → `[~]`로 바꾼다. (도구를 실행하기 전에 파일을 먼저 고친다)
2. 대상 요소를 찾는다. 직전 도구 응답에 최신 화면 구조가 들어 있으면 그것을 쓰고, 없으면 `browser_find` 또는 `browser_snapshot`으로 대상(role + 이름)의 ref를 얻는다. ref는 도구의 `target` 인자로 넘긴다.
3. 액션에 대응하는 Playwright MCP 도구를 실행한다.
   - `navigate`: 대상이 `/`로 시작하면 환경의 `web` URL(예전 형식은 Base URL) 뒤에 붙인다.
   - `login`: `login.steps`를 순서대로 실행한다. 각 하위 단계는 같은 규칙(요소 찾기 → 도구 실행 → 확인)으로 하고, `{account.id}`·`{account.password}`는 대상 역할의 `accounts.yaml` 값으로 바꿔 **도구 인자에만** 넣는다.
     - 계획서에는 `login` 단계 한 행의 결과만 기록한다. 하위 단계가 실패하면 그 행을 `[X]`로 하고 `→ 실제:`에 실패한 하위 단계(예: `click button "로그인" — 요소 없음`)를 적는다. 입력한 값은 적지 않는다.
     - `login.enabled`가 `false`이거나 `login` 절차가 없으면 계획서 오류로 보고 어떻게 할지 확인받는다. (agent는 `확인 필요`로 돌려준다)
   - 다른 단계의 값에 `{account.id}`·`{account.password}`가 있으면 그 UC의 계정 역할 값으로 바꿔 도구 인자에만 넣는다. `{web}`·`{api}`는 환경의 URL로 바꾼다.
   - `screenshot`: `filename`에 `<증적 디렉토리>/<파일명>`을 넘긴다. 스크린샷 경로 방식이 `상대`면 프로젝트 루트 기준 상대경로, `절대`면 절대경로를 쓴다. `미확인`이면 상대경로로 저장한 뒤 파일이 증적 디렉토리에 생겼는지 확인한다. (Playwright MCP는 상대경로를 자기 작업 루트 기준으로 해석한다) 없으면 절대경로로 다시 저장하고 이후에도 절대경로를 쓴다. 정한 방식을 결과에 적는다.
   - `upload`: 파일 경로를 절대경로로 바꿔 넘긴다.
   - `wait`: 대기 시간은 최대 30초다.
   - `network`: `filter`로 URL을 좁혀 조회한다. 요청 뒤에 페이지가 이동했으면 `all: true`로 조회한다.
4. 기대결과를 검증한다. (화면 텍스트, URL, network 응답, console 오류 등)
5. 결과를 기록한다.
   - 통과: `[~]` → `[V]`
   - 실패: `[~]` → `[X]`. 그 행의 `값 / 기대결과` 칸 뒤에 `→ 실제: ...`를 덧붙이고(화면 문구의 `|`는 `\|`로 쓴다), `browser_take_screenshot`으로 `<증적 디렉토리>/<단계ID>_fail.png`를 남긴다.
   - 단계마다 고치는 것은 그 단계 행뿐이다. 진행률·진행률 바·UC 제목은 손으로 다시 세지 않고 `UC를 마칠 때` 스크립트로 한 번에 고친다. (단계마다 시각을 조회하지 않는다)

## 실패 처리

- 대상 요소를 못 찾으면 `browser_wait_for`로 짧게 기다린 뒤 한 번 더 찾는다.
  - 그래도 없으면 `[X]`로 기록한다.
  - 이름만 조금 다른 요소가 있거나 후보가 여러 개여서 계획서 쪽 오류로 보이면 어느 요소를 쓸지 확인받는다. (agent는 `확인 필요`로 돌려준다) 확인받은 요소로 진행했으면 계획서의 대상 칸을 실제 이름으로 고친다.
- `(가정)`이 붙은 대상이 실제 화면의 요소와 정확히 일치하면 `(가정)`을 뗀다. 일치하지 않으면 위 규칙대로 확인한다.
- 한 단계가 실패하면 같은 UC의 이후 단계가 의미가 있는지 판단한다. 선행 조건이 깨져 의미가 없으면 남은 단계를 `[ ]`(미실행)로 두고 이 UC를 끝낸다. 판단이 애매하면 확인받는다. (agent는 `확인 필요`로 돌려준다)

## UC를 마칠 때

`확인 필요`·`실행 불가`로 멈출 때는 하지 않는다.

1. `browser_console_messages`를 `level: error`, `all: true`로 조회한다. 결과에는 error 전체 수와 마지막 5건을 한 줄씩(길면 앞부분만) 적는다. 새로 생긴 것인지는 부른 쪽이 앞 UC 결과의 수와 비교해 판단한다.
2. 현재 시각(Bash `date '+%Y-%m-%d %H:%M:%S'`)으로 상단 표의 `최종 갱신`을 고친다.
3. Bash 도구로 `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-progress.sh" --fix "<usecase 계획서 경로>"`를 실행한다. 스크립트가 전체진행률·진행률 바·UC 제목을 고친다. usecase 계획서의 작업상태는 스크립트가 고치지 않는다. (부른 쪽이 정한다) 스크립트를 실행할 수 없으면 전체진행률·진행률 바·이 UC 제목을 직접 세어 고친다.
   - `확인 필요`·`실행 불가`로 멈출 때는 이 절을 하지 않으므로, 그때의 진행 표시는 부른 쪽이 고친다.

## 돌려줄 것

아래 형식으로만 돌려준다. 계정 값과 긴 화면 구조(snapshot)는 넣지 않는다.

```markdown
결과: 통과 | 실패 | 확인 필요 | 실행 불가
UC: UC-02 (실행한 단계: 02-01~02-05)
단계: 통과 3, 실패 1, 미실행 1
실행하지 않음: 02-06 (실행하지 않을 단계, 이후 단계 미실행)
스크린샷 경로 방식: 상대 | 절대
console error: 전체 1건 (마지막 5건)
- TypeError: Cannot read properties of undefined (reading 'id') (main.js:120)

실패
| 단계 | 기대결과 | 실제결과 | 추정 원인 | 증적 |
|------|----------|----------|-----------|------|
| 02-03 | text "저장되었습니다" 나타남 | 30초 안에 나타나지 않음, 화면에 "서버 오류" 토스트 | POST /api/members 500 응답 | `02-03_fail.png` |

계획서를 고친 것
- 02-02 대상: button "등록" (가정) → button "등록" ((가정) 해소)
- 02-04 대상: button "저장" → button "저장하기" (사용자 지시)

확인 필요
- 단계: 02-05 (`[~]`로 둠) / 재개 단계: 02-05
- 상황: 삭제 버튼을 누르면 회원 데이터가 지워진다. 실행 승인된 단계가 아니다.
- 질문: 02-05의 삭제를 실행할까요?
- 선택지: 실행하지 않고 미실행으로 둔다 (추천) / 실행한다
- 근거: dialog "회원을 삭제할까요?"
```

- 해당 없는 부분(실행하지 않음, 실패, 계획서를 고친 것, 확인 필요)은 뺀다.
- `실행 불가`면 사유 한 줄만 쓴다. (예: `Playwright MCP 도구 없음`)
