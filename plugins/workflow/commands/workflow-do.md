# workflow-do

`workflow-plan`으로 생성한 작업계획서를 기준으로 **구현(코딩)** 을 진행하고, 항목마다 계획서의 진행 상황을 실시간으로 갱신한다.

## 입력

```
$ARGUMENTS
```

- mention(`@경로`) 또는 경로로 지정된 작업계획서를 대상으로 한다. `@`를 뗀 경로의 파일을 직접 읽는다. (자동 첨부에 기대지 않는다)
  - 그 경로에 파일이 없으면 다른 브랜치에만 있는 계획서일 수 있다. `workflow-plan`이 계획서를 새 작업 브랜치에 커밋하므로, 기본 브랜치로 돌아와 실행하면 이렇게 된다. git 저장소이면 다른 확인보다 먼저 그 경로에 파일이 있는 브랜치를 찾는다. 로컬·원격 브랜치(`git for-each-ref --format='%(refname:short)' refs/heads refs/remotes`)마다 `git cat-file -e <ref>:<경로>`로 확인하고, 로컬 브랜치와 그 원격 추적 브랜치는 하나로 센다. `<원격>/HEAD`(short 이름이 `origin`처럼 원격 이름만 나오는 ref)는 다른 브랜치를 가리키는 별칭이라 뺀다.
    - 찾은 브랜치가 현재 브랜치뿐이면, 로컬 브랜치가 원격보다 뒤처져 계획서가 원격(`<원격>/<현재 브랜치>`)에만 있는 것이다. 전환할 곳이 없으므로 `git pull --ff-only 후 진행 (Recommended)` / `중단`으로 묻는다. 질문 본문에 미커밋 변경이 있으면 그 목록을 적는다. pull이 실패하면(fast-forward 불가, 충돌) 그 내용을 알리고 중단한다.
    - 그 밖이면 찾은 브랜치마다 사본의 상단 표 `작업 브랜치`를 `git show <ref>:<경로>`로 읽고, 어느 브랜치로 전환할지 AskUserQuestion으로 묻는다. 같은 브랜치에 로컬과 원격 사본이 둘 다 있으면 로컬 사본을 읽는다. 질문 본문에 계획서가 현재 브랜치에 없다는 것, 찾은 브랜치와 각 사본의 `작업 브랜치`, 그리고 준비 2번 질문과 같은 미커밋 변경 안내를 적는다. 선택지는 `중단`을 포함해 4개까지다. 넘으면 사본의 `작업 브랜치`와 같은 브랜치는 꼭 넣고, 나머지를 최근 커밋 순으로 고른다.
      - `<브랜치>로 전환`: 찾은 브랜치마다 하나. 사본의 `작업 브랜치`가 그 브랜치와 같은 것에 `(Recommended)`를 붙인다. 그런 브랜치가 없고 찾은 브랜치가 하나면 그 브랜치에 붙인다. (작업 브랜치 이름을 바꾼 경우 등이다. 전환한 뒤 준비 2번 질문에서 작업 브랜치를 맞춘다)
      - `중단`
    - 전환은 로컬에 있으면 `git switch <브랜치>`, 원격에만 있으면 `git switch --track <원격>/<브랜치>`로 한다. 실패하면 준비 2번의 `전환이 실패하면`대로 한다. 전환하면 파일에서 계획서를 읽고 입력 확인부터 이어 간다. 답은 계획서를 고칠 수 있게 된 뒤(준비 2번) `do · 브랜치`로 기록한다.
    - 어느 브랜치에도 없거나 git 저장소가 아니면, 그 사실을 알리고 중단한다.
- 지정이 없으면 `ai-work/plans/` 하위 최신 계획서를 찾아 AskUserQuestion으로 대상이 맞는지 확인한다.
  - git 저장소이면 작업 트리와 함께 로컬·원격 브랜치(`git for-each-ref --format='%(refname:short)' refs/heads refs/remotes`)마다 `git ls-tree -r --name-only <ref> -- ai-work/plans`로도 찾는다. 위 `그 경로에 파일이 없으면`처럼 로컬 브랜치와 그 원격 추적 브랜치는 하나로 세고 `<원격>/HEAD`는 뺀다. 계획서는 작업 브랜치에만 커밋되므로, 다른 브랜치(main 등)에서 실행하면 작업 트리에 없는 경우가 많다. 다른 사람이 push한 작업 브랜치는 원격에만 있기도 하다.
  - 고른 계획서가 작업 트리에 없으면 그 선택지에 계획서가 있는 브랜치를 함께 적는다. (예: `<경로와 제목> — feature/xxx로 전환`) 이때 질문 본문에 미커밋 변경 목록(`git status --short`, 많으면 앞의 5개와 개수)을 적고, 전환하면 충돌이 없는 한 그 변경이 그 브랜치로 따라온다고 적는다. (이 선택이 전환 답을 겸하므로, 따로 하는 브랜치 질문의 안내를 여기서 한다)
    - 그 계획서가 한 브랜치에만 있으면, 이 선택지를 고른 것을 전환 답으로 보고 위 `그 경로에 파일이 없으면`의 브랜치 질문은 하지 않는다. 그 절의 전환 방법대로 전환한다. (같은 답을 두 번 묻지 않는다)
    - 여러 브랜치에 있으면 대상으로 정한 뒤 `그 경로에 파일이 없으면`의 브랜치 질문으로 이어 간다.
    - 답은 계획서를 고칠 수 있게 된 뒤(준비 2번) `do · 대상`으로 기록하고, 전환했으면 `비고`에 `<브랜치>로 전환`을 적는다.
  - 하나도 없으면 `/workflow:workflow-plan`으로 계획서를 먼저 만들라고 알리고 중단한다.
- 진행 범위
  - 항목 ID(`1.2`, `2.1,2.3`)나 `Phase 2`가 주어지면 그 범위만 진행한다. 범위는 계획서 경로 바로 뒤에 오는 항목 ID 목록이나 `Phase N`이고, 그 뒤의 문장은 추가 지시다. (예: `@<계획서> Phase 2 잠금 해제 응답을 200으로` → 범위 `Phase 2`, 추가 지시 `잠금 해제 응답을 200으로`)
  - 없으면 `5. 작업 항목`에서 `[V]`가 아닌 첫 항목부터 끝까지 순서대로 진행한다. (`(병렬 A)` 같은 표시가 붙은 그룹은 2단계의 `병렬 그룹 실행`대로 함께 진행한다. 체크박스가 있는 줄만 대상이다. `6. 완료 기준`은 3단계에서 확인하고, 취소선 줄은 건너뛴다)
  - 범위가 `코드 정리 및 리뷰` Phase인데 앞 Phase가 모두 `[V]`가 아니면, 그 사실을 알리고 중단한다.
  - 그 밖의 범위를 지정했는데 범위보다 앞에 `[V]`가 아닌 작업항목이 있으면, 범위의 항목이 그 항목의 결과(테이블, 함수, API 등)를 쓰는지 계획서(항목 내용, 정의 표의 `연결 API` 등)와 코드로 확인한다. 코드를 보므로 준비 2번(브랜치 확인)을 마친 뒤에 한다.
    - 쓰면 AskUserQuestion으로 묻는다. 질문 본문에 남은 앞 항목과 의존 관계(예: `3.2가 부르는 API 3은 2.3에서 구현`)를 적는다. 선택지는 `앞 항목부터 함께 진행`(범위를 남은 앞 항목까지 넓힌다) / `지정한 범위만 진행` / `중단`이다. 앞 항목 없이는 범위의 테스트·빌드가 통과할 수 없으면 첫 번째를, 소스 대조처럼 범위만으로 검증할 수 있으면 두 번째를 추천한다. 답은 `do · 범위`로 기록한다.
    - 쓰지 않으면 묻지 않고 진행한다.
    - 어느 경우든 남은 앞 항목의 ID를 `do 시작` 행과 완료 보고에 적는다.
- 그 밖의 텍스트는 추가 지시로 반영한다.
  - 추가 지시가 계획서에 없는 작업(예: usecase 실패 수정, 문구 변경)이면 먼저 계획서와 대조해 충돌하는 곳을 찾는다. 대상은 `3. 작업 범위`의 제외 항목, `2. 결정 사항`, `1. 요구사항`의 `현재 동작 → 변경 후 동작` 표, `4. 영향 범위`(파일별 변경 내용 줄과 정의 표 `### DB 변경`·`### API 변경`·`### 화면 변경`), `5. 작업 항목`의 항목 내용, `6. 완료 기준`이다. (예: 정의 표에 `등록되었습니다 (변경 없음)`, DoD에 `등록되었습니다가 보인다`가 있는데 그 문구를 바꾸라는 지시)
  - **업무 파일 반영 지시** — 로드맵 업무 계획서(종료 처리 1번의 `로드맵 갱신` 판정)이고 지시가 업무 파일의 바뀐 내용을 반영하는 것이면(`workflow-roadmap`이 안내하는 지시는 `업무 파일 반영: <요약>`으로 시작한다), 지시의 요약에 기대지 않고 바뀐 내용을 직접 읽는다. 요약은 안내를 만든 시점의 한 줄이라, 그 뒤에 업무 파일이 또 바뀌었거나 요약에서 빠진 변경이 있을 수 있다. 요약에 있는 것만 반영하고 커밋 값을 바꾸면 나머지 변경은 계획서에 들어가지 않은 채 `반영 필요`만 풀린다.
    - 지시가 `업무 파일 반영:`으로 시작하지 않아도(이전 버전 README 규칙 블록의 `/workflow:workflow-do @<계획서> <변경 내용>`대로 실행한 경우), 로드맵 업무 계획서이고 `git log --oneline <계획서의 커밋 값>..HEAD -- <업무 파일>`이 비어 있지 않으면 업무 파일이 바뀐 상태다. 지시가 그 바뀐 내용에 대한 것이면 업무 파일 반영 지시로 다룬다.
    - `### 요구사항 문서` 제목 아래의 `커밋 <해시>`로 `git diff <해시> -- <업무 파일>`을 실행해 전체를 읽고, 이때의 업무 파일 커밋(`git log -1 --format=%h -- <업무 파일>`)을 조회해 둔다. 커밋 표기가 없으면 업무 파일 전체를 계획서와 맞춰 본다. 업무 파일에 미커밋 변경이 있으면 그것까지 읽고 질문 본문에 미커밋이라고 적는다.
    - 바뀐 섹션마다 계획서와 맞춰 고칠 곳을 찾는다. **계획서가 바뀐 내용을 담고 있지 않으면 고칠 곳이다.** 다르게 적혀 있을 때뿐 아니라, 그 사항을 아예 다루지 않을 때도 고칠 곳이다. (예: 공통 결정 "비밀번호는 해시로만 저장"이 더해졌는데 계획서의 결정 사항·정의 표·작업항목·완료 기준 어디에도 비밀번호 저장이 없다) `이미 반영됨`은 그 내용을 담은 계획서의 줄(결정 번호, 정의 표 행, 작업항목·완료 기준 ID)을 짚을 수 있을 때만이고, 짚은 곳을 작업 이력 행에 적는다.
      - `## 요구 항목`: 계획서 `### 요구사항 문서`의 항목과 그 항목을 구현하는 작업항목·정의·완료 기준.
      - `## 이 업무가 기대는 것`·`## 다른 업무에 넘길 것`(공통 결정, 업무 간 약속, 약속에 적힌 이름): 계획서의 정의 표, `4. 영향 범위`의 `(로드맵 약속: …)`, 작업항목, 완료 기준이 바뀐 내용과 맞는지 본다. 다르면 고칠 곳이다. (예: 넘길 값의 이름이 `employeeId`에서 `userId`로 바뀌었는데 계획서는 옛 이름을 쓴다)
      - `## 정하지 않은 것`: 줄이 빠졌으면 로드맵에서 정해진 것이다. 정해진 내용은 같은 diff의 공통 결정·요구 항목에 있으므로 그쪽에서 계획서와 맞춘다. 계획서 `2. 결정 사항`이 같은 사항을 다르게 정했으면 그것도 고칠 곳이다.
      - 업무 번호만 빠지거나 바뀐 줄(다른 업무의 취소·병합 뒷정리)과 결정 번호 표기만 바뀐 줄(`(결정 #n)` → `(로드맵 결정 #n)`)은 계획서에 고칠 곳이 없다.
    - 아래 질문의 본문에 바뀐 내용을 섹션별로 적고, 지시 요약에 없던 변경에는 `(요약에 없음)`을 붙인다. 고칠 곳이 하나도 없으면 묻지 않고 아래 `이미 반영됨`으로 처리한다.
  - 계획서에 반영할지 AskUserQuestion으로 묻는다. 질문 본문에 넣을 위치(또는 고칠 항목)와 충돌하는 곳을 적는다. 답은 `do · 추가 지시`로 기록한다.
    - 고칠 항목: 지시가 바꾸는 동작을 아직 `[ ]`인 작업항목이 구현하기로 되어 있으면(예: 지시는 성공 응답 200, `[ ]`인 2.3은 204 응답 추가) 새 항목을 더하지 않고 그 항목의 내용을 고친다. 새 항목으로 넣으면 앞 항목이 옛 동작을 만들고 곧바로 새 항목이 그것을 고치게 된다. 그 항목이 `[~]`·`[V]`이면 이미 구현을 시작했으므로 새 항목으로 넣는다.
    - 넣을 위치: 같은 계층(DB·서버·화면 등)을 다루는 Phase가 아직 `[V]`가 아니면 그 Phase의 마지막 번호 다음이다. 그런 Phase가 없거나 이미 `[V]`이면 `코드 정리 및 리뷰` 앞에 새 Phase를 둔다. (`진행 관리 규칙`의 새 Phase 규칙)
    - `코드 정리 및 리뷰` Phase에 이미 `[~]`·`[V]`가 있으면 그 Phase의 번호를 밀지 않는다. (이미 커밋 메시지·이력이 그 번호를 가리킨다) 새 Phase는 쓰지 않은 다음 번호(예: Phase 5)로 `코드 정리 및 리뷰` Phase(예: Phase 4) 앞에 둔다. `진행 관리 규칙`이 이 경우 먼저 확인받으라고 하므로, 아래 추가 질문의 `추가` 선택지에 `Phase 5로, Phase 4 앞에 둠 (번호는 밀지 않음)`처럼 적어 함께 묻는다. 계획서에 적힌 순서가 실행 순서라 새 Phase가 먼저 실행된다.
    - 선택지는 `추가`(고칠 항목이 있으면 `<항목 ID> 내용 수정`) / `반영하지 않음`이다. 제외 항목이나 결정 사항과 충돌하지 않으면 앞의 것을 추천한다. (정의 표·완료 기준·작업항목·영향 범위와의 충돌은 지시대로 함께 고치는 곳이라 추천을 막지 않는다) 제외 항목이나 결정 사항과 충돌하면 추천을 붙이지 않는다. 그 지시가 이전 결정을 바꾼다는 것을 본문에 적고(예: `결정 #4 변경`) 사용자가 고르게 한다.
  - 반영하면 계획서 `진행 관리 규칙`대로 새 항목에 번호를 붙이고(내용을 고친 항목은 ID를 그대로 둔다), 충돌하는 곳도 같은 수정에서 함께 고친다.
    - `4. 영향 범위`의 파일별 변경 내용 줄은 바뀐 내용으로 고친다.
    - 정의 표는 해당 skill의 결과 형식으로 고친다. (2단계 3번처럼 skill의 `4. 결과 형식` 섹션만 읽는다) 정의가 새로 생기거나 구조가 바뀌면 절대 규칙의 설계 변경처럼 skill을 인자 `설계`로 부른다. 구조가 바뀐다는 것은 정의 표에 행(테이블·엔드포인트·화면)이 생기거나 빠지는 것이다. 한 행 안의 값·상태 코드·응답 필드·문구만 바뀌면 결과 형식 섹션만 읽어 고친다. 바뀐 값이 그 정의의 `따른 관례`와 다르면(예: 관례는 본문 없는 성공 204, 지시는 200과 본문) 그 행의 비고에 `관례와 다름 — <지시 요약> (결정 #n)`을 적는다.
    - `6. 완료 기준`은 내용을 고치고 ID는 유지한다. 이미 `[V]`인 기준의 내용이 바뀌면 `[ ]`로 되돌린다.
    - `1. 요구사항`은 지시가 이미 있는 코드의 동작을 바꿀 때만 `현재 동작 → 변경 후 동작` 표에 행을 더한다. (아직 구현하지 않은 계획 내용만 바꾸면 더하지 않는다) 요구사항 원문 인용은 고치지 않는다. `3. 작업 범위`의 제외 항목에 걸렸으면 포함으로 옮긴다.
    - `2. 결정 사항`에는 지시(`do · 대화 지시`)와 질문의 답을 남기고, 바뀐 결정은 `#n 변경`으로 적는다. `8. 작업 이력`에 구분 `계획 변경`으로 남긴다.
    - `업무 파일 반영` 지시면 위에서 찾은 고칠 곳을 모두 고친다. `### 요구사항 문서`의 항목은 업무 파일 `## 요구 항목`의 지금 내용대로 고친다. (새 항목은 번호를 이어 붙이고 `— 반영`을 단다. 일부 이미 충족 표기는 `workflow-plan`이 업무 파일을 옮길 때와 같게 쓴다) 항목 원문(반영 표시 `—` 앞)에 있는 결정 번호는 로드맵 README의 번호이므로 `(로드맵 결정 #n)`으로 쓴다. 바뀌지 않은 기존 항목에 `(결정 #n)`으로만 적혀 있으면(이전 버전으로 만든 계획서) 그것도 이때 `(로드맵 결정 #n)`으로 바꾼다. 그대로 두면 이 계획서 `2. 결정 사항`의 같은 번호로 읽힌다. 반영 표시 쪽(`— 일부 반영 — … (결정 #n)` 등)의 번호는 이 계획서의 결정이므로 바꾸지 않는다. 그런 뒤 제목 아래의 읽은 시점과 커밋을 diff를 읽을 때 조회해 둔 값으로 바꾼다. 이 커밋 값으로 `workflow-roadmap`·`workflow-status`가 `반영 필요`를 판정하므로, diff에서 읽은 변경을 모두 맞춰 본 뒤에만 바꾼다. (업무 파일에 미커밋 변경이 있었으면 커밋 값 뒤에 `(미커밋 변경 포함)`을 붙인다)
    - 항목을 추가했으면 `진행 표시 확인`을 실행해 체크 항목 수가 바뀐 진행 표시를 맞춘다.
    - 추가 전 작업상태가 `완료`였던 로드맵 업무 계획서면, 이어서 종료 처리 1번의 `로드맵 갱신`을 바로 한 번 해 README 이 업무 행을 `진행`으로 되돌린다. (종료 처리 전에 Phase 커밋이 먼저 일어나거나 실행이 끊겨도 README와 계획서가 어긋나지 않게 한다) 고친 README는 다음 커밋에 넣는다. 종료 처리 1번은 그때 다시 판정한다.
    - 그다음 일반 항목처럼 진행한다. 이 계획 변경은 준비 6번의 `do 시작` 행보다 먼저 기록하고, `do 시작`의 시작 진행률은 추가 뒤의 값으로 쓴다.
  - 반영하지 않으면 그 지시는 하지 않는다.
    - 단, `업무 파일 반영` 지시인데 `반영하지 않음`을 골랐거나, 업무 파일의 바뀐 내용이 계획서에 이미 들어 있어 고칠 곳이 없으면(위 `업무 파일 반영 지시`에서 diff 전체를 맞춰 본 결과다. 업무 번호만 바뀐 경우도 여기에 든다), 작업항목은 고치지 않고 `### 요구사항 문서` 제목 아래의 읽은 시점과 커밋만 diff를 읽을 때 조회해 둔 값으로 바꾸고 줄 끝에 `(바뀐 내용 확인 — 반영하지 않음, 결정 #n)` 또는 `(바뀐 내용 확인 — 이미 반영됨)`을 붙인다. 그래야 `반영 필요`가 풀린다. 이때도 요구사항 문서 항목 원문의 옛 표기 `(결정 #n)`은 `(로드맵 결정 #n)`으로 바꾼다. `8. 작업 이력`에 구분 `계획 변경`으로 남기고, 남은 작업이 없으면 `커밋 규칙`대로 계획서만 커밋하고 종료 처리를 한다.
  - `코드 정리 및 리뷰` Phase가 이미 `[V]`인데 새 항목이 추가되면, 그 Phase에 `/code-review medium` 재실행 항목을 새 번호로 추가할지 함께 묻는다. 선택지는 `재실행 항목 추가 (Recommended)` / `추가하지 않음`이다. 새 항목이 코드를 바꾸지 않으면(문서·계획서만) 뒤의 것을 추천해 첫 번째에 둔다. 재실행 항목의 리뷰 대상은 아래 `코드 정리 및 리뷰 Phase`의 `작업 기준 커밋` 예외대로 이번 실행에서 바뀐 것만이다.
- 남은 항목(`[V]`가 아닌 작업항목)이 없고 추가 지시도 없을 때
  - `6. 완료 기준`에 `[V]`가 아닌 기준이 남아 있으면, 1단계 준비를 마친 뒤 2단계를 건너뛰고 3단계(완료 기준 확인)만 진행한다. `do 시작` 행의 진행 범위는 `완료 기준`으로 쓴다. 준비 5번에서 항목을 `[~]`로 되돌리거나 수정 작업항목을 더했으면 남은 작업항목이 생긴 것이므로, 건너뛰지 않고 2단계부터 진행한다. (`do 시작` 행의 진행 범위는 그 항목 ID다)
  - 남은 완료 기준도 없으면 진행률만 보고하고 종료한다.
- 대상이 `workflow-plan` 형식이 아니면(`5. 작업 항목`·`6. 완료 기준` 제목이 없으면) 그 사실을 알리고, 계속할지 AskUserQuestion으로 확인한다. 답은 `do · 대상`으로 기록한다. 두 제목은 있고 규칙 블록만 없거나 다르면 형식이 아닌 것이 아니라 아래의 예전 형식이다. (`workflow-plan-review`와 같은 기준)
- 이 입력 확인 중 계획서를 고치는 일(형식 올리기, 추가 지시의 항목 추가)은 준비 2번(브랜치 확인)을 마친 뒤에 한다.
- 예전 형식으로 만든 계획서인지 확인한다. `${CLAUDE_PLUGIN_ROOT}/templates/plan-template.md`(`workflow-plan`의 템플릿)를 Read 해서 비교한다. 다음 중 하나라도 해당하면 예전 형식이다.
  - 상단 표에 `커밋 방식` 행이 없다
  - `진행 관리 규칙`·`결정 · 이력 기록 규칙` 블록이 없거나, 템플릿의 같은 블록과 다르다 (블록은 있는데 그 안의 줄이 빠진 경우 포함. 예: 커밋 방식 기능 전에 만든 계획서는 `진행 관리 규칙`에 커밋 줄이 없다)
  - `2. 결정 사항` 표 머리글이 `# | 일시 | 단계 | 질문 | 선택지 | 선택 | 비고`가 아니거나, `8. 작업 이력` 표 머리글이 `일시 | 구분 | 내용`이 아니다
- 규칙 블록만 다르고(`커밋 방식` 행과 두 표 머리글은 맞다) 템플릿 줄이 빠지기만 했으면(템플릿에 없는 줄이 블록에 없으면. 1.5.0 전 템플릿의 커밋 예외 줄 ``> - `자동`이어도 다음 경우에는 커밋 전에 묻는다:``로 시작하는 줄은 템플릿에 없어도 이 판정에서 뺀다) 묻지 않고 두 규칙 블록을 템플릿의 블록으로 바꾼다. 블록은 템플릿 문구라 계획마다 다른 내용이 없어 답이 하나뿐이다. (템플릿 문구가 바뀌면 진행 중인 계획서가 모두 여기에 걸린다) `8. 작업 이력`에 구분 `계획 변경`으로 `규칙 블록 갱신 — <더한 줄 요약>`을 남긴다. 계획서를 고치는 일이라 준비 2번(브랜치 확인)을 마친 뒤에 한다.
- 그 밖의 예전 형식이면 형식을 올릴지 AskUserQuestion으로 질문 하나로 묻는다. 질문 본문에 다른 곳을 적는다. 답은 `2. 결정 사항`에 단계 `do · 형식`으로 기록한다.
  - `커밋 방식` 행이 없으면 선택지는 `올린다 — 커밋 방식 <값> (Recommended)` / `올린다 — 커밋 방식 <다른 값>` / `올리지 않는다`다. `<값>`은 `2. 결정 사항`에 `plan · 커밋 방식` 행이 있으면 그 `선택`, 없으면 `확인`이다. `<다른 값>`은 `확인`이면 `자동`, 그 밖이면 `확인`이다.
  - `커밋 방식` 행이 있으면 선택지는 `올린다 (Recommended)` / `올리지 않는다`다.
- 올리면 두 규칙 블록을 템플릿의 블록으로 통째로 바꾼다. (규칙 블록은 템플릿 문구라 계획마다 다르지 않다) 예전 블록에만 있던 줄은 질문 본문에 적어 사라진다는 것을 알린다. `커밋 방식` 행이 없으면 고른 값으로 넣는다.
  - 표(`2. 결정 사항`·`8. 작업 이력`, 머리글이 템플릿과 다르면 `설계안 비교`도)는 기존 행의 내용을 고치지 않고 열만 맞춘다. (`설계안 비교` 머리글만 다른 것은 예전 형식 판정에 넣지 않는다. 이 표의 열을 읽는 커맨드가 없어 올리지 않아도 결과가 같다) 이름이 같은 열은 그대로 옮기고 새 열은 `-`로 채운다. 이름이 다른 예전 열은 `2. 결정 사항`의 `확정 내용`은 `선택`으로 옮기고, 그 밖에 맞는 열이 없는 것은 `비고`에 `<열 이름>: <값>`으로 옮긴다. 한 칸에 섞인 내용(예: `선택 — 비고`)은 나누지 않는다.
  - `8. 작업 이력`에 구분 `계획 변경`으로 `예전 형식 올림 — <바꾼 것>`을 남긴다. 올리지 않으면 새로 추가하는 행도 기존 표 형식에 맞춘다. 커밋 방식은 상단 표에 `커밋 방식` 행이 있으면 그 값을, 없으면 `확인`으로 본다.
  - 판정·질문·올리는 방법은 `workflow-plan-review`의 `계획서 형식`과 같다. 한쪽을 고치면 다른 쪽도 고친다.

## 절대 규칙

- **계획서가 기준이다.** `3. 작업 범위`의 제외 항목이나 계획서에 없는 작업은 하지 않는다.
- **애매한 사항은 직접 결정하지 않는다.** 다음 경우 AskUserQuestion으로 확인한다. (한 번에 최대 4개, 추천안은 첫 번째 옵션 + `(Recommended)`)
  - 항목 설명만으로 구현 방법이 둘 이상으로 갈릴 때
  - 코드를 보니 계획서와 실제 구조가 달라 계획 변경이 필요할 때 (항목 추가·분할·병합·취소, 영향 범위 변경)
  - 구현 중 `설계안 비교`에서 선택한 안의 `성립 전제`가 깨져 그 안으로 진행할 수 없을 때. 혼자 방향을 바꾸지 않는다. 막힌 이유와 함께 선택하지 않은 안을 다시 보여 주고 방향을 바꿀지 묻는다. 바꾸면 `설계안 비교`의 선택 결과를 고치고, 바뀌기 전 안은 선택하지 않은 안으로 이유와 함께 옮긴다. 새 설계에 맞게 작업항목과 `4. 영향 범위`를 고친다. `DB 변경`·`API 변경`·`화면 변경` 정의가 바뀌면 해당 skill을 인자 `설계`로 불러 정의를 다시 정하고(여럿이면 `workflow:db-design` → `workflow:api-design` → `workflow:ui-design` 순서), skill이 돌려준 `미정 사항`도 AskUserQuestion으로 묻는다. 이전 설계로만 의미 있는 항목은 취소 표기로 바꾼다. 이전 설계로 이미 `[V]`가 된 항목은 어떻게 할지 먼저 확인한다. `8. 작업 이력`에 구분 `계획 변경`으로 남긴다.
  - 계획서에 없는 파일을 크게 고쳐야 할 때
  - 코드의 실제 동작이 `1. 요구사항`의 `현재 동작` 표와 달라, 요구사항의 전제가 맞지 않을 때
  - `4. 영향 범위`의 `DB 변경`·`API 변경`·`화면 변경` 정의(테이블·컬럼·인덱스, URL·요청·응답·오류 코드, 화면 경로·요소 이름·검증·문구·권한별 노출)와 다르게 구현해야 할 때. 이 표가 구현의 기준이다. 확인받아 바꿨으면 표도 함께 고친다.
  - 되돌리기 어려운 작업을 할 때
    - 계획서에 없는 DB 마이그레이션·파일 삭제·외부 서비스 호출: 위의 계획 변경으로 묻는다.
    - 계획서에 있어도 효과가 밖에 남는 실행: 테스트용(메모리·임시 파일·테스트 컨테이너)이 아닌 DB(로컬 개발 DB 포함)에 마이그레이션을 적용하거나, 실제 외부 서비스를 호출·발송하는 경우다. 선택지는 `실제 적용 없이 진행 — 테스트용 DB·모의 호출로만 검증 (Recommended)` / `실제로 실행` / `중단`이다.
    - 묻지 않는 것: 계획서 항목의 마이그레이션 파일 작성, 테스트용 DB에서의 적용·검증, 계획서 항목의 파일 삭제. 계획 단계에서 정했고(`(단독 커밋)`) 커밋 전까지 git으로 되돌릴 수 있다.
  - AskUserQuestion을 쓸 수 없는 환경(비대화형 실행 등)이면 그 항목을 `[~]`로 둔 채 중단한다. (아래 `중단`)
- **중단**: 이 문서에서 "중단한다"는 다음을 뜻한다.
  - 준비 6번의 `do 시작` 행을 쓰기 전에 멈추면, 계획서를 아직 고치지 않았으면 사유만 보고하고 끝낸다. 준비 2번 뒤에 계획서를 고쳤으면(형식 올리기, 미결 확정, 항목 추가 등) 4단계 종료 처리를 `do 중단`으로 한다.
  - `do 시작` 행을 쓴 뒤 멈추면 4단계 종료 처리를 한다. 이력 구분은 `do 중단`이고, 그 행은 4단계에서만 쓴다. 멈춘 자리에서 따로 쓰지 않는다.
  - AskUserQuestion을 쓸 수 없는 환경에서는 커밋 질문을 해야 하는 시점에 커밋하지 않고 진행한다. 종료 처리에서도 커밋하지 않고, 완료 보고에 커밋하지 않은 변경을 적는다.
- AskUserQuestion으로 받은 답은 질문·선택지·선택 결과를 작업계획서 `2. 결정 사항`에 한 행씩 추가한다. 기존 행은 고치거나 지우지 않는다. (기록 형식은 계획서의 `결정 · 이력 기록 규칙` 참고) 질문의 답이 아니라 사용자가 대화로 직접 준 지시·정정도 같은 표에 `do · 대화 지시`로 남기고, 인자로 준 추가 지시도 여기에 남긴다. 계획을 바꿨으면 `8. 작업 이력`에도 구분 `계획 변경`으로 남긴다.
  - `단계` 값은 질문한 곳에 따라 정한다. 한 질문이 여러 항목에 걸치면 `do · 3.1, 3.2`처럼 모두 쓴다.
    - `do · 대상`: 대상 계획서 확인, 형식이 아닌 계획서를 계속할지
    - `do · 브랜치` / `do · 범위` / `do · 형식`: 입력과 준비 2번의 브랜치·범위·형식 질문
    - `do · 추가 지시`: 입력의 추가 지시를 계획서에 반영할지 (지시 자체는 `do · 대화 지시`)
    - `do · 미결 확정`: 준비 3번의 모든 질문 (항목에 걸린 미결이어도 이 값을 쓰고, `비고`에 위치를 적는다)
    - `do · 준비`: 준비 4·5번 (이미 `[V]`인 항목의 미커밋 변경, 애매한 파일, 기준 상태 실패, 빌드·테스트 명령, 의존성 설치). 질문이 항목 하나에 걸려도 이 값을 쓰고 `비고`에 항목 ID를 적는다. 예외는 `[~]` 항목 재개 질문으로, `do · <항목 ID>`를 쓴다
    - `do · <항목 ID>`: 2단계 항목 구현·검증 중의 모든 질문 (구현 방법, 계획 변경, 기준 상태 미확인 실패, 3회 실패 뒤 계속, 병렬 그룹의 `직접 정한 것`·`확인 필요`·목록 밖 파일, 리뷰 기준 커밋, code-review 반영 선택)
    - `do · <완료 기준 ID>`: 3단계
    - `do · 커밋`: 커밋 질문과 커밋 실패 뒤 다시 커밋할지
  - `일시`는 답을 받은 시점이다. 답을 받으면 바로 시각을 조회해 둔다. (다음 명령에 붙여 조회해도 된다) 준비 6번처럼 나중에 몰아 기록하는 답도 받은 시점의 시각을 쓴다. 인자로 받은 추가 지시(`do · 대화 지시`)는 커맨드를 시작할 때 조회한 시각을 쓴다.
- 상태 표기·진행률·작업상태, 항목 ID와 항목 추가·취소·병합·분할은 계획서 안의 `진행 관리 규칙`을 그대로 따른다. 기존 ID(`1.1`, `DoD-1`)는 바꾸지 않는다.
- **진행 표시 확인**: 진행률·진행률 바·작업상태·Phase 제목의 상태는 손으로 다시 세지 않는다. Bash 도구로 `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-progress.sh" --fix "<계획서 경로>"`를 실행한다. 스크립트가 체크 표기를 세어 상단 표의 작업상태·전체진행률, 진행률 바, Phase 제목의 상태/진행률 중 다른 곳을 직접 고치고, 고친 곳을 `적힌 값 → 맞는 값`으로 출력한다. (`진행 표시 일치`면 고친 곳 없음) 체크 표기의 상태와 `최종 갱신`은 고치지 않는다. 스크립트가 파일을 고쳤으면, 다음에 Edit 도구로 계획서를 고치기 전에 Read로 몇 줄(`limit`)만 다시 읽는다. (Edit 도구는 밖에서 바뀐 파일을 다시 읽어야 고칠 수 있다. 바뀐 값은 출력에 있으므로 전체를 다시 읽지 않는다) 스크립트를 실행할 수 없으면 `진행 관리 규칙`대로 직접 센다.
- **커밋은 계획서 상단 표의 `커밋 방식`을 따르고, push는 하지 않는다.** 커밋 시점은 Phase 완료, `(단독 커밋)` 항목 시작 전(앞 항목의 선행 커밋)과 완료, `/simplify` 전(앞 Phase의 남은 변경), `코드 정리 및 리뷰` Phase의 각 항목 완료, 종료 처리다. (아래 `커밋 규칙` 참고)

## 커밋 규칙

- **단위**: 기본은 Phase 단위다. 계획서에서 `(단독 커밋)`이 붙은 항목(DB 마이그레이션, 파일 삭제 등 되돌리기 어려운 작업)은 그 항목만 따로 커밋하고, `코드 정리 및 리뷰` Phase는 `/simplify`와 `/code-review` 반영을 각각 커밋한다. 한 커밋은 검증(테스트·빌드)을 통과한 상태여야 한다.
- **마지막 커밋 시점은 종료 처리로 미룬다**: 커밋 시점 뒤에 이번 실행에서 계획서를 고칠 일이 종료 처리만 남았으면(진행 범위를 모두 마쳤고, 3단계를 건너뛰거나 3단계에서 확인할 완료 기준이 없을 때) 그 시점에는 커밋하지 않는다. 4단계 종료 처리에서 `do 종료` 행을 쓴 뒤 미룬 변경과 함께 한 번에 커밋하고, 메시지는 미룬 시점의 것을 쓴다. 이렇게 해야 `do 종료` 행 하나만 담은 커밋이 따로 생기지 않는다. 미뤄도 커밋 내용은 미룬 시점의 단위(Phase, `(단독 커밋)` 항목 등) 그대로다.
- **커밋 방식**: 계획서 상단 표의 `커밋 방식` 값에 따라 커밋 시점마다 다음과 같이 한다. 값이 없으면(예전 계획서) `확인`으로 본다. git 저장소가 아니거나 `해당 없음`이면 커밋하지 않는다.
  - `자동`: 묻지 않고 커밋한 뒤 `커밋 <해시> <제목>` 한 줄로 알린다. 아래 **자동 커밋 예외**도 묻지 않고 정해진 대로 처리한다. 작업 브랜치가 기본 브랜치일 때만 커밋 시점마다 커밋 질문으로 묻는다. 기본 브랜치는 `git symbolic-ref --short refs/remotes/origin/HEAD`(앞의 `origin/`을 뗀다)가 가리키는 브랜치(없으면 로컬 브랜치 중 `main` → `master` → `develop` 순서로 처음 있는 것)와, 있으면 `develop`이다. (`workflow-plan` 1단계와 같은 기준)
  - `확인`: 시점마다 아래 **커밋 질문**으로 묻는다.
  - `끝에 한꺼번에`: 중간 시점에는 커밋하지 않고, 종료 처리에서만 커밋 질문으로 묻는다.
  - 사용자가 추가 지시나 대화로 커밋 방식을 바꾸면 상단 표의 값을 고치고 `2. 결정 사항`에 `do · 대화 지시`, `8. 작업 이력`에 구분 `계획 변경`으로 남긴다.
- **자동 커밋 예외** — `자동`이면 다음 경우에도 묻지 않고 아래처럼 처리하고, 한 줄로 알린다. 알리는 줄은 모든 workflow 커맨드가 같은 형식이다: 커밋하면 `커밋 <해시> <제목>`에 해당하는 것을 `(제외: <파일>, …)`·`(실행 전 변경 포함: <파일>, …)`로 붙이고, 다음 시점으로 미루면 `커밋 미룸 — <사유>`, 이번 실행에서 커밋하지 않으면 `커밋 안 함 — <사유>`로 쓴다. (예: `커밋 미룸 — 1.3 검증 중`, `커밋 a1b2c3d feat: 로그인 화면 (3.1~3.2) (제외: public/login.html)`) 처리한 내용은 완료 보고에도 적는다. 작업 브랜치가 기본 브랜치이면 이 경우도 커밋 질문으로 묻고 질문 본문에 사유를 적는다. 커밋 질문(기본 브랜치, `확인`·`끝에 한꺼번에`)에서의 추천은 각 경우에 적은 대로다.
  - 검증이 끝나지 않은(`[~]`) 항목의 변경이 섞인다 → `커밋하지 않고 계속`(종료 처리에서는 `커밋하지 않음`)으로 처리한다. 커밋 질문에서는 이 선택지를 첫 번째에 두고 `(Recommended)`를 붙인다.
  - 계획서상 뒤 항목에 맡긴 테스트 실패(2단계 3번)가 아직 남아 있다 → 위와 같이 처리하고 추천한다. 알리는 줄과 질문 본문에 남은 실패와 그것을 고칠 항목 ID를 적는다.
  - 커밋할 파일에 `시작 전 미커밋 변경` 파일이 섞인다(이번 작업에서도 그 파일을 고쳤다. 아래 `스테이징`) → 그 파일만 빼고 커밋한다. 그 파일은 종료 처리까지 커밋하지 않고, 완료 보고에 시작 전 변경과 이번 작업의 변경이 섞여 있어 커밋하지 않았다고 적는다. (사용자가 확인한 뒤 직접 커밋한다) 그 파일 때문에 이 커밋에 코드가 빠진 항목이 있으면 커밋 메시지 본문(`Plan:` 줄 앞)에 `미커밋: <파일> (<항목 ID>, 시작 전 변경 섞임)` 줄을 넣고, 그 커밋 단위의 이력 행(`Phase` 행. `(단독 커밋)` 항목이면 그 `항목` 행. 마지막 커밋 시점을 종료 처리로 미뤄 커밋 직전 행이 `do 종료` 행이어도 그 단위의 행) 끝에 `(<항목 ID> 코드 일부 미커밋: <파일>)`을 붙인다. 계획서의 `[V]`와 커밋 내용이 다르다는 것을 커밋과 계획서에서 알 수 있게 하기 위해서다. 커밋 질문에서는 그 파일을 넣은 `커밋 (Recommended)`으로 묻고, 질문 본문에 함께 들어가는 시작 전 변경을 적는다.
  - 비밀값 파일(`.env`, 키·인증서·credentials 파일 등)로 보이는 파일이 변경에 있다 → 그 파일은 빼고 커밋한다. (아래 `스테이징`)
  - 커밋 훅이 실패했다 → 아래 `실패 처리`
- **커밋 질문**: AskUserQuestion으로 묻는다. 질문 본문에 커밋할 파일 목록과 메시지 초안을 적는다. 선택지:
  - `커밋 (Recommended)`
  - `커밋하지 않고 계속`: 변경은 다음 커밋 시점에 함께 다룬다.
  - `이번 실행은 끝에 한꺼번에`: 이번 실행에서는 중간 시점에 커밋하지 않고 종료 처리에서만 묻는다. (계획서의 `커밋 방식`은 바꾸지 않는다)
  - 종료 처리에서는 `커밋 (Recommended)` / `커밋하지 않음` 두 개만 둔다.
  - 답은 `2. 결정 사항`에 `do · 커밋`으로 기록한 뒤 커밋한다. (그 행도 같은 커밋에 들어간다) 묻지 않고 한 자동 커밋은 결정 사항에 기록하지 않는다.
- **스테이징**: 지난 커밋 이후 이번 실행에서 바꾼 파일, 준비 2번의 이전 실행 변경 중 아직 커밋하지 않은 파일, 계획서, 입력의 추가 지시 처리나 종료 처리 1번에서 고친 로드맵 README만 `git add -- <경로...>`로 스테이징하고 `git commit -- <경로...>`처럼 그 파일들만 커밋한다. `git add -A`, `git add .`는 쓰지 않는다.
  - 준비 4번에서 `이번 작업의 변경으로 다룸`을 고른 애매한 파일 중 아직 `[ ]`인 항목의 파일은, 그 항목을 구현해 커밋하는 시점에만 넣는다. (커밋 내용은 그 커밋 단위의 것이어야 한다)
  - 준비 단계에서 기록한 `시작 전 미커밋 변경` 파일은 넣지 않는다. 이번 작업에서도 그 파일을 고쳤으면 시작 전 변경과 섞이므로 위 자동 커밋 예외의 `시작 전 미커밋 변경 파일이 섞인다`로 다룬다. (`자동`이면 빼고, 커밋 질문이면 넣고 묻는다)
  - 비밀값 파일(`.env` 등)과 usecase 증적, 준비 5번의 의존성 설치로 바뀐 lock·매니페스트 파일은 넣지 않는다.
- **계획서도 함께 커밋한다.** 그 단위에서 갱신한 `[V]` 표기, 진행률, 작업 이력, 영향 범위가 소스와 같은 커밋에 들어가야 코드와 진행 상태가 맞는다.
- **메시지**: 제목은 프로젝트 규칙(CLAUDE.md 등)의 커밋 형식이 있으면 그것을 따르고, 없으면 아래 형식을 쓴다. 본문 끝 줄 `Plan:`은 프로젝트 형식이 있어도 붙인다. (프로젝트 규칙이 본문 형식을 따로 정해 막는 경우만 뺀다)
  - 제목: `<type>(<scope>): <요약> (<항목 ID>)` — 예: `feat(auth): 로그인 실패 횟수 저장 (1.1~1.3)`, `refactor: simplify 정리 (3.1)`, `fix: code-review 지적 2건 반영 (3.2)`, `docs(plan): 완료 기준 확인 (DoD-1~3)`. 종료 처리에서 계획서만 커밋하면(중간에 멈춰 기록만 남은 경우 등) `docs(plan): workflow-do 종료 기록 (<진행 범위>)`이다.
  - 프로젝트 형식을 따를 때: type·모듈 같은 분류 자리에는 그 프로젝트의 값을 쓰고, 설명은 위 형식의 `<요약> (<항목 ID>)`를 쓴다. 분류가 모듈처럼 위치로 정해지는데 바뀐 파일이 모듈 밖(예: `public/`)에 있거나 여러 모듈에 걸치면, 업무 규칙이 바뀐 모듈을 쓴다. 모듈 밖 파일만 바뀌었으면 `git log --format=%s -5 -- <경로>`로 그 경로를 바꾼 이전 커밋의 분류값을 따른다. (새 파일이면 그 파일이 있는 폴더로 찾는다) 분류값이 있는 커밋이 없으면 그 변경이 다루는 모듈(예: `reservations` 테이블 마이그레이션이면 `[reservations]`)을 쓰고, 그것도 정할 수 없을 때만 가장 가까운 상위 폴더 이름(예: `[public]`)을 쓴다. 항목 ID는 어느 항목의 커밋인지 찾는 근거이므로 프로젝트 형식이어도 붙인다. (프로젝트 규칙이 제목 형식을 따로 정해 막는 경우만 뺀다) 계획서만 바뀐 커밋(완료 기준 확인 등)은 분류 자리에 그 프로젝트가 문서 변경에 쓰는 값(`docs`, `[docs]` 등, 정해진 값이 없으면 `docs`)을 쓴다. 예: 형식이 `type: 설명`이면 `feat: 로그인 잠금 안내 화면 (3.1~3.2)`, `[모듈] 설명`이면 `[reservations] 예약 겹침 검사 추가 (1.1~1.2)`, `[docs] 완료 기준 확인 (DoD-1~3)`
  - 본문 끝 줄: `Plan: <계획서 경로>`
- **실패 처리**: 커밋이 실패하면(훅 실패 등) `--no-verify`로 우회하지 않고 원인을 알린다.
  - `자동`이고 작업 브랜치가 기본 브랜치가 아니면 묻지 않는다. 고칠 수 있으면(훅이 지적한 lint·포맷 문제 등) 고치고, 소스를 고쳤으면 검증(테스트·빌드)을 다시 통과시킨 뒤 한 번 다시 커밋한다. 고칠 수 없거나 다시 실패하면 `커밋하지 않고 계속`으로 처리하고(변경은 다음 커밋 시점에 함께 다룬다) 완료 보고에 원인을 적는다.
  - 그 밖에는 고칠 수 있으면 고친 뒤 다시 커밋할지 AskUserQuestion으로 묻는다.
- 커밋 해시는 계획서에 쓰지 않는다. (기록 후 커밋하므로 알 수 없다) 완료 보고에 적는다.

## 처리 절차

### 1. 준비
1. 계획서를 읽고 요구사항(`현재 동작 → 변경 후 동작` 표가 있으면 포함), 결정 사항(선택한 설계안과 그 전제 포함), 작업 범위, 영향 범위(`DB 변경`·`API 변경`·`화면 변경` 정의 표가 있으면 포함), 진행 범위의 항목을 파악한다.
2. 브랜치를 확인한다. 계획서를 고치거나 코드를 보기 전에 한다.
   - **작업 브랜치 확인** — 계획서의 `작업 브랜치`에서 실행되도록, 코드를 보거나 문서를 고치기 전에 먼저 한다.
     - git 저장소가 아니거나 `작업 브랜치`가 `해당 없음`으로 시작하면(`해당 없음 (detached HEAD)` 포함) 건너뛴다.
     - 현재 브랜치(`git branch --show-current`)가 `작업 브랜치`와 같으면 그대로 진행한다. 출력이 비어 있으면(detached HEAD) 다른 것으로 본다.
     - 다르면 AskUserQuestion으로 묻는다. 질문 본문에 현재 브랜치, 작업 브랜치, 미커밋 변경 파일 목록(`git status --short`)을 적는다. 미커밋 변경이 있으면, 전환해도 충돌이 없는 한 그 변경이 작업 브랜치로 그대로 따라온다는 것도 적는다. (그 파일들은 아래 `시작 전 미커밋 변경`으로 커밋에서 빠진다) 선택지:
       - `작업 브랜치로 전환 (Recommended)`: 로컬에 있으면 `git switch <작업 브랜치>`, 원격에만 있으면 `git switch --track <원격>/<작업 브랜치>`. 어디에도 없으면 이 선택지를 `현재 위치에서 작업 브랜치를 새로 만들어 전환`(`git switch -c <작업 브랜치>`)으로 바꾸고 추천을 붙이지 않는다. 대신 `현재 브랜치에서 진행`을 첫 번째에 두고 추천한다. (작업 브랜치 이름을 바꿨거나 브랜치를 지운 경우다. 계획서가 있는 지금 브랜치를 작업 브랜치로 삼는 편이 맞다) detached HEAD이면 추천을 붙이지 않는다.
       - `현재 브랜치에서 진행`: 계획서 상단 표의 `작업 브랜치`를 현재 브랜치로 고치고 `8. 작업 이력`에 구분 `계획 변경`으로 남긴다. (detached HEAD이면 이 선택지는 뺀다)
       - `중단`
     - 전환이 실패하면(미커밋 변경 충돌 등) stash나 강제 전환을 하지 않는다. 실패 내용을 알리고 중단한다.
     - 전환했으면 계획서를 다시 읽는다. (브랜치마다 내용이 다를 수 있다)
     - 답은 작업계획서 `2. 결정 사항`에 `do · 브랜치`로 기록한다.
   - 브랜치 확인을 마치면 `git status --short`로 미커밋 변경 파일을 확인해 둘로 나눈다. 계획서 자체가 목록에 있으면 그 사실만 기억하고 커밋에서는 계획서를 넣는다.
     - **이전 실행 변경**: 이전 `workflow-do` 실행이 커밋하지 않고 남긴 변경이다. 이번 작업의 변경으로 다룬다. 커밋·리뷰·병렬 그룹 조건에서 시작 전 변경으로 보지 않는다. `8. 작업 이력`의 마지막 `do 시작` 행 뒤에 오는 `do 종료`·`do 중단` 행(여럿이면 마지막 행)으로 가린다.
       - 그 행에 `미커밋:` 목록이 있으면(종료 처리 3번) 그 목록의 파일 중 지금도 바뀌어 있는 것만 이전 실행 변경이다. 목록에서 `(시작 전 변경 섞임)`이 붙은 파일은 이전 실행 변경이 아니라 `시작 전 미커밋 변경`과 섞인 파일로 계속 다룬다. (`커밋 규칙`의 자동 커밋 예외) 목록에 없는 파일은 이 계획의 항목 파일이어도 이전 실행이 남긴 것이 아니다. (이전 실행이 끝난 뒤 사용자가 고친 것이다) 아래 애매한 파일과 같이 준비 4번에서 묻는다. 단, 같은 행의 `시작 전 변경:` 목록에 있는 파일(이전 실행에서 이미 시작 전 변경으로 두기로 답한 파일)은 다시 묻지 않고 `시작 전 미커밋 변경`으로 본다.
       - 마지막 `do 시작` 뒤에 종료 행이 없거나(세션이 끊겨 종료 처리를 못 함), 종료 행에 `미커밋:`이 없으면(1.5.1 전 형식) 파일로 판정한다. 바뀐 파일이 이 계획의 `[~]`·`[V]` 항목이 고치는 파일(항목 내용, `파일:` 줄, 그 항목 때문에 `4. 영향 범위`에 추가된 파일)이면 이전 실행 변경이다. 이때는 이전 실행이 끝난 뒤의 사용자 변경과 가릴 수 없으므로, 준비 4번의 `[V]` 항목 질문을 커밋 방식과 상관없이 묻는다.
       - `8. 작업 이력`에 이전 `do 시작` 행이 없으면 이전 실행 변경은 없다.
     - **시작 전 미커밋 변경**: 그 밖의 변경(이 계획과 관계없는 사용자 변경)이다. 커밋할 때 넣지 않는다. (`커밋 규칙` 참고)
     - **기준 커밋**: 이 분류를 마치면 `git rev-parse --short HEAD`로 이번 실행의 기준 커밋을 조회해 둔다. 준비 4번의 `지금 커밋`보다 먼저 조회해야 그 커밋도 이번 실행의 커밋 목록과 되돌리기(`git reset --soft`)에 들어간다. 준비 6번의 `do 시작` 행에 이 값을 쓴다.
     - 어느 쪽인지 애매한 파일과, 이미 `[V]`인 항목의 이전 실행 변경은 준비 4번에서 처리를 묻는다. 애매한 파일은 이 계획의 아직 `[ ]`인 항목이 고칠 파일, `4. 영향 범위`에만 있고 어느 항목의 파일인지 적히지 않은 파일, 그리고 위 `미커밋:` 목록에 없는 `[~]`·`[V]` 항목의 파일이다. `[ ]` 항목은 이전 실행이 아직 손대지 않은 항목이므로(`workflow-do`는 코드를 고치기 전에 항목을 `[~]`로 바꾼다) 그 파일의 변경은 대개 사용자 변경이다.
3. **미결 사항을 확정한다.** 구현을 시작하기 전에 계획서에서 아직 정해지지 않은 사항을 찾아, AskUserQuestion으로 확답을 받고 계획서를 고친 뒤 진행한다.
   - **찾는 대상**
     - `(미결)`·`(미결: 결정 #n)` 표시가 붙은 곳 (`2. 결정 사항` 표와 `9. 리뷰 결과`는 아래 규칙으로 따로 본다)
     - `2. 결정 사항`에서 `선택`이 비어 있거나, `(미결)`이 붙었거나, `미정`·`보류`·`추후 결정`·`TBD`인 행. 단, 뒤에 그 행을 `#n 확정`·`#n 변경`·`#n 정정`으로 가리키는 행이 있으면 이미 확정된 것이다. (`#n 정정` 행의 `선택`이 여전히 미정이면 미결이다) `비고`에 `#n 보류`가 있는 행(같은 사항을 다시 미룬 행. 이전 `workflow-do`의 보류, `workflow-plan-review`에서 다시 미룬 답)은 `#n` 행과 한 사항이다. `#n`이 확정되면 함께 확정된 것으로 보고, 따로 세거나 묻지 않는다.
     - `설계안 비교`에서 선택한 안이 비어 있거나 `미정`인 경우
     - `3. 작업 범위`·`4. 영향 범위`·`5. 작업 항목`·`6. 완료 기준`·`7. 리스크 및 고려사항`에서 `미정`·`TBD`·`확인 필요`·`결정 필요`·`추후 결정`이 적힌 곳
     - `9. 리뷰 결과`에서 `조치`가 `미결`·`보류`·`추후 결정`인 지적. 단, `2. 결정 사항`에서 `비고`에 `리뷰 N차 #n`이 든 행이 확정된 것이면 이미 확정된 것이다. 그 행의 `선택`이 확정된 값(`(미결)`이나 위의 미정 표현이 아님)이거나, 위 규칙대로 뒤 행이 그 행을 확정한 경우다(`#k 확정` 행이 있다, `#m 보류` 행인데 `#m`이 확정됐다). (리뷰 회차 표는 확정 후에도 고치지 않기 때문이다. 리뷰가 `(미결)`로 남긴 행도 `비고`에 같은 지적 번호를 쓰므로 그 행이 확정됐는지로 가린다. `비고`에는 `리뷰 1차 #3, #4 보류`처럼 다른 표시가 함께 있을 수 있다)
     - 제외: 계획서 상단 규칙 블록(`진행 관리 규칙`, `결정 · 이력 기록 규칙`) 안의 설명 문구, `1. 요구사항`의 원문 인용(`>` 줄), `8. 작업 이력`, 취소선 줄, `2. 결정 사항`의 `질문` 칸
     - `### 요구사항 문서`의 항목 줄은 찾는 대상이다. 문서 원문 뒤의 반영 표시(`— 반영 …`, `— 일부 반영 …`)에 `(미결)`이 있으면 그 사항을 묻고, 확정하면 반영 표시만 고친다. 원문 부분은 고치지 않는다.
     - 같은 사항을 가리키는 표시(본문의 `(미결)`, 그 결정 사항 행, 그 행을 `#n 보류`로 가리키는 행, 그 행들의 `비고`가 가리키는 리뷰 지적)는 하나로 묶어 한 번만 묻는다.
   - **질문하기**
     - 미결 사항마다 질문 하나를 만든다. 질문 본문에 계획서의 위치(예: `5. 작업 항목 2.3`)와 무엇이 정해지지 않았는지 적는다.
     - 선택지는 계획서 내용(결정 사항, 설계안 비교, 리뷰 지적)과 관련 코드를 직접 확인해 만든다. 추천안을 첫 번째에 두고 `(Recommended)`를 붙인다. 설계 방향이 미결이면 `workflow-plan`의 설계안 비교처럼 `preview`에 각 안의 요약과 장단점을 넣는다.
     - 마지막 선택지는 `보류 (이번 실행에서 관련 항목 제외)`로 둔다.
     - 한 번에 최대 4개씩 나누어 묻는다.
   - **계획서 고치기** (모든 답을 받은 뒤, 구현 전에)
     - 확정한 사항은 그 자리의 `(미결)`이나 미정 표현을 확정 내용으로 바꾼다. 본문에서 그 결정을 번호로 가리키던 곳(완료 기준의 `결정 #11대로` 등)은 확정 행 번호로 바꾼다. (`#11` 행의 `선택`은 `(미결)`로 남으므로, 그대로 두면 확인할 때 확정 행을 다시 찾아야 한다) 작업항목이 바뀌면 `진행 관리 규칙`의 추가·취소·병합·분할 표기를, 설계 방향이 바뀌면 절대 규칙의 설계 변경 처리를 따른다.
     - `2. 결정 사항`에 질문마다 한 행을 추가한다. `단계`는 `do · 미결 확정`이다. 기존 결정 사항 행을 확정했으면 새 행 `비고`에 `#n 확정`을 쓰고, 기존 행은 그대로 둔다. `n`은 그 사항을 처음 미결로 남긴 행의 번호다. (본문 표시 `(미결: 결정 #n)`의 번호. 그 행을 `#n 보류`로 가리키는 행은 찾는 대상의 규칙대로 함께 확정되므로 따로 적지 않아도 된다) 다른 섹션이었으면 `비고`에 위치를 쓴다.
     - 보류한 사항은 새 행 `선택`에 `보류 (이번 실행에서 관련 항목 제외)`를, `비고`에 `#n 보류`를 쓴다. (`n`은 위와 같다. 이렇게 써야 나중에 `#n`이 확정될 때 이 행도 함께 닫힌다) 결정 사항 행이 없던 미결(다른 섹션의 `미정` 등)이면 `비고`에 위치를 쓰고, 다음에 확정할 때 이 행 번호를 `#n 확정`으로 가리킨다.
     - `9. 리뷰 결과`의 지적을 확정했으면 그 회차 표는 고치지 않는다. 결정 사항 행 `비고`에 `리뷰 N차 #n`을 쓴다.
     - `8. 작업 이력`에 구분 `계획 변경`으로 한 행을 남긴다. (예: `미결 3건 확정, 1건 보류 — 2.3, 리스크 2, 리뷰 1차 #4`)
   - **보류한 사항**: `(미결)` 표시를 그대로 둔다. 그 사항에 영향을 받는 작업항목은 이번 실행에서 진행하지 않고 `[ ]`로 둔다. 진행 범위의 모든 항목이 영향을 받으면 그 사실을 알리고 중단한다. (절대 규칙의 `중단`. 확정한 사항으로 계획서를 고쳤으면 종료 처리를 한다)
   - 미결 사항이 없으면 이 단계를 건너뛴다. AskUserQuestion을 쓸 수 없는 환경이면 계획서를 고치지 않고 미결 사항 목록을 출력한 뒤 중단한다.
4. **이전 실행이 남긴 상태를 정리한다.** 아래 질문의 답은 `do · 준비`(`[~]` 항목 재개 질문만 `do · <항목 ID>`)로 기록한다.
   - 진행 범위 안에 `[~]`로 남은 항목이 있으면 이전 작업이 중단된 것이다. 항목마다 변경 상태(`파일:` 줄이 있으면 그 파일, 없으면 항목 내용과 `git status`로 가린 그 항목의 파일)를 확인하고, AskUserQuestion 한 번에 항목마다 질문 하나로 묻는다. (항목이 4개를 넘으면 나눈다) 선택지는 `이어서 (Recommended)` / `처음부터 다시`다. 질문 본문에 그 항목의 바뀐 파일을 적는다.
     - 같은 병렬 그룹의 항목이 여럿 `[~]`이면 병렬 실행 중에 중단된 것이다. 이어서 하면 그 항목들은 agent 없이 순서대로 직접 진행한다.
     - `처음부터 다시`는 그 항목의 변경만 되돌린다. 그 항목의 파일 중 다른 항목의 변경이나 시작 전 미커밋 변경과 겹치지 않는 파일만 되돌린다. 추적하는 파일은 `git restore --source=HEAD --worktree -- <파일>`로, 그 항목이 새로 만든 파일은 삭제한다. 겹치는 파일은 되돌리지 않고, diff를 보여 준 뒤 어떻게 할지 묻는다. `git checkout -- .`처럼 파일을 가리지 않고 되돌리지 않는다.
     - 진행 범위 밖의 `[~]` 항목은 묻지 않고 그대로 둔다. 그 변경이 커밋에 섞이면 `커밋 규칙`의 `[~]` 변경 예외로 다룬다.
   - 이미 `[V]`인 항목의 변경이 커밋되지 않고 남아 있으면(2번의 이전 실행 변경) 어떻게 할지 묻는다. 질문 본문에 항목 ID와 파일을 적는다. 선택지는 `지금 커밋` / `이번 작업의 다음 커밋 시점에 함께 커밋` / `커밋에서 빼고 그대로 둠`이다.
     - 계획서의 `커밋 방식`이 `끝에 한꺼번에`이면 두 번째를, 그 밖이면 첫 번째를 추천한다.
     - 2번에서 파일로 판정한 경우(`미커밋:` 목록이 없음)는 사용자 변경일 수 있다. 질문 본문에 파일마다 diff 요약(`git diff --stat`과 바뀐 줄 몇 개)과 "직접 고친 것이면 `커밋에서 빼고 그대로 둠`을 고른다"를 적는다. diff가 그 `[V]` 항목의 내용(항목 설명, 정의 표, 테스트)과 맞으면 위 추천대로, 맞지 않으면(주석·메모, 항목과 관계없는 수정 등) `커밋에서 빼고 그대로 둠`을 첫 번째에 두고 추천한다.
     - `커밋 방식`이 `자동`이고 작업 브랜치가 기본 브랜치가 아니면 묻지 않고 `지금 커밋`으로 정해 한 줄로 알린다. (결정 사항에 기록하지 않는다) 단, 2번에서 파일로 판정한 경우(`미커밋:` 목록이 없음)는 묻는다. 아래 `[~]` 항목과 겹치는 경우는 그 규칙대로 한다.
     - 그 항목의 파일 중 하나라도 `[~]` 항목도 고쳤으면 묻지 않는다. 파일 단위로 스테이징하므로 `[V]` 항목의 변경만 떼어 커밋할 수 없고(`지금 커밋` 불가), `[~]` 항목을 이어서 하면 겹치는 파일은 어차피 커밋에 들어가며, 겹치지 않는 파일만 빼면 코드와 테스트가 갈린다(`커밋에서 빼고 그대로 둠` 불가). `이번 작업의 다음 커밋 시점에 함께 커밋`으로 정하고, 겹치는 `[~]` 항목과 파일을 `do 시작` 행과 완료 보고에 적는다.
     - `지금 커밋`이면 항목 구현을 시작하기 전에 `커밋 규칙`대로 커밋한다. 커밋하기 전에 그때까지 받은 답(이 질문의 답 포함)을 `2. 결정 사항`에 먼저 기록해 이 커밋에 넣는다. (준비 6번에서는 이미 기록한 답을 다시 기록하지 않는다) 끝난 Phase의 변경은 그 Phase 단위로, 끝나지 않은 Phase의 변경은 그 Phase에서 지금까지 끝난 항목 단위로 커밋하고, 계획서도 함께 넣는다. 한 커밋은 검증을 통과한 상태여야 하므로, 커밋은 준비 5번의 기준 상태 확인(테스트·빌드)이 통과한 뒤에 한다. 통과하지 않으면 커밋하지 않고 `이번 작업의 다음 커밋 시점에 함께 커밋`으로 바꿔 알린다.
     - `커밋에서 빼고 그대로 둠`이면 그 파일을 시작 전 미커밋 변경으로 옮긴다.
   - 2번에서 애매하다고 본 파일은 파일마다 `이번 작업의 변경으로 다룸` / `시작 전 변경으로 두고 커밋에서 뺌`으로 묻는다. 질문 본문에 그 파일의 diff 요약(`git diff --stat`과 바뀐 줄 몇 개)과 그 파일을 고칠 항목을 적는다.
     - 아직 `[ ]`인 항목의 파일이면 뒤의 것을 추천한다. (2번: 이전 실행은 `[ ]` 항목을 시작하지 않았다) 그 항목이 이번 진행 범위 안이면, 질문 본문에 "그 항목을 구현하면 같은 파일을 고치므로, 뒤의 것을 고르면 그 항목을 구현할 때 이 변경과 섞인다(커밋 방식이 `자동`이면 그 파일은 커밋에서 빠져 그 항목의 코드가 커밋되지 않고, 그 밖이면 함께 넣어 커밋 전에 다시 묻는다). 섞이지 않게 하려면 중단하고 이 변경을 먼저 따로 커밋하거나 stash한 뒤 다시 실행한다"고 적고, 선택지에 `중단 (이 변경을 먼저 커밋·stash한 뒤 다시 실행)`을 더한다. (`커밋 규칙`의 자동 커밋 예외: 시작 전 변경 파일을 이번 작업에서도 고친 경우) `중단`이면 절대 규칙의 `중단`대로 끝낸다. `4. 영향 범위`에만 있는 파일이면, diff가 `[~]`·`[V]` 항목의 내용(항목 설명, 정의 표)과 맞을 때 앞의 것을, 아니면 뒤의 것을 추천한다.
     - `미커밋:` 목록에 없는 `[~]`·`[V]` 항목의 파일이면(이전 실행이 끝난 뒤의 변경) 뒤의 것을 추천한다. 질문 본문에 이전 실행이 이 파일을 커밋하지 않은 채 남기지 않았다는 것을 적는다.
     - `이번 작업의 변경으로 다룸`을 고른 파일이 아직 `[ ]`인 항목의 파일이면, 그 항목을 구현해 커밋하는 시점에 스테이징하고 그 전의 커밋 시점에는 넣지 않는다. 그 항목이 이번 진행 범위 밖이면 이번 실행에서는 커밋하지 않고, 완료 보고에 남은 변경으로 적는다.
   - **로드맵 선행 확인**: 로드맵 업무 계획서(종료 처리 1번의 `로드맵 갱신` 판정)이고 진행 범위에 `[V]`가 아닌 작업항목이 있으면, README `2. 업무 목록`에서 이 업무의 `선행`을 읽는다. `완료`가 아닌 선행 업무가 있으면 구현을 시작하기 전에 AskUserQuestion으로 묻는다. 추가 지시의 계획서 반영(업무 파일 반영 등)은 선행과 관계없으므로 그것을 마친 뒤에 묻는다.
     - 질문 본문에 그 선행 업무와 상태, 이 계획서가 그 업무에서 쓰는 것(업무 파일 `이 업무가 기대는 것`, `7. 리스크 및 고려사항`의 가정)을 적는다. 선택지는 `중단 — 선행 업무부터 (Recommended)` / `그대로 진행`이다.
     - `중단`이면 절대 규칙의 `중단`대로 끝낸다. 앞에서 고친 계획서(업무 파일 반영 등)는 그대로 남고 종료 처리에서 커밋된다. 완료 보고에 선행 업무를 먼저 진행하라고 적고 `/workflow:workflow-roadmap @<README>`(현황이 다음 커맨드를 안내한다)를 안내한다. `workflow-roadmap` 현황의 반영 커맨드는 선행을 보지 않고 안내되므로, 반영만 하고 여기서 멈출 수 있어야 한다.
     - 이 계획서 `2. 결정 사항`에 같은 선행 업무에 대해 `그대로 진행`을 고른 `do · 준비` 행이 있으면 다시 묻지 않는다. `workflow-plan`의 `그대로 진행`(`plan · 로드맵`)은 계획서를 먼저 쓰겠다는 답이라 구현 시작의 답으로 보지 않는다.
5. 프로젝트의 빌드·테스트·lint 명령을 파악한다. (CLAUDE.md, README, `package.json`, `build.gradle`, `pom.xml`, `Makefile` 등) 찾지 못하면 AskUserQuestion으로 확인한다.
   - 의존성이 설치되지 않아 테스트·빌드를 실행할 수 없으면(예: `node_modules` 없음, 의존성 해석 실패) AskUserQuestion으로 묻는다. 질문 본문에 실행할 설치 명령을 적는다. lock 파일이 있으면 lock을 바꾸지 않는 명령(`npm ci`, `pnpm install --frozen-lockfile` 등)을 쓴다. 선택지는 `설치 후 진행 (Recommended)` / `설치하지 않고 진행 (테스트·빌드 검증 없이. 사유는 준비 6번의 `do 시작` 행에 적는다)` / `중단`이다. 설치로 lock 파일이나 매니페스트가 바뀌면 그 변경은 이번 작업의 커밋에 넣지 않고 완료 보고에 적는다. (계획서 항목이 의존성 추가를 다루면 그 항목의 변경이다) 답은 `do · 준비`로 기록한다.
   - 테스트 명령을 알고 오래 걸리지 않으면, 코드를 고치기 전에 한 번 실행해 **기준 상태**를 확인한다. 이미 실패하는 테스트가 있으면 그 목록을 기록해 둔다. 준비 4번에서 `지금 커밋`을 골랐으면 기준 상태가 통과한 뒤 그 커밋을 한다.
     - 실패한 테스트가 이전 실행 변경 파일에 있거나, 실패 위치가 이전 실행 변경 파일이면 기존 실패가 아니다. 원인이 `[~]` 항목의 미완성이면(실패한 테스트가 `[V]` 항목의 것이어도) 그 `[~]` 항목의 실패로 적어 두고, 그 항목을 검증할 때 통과해야 한다. `[~]` 항목과 관계없이 이미 `[V]`인 항목의 테스트가 실패하면 `그 항목을 [~]로 되돌려 고침 (Recommended)` / `기존 실패로 두고 진행`으로 묻는다. 되돌리면 그 항목을 이번 진행 범위에 넣는다.
     - 이 계획이 이미 커밋한 변경에서 난 실패도 기존 실패가 아니다. 실패한 테스트의 파일이나 실패 위치가 첫 `do 시작` 행의 기준 커밋 이후 바뀐 파일(`git diff --name-only <기준 커밋> -- . ':(exclude)ai-work'`)이면 이 계획의 실패다. (끝난 항목이 넣은 테스트가 날짜·환경에 기대어 뒤늦게 깨진 경우 등이다. 기존 실패로 적으면 이 계획이 만든 문제가 원래 있던 것으로 보고된다) 첫 `do 시작` 행이 없으면(이번이 첫 실행) 해당하지 않는다.
       - 그 변경은 이미 커밋됐으므로 항목을 `[~]`로 되돌리지 않는다. `수정 작업항목 추가 후 진행 (Recommended)` / `이 계획의 실패로 적어 두고 진행`으로 묻는다. 질문 본문에 실패한 테스트, 그 테스트를 넣은 항목 ID, 추정 원인을 적는다. 원인이 같은 실패는 질문 하나로 묶는다.
       - 앞의 것이면 3단계의 `수정 작업항목 추가 후 진행`과 같이 한다. 입력의 추가 지시 처리대로 넣을 위치를 정하고, `코드 정리 및 리뷰` Phase가 이미 `[V]`이면 재실행 항목도 함께 묻는다. 더한 항목은 이번 진행 범위에 넣는다.
       - 뒤의 것이면 `do 시작` 행에 `이 계획의 실패 N건(<테스트>)`으로 적는다. 2단계 4번에서는 기존 실패처럼 항목의 실패로 보지 않고, 3단계에서 그 테스트에 걸린 완료 기준을 확인할 때 다시 다룬다.
     - 그 밖의 실패만 **기존 실패**로 기록한다. 2단계 4번에서 항목의 실패로 보지 않는 것은 이 목록뿐이다.
6. **작업 시작 이력을 남긴다.** 지금까지(입력 확인, 2번, 4~5번) 받은 답과 추가 지시를 `2. 결정 사항`에 기록한 뒤, `8. 작업 이력`에 구분 `do 시작`으로 한 행을 추가한다.
   - 내용: 진행 범위(`전체` / `1.2` / `Phase 2`. 범위 앞에 남은 항목이 있으면 그 ID와 처리, 예: `Phase 3 (앞 1.1~2.3 미완료, 범위만 진행)`), 브랜치, 기준 커밋(2번에서 조회해 둔 값), 시작 시 진행률, 시작 전 미커밋 변경 파일 수와 이전 실행 변경 파일 수·처리(있을 때), 미결 확정·보류 건수, 기준 상태의 테스트 결과(실패가 있으면 그 테스트), 추가 지시가 있으면 그 요약
   - 예: `범위: 전체 / 브랜치: feature/add-login / 기준 커밋: a1b2c3d / 진행률 20% (2/10)`
   - 중단된 작업을 이어서 하면 `재개`를 덧붙인다.
7. 관련 코드 위치와 기존 관례를 파악한다. 먼저 저장소 크기를 센다. (추적 중인 파일 수 `git ls-files | wc -l`, git 저장소가 아니면 Glob `**/*`에서 의존성·빌드 산출물 폴더를 뺀 수)
   - **대략 50개 미만**: agent 없이 계획서의 `4. 영향 범위` 파일과 주변 코드를 직접 읽는다. 이 크기는 직접 읽는 편이 agent를 띄우고 결과를 다시 확인하는 것보다 빠르다.
   - **그 이상**: `4. 영향 범위`와 Glob/Grep 몇 번으로 확인할 후보를 가늠한다. 계획서에 적힌 파일 밖에서 확인할 후보가 많으면(대략 20개 이상, 또는 2개 이상의 모듈/계층에 걸치면서 10개 이상) Agent 도구를 `subagent_type: "Explore"`로 2~3개, 영역을 겹치지 않게 나누어 한 메시지에서 동시에 실행한다. agent는 후보와 근거만 보고하게 하고, 고칠 파일은 직접 열어 확인한다. 후보가 그보다 적거나 Agent 도구를 쓸 수 없으면 직접 탐색한다.

### 2. 항목 구현 (Phase 순서대로, 항목 순서대로)
Phase와 항목은 계획서에 적힌 순서대로 진행한다. (번호 순서가 아니다. 입력의 `넣을 위치` 규칙으로 번호가 앞뒤로 섞일 수 있다)
각 항목마다 다음을 **반드시 순서대로** 수행한다. 병렬 그룹은 아래 `병렬 그룹 실행`을 따른다.

1. 계획서의 해당 항목을 `[ ]` → `[~]`로 바꾼다. 같은 수정에서 상단 표의 작업상태·`최종 갱신`, 해당 Phase 제목의 상태를 고친다. (코드를 고치기 전에 계획서를 먼저 고친다)
   - 항목에 `(단독 커밋)`이 붙어 있으면 `[~]`로 바꾸기 **전에** 앞 항목의 미커밋 소스 변경이 쌓여 있는지 본다. 있으면 그 변경과 계획서를 `커밋 규칙`대로 먼저 커밋한다. (선행 커밋. 이 항목의 변경과 섞이면 나눌 수 없기 때문이다) 계획서의 기록 변경(`do 시작` 행, 결정 사항 등)만 쌓여 있으면 따로 커밋하지 않고 이 항목의 커밋에 함께 넣는다. `끝에 한꺼번에`이면 선행 커밋을 하지 않고, 섞일 수 있다는 것만 완료 보고에 적는다.
2. 항목을 구현한다. 기존 코드의 관례(구조, 네이밍, 스타일)를 따른다.
3. 항목을 검증한다.
   - 해당 범위의 테스트·빌드·lint 중 실행 가능한 것을 돌린다. 실행할 수 없으면 그 이유를 4번의 `항목` 이력 행에 적는다.
   - 계획서상 뒤 항목에 맡긴 테스트는 이 항목의 판정에 쓰지 않는다. 다음 두 경우다.
     - 이 항목의 새 동작을 검증할 테스트를 뒤 항목에서 쓴다. (테스트 작성 항목이 따로 있다)
     - 이 항목 때문에 실패하는 기존 테스트를 뒤 항목에서 고친다. (뒤 항목에 그 테스트 이름이 있다)
     - 이때는 새 동작을 커밋하지 않는 임시 확인(스크립트 실행 등, 만든 파일은 지운다)으로 확인한다. 그 밖의 테스트는 통과해야 한다. 이력 행에 `검증: 임시 확인, 테스트는 1.4`나 `create and authenticate 1건 실패, 1.2에서 수정 예정`처럼 적는다.
     - 한 커밋은 검증을 통과한 상태여야 한다. (`커밋 규칙`) 그래서 그 실패가 남아 있는 동안 커밋 시점이 오면(`(단독 커밋)`의 선행 커밋이나 항목 커밋, 범위를 일부만 준 실행의 종료 처리 등) 커밋하지 않는다. (`커밋 규칙`의 자동 커밋 예외. 커밋 질문을 하는 경우에는 `커밋하지 않고 계속`을 추천한다) Phase 커밋 때는 그 실패를 고치는 뒤 항목도 `[V]`가 되어 있으므로 해소돼 있다.
     - 계획서에 적히지 않은 실패와, 맡은 뒤 항목을 마쳤는데도 남은 실패는 아래 4번의 검증 실패로 다룬다.
   - 항목이 `### DB 변경`·`### API 변경`·`### 화면 변경` 정의에 걸려 있으면 구현 결과를 정의와 대조한다. 정의와 같아야 검증 통과다. (`[V]`로 바꾸기 전에 한다)
     - 걸렸는지는 항목 끝의 `(정의: DB <테이블>, API <번호>, 화면 <번호>)` 표시로 정한다. (`workflow-plan`의 템플릿 작성 지침) 표시가 없으면(예전 계획서) 항목 내용과 고친 코드로 판단한다. 항목에 정의 번호(`API 1`, `화면 변경 2번` 등)가 적혀 있으면 그것을 쓰고, 그것도 없으면 정의 표의 대상을 만들거나 바꾸는 항목이 걸린 것이다. DB는 테이블·컬럼·제약·마이그레이션, API는 URL·요청 검증·응답 필드·오류 코드, 화면은 경로·요소·문구·입력 검증이다. 정의의 일부만 만드는 항목(예: 서비스에서 오류 조건만 만들고 HTTP 응답은 뒤 라우트 항목에서 만듦)도 걸린 것으로 보고, 그 항목이 만든 부분만 대조한다.
     - 대조 기준은 이 플러그인 skill(`db-design`·`api-design`·`ui-design`)의 `3. 점검 모드` 섹션 중 구현 점검(`점검 구현`)에 쓰는 행이다. skill 전체를 Skill 도구로 부르지 않고 그 섹션만 읽는다. (skill 하나가 약 180줄이고 대부분 설계 모드라, 구현 점검에는 그 섹션이면 된다) 이번 실행에서 그런 항목을 처음 검증할 때 Bash 도구로 `sed -n '/^## 3\. 점검 모드/,/^## 4\./p' "${CLAUDE_PLUGIN_ROOT}/skills/<db-design|api-design|ui-design>/SKILL.md"`를 실행해 읽는다. 이후 항목에서는 다시 읽지 않고 같은 기준으로 직접 대조한다. Bash를 쓸 수 없으면 SKILL.md에서 그 섹션 범위만 Read 한다.
     - 화면은 소스(라우트, 요소 이름, 검증 규칙, 문구 리소스, 권한 조건)로만 대조한다. 화면을 띄워 보는 검증은 `workflow-usecase-do`가 한다.
     - 이 항목이 다루는 정의에 대한 지적만 본다. 아직 구현하지 않은 항목의 정의는 지적으로 보지 않는다.
     - 구현이 정의와 다르면 구현을 정의에 맞게 고치고 다시 검증한다. 정의를 바꿔야 하면 절대 규칙대로 AskUserQuestion으로 확인한 뒤 정의도 함께 고친다. 고칠 때는 같은 방법으로 그 skill의 `4. 결과 형식` 섹션(`/^## 4\./,/^## 5\./`)을 읽어 그 형식과 섹션 제목을 따른다. 정의가 새로 생기거나 구조가 바뀌면 절대 규칙의 설계 변경처럼 skill을 인자 `설계`로 부른다.
4. 결과를 기록한다.
   - 검증 통과: `[~]` → `[V]`. `8. 작업 이력`에 구분 `항목`으로 한 행(예: `1.1 완료 — 로그인 폼 컴포넌트 추가`)을 추가하고, 상단 표의 `최종 갱신`을 고친다. 마지막에 `진행 표시 확인`을 실행한다. (스크립트가 상단 표의 작업상태·전체진행률, 진행률 바, 해당 Phase 제목의 상태/진행률을 고친다. `[V]`가 될 때마다 한 번 실행한다. `[~]`로 바꿀 때는 1번처럼 직접 고친다)
   - 준비 5번에서 **기존 실패**로 기록한 테스트는 이 항목의 실패로 보지 않는다. (이전 실행 변경 때문에 실패해 그 항목의 실패로 적어 둔 테스트는 해당하지 않는다) 고치지 않고, 이력 행에 `기존 실패 N건 유지`로 적는다. 단, 그 테스트를 고치려고 더한 수정 작업항목(3단계의 `수정 작업항목 추가 후 진행`)에서는 고친다. 고쳐서 통과하면 기존 실패 목록에서 빼고, 그 뒤 항목부터는 그 테스트도 통과해야 한다. 기준 상태를 확인하지 못했는데 실패가 이 항목과 관계없어 보이면, 고치기 전에 AskUserQuestion으로 확인한다.
   - 검증 실패: 원인을 고쳐 다시 검증한다. 같은 원인으로 3번 실패하면 `[~]`로 둔 채 `8. 작업 이력`에 구분 `항목`으로 실패 내용(예: `1.2 검증 3회 실패 — 원인 요약`)을 남기고, 계속할지 AskUserQuestion으로 확인한다.
5. `4. 영향 범위`에 없던 파일을 고쳤으면 그 파일을 영향 범위에 추가한다.
6. 항목에 `(단독 커밋)`이 붙어 있으면 `커밋 규칙`대로 처리해 이 항목의 변경을 따로 커밋한다. (앞 항목의 변경은 1번의 선행 커밋으로 이미 나뉘어 있다)
   - 이 항목이 Phase의 마지막 항목이면 아래 Phase 완료의 `Phase` 행을 먼저 쓰고 한 번만 커밋한다. 이 커밋이 단독 커밋이자 Phase 커밋이다. (`Phase` 행만 담은 커밋이 따로 생기지 않게 한다)

#### 병렬 그룹 실행
같은 Phase에서 끝에 `(병렬 A)`처럼 같은 표시가 붙은 항목들은 `item-implementer` agent에 하나씩 맡겨 동시에 구현한다. 메인 대화에 각 항목의 코드 탐색·작성 과정이 쌓이지 않고, 구현이 동시에 진행된다. 검증과 계획서 갱신은 메인이 한다.

- **조건** — 순서상 그룹의 첫 항목에 이르렀을 때 다음을 모두 만족하면 병렬로 진행한다. 하나라도 아니면 그룹 표시를 무시하고 위 1~6을 항목마다 순서대로 한다. (계획서의 표시는 그대로 둔다)
  - 그룹에서 진행할 항목(`[ ]`)이 2개 이상이고, 모두 이번 진행 범위 안에 있으며, 보류한 미결 사항에 걸리지 않는다. 진행할 항목이 1개뿐이면 순서대로 한다.
  - 그 항목마다 `파일:` 줄이 있고, 파일이 서로 겹치지 않으며, 준비 단계의 `시작 전 미커밋 변경` 파일과도 겹치지 않는다.
  - 그 항목마다 복잡도가 `중` 이상이다. `복잡도:` 줄이 있으면 그 값을 쓰고, 없으면(예전 계획서) 메인이 `workflow-plan`의 `복잡도` 기준으로 판단한다. `하`인 항목은 빼고, 남은 항목이 2개 이상이면 병렬로, 뺀 항목은 그룹 뒤에 순서대로 한다. (계획서의 표시는 그대로 두고, 완료 보고에 순서대로 바꾼 이유를 적는다)
  - `(단독 커밋)` 항목이나 `코드 정리 및 리뷰` Phase 항목이 섞여 있지 않다. (섞여 있으면 그 항목만 빼고 나머지가 2개 이상이면 병렬로, 뺀 항목은 그룹 뒤에 순서대로 한다)
  - **한 번에 최대 3개**: 조건을 거친 뒤 진행할 항목이 3개를 넘으면(손으로 고친 계획서 등) 계획서 순서대로 3개씩 나누어 차례로 실행한다. 묶음마다 아래 실행·결과 확인·검증을 끝내고 `[V]`까지 기록한 뒤 다음 묶음을 시작한다. 마지막 묶음이 1개면 그 항목은 순서대로 한다.
  - Agent 도구에 이 플러그인의 `item-implementer` agent가 있다. (목록에 표시된 이름, 보통 `workflow:item-implementer`)
- **실행**
  1. 그 항목들을 계획서에서 한 번의 수정으로 모두 `[ ]` → `[~]`로 바꾸고, 같은 수정에서 상단 표의 작업상태·`최종 갱신`과 해당 Phase 제목의 상태를 고친다. 계획서의 `진행 관리 규칙` 블록에 병렬 그룹 줄(`(병렬 A)` 설명과 한 번에 `[~]`로 바꾸는 예외)이 없으면(손으로 표시를 붙인 계획서 등) 같은 수정에서 템플릿(`${CLAUDE_PLUGIN_ROOT}/templates/plan-template.md`)의 문구 그대로 넣는다.
  2. git 저장소이면 agent를 띄우기 직전에 작업 트리의 **스냅샷**을 남긴다. `git stash create`로 현재 변경을 담은 커밋 해시를 얻는다. (작업 트리와 stash 목록은 바뀌지 않는다. 출력이 비어 있으면 `HEAD`를 쓴다) `git ls-files --others --exclude-standard`로 추적하지 않는 파일 목록도 남긴다. `git stash create`는 추적하지 않는 파일을 담지 않으므로, 그 목록의 파일마다 `git hash-object -w --no-filters <파일>`로 내용을 git 객체로 저장하고 경로와 해시를 함께 기억해 둔다. (앞 항목이 새로 만들고 아직 커밋하지 않은 파일을 agent가 고쳤을 때 찾고 되돌리기 위해서다. `--no-filters`는 줄 끝 변환 없이 내용 그대로 저장한다. 객체만 저장되고 작업 트리·index·커밋은 바뀌지 않는다)
  3. Agent 도구로 항목마다 `item-implementer`를 **한 메시지에서 동시에** 실행한다. 프롬프트에는 agent 파일의 `입력` 항목을 넣는다: 계획서 경로, 맡은 항목 ID·내용·`파일:` 목록, 같은 그룹의 다른 항목 ID·파일 목록, 추가 지시와 준비 7번에서 찾은 관례 중 그 항목에 해당하는 것.
  4. **모든 agent의 결과를 받을 때까지 기다린다.** 환경에 따라 agent가 백그라운드로 실행되고 결과가 하나씩 따로 도착한다. 먼저 끝난 agent의 결과를 받아도 나머지가 모두 끝날 때까지 계획서와 소스를 건드리지 않고, 결과 확인도 시작하지 않는다.
- **결과 확인** — 모든 agent의 결과를 받은 뒤 검증 전에 한다.
  - agent가 바꾼 파일은 스냅샷과 비교해 찾는다: `git diff --name-only <스냅샷>`(추적하는 파일)과, 지금의 `git ls-files --others --exclude-standard`에서 스냅샷 때 목록에 없던 파일(새 파일). 이렇게 하면 앞 항목이 남긴 미커밋 변경과 시작 전 미커밋 변경은 빠지고, 이미 변경이 있던 파일을 agent가 또 고친 것도 잡힌다. 스냅샷 때 이미 있던 추적하지 않는 파일(앞 항목이 새로 만든 파일 등)은 `git hash-object --no-filters <파일>`이 기억해 둔 해시와 다르면 바뀐 것이다. agent가 돌려준 `바꾼 파일`도 함께 대조한다. git 저장소가 아니면 agent가 돌려준 `바꾼 파일`로 대신한다.
  - 찾은 파일을 각 항목의 `파일:` 목록과 대조한다. 계획서는 대조에서 뺀다. 목록 밖 파일이 바뀌었으면 그 변경(`git diff <스냅샷> -- <파일>`)을 보여 주고, 유지할지 되돌릴지 AskUserQuestion으로 묻는다.
    - 유지: 그 파일을 `4. 영향 범위`와 해당 항목의 `파일:` 줄에 추가한다.
    - 되돌리기: agent의 변경만 되돌린다. 추적하는 파일은 `git restore --source=<스냅샷> --worktree -- <파일>`로 스냅샷 때의 내용(앞 항목의 변경 포함)으로 되돌리고, 스냅샷 때 없던 새 파일은 삭제한다. 스냅샷 때 이미 있던 추적하지 않는 파일은 지우지 않고, 기억해 둔 해시로 `git cat-file -p <해시> > <파일>` 해서 그때 내용으로 되돌린다. 작업 트리만 바꾸고 index(스테이징)는 건드리지 않는다. `git checkout <스냅샷> -- <파일>`은 index까지 바꾸므로 쓰지 않는다. `git checkout -- <파일>`이나 `--source` 없는 `git restore`로 HEAD까지 되돌리지 않는다.
  - `직접 정한 것`: agent가 계획서에 없어 스스로 정한 세부 사항이다. 메인이 하나씩 본다.
    - 사용자에게 보이는 동작, 오류 코드·메시지, 정의 표에 들어갈 내용, 업무 규칙처럼 요구사항 수준이면 AskUserQuestion으로 확인한다. 선택지에는 agent가 정한 것(끝에 `(현재 구현)`)과 다른 후보를 넣는다. 추천은 메인이 요구사항·정의 표·화면 문구와 대조해 정한다. agent가 정한 것이 맞으면 그것을 추천한다. 다른 후보가 더 맞으면(예: 문구가 "{시각} 이후에 다시 시도하세요"인데 초를 버리면 표시 시각 직후에도 아직 잠겨 있다) 그 후보를 첫 번째에 두고 `(Recommended)`를 붙인 뒤, 질문 본문에 이유를 적는다. 답은 `do · <항목 ID>`로 기록하고, 답이 다르면 메인이 고친다. 여러 항목의 것은 한 번에 최대 4개씩 묶어 묻는다.
    - 같은 주제(시각·금액 표시 형식, 오류 문구 형식, 같은 값의 검사 규칙 등)를 여러 항목이 각자 정했으면 항목끼리 비교한다. agent는 서로의 구현을 보지 않고 정하기 때문이다. 서로 다르면 하나로 맞추는 질문 하나로 묻는다. 구현 세부라도 사용자에게 보이는 결과가 화면·API마다 달라지면 묻는다. 서로 같고 요구사항 수준이면 한 번만 묻는다. 기록 단계는 `do · 3.1, 3.2`처럼 쓴다.
    - 변수명, 내부 함수 분리처럼 구현 세부면 묻지 않고 그대로 둔다.
  - `확인 필요`: 질문을 AskUserQuestion으로 묻고 답을 `do · <항목 ID>`로 기록한다. 그 항목은 agent를 다시 실행하지 않고, agent가 한 변경을 이어받아 메인이 답대로 직접 구현한다. 계획 변경이 필요하면 절대 규칙대로 처리한다.
  - `실행 불가`, 결과 형식이 아님, agent가 중간에 실패함: 그 항목은 `[~]`로 둔 채 남은 변경을 확인하고 메인이 직접 이어서 구현한다.
- **검증** — 그룹의 구현이 모두 끝난 뒤(메인이 이어서 한 항목 포함) 한 번에 한다. 같은 작업 트리에서 빌드·테스트를 동시에 돌리면 서로 충돌하기 때문이다.
  - 테스트·빌드·lint는 그룹 전체에 대해 한 번 실행한다. 정의 대조(위 3번)는 항목마다 한다.
  - 실패하면 오류 위치로 원인 항목을 가려 메인이 고치고 다시 검증한다. 같은 원인으로 3번 실패하는 규칙(위 4번)은 항목마다 적용한다. 원인 항목을 가릴 수 없으면 그룹의 모든 항목을 `[~]`로 둔 채 고친다.
  - 그룹 전체의 테스트·빌드가 통과하기 전에는 그룹의 어떤 항목도 `[V]`로 바꾸지 않는다. (커밋은 검증을 통과한 상태여야 한다) 단, 2단계 3번의 `뒤 항목에 맡긴 테스트`(그룹 뒤 항목이 쓰거나 고치기로 계획된 테스트)의 실패는 빼고 본다. 그 실패는 2단계 3번대로 임시 확인과 이력 행으로 다룬다.
  - 통과하면 정의 대조까지 마친 항목을 **하나씩** 위 4~5번대로 `[V]`, `항목` 이력 행, `진행 표시 확인`을 한다. 이력 행 내용 끝에 `(병렬 A)`를 붙인다. (예: `2.1 완료 — 회원 조회 API 추가 (병렬 A)`)

#### 코드 정리 및 리뷰 Phase
`코드 정리 및 리뷰` Phase의 두 항목은 구현 대신 Skill 도구로 skill을 실행한다. 앞 Phase가 모두 `[V]`일 때만 진행한다. 위 1~5 순서(`[~]` 표시 → 실행 → 검증 → 기록)는 같다.

- **리뷰·정리 대상** — 두 항목 모두 이번 작업 전체가 대상이다. Phase마다 커밋하므로 현재 미커밋 변경만으로는 부족하다.
  - **작업 기준 커밋**: `8. 작업 이력`에서 첫 `do 시작` 행의 기준 커밋이다. 그 행이 없거나 기준 커밋이 적혀 있지 않으면(예전 형식) 어느 커밋부터 볼지 AskUserQuestion으로 묻는다.
    - 예외: `코드 정리 및 리뷰` Phase가 이미 `[V]`인데 더한 재실행 항목(`/code-review medium` 재실행. 추가 지시, 준비 5번이나 3단계의 수정 작업항목 때문에 더한 것 모두)은 그 Phase를 다시 하게 만든 새 항목만 리뷰한다. 이때는 그 항목을 추가한 실행의 `do 시작` 행 기준 커밋을 쓴다. (첫 기준 커밋을 쓰면 이미 리뷰한 원래 구현 전체를 다시 본다)
  - **대상 diff**: `git diff <작업 기준 커밋> -- . ':(exclude)ai-work'`이다. 작업 기준 커밋 이후의 커밋된 변경과 현재 미커밋 변경이 함께 들어가고, 계획서·usecase 문서는 빠진다. `시작 전 미커밋 변경` 파일이 있으면 `':(exclude)<경로>'`를 더해 뺀다. 단, 이번 작업에서도 고쳐 시작 전 변경과 섞인 파일(`커밋 규칙`의 자동 커밋 예외, 이전 `미커밋:` 목록의 `(시작 전 변경 섞임)` 파일)은 빼지 않는다. 빼면 그 항목의 코드가 커밋도 리뷰도 되지 않는다. 대신 skill에 넘기는 대상 문장에 `<파일>에는 사용자의 시작 전 변경도 섞여 있다`를 적는다. 추적하지 않는 새 파일은 이 diff에 나오지 않으므로, 이번 작업이 만든 것이 있으면 그 경로도 대상에 적는다. `git ls-files --others --exclude-standard`에서 `시작 전 미커밋 변경` 파일을 뺀 것이다. (그 목록에는 사용자가 추적하지 않고 둔 파일도 나온다. `':(exclude)'`는 추적하지 않는 파일을 빼 주지 않으므로 목록에서 직접 뺀다)
  - **넘기는 방법**: 두 skill은 커밋 범위를 받는 인자가 없고, 대상을 스스로 정한다. (`main...HEAD`, upstream, 현재 미커밋 변경 등) 그러면 계획서 작성 커밋이나 이번 작업 전의 커밋이 섞이거나, 마지막 Phase만 보게 된다. 그래서 Skill 도구 인자에 대상 diff 명령을 문장으로 적고, skill이 대상을 정하는 단계에서 그 diff를 쓰게 한다. 예: `medium 대상: git diff a1b2c3d -- . ':(exclude)ai-work' 의 변경 전체 (다른 기준으로 diff를 잡지 않는다)`. simplify는 수준 없이 `대상: ...` 문장만 넘긴다.
  - skill이 백그라운드(포크)로 실행되면 결과가 올 때까지 기다린다. 결과를 받으면 지적 위치가 대상 diff 안인지 확인하고, 밖의 지적은 대상 밖으로 구분해 보여 준다.
  - 대상 diff가 비어 있으면 그 항목은 skill을 실행하지 않고 `[V]`로 바꾸며, 이력 행에 `대상 변경 없음`을 쓴다.
- **`/simplify` 항목**
  - Skill 도구로 `simplify`를 실행한다. 이 skill은 정리 내용을 코드에 직접 반영한다.
  - 정의 표(`### DB 변경`·`### API 변경`·`### 화면 변경`)에 적힌 이름·형식·처리 방식(예: 비고의 원자적 증가)을 바꾸는 정리는 반영하지 않는다. `2. 결정 사항`과 선택한 설계안에 어긋나는 정리(예: 선택하지 않은 안의 구조로 바꾸는 공통 헬퍼 추출, 결정으로 유지하기로 한 기존 패턴 바꾸기)도 반영하지 않는다. 동작과 결정을 바꾸지 않는 정리가 이 항목의 범위다. 반영하지 않은 제안은 이력 행에 `미반영: <사유, 결정 #n>`으로 적는다.
  - 반영 후 테스트·빌드로 동작이 바뀌지 않았는지 검증한다. 정의 표에 걸린 코드가 바뀌었으면 2단계 3번대로 정의와 다시 대조한다. 실패하면 일반 항목처럼 원인을 고친다.
  - 이 항목의 `항목` 이력 행 내용에 바뀐 내용을 요약한다. (예: `3.1 완료 — simplify: 중복 함수 2개 통합`, 반영하지 않은 제안은 `미반영: 사유`)
- **`/code-review medium` 항목**
  - Skill 도구로 `code-review`를 `medium` 수준으로 실행한다. `--fix`는 쓰지 않고, 인자의 대상 문장 끝에 `지적만 보고하고 파일은 고치지 않는다`를 붙인다.
  - skill이 그래도 파일을 고쳐 놓을 수 있다. (포크로 실행된 skill이 `--fix` 없이 지적의 수정을 작업 트리에 반영해 돌려준 적이 있다) 그대로 두면 사용자가 고르지 않은 수정이 이 항목의 커밋에 들어간다. git 저장소이면 부르기 직전에 `병렬 그룹 실행`의 스냅샷과 같은 방법(`git stash create`, 출력이 비면 `HEAD`. 추적하지 않는 파일 목록)으로 작업 트리 상태를 남기고, 결과를 받으면 `git diff --name-only <스냅샷>`과 새로 생긴 추적하지 않는 파일로 skill이 바꾼 파일을 찾는다.
    - 바뀐 파일이 있으면 지적을 보여 주기 전에 모두 스냅샷 때의 내용으로 되돌린다. (`git restore --source=<스냅샷> --worktree -- <파일>`, 새로 생긴 파일은 삭제. `병렬 그룹 실행`의 `되돌리기`와 같다) 되돌리기 전에 `git diff <스냅샷>`으로 그 수정을 읽어 두고, 사용자가 고른 지적을 고칠 때 참고한다. 지적별로 골라 남기지 않는 이유는, 한 파일에 여러 지적의 수정이 섞이면 고르지 않은 것만 떼어 내기 어렵기 때문이다.
  - 지적 사항 목록(위치, 내용, 심각도)을 사용자에게 보여 준 뒤, 반영할 항목을 AskUserQuestion(`multiSelect: true`)으로 고르게 한다.
    - 한 질문의 선택지는 2~4개다. 지적이 4개를 넘으면 중요한 것부터 여러 질문으로 나누되, 질문마다 2개 이상이 되게 나눈다. (예: 5개는 3+2) 고를 지적이 1개뿐이면 단일 선택으로 `#n 반영` / `반영하지 않음`을 묻는다.
    - `(Recommended)`는 질문마다 첫 번째 선택지 하나에만 붙인다. 추천하는 지적을 앞에 두고, 둘째 이후의 추천 지적은 설명 끝에 `(추천)`을 적는다. 추천할 지적이 없는 질문에는 붙이지 않는다.
    - 지적마다 계획서와 대조해 선택지 설명에 표시한다.
      - `(이번 변경)` / `(기존 문제)`: skill이 준 구분(예: `pre_existing`)을 쓴다.
      - `(계획서와 충돌: <결정 #n | 3. 작업 범위 제외 | 정의 표 | 7. 리스크>)`: 반영하려면 결정·범위·정의를 바꿔야 하는 지적이다.
      - 수정안이 여럿이면 반영할 안을 적는다. (예: `#1 — 조회를 삭제 앞으로`)
    - 추천하는 지적: 이번 변경이 만든 정확성·보안·데이터 문제이면서 계획서와 충돌하지 않는 지적이다. 기존 문제라도 이번 변경이 다시 쓴 줄(대상 diff에 나오는 줄)에 있거나, 이번 변경이 만든 새 경로(새 API·화면·입력)로 닿게 된 보안·데이터 문제면 이번 변경의 지적처럼 추천하고 `(기존 문제, 이번 변경이 고친 줄)`로 표시한다. nit은 변경이 작고 충돌하지 않을 때만 추천한다. 그 밖의 기존 문제와 계획서와 충돌하는 지적은 추천하지 않는다. 지적이 말하는 실패 상황이 코드·설정·DB 제약 때문에 실제로 생길 수 없으면(예: FK 제약이 켜져 있어 없는 회원을 가리키는 예약이 생기지 않는다) 심각도와 상관없이 추천하지 않고, 선택지 설명에 `(발생 조건 없음: <근거 path:line>)`을 적는다. 추천할 것이 없는 질문도 그대로 묻는다.
    - 계획서와 충돌하는데 심각한 지적은 이 선택에 넣지 않고 지적마다 따로 묻는다. 심각한 지적은 보안 취약점·권한 우회, 데이터 손실, 사용자가 바꾸지 않은 값이 바뀌거나 잘못 저장되는 것이다. 선택지는 `리스크로 기록하고 수용` / `계획 변경 후 반영` / `반영하지 않음`이다. 충돌하는 결정의 근거가 지금도 맞으면 `리스크로 기록하고 수용`을, 결정 때 몰랐던 위험이라 근거가 흔들리면 `계획 변경 후 반영`을 추천한다. 충돌 상대가 결정이 아니라 정의 표·완료 기준·리스크·제외 범위면 그것을 정한 근거(정의 표의 `따른 관례`나 그 행을 정한 결정, 리스크 줄의 이유, 제외의 결정 번호)를 같은 기준으로 본다. 추천하는 것을 첫 번째에 둔다. `리스크로 기록하고 수용`이면 `7. 리스크 및 고려사항`에 한 줄을 추가하고, `계획 변경 후 반영`이면 입력의 추가 지시 처리(충돌하는 곳을 함께 고치는 절차)처럼 결정·범위·정의를 고친 뒤 반영한다. 둘 다 `8. 작업 이력`에 `계획 변경`으로 남긴다.
    - 리뷰가 계획서 자체를 지적하면(정의 표·완료 기준이 구현과 다름 등) 같은 선택에 넣는다. 고르면 계획서를 고치고 `8. 작업 이력`에 `계획 변경`으로 남긴다.
    - 답은 `2. 결정 사항`에 단계 `do · <항목 ID>`, `선택`에 고른 지적 번호(`#1, #3`)로 기록한다. 기존 문제를 골랐으면 사용자 지시로 보고 이 항목에서 반영한다.
  - 고른 항목만 고치고 테스트·빌드로 검증한다. 고친 코드가 정의 표에 걸리면 2단계 3번대로 정의와 다시 대조하고, 정의를 바꿔야 하는 수정이면 정의 표도 함께 고친다.
  - 이 항목의 `항목` 이력 행 내용에 결과를 쓴다. (예: `3.2 완료 — code-review: 지적 N건, 반영 M건 (미반영: 위치·사유)`)
  - 지적 사항이 없으면 그대로 `[V]`로 바꾸고 이력 행에 `code-review: 지적 없음`을 쓴다.
- 이 Phase는 Phase 완료 시점이 아니라 **각 항목이 `[V]`가 될 때마다** `커밋 규칙`대로 커밋한다. (동작을 바꾸지 않는 정리와 리뷰 반영을 따로 되돌릴 수 있게 한다) `/simplify` 전에 앞 Phase의 미커밋 변경이 남아 있으면 먼저 그 변경을 커밋 규칙대로 커밋한다. 항목이 소스를 바꾸지 않았으면(정리할 것이 없음, 지적 없음, 반영할 지적을 고르지 않음) 그 항목은 커밋하지 않는다. 계획서 변경은 다음 커밋 시점에 함께 넣는다. (계획서만 담은 커밋이 따로 생기지 않게 한다)
- skill을 쓸 수 없는 환경이면 항목을 `[~]`로 둔 채 AskUserQuestion으로 확인한다. 선택지:
  - 직접 같은 관점으로 정리·리뷰한다
  - 나중에 한다 (`[ ]`로 되돌림. 계획서는 완료 상태가 되지 않는다)
  - 생략한다 (계획서 `진행 관리 규칙`의 취소 표기로 바꾼다. 예: `(취소: do, skill 없음)`)

- 현재 시각은 Bash `date '+%Y-%m-%d %H:%M:%S'` 또는 PowerShell `Get-Date -Format 'yyyy-MM-dd HH:mm:ss'`로 조회한다. `최종 갱신`은 계획서 `진행 관리 규칙`대로 항목 상태를 바꿀 때마다(`[~]`, `[V]`) 고친다.
- 여러 항목을 몰아서 한꺼번에 `[V]`로 바꾸지 않는다. (병렬 그룹도 `[V]`는 항목마다 따로 바꾼다)
- Phase가 끝날 때마다(그 Phase의 모든 작업항목이 `[V]`) `8. 작업 이력`에 구분 `Phase`로 한 행을 남긴다. (예: `Phase 1 완료 (3/3)`) 이어서 `커밋 규칙`대로 이 Phase를 커밋한다. `코드 정리 및 리뷰` Phase는 위 규칙대로 항목마다 커밋한다. 이번 실행의 마지막 커밋 시점이면 `커밋 규칙`의 `마지막 커밋 시점은 종료 처리로 미룬다`를 따른다.

### 3. 완료 기준 확인
진행 범위와 상관없이 `5. 작업 항목`의 모든 항목(취소선 줄 제외)이 `[V]`가 되면 `6. 완료 기준`에서 `[V]`가 아닌 기준을 확인한다. 아직 남은 작업항목이 있으면 이 단계를 건너뛴다. (보류한 미결 사항 때문에 남은 항목도 남은 작업항목이다)

기준마다 아래 셋 중 하나로 나눈다. 기준 줄 끝의 `(확인: …)` 표시를 따른다. `테스트`·`명령`이면 명령으로 확인하는 기준, `usecase`면 화면 확인 기준, `사용자`면 사람이 판단하는 기준이다. (`usecase`는 API 응답처럼 명령으로도 확인할 수 있어도 화면 기준과 같이 다룬다) 표시가 없으면(예전 계획서) 기준 줄에 적힌 확인 방법(예: `(테스트 1.4)`, `workflow-usecase-plan` → `workflow-usecase-do`로 확인)을 따르고, 그것도 없으면 내용으로 나눈다.

- **명령으로 확인할 수 있는 기준**(빌드, 테스트 등)
  - `(확인: 명령 …)`에 실행할 명령 대신 절차(예: `001~003만 적용한 임시 DB에 004 적용`)가 적혀 있으면, 그 절차대로 확인하는 임시 스크립트를 만들어 실행한다. 확인에 쓴 임시 스크립트·DB 파일은 확인 뒤 지우고 커밋하지 않는다. (2단계 3번의 임시 확인과 같다) 이력 행에 실행한 방법을 한 줄로 적는다.
  - 실행해서 통과하면 `[V]`로 바꾸고, `8. 작업 이력`에 구분 `항목`으로 한 행(예: `DoD-1 확인 — ./gradlew build 통과`)을 남긴다. 진행 표시는 `진행 표시 확인`으로 고친다.
  - 실패하면 `[ ]`로 두고 `8. 작업 이력`에 구분 `항목`으로 실패 내용(예: `DoD-1 실패 — UserServiceTest 2건 실패`)을 남긴다. 실패 원인을 확인한 뒤 AskUserQuestion으로 묻는다. 질문 본문에 실패 내용과 추정 원인을 적고, 기준 상태에서 이미 실패하던 테스트(기존 실패, 준비 5번에서 `이 계획의 실패`로 적어 둔 것) 때문이면 그 사실도 적는다. 선택지:
    - `수정 작업항목 추가 후 진행 (Recommended)`: 입력의 추가 지시 처리(`넣을 위치`, 충돌하는 곳을 함께 고치기)대로 새 작업항목을 추가하고, 2단계의 일반 항목처럼 구현·검증한 뒤 이 단계를 다시 한다. 이 단계에서는 모든 작업항목이 `[V]`이므로 새 Phase가 되고, `코드 정리 및 리뷰` Phase가 있으면 그 번호를 밀지 않고 앞에 둔다. 그 Phase가 이미 `[V]`이면 입력의 규칙대로 `/code-review medium` 재실행 항목도 추가할지 함께 묻는다. (재실행 항목은 그 Phase 끝에 붙어 새 Phase 뒤에 실행된다)
    - `[ ]로 두고 종료`: 완료 보고에 실패 내용을 적는다.
- **화면 확인이 필요한 기준**(기준 줄이 usecase 확인을 지정한 기준 포함)은 `[ ]`로 두고, `workflow-usecase-plan` → `workflow-usecase-do`로 검증하도록 안내한다.
- **사람이 판단해야 하는 기준**은 AskUserQuestion으로 충족 여부를 확인받는다. 질문 본문에 기준 내용과 판단 근거(관련 변경 파일, 실행한 검증 결과, 관련 결정 사항)를 적는다. 한 번에 최대 4개씩 묻는다. 선택지:
  - `충족 — [V]로 표시`: `[V]`로 바꾸고 `8. 작업 이력`에 구분 `항목`으로 `DoD-2 확인 — 사용자 확인`을 남긴다. 진행 표시는 `진행 표시 확인`으로 고친다.
  - `미충족 — 수정 작업항목 추가`: 위 명령 기준 실패의 `수정 작업항목 추가 후 진행`과 같이 처리한다.
  - `나중에 확인 ([ ] 유지)`: 완료 보고에 적는다.
- 이 단계의 답은 `2. 결정 사항`에 `do · DoD-2`처럼 기준 ID를 붙여 기록한다.
- AskUserQuestion을 쓸 수 없는 환경이면 묻는 기준은 `[ ]`로 두고 완료 보고에 적는다.

### 4. 종료 처리
1. `진행 표시 확인`을 실행해 전체진행률, 진행률 바, Phase별 상태, 작업상태를 확정한다. (중단해 `[~]`로 남은 항목도 그대로 센다)
   - **로드맵 갱신**: 계획서 `### 요구사항 문서`의 경로가 `ai-work/roadmaps/` 아래 업무 파일이면 로드맵 업무 계획서다. 그 업무 파일 상단 표의 `로드맵` README에서 이 업무 행(`계획서` 칸이 이 계획서인 행)을 찾는다.
     - 확정한 작업상태가 `완료`인데 행의 `상태`가 `완료`가 아니면 `완료`로, `완료`가 아닌데 행이 `완료`이면 `진행`으로 바꾼다. 같으면 고치지 않는다.
     - 바꾸면 README의 `로드맵 관리 규칙`대로 상단 표(작업상태·전체진행률·최종 갱신)를 고치고, `5. 작업 이력`에 구분 `업무 완료` 또는 `업무 진행`으로 `<번호> 완료 — <계획서 경로>`처럼 남긴다.
     - README가 작업 트리에 없거나 `계획서` 칸이 이 계획서가 아니면(다른 계획서로 바뀜) 고치지 않고 완료 보고에 적는다.
     - 고친 README는 2번에서 정하는 종료 커밋에 넣는다. (`커밋 규칙`의 스테이징 대상)
2. **커밋할지 먼저 정한다.** git 저장소이고 `커밋 방식`이 `해당 없음`이 아니면 `git status --short`로 이번 실행에서 아직 커밋하지 않은 변경을 확인한다. (`마지막 커밋 시점은 종료 처리로 미룬다`로 미룬 변경, 완료 기준 확인으로 바뀐 계획서, 중단된 항목의 변경, `커밋하지 않고 계속`으로 미룬 변경 등) 3번의 `do 종료` 행도 이 커밋에 들어간다.
   - `커밋 규칙`대로 정한다. `자동`이면 묻지 않고 커밋하기로 하고(작업 브랜치가 기본 브랜치이면 커밋 질문), `확인`·`끝에 한꺼번에`·이번 실행에서 `끝에 한꺼번에`를 고른 경우는 지금 커밋 질문으로 묻는다. 질문 본문의 파일 목록에 계획서(`do 종료` 행 포함)를 넣는다. 답은 `do · 커밋`으로 기록한다.
   - 중단된 항목(`[~]`)의 변경이 섞여 있거나, 뒤 항목에 맡긴 테스트 실패가 남아 있으면(범위를 Phase 중간까지만 준 경우 등) 자동 커밋 예외다. `자동`이면 묻지 않고 커밋하지 않기로 하고, 완료 보고에 커밋하지 않은 변경과 사유를 적는다. 커밋 질문을 하는 경우에는 질문 본문에 검증되지 않은 변경이나 남은 실패가 포함된다는 것을 적고, `커밋하지 않음`을 첫 번째에 두고 `(Recommended)`를 붙인다.
   - `시작 전 미커밋 변경`과 섞인 파일·비밀값 파일은 `자동`이면 빼고 나머지를 커밋한다. (`커밋 규칙`의 자동 커밋 예외)
   - `do 종료` 행보다 먼저 정하는 이유는, 그 행에 이번 실행의 커밋 횟수와 결정 건수를 정확히 적기 위해서다.
3. `8. 작업 이력`에 구분 `do 종료`(중간에 멈췄으면 `do 중단`)로 한 행을 남긴다.
   - 내용: 완료 항목 수 / 남은 항목 수, 변경 파일 수, 실행한 검증과 결과, 계획 변경·새 결정 건수, 이번 실행의 커밋 횟수, 미커밋 목록
   - 예: `완료 5건(1.1~2.2), 남음 2건 / 변경 파일 7개 / ./gradlew test 통과 / 결정 2건 추가 / 커밋 3회 / 미커밋: 없음`
   - **미커밋 목록**: 이번 실행의 작업 변경 중 2번의 결정대로 하면 커밋되지 않고 남는 파일을 `미커밋: <파일>, <파일>`로 쓴다. 없으면 `미커밋: 없음`. `시작 전 미커밋 변경`과 섞여 뺀 파일은 `<파일>(시작 전 변경 섞임)`으로 쓴다. 이전 `미커밋:` 목록에서 이어받은 섞인 파일도 지금 바뀌어 있으면 이번에 고치지 않았어도 다시 쓴다. (빠뜨리면 다음 실행이 그 파일을 사용자 변경으로 잘못 안내한다) 이번 작업과 관계없는 `시작 전 미커밋 변경`과 비밀값 파일은 쓰지 않는다.
   - **시작 전 변경 목록**: 준비 4번에서 `시작 전 변경으로 두고 커밋에서 뺌`·`커밋에서 빼고 그대로 둠`을 고른 파일과, 이전 `시작 전 변경:` 목록에서 이어받은 파일 중 지금도 바뀌어 있고 이번 작업이 고치지 않은 것을 `시작 전 변경: <파일>, …`으로 미커밋 목록 뒤에 쓴다. 없으면 쓰지 않는다. 다음 실행이 같은 파일을 다시 묻지 않게 한다. 다음 실행이 준비 2번에서 이 목록으로 이전 실행 변경을 가린다. 커밋이 실패한 채 끝나 4번의 `do 중단` 행을 더할 때는 그 행에 커밋하지 못한 작업 변경 파일 전체로 다시 쓴다. (계획서 자신은 넣지 않는다)
   - 커밋 횟수는 2번에서 커밋하기로 한 것까지 세고, 결정 건수는 2번의 `do · 커밋` 행까지 센다. 커밋 해시는 계획서에 쓰지 않는다. (`커밋 규칙` 참고)
4. 2번에서 커밋하기로 했으면 커밋한다. 커밋이 실패한 채 끝나면(`커밋 규칙`의 `실패 처리`) 3번 행은 고치지 않는다. (작업 이력은 추가만 한다) `8. 작업 이력`에 구분 `do 중단`으로 `종료 커밋 실패 — <원인>, 이번 실행 커밋 N회 / 미커밋: <파일...>`을 한 행 더하고, 계획서는 커밋하지 않은 채로 둔다.

## 완료 보고
- 대상 계획서 경로와 진행 범위 (범위 앞에 남은 항목이 있었으면 그 ID와, 범위만 진행했다면 그 항목 없이 확인하지 못한 것)
- 완료한 항목 / 남은 항목, 전체진행률과 작업상태
- 변경한 파일 목록
- 병렬로 진행한 그룹과 순서대로 바꿔 진행한 그룹 (그 이유. 해당 없으면 생략)
- 커밋 방식, 이번 실행의 커밋 목록(`git log --format='%h %s' <이번 실행의 기준 커밋>..HEAD`)과 커밋하지 않고 남은 변경
- 커밋했으면 되돌리는 방법: push 전이면 `git reset --soft <이번 실행의 기준 커밋>` (변경은 작업 트리에 남는다)
- 실행한 검증(테스트·빌드)과 결과
- 확정한 미결 사항과 보류한 미결 사항(보류 때문에 진행하지 않은 항목 포함)
- 계획 변경 사항(추가·분할·병합·취소한 항목, 설계 방향 변경, 새 결정 사항)
- 기준 상태에서 이미 실패하던 테스트가 있으면 그 목록
- 완료 기준 확인 결과(통과, 실패와 추가한 수정 항목, 사용자 확인으로 충족·미충족·보류한 기준)
- 남은 완료 기준과 확인 방법. 화면 검증이 필요하면 `/workflow:workflow-usecase-plan @<계획서 경로>` 실행을 안내한다.
- 로드맵 업무 계획서면 로드맵 README에 반영한 상태(또는 반영하지 못한 이유). 업무가 `완료`가 됐으면 `/workflow:workflow-roadmap @<README>`로 다음 업무를 확인하라고 안내하고, 다음 업무 전에 `/clear`로 대화를 비우면 컨텍스트가 가볍게 유지된다고 한 줄 적는다.
- 중단했으면 중단 사유와, `/workflow:workflow-do @<계획서 경로>`로 이어서 진행할 수 있다는 점
