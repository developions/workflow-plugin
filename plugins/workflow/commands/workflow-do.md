# workflow-do

`workflow-plan`으로 생성한 작업계획서를 기준으로 **구현(코딩)** 을 진행하고, 항목마다 계획서의 진행 상황을 실시간으로 갱신한다.

## 입력

```
$ARGUMENTS
```

- mention(`@경로`) 또는 경로로 지정된 작업계획서를 대상으로 한다. `@`를 뗀 경로의 파일을 직접 읽는다. (자동 첨부에 기대지 않는다)
- 지정이 없으면 `ai-work/plans/` 하위 최신 계획서를 찾아 AskUserQuestion으로 대상이 맞는지 확인한다.
- 진행 범위
  - 항목 ID(`1.2`, `2.1,2.3`)나 `Phase 2`가 주어지면 그 범위만 진행한다.
  - 없으면 `5. 작업 항목`에서 `[V]`가 아닌 첫 항목부터 끝까지 순서대로 진행한다. (`(병렬 A)` 같은 표시가 붙은 그룹은 2단계의 `병렬 그룹 실행`대로 함께 진행한다. 체크박스가 있는 줄만 대상이다. `6. 완료 기준`은 3단계에서 확인하고, 취소선 줄은 건너뛴다)
  - 범위가 `코드 정리 및 리뷰` Phase인데 앞 Phase가 모두 `[V]`가 아니면, 그 사실을 알리고 중단한다.
- 그 밖의 텍스트는 추가 지시로 반영한다.
  - 추가 지시가 계획서에 없는 작업(예: usecase 실패 수정)이면, 새 작업항목으로 추가할지 AskUserQuestion으로 묻는다. 추가하면 계획서 `진행 관리 규칙`대로 번호를 붙이고, 일반 항목처럼 진행한다. 추가하지 않으면 그 지시는 하지 않는다.
  - `코드 정리 및 리뷰` Phase가 이미 `[V]`인데 새 항목이 추가되면, 그 Phase에 `/code-review medium` 재실행 항목을 새 번호로 추가할지 함께 묻는다.
- 남은 항목(`[V]`가 아닌 작업항목)이 없고 추가 지시도 없을 때
  - `6. 완료 기준`에 `[V]`가 아닌 기준이 남아 있으면, 1단계 준비를 마친 뒤 2단계를 건너뛰고 3단계(완료 기준 확인)만 진행한다. `do 시작` 행의 진행 범위는 `완료 기준`으로 쓴다.
  - 남은 완료 기준도 없으면 진행률만 보고하고 종료한다.
- 대상이 `workflow-plan` 형식(`진행 관리 규칙`, `5. 작업 항목`, `6. 완료 기준`)이 아니면 그 사실을 알리고, 계속할지 AskUserQuestion으로 확인한다.
- 이 입력 확인 중 계획서를 고치는 일(형식 올리기, 추가 지시의 항목 추가)은 준비 2번(브랜치 확인)을 마친 뒤에 한다.
- 예전 형식으로 만든 계획서인지 확인한다. `결정 · 이력 기록 규칙` 블록이 없거나, 상단 표에 `커밋 방식` 행이 없거나, `2. 결정 사항` 표 머리글이 `# | 일시 | 단계 | 질문 | 선택지 | 선택 | 비고`, `8. 작업 이력` 표 머리글이 `일시 | 구분 | 내용`이 아니면 형식을 올릴지 AskUserQuestion으로 한 번 묻는다. 올리면 `${CLAUDE_PLUGIN_ROOT}/templates/plan-template.md`(`workflow-plan`의 템플릿)를 Read 해서 빠진 블록을 그 문구 그대로 넣고, 표는 기존 행을 그대로 두고 새 열을 `-`로 채운다. `커밋 방식` 행이 없으면 `확인`으로 넣는다. (같은 질문에서 `자동`으로 바꿀지도 함께 묻는다) 올리지 않으면 새로 추가하는 행도 기존 표 형식에 맞추고, 커밋 방식은 `확인`으로 본다.

## 절대 규칙

- **계획서가 기준이다.** `3. 작업 범위`의 제외 항목이나 계획서에 없는 작업은 하지 않는다.
- **애매한 사항은 직접 결정하지 않는다.** 다음 경우 AskUserQuestion으로 확인한다. (한 번에 최대 4개, 추천안은 첫 번째 옵션 + `(Recommended)`)
  - 항목 설명만으로 구현 방법이 둘 이상으로 갈릴 때
  - 코드를 보니 계획서와 실제 구조가 달라 계획 변경이 필요할 때 (항목 추가·분할·병합·취소, 영향 범위 변경)
  - 구현 중 `설계안 비교`에서 선택한 안의 `성립 전제`가 깨져 그 안으로 진행할 수 없을 때. 혼자 방향을 바꾸지 않는다. 막힌 이유와 함께 선택하지 않은 안을 다시 보여 주고 방향을 바꿀지 묻는다. 바꾸면 `설계안 비교`의 선택 결과를 고치고, 바뀌기 전 안은 선택하지 않은 안으로 이유와 함께 옮긴다. 새 설계에 맞게 작업항목과 `4. 영향 범위`를 고친다. `DB 변경`·`API 변경`·`화면 변경` 정의가 바뀌면 해당 skill을 인자 `설계`로 불러 정의를 다시 정하고(여럿이면 `workflow:db-design` → `workflow:api-design` → `workflow:ui-design` 순서), skill이 돌려준 `미정 사항`도 AskUserQuestion으로 묻는다. 이전 설계로만 의미 있는 항목은 취소 표기로 바꾼다. 이전 설계로 이미 `[V]`가 된 항목은 어떻게 할지 먼저 확인한다. `8. 작업 이력`에 구분 `계획 변경`으로 남긴다.
  - 계획서에 없는 파일을 크게 고쳐야 할 때
  - 코드의 실제 동작이 `1. 요구사항`의 `현재 동작` 표와 달라, 요구사항의 전제가 맞지 않을 때
  - `4. 영향 범위`의 `DB 변경`·`API 변경`·`화면 변경` 정의(테이블·컬럼·인덱스, URL·요청·응답·오류 코드, 화면 경로·요소 이름·검증·문구·권한별 노출)와 다르게 구현해야 할 때. 이 표가 구현의 기준이다. 확인받아 바꿨으면 표도 함께 고친다.
  - DB 마이그레이션, 파일 삭제, 외부 서비스 호출처럼 되돌리기 어려운 작업을 할 때
  - AskUserQuestion을 쓸 수 없는 환경(비대화형 실행 등)이면 그 항목을 `[~]`로 둔 채 `8. 작업 이력`에 구분 `do 중단`으로 사유를 남기고 중단한다.
- AskUserQuestion으로 받은 답은 질문·선택지·선택 결과를 작업계획서 `2. 결정 사항`에 한 행씩 추가한다. 기존 행은 고치거나 지우지 않는다. (기록 형식은 계획서의 `결정 · 이력 기록 규칙` 참고) `단계`는 `do`이고, 특정 항목에서 물었으면 `do · 1.2`처럼 항목 ID를 붙인다. 질문의 답이 아니라 사용자가 대화로 직접 준 지시·정정도 같은 표에 `do · 대화 지시`로 남기고, 인자로 준 추가 지시도 여기에 남긴다. `일시`는 답을 받은 시점이다. 계획을 바꿨으면 `8. 작업 이력`에도 구분 `계획 변경`으로 남긴다.
- 상태 표기·진행률·작업상태, 항목 ID와 항목 추가·취소·병합·분할은 계획서 안의 `진행 관리 규칙`을 그대로 따른다. 기존 ID(`1.1`, `DoD-1`)는 바꾸지 않는다.
- **진행 표시 확인**: 진행률·진행률 바·작업상태·Phase 제목의 상태는 손으로 다시 세지 않는다. Bash 도구로 `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-progress.sh" "<계획서 경로>"`를 실행한다. 스크립트가 적힌 값과 다른 곳만 `적힌 값 → 맞는 값`으로 출력하면 체크 표기는 그대로 두고 그 값으로 고친다. (`진행 표시 일치`면 고칠 곳 없음) `최종 갱신`은 확인하지 않으므로 따로 고친다. 스크립트를 실행할 수 없으면 `진행 관리 규칙`대로 직접 센다.
- **커밋은 계획서 상단 표의 `커밋 방식`을 따르고, push는 하지 않는다.** 커밋 시점은 Phase 완료, `(단독 커밋)` 항목 완료, `코드 정리 및 리뷰` Phase의 각 항목 완료, 종료 처리다. (아래 `커밋 규칙` 참고)

## 커밋 규칙

- **단위**: 기본은 Phase 단위다. 계획서에서 `(단독 커밋)`이 붙은 항목(DB 마이그레이션, 파일 삭제 등 되돌리기 어려운 작업)은 그 항목만 따로 커밋하고, `코드 정리 및 리뷰` Phase는 `/simplify`와 `/code-review` 반영을 각각 커밋한다. 한 커밋은 검증(테스트·빌드)을 통과한 상태여야 한다.
- **커밋 방식**: 계획서 상단 표의 `커밋 방식` 값에 따라 커밋 시점마다 다음과 같이 한다. 값이 없으면(예전 계획서) `확인`으로 본다. git 저장소가 아니거나 `해당 없음`이면 커밋하지 않는다.
  - `자동`: 묻지 않고 커밋한 뒤 `커밋 <해시> <제목>` 한 줄로 알린다. 아래 **자동 커밋 예외**에 해당하면 그 시점에만 묻는다.
  - `확인`: 시점마다 아래 **커밋 질문**으로 묻는다.
  - `끝에 한꺼번에`: 중간 시점에는 커밋하지 않고, 종료 처리에서만 커밋 질문으로 묻는다.
  - 사용자가 추가 지시나 대화로 커밋 방식을 바꾸면 상단 표의 값을 고치고 `2. 결정 사항`에 `do · 대화 지시`, `8. 작업 이력`에 구분 `계획 변경`으로 남긴다.
- **자동 커밋 예외** — `자동`이어도 다음 중 하나면 커밋 질문으로 묻는다. 질문 본문에 해당 사유를 적는다.
  - 작업 브랜치가 기본 브랜치(main/master/develop 등)다
  - 커밋할 파일에 `시작 전 미커밋 변경` 파일이 섞인다
  - 검증이 끝나지 않은(`[~]`) 항목의 변경이 섞인다 → `커밋하지 않고 계속`을 첫 번째에 두고 `(Recommended)`를 붙인다
  - 비밀값 파일(`.env`, 키·인증서·credentials 파일 등)로 보이는 파일이 변경에 있다 → 그 파일은 빼고 커밋할지 묻는다
  - 커밋 훅이 실패했다 (아래 `실패 처리`)
- **커밋 질문**: AskUserQuestion으로 묻는다. 질문 본문에 커밋할 파일 목록과 메시지 초안을 적는다. 선택지:
  - `커밋 (Recommended)`
  - `커밋하지 않고 계속`: 변경은 다음 커밋 시점에 함께 다룬다.
  - `이번 실행은 끝에 한꺼번에`: 이번 실행에서는 중간 시점에 커밋하지 않고 종료 처리에서만 묻는다. (계획서의 `커밋 방식`은 바꾸지 않는다)
  - 종료 처리에서는 `커밋 (Recommended)` / `커밋하지 않음` 두 개만 둔다.
  - 답은 `2. 결정 사항`에 `do · 커밋`으로 기록한 뒤 커밋한다. (그 행도 같은 커밋에 들어간다) 묻지 않고 한 자동 커밋은 결정 사항에 기록하지 않는다.
- **스테이징**: 지난 커밋 이후 이번 실행에서 바꾼 파일과 계획서만 `git add -- <경로...>`로 스테이징하고 `git commit -- <경로...>`처럼 그 파일들만 커밋한다. `git add -A`, `git add .`는 쓰지 않는다.
  - 준비 단계에서 기록한 `시작 전 미커밋 변경` 파일은 넣지 않는다. 그 파일을 이번 작업에서도 고쳤으면 시작 전 변경도 함께 커밋된다는 것을 질문 본문에 적는다.
  - 비밀값 파일(`.env` 등)과 usecase 증적은 넣지 않는다.
- **계획서도 함께 커밋한다.** 그 단위에서 갱신한 `[V]` 표기, 진행률, 작업 이력, 영향 범위가 소스와 같은 커밋에 들어가야 코드와 진행 상태가 맞는다.
- **메시지**: 프로젝트 규칙(CLAUDE.md 등)의 커밋 형식이 있으면 그것을 따른다. 없으면 다음 형식을 쓴다.
  - 제목: `<type>(<scope>): <요약> (<항목 ID>)` — 예: `feat(auth): 로그인 실패 횟수 저장 (1.1~1.3)`, `refactor: simplify 정리 (3.1)`, `fix: code-review 지적 2건 반영 (3.2)`, `docs(plan): 완료 기준 확인 (DoD-1~3)`
  - 본문 끝 줄: `Plan: <계획서 경로>`
- **실패 처리**: 커밋이 실패하면(훅 실패 등) `--no-verify`로 우회하지 않는다. 커밋 방식과 상관없이 원인을 알리고, 고칠 수 있으면 고친 뒤 다시 커밋할지 AskUserQuestion으로 묻는다.
- 커밋 해시는 계획서에 쓰지 않는다. (기록 후 커밋하므로 알 수 없다) 완료 보고에 적는다.

## 처리 절차

### 1. 준비
1. 계획서를 읽고 요구사항(`현재 동작 → 변경 후 동작` 표가 있으면 포함), 결정 사항(선택한 설계안과 그 전제 포함), 작업 범위, 영향 범위(`DB 변경`·`API 변경`·`화면 변경` 정의 표가 있으면 포함), 진행 범위의 항목을 파악한다.
2. 브랜치를 확인한다. 계획서를 고치거나 코드를 보기 전에 한다.
   - **작업 브랜치 확인** — 계획서의 `작업 브랜치`에서 실행되도록, 코드를 보거나 문서를 고치기 전에 먼저 한다.
     - git 저장소가 아니거나 `작업 브랜치`가 `해당 없음`으로 시작하면(`해당 없음 (detached HEAD)` 포함) 건너뛴다.
     - 현재 브랜치(`git branch --show-current`)가 `작업 브랜치`와 같으면 그대로 진행한다. 출력이 비어 있으면(detached HEAD) 다른 것으로 본다.
     - 다르면 AskUserQuestion으로 묻는다. 질문 본문에 현재 브랜치, 작업 브랜치, 미커밋 변경사항(`git status --short`) 유무를 적는다. 선택지:
       - `작업 브랜치로 전환 (Recommended)`: 로컬에 있으면 `git switch <작업 브랜치>`, 원격에만 있으면 `git switch --track origin/<작업 브랜치>`. 어디에도 없으면 이 선택지를 `현재 위치에서 작업 브랜치를 새로 만들어 전환`(`git switch -c <작업 브랜치>`)으로 바꾼다.
       - `현재 브랜치에서 진행`: 계획서 상단 표의 `작업 브랜치`를 현재 브랜치로 고치고 `8. 작업 이력`에 구분 `계획 변경`으로 남긴다. (detached HEAD이면 이 선택지는 뺀다)
       - `중단`
     - 전환이 실패하면(미커밋 변경 충돌 등) stash나 강제 전환을 하지 않는다. 실패 내용을 알리고 중단한다.
     - 전환했으면 계획서를 다시 읽는다. (브랜치마다 내용이 다를 수 있다)
     - 지정한 경로에 계획서가 없으면 `git log --all --format=%h -1 -- <경로>`로 그 파일을 마지막으로 바꾼 커밋을 찾고 `git branch -a --contains <커밋>`으로 어느 브랜치에 있는지 찾아 알리고 중단한다.
     - 답은 작업계획서 `2. 결정 사항`에 `do · 브랜치`로 기록한다.
   - 브랜치 확인을 마치면 `git status --short`로 **시작 전 미커밋 변경** 파일 목록을 기록해 둔다. 커밋할 때 이 파일들은 넣지 않는다. (`커밋 규칙` 참고) 계획서 자체가 목록에 있으면 그 사실만 기억하고 커밋에서는 계획서를 넣는다.
3. **미결 사항을 확정한다.** 구현을 시작하기 전에 계획서에서 아직 정해지지 않은 사항을 찾아, AskUserQuestion으로 확답을 받고 계획서를 고친 뒤 진행한다.
   - **찾는 대상**
     - `(미결)` 표시가 붙은 곳 (`2. 결정 사항` 표와 `9. 리뷰 결과`는 아래 규칙으로 따로 본다)
     - `2. 결정 사항`에서 `선택`이 비어 있거나 `미정`·`보류`·`추후 결정`·`TBD`인 행. 단, 뒤에 그 행을 `#n 확정`·`#n 변경`으로 가리키는 행이 있으면 이미 확정된 것이다.
     - `설계안 비교`에서 선택한 안이 비어 있거나 `미정`인 경우
     - `3. 작업 범위`·`4. 영향 범위`·`5. 작업 항목`·`6. 완료 기준`·`7. 리스크 및 고려사항`에서 `미정`·`TBD`·`확인 필요`·`결정 필요`·`추후 결정`이 적힌 곳
     - `9. 리뷰 결과`에서 `조치`가 `미결`·`보류`·`추후 결정`인 지적. 단, `2. 결정 사항`에 `비고`가 `리뷰 N차 #n`인 확정 행이 있으면 이미 확정된 것이다. (리뷰 회차 표는 확정 후에도 고치지 않기 때문이다)
     - 제외: 계획서 상단 규칙 블록(`진행 관리 규칙`, `결정 · 이력 기록 규칙`) 안의 설명 문구, `1. 요구사항`의 원문 인용, `8. 작업 이력`, 취소선 줄, `2. 결정 사항`의 `질문` 칸
     - 같은 사항을 가리키는 표시(본문의 `(미결)`, 그 결정 사항 행, 이전 실행의 보류 행)는 하나로 묶어 한 번만 묻는다.
   - **질문하기**
     - 미결 사항마다 질문 하나를 만든다. 질문 본문에 계획서의 위치(예: `5. 작업 항목 2.3`)와 무엇이 정해지지 않았는지 적는다.
     - 선택지는 계획서 내용(결정 사항, 설계안 비교, 리뷰 지적)과 관련 코드를 직접 확인해 만든다. 추천안을 첫 번째에 두고 `(Recommended)`를 붙인다. 설계 방향이 미결이면 `workflow-plan`의 설계안 비교처럼 `preview`에 각 안의 요약과 장단점을 넣는다.
     - 마지막 선택지는 `보류 (이번 실행에서 관련 항목 제외)`로 둔다.
     - 한 번에 최대 4개씩 나누어 묻는다.
   - **계획서 고치기** (모든 답을 받은 뒤, 구현 전에)
     - 확정한 사항은 그 자리의 `(미결)`이나 미정 표현을 확정 내용으로 바꾼다. 작업항목이 바뀌면 `진행 관리 규칙`의 추가·취소·병합·분할 표기를, 설계 방향이 바뀌면 절대 규칙의 설계 변경 처리를 따른다.
     - `2. 결정 사항`에 질문마다 한 행을 추가한다. `단계`는 `do · 미결 확정`이다. 기존 결정 사항 행을 확정했으면 새 행 `비고`에 `#n 확정`을 쓰고, 기존 행은 그대로 둔다. 다른 섹션이었으면 `비고`에 위치를 쓴다.
     - `9. 리뷰 결과`의 지적을 확정했으면 그 회차 표는 고치지 않는다. 결정 사항 행 `비고`에 `리뷰 N차 #n`을 쓴다.
     - `8. 작업 이력`에 구분 `계획 변경`으로 한 행을 남긴다. (예: `미결 3건 확정, 1건 보류 — 2.3, 리스크 2, 리뷰 1차 #4`)
   - **보류한 사항**: `(미결)` 표시를 그대로 둔다. 그 사항에 영향을 받는 작업항목은 이번 실행에서 진행하지 않고 `[ ]`로 둔다. 진행 범위의 모든 항목이 영향을 받으면 그 사실을 알리고 종료한다.
   - 미결 사항이 없으면 이 단계를 건너뛴다. AskUserQuestion을 쓸 수 없는 환경이면 계획서를 고치지 않고 미결 사항 목록을 출력한 뒤 중단한다.
4. `[~]`로 남은 항목이 있으면 이전 작업이 중단된 것이다. 해당 항목의 변경 상태를 확인하고, 이어서 할지 처음부터 다시 할지 AskUserQuestion으로 확인한다. 같은 병렬 그룹의 항목이 여럿 `[~]`이면 병렬 실행 중에 중단된 것이다. 항목마다 `파일:` 줄의 파일 변경 상태를 보고, 한 질문에 항목별로 묻는다. 이어서 하면 그 항목들은 agent 없이 순서대로 직접 진행한다.
5. 프로젝트의 빌드·테스트·lint 명령을 파악한다. (CLAUDE.md, README, `package.json`, `build.gradle`, `pom.xml`, `Makefile` 등) 찾지 못하면 AskUserQuestion으로 확인한다.
   - 테스트 명령을 알고 오래 걸리지 않으면, 코드를 고치기 전에 한 번 실행해 **기준 상태**를 확인한다. 이미 실패하는 테스트가 있으면 그 목록을 기록해 둔다.
6. **작업 시작 이력을 남긴다.** 지금까지(입력 확인, 2번, 4~5번) 받은 답과 추가 지시를 `2. 결정 사항`에 기록한 뒤, `8. 작업 이력`에 구분 `do 시작`으로 한 행을 추가한다.
   - 내용: 진행 범위(`전체` / `1.2` / `Phase 2`), 브랜치, 기준 커밋(`git rev-parse --short HEAD`), 시작 시 진행률, 시작 전 미커밋 변경 파일 수(있을 때), 미결 확정·보류 건수, 기준 상태의 테스트 결과(실패가 있으면 그 테스트), 추가 지시가 있으면 그 요약
   - 예: `범위: 전체 / 브랜치: feature/add-login / 기준 커밋: a1b2c3d / 진행률 20% (2/10)`
   - 중단된 작업을 이어서 하면 `재개`를 덧붙인다.
7. 영향 범위가 넓으면(2개 이상의 모듈/계층에 걸치거나, 계획서에 적힌 파일 외에 확인할 후보가 많을 때) Agent 도구를 `subagent_type: "Explore"`로 2~3개, 영역을 겹치지 않게 나누어 한 메시지에서 동시에 실행해 관련 코드 위치와 기존 관례를 파악한다. agent는 후보와 근거만 보고하게 하고, 고칠 파일은 직접 열어 확인한다. 범위가 작거나 Agent 도구를 쓸 수 없으면 직접 탐색한다.

### 2. 항목 구현 (Phase 순서대로, 항목 순서대로)
각 항목마다 다음을 **반드시 순서대로** 수행한다. 병렬 그룹은 아래 `병렬 그룹 실행`을 따른다.

1. 계획서의 해당 항목을 `[ ]` → `[~]`로 바꾼다. 같은 수정에서 상단 표의 작업상태, 해당 Phase 제목의 상태를 고친다. (코드를 고치기 전에 계획서를 먼저 고친다)
2. 항목을 구현한다. 기존 코드의 관례(구조, 네이밍, 스타일)를 따른다.
3. 항목을 검증한다.
   - 해당 범위의 테스트·빌드·lint 중 실행 가능한 것을 돌린다. 실행할 수 없으면 그 이유를 기록한다.
   - 항목이 `### DB 변경`·`### API 변경`·`### 화면 변경` 정의에 걸려 있으면 구현 결과를 정의와 대조한다. 정의와 같아야 검증 통과다. (`[V]`로 바꾸기 전에 한다)
     - 대조 기준은 이 플러그인의 skill이다. 이번 실행에서 그런 항목을 처음 검증할 때 Skill 도구로 `workflow:db-design`(DB), `workflow:api-design`(API) 또는 `workflow:ui-design`(화면)을 인자 `점검 구현`으로 부르고, 이후 항목에서는 다시 부르지 않고 같은 기준으로 직접 대조한다. skill을 쓸 수 없으면 `${CLAUDE_PLUGIN_ROOT}/skills/<db-design|api-design|ui-design>/SKILL.md`를 Read 한다.
     - 화면은 소스(라우트, 요소 이름, 검증 규칙, 문구 리소스, 권한 조건)로만 대조한다. 화면을 띄워 보는 검증은 `workflow-usecase-do`가 한다.
     - 이 항목이 다루는 정의에 대한 지적만 본다. 아직 구현하지 않은 항목의 정의는 지적으로 보지 않는다.
     - 구현이 정의와 다르면 구현을 정의에 맞게 고치고 다시 검증한다. 정의를 바꿔야 하면 절대 규칙대로 AskUserQuestion으로 확인한 뒤 정의도 함께 고친다. (형식은 skill의 결과 형식, 섹션 제목은 그대로) skill이 돌려준 `미정 사항`이 있으면 같은 질문에 함께 넣는다.
     - skill은 기준만 준다. 대조를 마치면 이 절차를 이어서 한다.
4. 결과를 기록한다.
   - 검증 통과: `[~]` → `[V]`. `8. 작업 이력`에 구분 `항목`으로 한 행(예: `1.1 완료 — 로그인 폼 컴포넌트 추가`)을 추가한다. 이어서 `진행 표시 확인`을 실행해 출력된 곳(상단 표의 작업상태·전체진행률, 진행률 바, 해당 Phase 제목의 상태/진행률)을 고치고, 상단 표의 `최종 갱신`을 고친다. (`[V]`가 될 때마다 한 번 실행한다. `[~]`로 바꿀 때는 1번처럼 직접 고친다)
   - 기준 상태에서 이미 실패하던 테스트는 이 항목의 실패로 보지 않는다. 고치지 않고, 이력 행에 `기존 실패 N건 유지`로 적는다. 기준 상태를 확인하지 못했는데 실패가 이 항목과 관계없어 보이면, 고치기 전에 AskUserQuestion으로 확인한다.
   - 검증 실패: 원인을 고쳐 다시 검증한다. 같은 원인으로 3번 실패하면 `[~]`로 둔 채 `8. 작업 이력`에 구분 `항목`으로 실패 내용(예: `1.2 검증 3회 실패 — 원인 요약`)을 남기고, 계속할지 AskUserQuestion으로 확인한다.
5. `4. 영향 범위`에 없던 파일을 고쳤으면 그 파일을 영향 범위에 추가한다.
6. 항목에 `(단독 커밋)`이 붙어 있으면 `커밋 규칙`대로 처리해 이 항목의 변경을 따로 커밋한다. 같은 커밋에 섞이지 않도록, 이 항목을 `[~]`로 바꾸기 전에 쌓인 미커밋 변경이 있으면 그 변경을 먼저 커밋 규칙대로 커밋한다. (`끝에 한꺼번에`이면 섞일 수 있다는 것만 완료 보고에 적는다)

#### 병렬 그룹 실행
같은 Phase에서 끝에 `(병렬 A)`처럼 같은 표시가 붙은 항목들은 `item-implementer` agent에 하나씩 맡겨 동시에 구현한다. 메인 대화에 각 항목의 코드 탐색·작성 과정이 쌓이지 않고, 구현이 동시에 진행된다. 검증과 계획서 갱신은 메인이 한다.

- **조건** — 순서상 그룹의 첫 항목에 이르렀을 때 다음을 모두 만족하면 병렬로 진행한다. 하나라도 아니면 그룹 표시를 무시하고 위 1~6을 항목마다 순서대로 한다. (계획서의 표시는 그대로 둔다)
  - 그룹에서 진행할 항목(`[ ]`)이 2개 이상이고, 모두 이번 진행 범위 안에 있으며, 보류한 미결 사항에 걸리지 않는다. 진행할 항목이 1개뿐이면 순서대로 한다.
  - 그 항목마다 `파일:` 줄이 있고, 파일이 서로 겹치지 않으며, 준비 단계의 `시작 전 미커밋 변경` 파일과도 겹치지 않는다.
  - `(단독 커밋)` 항목이나 `코드 정리 및 리뷰` Phase 항목이 섞여 있지 않다. (섞여 있으면 그 항목만 빼고 나머지가 2개 이상이면 병렬로, 뺀 항목은 그룹 뒤에 순서대로 한다)
  - Agent 도구에 이 플러그인의 `item-implementer` agent가 있다. (목록에 표시된 이름, 보통 `workflow:item-implementer`)
- **실행**
  1. 그 항목들을 계획서에서 한 번의 수정으로 모두 `[ ]` → `[~]`로 바꾸고, 같은 수정에서 상단 표의 작업상태와 해당 Phase 제목의 상태를 고친다. 계획서의 `진행 관리 규칙` 블록에 병렬 그룹 줄(`(병렬 A)` 설명과 한 번에 `[~]`로 바꾸는 예외)이 없으면(손으로 표시를 붙인 계획서 등) 같은 수정에서 템플릿(`${CLAUDE_PLUGIN_ROOT}/templates/plan-template.md`)의 문구 그대로 넣는다.
  2. git 저장소이면 agent를 띄우기 직전에 작업 트리의 **스냅샷**을 남긴다. `git stash create`로 현재 변경을 담은 커밋 해시를 얻는다. (작업 트리와 stash 목록은 바뀌지 않는다. 출력이 비어 있으면 `HEAD`를 쓴다) `git ls-files --others --exclude-standard`로 추적하지 않는 파일 목록도 남긴다.
  3. Agent 도구로 항목마다 `item-implementer`를 **한 메시지에서 동시에** 실행한다. 프롬프트에는 agent 파일의 `입력` 항목을 넣는다: 계획서 경로, 맡은 항목 ID·내용·`파일:` 목록, 같은 그룹의 다른 항목 ID·파일 목록, 추가 지시와 준비 7번에서 찾은 관례 중 그 항목에 해당하는 것.
  4. **모든 agent의 결과를 받을 때까지 기다린다.** 환경에 따라 agent가 백그라운드로 실행되고 결과가 하나씩 따로 도착한다. 먼저 끝난 agent의 결과를 받아도 나머지가 모두 끝날 때까지 계획서와 소스를 건드리지 않고, 결과 확인도 시작하지 않는다.
- **결과 확인** — 모든 agent의 결과를 받은 뒤 검증 전에 한다.
  - agent가 바꾼 파일은 스냅샷과 비교해 찾는다: `git diff --name-only <스냅샷>`(추적하는 파일)과, 지금의 `git ls-files --others --exclude-standard`에서 스냅샷 때 목록에 없던 파일(새 파일). 이렇게 하면 앞 항목이 남긴 미커밋 변경과 시작 전 미커밋 변경은 빠지고, 이미 변경이 있던 파일을 agent가 또 고친 것도 잡힌다. 스냅샷 때 이미 있던 추적하지 않는 파일(앞 항목이 새로 만든 파일 등)을 고친 것은 잡히지 않으므로, agent가 돌려준 `바꾼 파일`도 함께 대조한다. git 저장소가 아니면 agent가 돌려준 `바꾼 파일`로 대신한다.
  - 찾은 파일을 각 항목의 `파일:` 목록과 대조한다. 계획서는 대조에서 뺀다. 목록 밖 파일이 바뀌었으면 그 변경(`git diff <스냅샷> -- <파일>`)을 보여 주고, 유지할지 되돌릴지 AskUserQuestion으로 묻는다.
    - 유지: 그 파일을 `4. 영향 범위`와 해당 항목의 `파일:` 줄에 추가한다.
    - 되돌리기: agent의 변경만 되돌린다. 추적하는 파일은 `git restore --source=<스냅샷> --worktree -- <파일>`로 스냅샷 때의 내용(앞 항목의 변경 포함)으로 되돌리고, 새 파일은 삭제한다. 작업 트리만 바꾸고 index(스테이징)는 건드리지 않는다. `git checkout <스냅샷> -- <파일>`은 index까지 바꾸므로 쓰지 않는다. `git checkout -- <파일>`이나 `--source` 없는 `git restore`로 HEAD까지 되돌리지 않는다.
  - `직접 정한 것`: agent가 계획서에 없어 스스로 정한 세부 사항이다. 메인이 하나씩 본다.
    - 사용자에게 보이는 동작, 오류 코드·메시지, 정의 표에 들어갈 내용, 업무 규칙처럼 요구사항 수준이면 AskUserQuestion으로 확인한다. 추천안은 agent가 정한 것을 첫 번째에 둔다. 답은 `do · <항목 ID>`로 기록하고, 답이 다르면 메인이 고친다. 여러 항목의 것은 한 번에 최대 4개씩 묶어 묻는다.
    - 변수명, 내부 함수 분리처럼 구현 세부면 묻지 않고 그대로 둔다.
  - `확인 필요`: 질문을 AskUserQuestion으로 묻고 답을 `do · <항목 ID>`로 기록한다. 그 항목은 agent를 다시 실행하지 않고, agent가 한 변경을 이어받아 메인이 답대로 직접 구현한다. 계획 변경이 필요하면 절대 규칙대로 처리한다.
  - `실행 불가`, 결과 형식이 아님, agent가 중간에 실패함: 그 항목은 `[~]`로 둔 채 남은 변경을 확인하고 메인이 직접 이어서 구현한다.
- **검증** — 그룹의 구현이 모두 끝난 뒤(메인이 이어서 한 항목 포함) 한 번에 한다. 같은 작업 트리에서 빌드·테스트를 동시에 돌리면 서로 충돌하기 때문이다.
  - 테스트·빌드·lint는 그룹 전체에 대해 한 번 실행한다. 정의 대조(위 3번)는 항목마다 한다.
  - 실패하면 오류 위치로 원인 항목을 가려 메인이 고치고 다시 검증한다. 같은 원인으로 3번 실패하는 규칙(위 4번)은 항목마다 적용한다. 원인 항목을 가릴 수 없으면 그룹의 모든 항목을 `[~]`로 둔 채 고친다.
  - 그룹 전체의 테스트·빌드가 통과하기 전에는 그룹의 어떤 항목도 `[V]`로 바꾸지 않는다. (커밋은 검증을 통과한 상태여야 한다)
  - 통과하면 정의 대조까지 마친 항목을 **하나씩** 위 4~5번대로 `[V]`, `항목` 이력 행, `진행 표시 확인`을 한다. 이력 행 내용 끝에 `(병렬 A)`를 붙인다. (예: `2.1 완료 — 회원 조회 API 추가 (병렬 A)`)

#### 코드 정리 및 리뷰 Phase
`코드 정리 및 리뷰` Phase의 두 항목은 구현 대신 Skill 도구로 skill을 실행한다. 앞 Phase가 모두 `[V]`일 때만 진행한다. 위 1~5 순서(`[~]` 표시 → 실행 → 검증 → 기록)는 같다.

- **`/simplify` 항목**
  - Skill 도구로 `simplify`를 실행한다. 이 skill은 정리 내용을 코드에 직접 반영한다. 정리 대상도 `/code-review` 항목의 작업 기준 커밋 이후 변경 전체다. 대상 지정 방법은 skill 설명을 따른다.
  - 반영 후 테스트·빌드로 동작이 바뀌지 않았는지 검증한다. 실패하면 일반 항목처럼 원인을 고친다.
  - 이 항목의 `항목` 이력 행 내용에 바뀐 내용을 요약한다. (예: `3.1 완료 — simplify: 중복 함수 2개 통합`)
- **`/code-review medium` 항목**
  - Skill 도구로 `code-review`를 `medium` 수준으로 실행한다. `--fix`는 쓰지 않는다.
  - 리뷰 대상은 이번 작업 전체다. Phase마다 커밋하므로 현재 미커밋 변경만으로는 부족하다.
    - **작업 기준 커밋**: `8. 작업 이력`에서 첫 `do 시작` 행의 기준 커밋이다. 그 행이 없거나 기준 커밋이 적혀 있지 않으면(예전 형식) 어느 커밋부터 리뷰할지 AskUserQuestion으로 묻는다.
    - 작업 기준 커밋 이후의 커밋된 변경과 현재 미커밋 변경이 모두 리뷰 대상에 들어가도록 지정한다. 대상 지정 방법은 skill 설명을 따른다. 커밋한 변경이 없으면 인자 없이 현재 변경(diff)을 대상으로 한다.
    - 시작 전 미커밋 변경 파일은 리뷰 결과에서 이번 작업과 구분해 보여 준다.
  - 지적 사항 목록(위치, 내용, 심각도)을 사용자에게 보여 준 뒤, 반영할 항목을 AskUserQuestion(`multiSelect: true`)으로 고르게 한다. 한 질문에 선택지가 4개까지이므로 많으면 여러 질문이나 여러 번으로 나눈다. 심각한 것을 앞에 두고 `(Recommended)`를 붙인다.
  - 고른 항목만 고치고 테스트·빌드로 검증한다.
  - 이 항목의 `항목` 이력 행 내용에 결과를 쓴다. (예: `3.2 완료 — code-review: 지적 N건, 반영 M건 (미반영: 위치·사유)`)
  - 지적 사항이 없으면 그대로 `[V]`로 바꾸고 이력 행에 `code-review: 지적 없음`을 쓴다.
- 이 Phase는 Phase 완료 시점이 아니라 **각 항목이 `[V]`가 될 때마다** `커밋 규칙`대로 커밋한다. (동작을 바꾸지 않는 정리와 리뷰 반영을 따로 되돌릴 수 있게 한다) `/simplify` 전에 앞 Phase의 미커밋 변경이 남아 있으면 먼저 그 변경을 커밋 규칙대로 커밋한다.
- skill을 쓸 수 없는 환경이면 항목을 `[~]`로 둔 채 AskUserQuestion으로 확인한다. 선택지:
  - 직접 같은 관점으로 정리·리뷰한다
  - 나중에 한다 (`[ ]`로 되돌림. 계획서는 완료 상태가 되지 않는다)
  - 생략한다 (계획서 `진행 관리 규칙`의 취소 표기로 바꾼다. 예: `(취소: do, skill 없음)`)

- 현재 시각은 Bash `date '+%Y-%m-%d %H:%M:%S'` 또는 PowerShell `Get-Date -Format 'yyyy-MM-dd HH:mm:ss'`로 조회한다. `최종 갱신`은 항목이 `[V]`가 될 때 고친다.
- 여러 항목을 몰아서 한꺼번에 `[V]`로 바꾸지 않는다. (병렬 그룹도 `[V]`는 항목마다 따로 바꾼다)
- Phase가 끝날 때마다(그 Phase의 모든 작업항목이 `[V]`) `8. 작업 이력`에 구분 `Phase`로 한 행을 남긴다. (예: `Phase 1 완료 (3/3)`) 이어서 `커밋 규칙`대로 이 Phase를 커밋한다. `코드 정리 및 리뷰` Phase는 위 규칙대로 항목마다 커밋한다.

### 3. 완료 기준 확인
진행 범위와 상관없이 `5. 작업 항목`의 모든 항목(취소선 줄 제외)이 `[V]`가 되면 `6. 완료 기준`에서 `[V]`가 아닌 기준을 확인한다. 아직 남은 작업항목이 있으면 이 단계를 건너뛴다. (보류한 미결 사항 때문에 남은 항목도 남은 작업항목이다)

- **명령으로 확인할 수 있는 기준**(빌드, 테스트 등)
  - 실행해서 통과하면 `[V]`로 바꾸고, `8. 작업 이력`에 구분 `항목`으로 한 행(예: `DoD-1 확인 — ./gradlew build 통과`)을 남긴다. 진행 표시는 `진행 표시 확인`으로 고친다.
  - 실패하면 `[ ]`로 두고 `8. 작업 이력`에 구분 `항목`으로 실패 내용(예: `DoD-1 실패 — UserServiceTest 2건 실패`)을 남긴다. 실패 원인을 확인한 뒤 AskUserQuestion으로 묻는다. 질문 본문에 실패 내용과 추정 원인을 적고, 기준 상태에서 이미 실패하던 테스트 때문이면 그 사실도 적는다. 선택지:
    - `수정 작업항목 추가 후 진행 (Recommended)`: 계획서 `진행 관리 규칙`대로 새 작업항목을 추가하고 2단계의 일반 항목처럼 구현·검증한 뒤 이 단계를 다시 한다. `코드 정리 및 리뷰` Phase가 이미 `[V]`이면 입력의 규칙대로 `/code-review medium` 재실행 항목도 추가할지 함께 묻는다.
    - `[ ]로 두고 종료`: 완료 보고에 실패 내용을 적는다.
- **화면 확인이 필요한 기준**은 `[ ]`로 두고, `workflow-usecase-plan` → `workflow-usecase-do`로 검증하도록 안내한다.
- **사람이 판단해야 하는 기준**은 AskUserQuestion으로 충족 여부를 확인받는다. 질문 본문에 기준 내용과 판단 근거(관련 변경 파일, 실행한 검증 결과, 관련 결정 사항)를 적는다. 한 번에 최대 4개씩 묻는다. 선택지:
  - `충족 — [V]로 표시`: `[V]`로 바꾸고 `8. 작업 이력`에 구분 `항목`으로 `DoD-2 확인 — 사용자 확인`을 남긴다. 진행 표시는 `진행 표시 확인`으로 고친다.
  - `미충족 — 수정 작업항목 추가`: 위 명령 기준 실패의 `수정 작업항목 추가 후 진행`과 같이 처리한다.
  - `나중에 확인 ([ ] 유지)`: 완료 보고에 적는다.
- 이 단계의 답은 `2. 결정 사항`에 `do · DoD-2`처럼 기준 ID를 붙여 기록한다.
- AskUserQuestion을 쓸 수 없는 환경이면 묻는 기준은 `[ ]`로 두고 완료 보고에 적는다.

### 4. 종료 처리
1. `진행 표시 확인`을 실행해 전체진행률, 진행률 바, Phase별 상태, 작업상태를 확정한다. (중단해 `[~]`로 남은 항목도 그대로 센다)
2. `8. 작업 이력`에 구분 `do 종료`(중간에 멈췄으면 `do 중단`)로 한 행을 남긴다.
   - 내용: 완료 항목 수 / 남은 항목 수, 변경 파일 수, 실행한 검증과 결과, 계획 변경·새 결정 건수
   - 예: `완료 5건(1.1~2.2), 남음 2건 / 변경 파일 7개 / ./gradlew test 통과 / 결정 2건 추가`
   - 이번 실행에서 커밋한 횟수도 적는다. 커밋 해시는 계획서에 쓰지 않는다. (`커밋 규칙` 참고)
3. git 저장소이면 `git status --short`로 이번 실행에서 아직 커밋하지 않은 변경(완료 기준 확인으로 바뀐 계획서, 중단된 항목의 변경, `커밋하지 않고 계속`으로 미룬 변경 등)을 확인한다. 있으면 `커밋 규칙`대로 처리한다. (`자동`이면 예외가 아닌 한 커밋하고, `확인`·`끝에 한꺼번에`·이번 실행에서 `끝에 한꺼번에`를 고른 경우는 묻는다) 없으면 건너뛴다.
   - 중단된 항목(`[~]`)의 변경이 섞여 있으면 자동 커밋 예외다. 질문 본문에 검증되지 않은 변경이 포함된다는 것을 적고, `커밋하지 않음`을 첫 번째에 두고 `(Recommended)`를 붙인다.

- 커밋 방식, 이번 실행의 커밋 목록(`git log --format='%h %s' <이번 실행의 기준 커밋>..HEAD`)과 커밋하지 않고 남은 변경
- 커밋했으면 되돌리는 방법: push 전이면 `git reset --soft <이번 실행의 기준 커밋>` (변경은 작업 트리에 남는다)
- 실행한 검증(테스트·빌드)과 결과
- 확정한 미결 사항과 보류한 미결 사항(보류 때문에 진행하지 않은 항목 포함)
- 계획 변경 사항(추가·분할·병합·취소한 항목, 설계 방향 변경, 새 결정 사항)
- 기준 상태에서 이미 실패하던 테스트가 있으면 그 목록
- 완료 기준 확인 결과(통과, 실패와 추가한 수정 항목, 사용자 확인으로 충족·미충족·보류한 기준)
- 남은 완료 기준과 확인 방법. 화면 검증이 필요하면 `/workflow:workflow-usecase-plan @<계획서 경로>` 실행을 안내한다.
- 중단했으면 중단 사유와, `/workflow:workflow-do @<계획서 경로>`로 이어서 진행할 수 있다는 점
