# workflow-plan-review

`workflow-plan`으로 생성한 작업계획서를 리뷰하고 내용을 보완한다.

## 입력

```
$ARGUMENTS
```

- mention(`@경로`) 또는 경로로 지정된 계획서를 대상으로 한다. `@`를 뗀 경로의 파일을 직접 읽는다. (자동 첨부에 기대지 않는다)
- 지정이 없으면 `ai-work/plans/` 하위에서 가장 최근(디렉토리명 YYMMDD, 파일명 HHMISS 기준) 계획서를 찾고, AskUserQuestion으로 대상이 맞는지 확인한다.
- 대상이 `workflow-plan` 형식(`5. 작업 항목`, `6. 완료 기준` 등)이 아니면 그 사실을 알리고, 계속할지 AskUserQuestion으로 확인한다.

## 절대 규칙

- **애매한 사항은 직접 결정하지 않는다.** 리뷰 중 발견한 범위 변경, 기술 선택, 우선순위 조정, 작업 분할/병합 등 판단이 필요한 사항은 AskUserQuestion으로 확답을 받은 뒤 반영한다.
  - AskUserQuestion을 쓸 수 없는 환경(비대화형 실행 등)이면 계획서를 고치지 말고, 지적 사항과 질문 목록을 출력한 뒤 중단한다.
- 이미 `[V]`(완료) 또는 `[~]`(진행중)인 항목의 상태는 임의로 바꾸지 않는다. 내용 수정이 필요하면 사용자에게 확인한다.
- 기존 항목의 ID(`1.1`, `DoD-1`)는 바꾸지 않는다. usecase 계획서가 이 ID로 항목을 참조한다.
- 상태 표기(`[ ]`, `[~]`, `[V]`), 전체진행률, 작업상태는 계획서의 `진행 관리 규칙`을 그대로 따른다.

## 리뷰 관점

계획서와 실제 코드베이스를 대조하여 아래 관점으로 점검한다.

1. **요구사항 커버리지** — 요구사항 중 작업항목으로 연결되지 않은 것이 있는가
2. **작업 분해 수준** — 한 항목이 너무 커서 검증이 어려운가 (하위 항목 분할 필요), 혹은 지나치게 잘게 쪼개졌는가
3. **영향 범위 누락** — 실제 코드 탐색 결과 변경이 필요한데 빠진 파일/모듈(호출부, 설정, DB 스키마, API 계약, 다국어 리소스 등)
4. **순서/의존성** — Phase 순서가 의존 관계에 맞는가, 병행 가능한 작업은 무엇인가
5. **완료 기준** — 테스트/빌드/화면 확인 등 검증 가능한 기준이 있는가
6. **리스크** — 하위호환, 데이터 마이그레이션, 성능, 보안, 롤백 방안
7. **테스트 계획** — 단위/통합/E2E(usecase) 테스트 항목이 있는가
8. **결정 사항** — 아직 확정되지 않은 애매한 항목이 남아 있는가
   - **설계안 전제** — `설계안 비교`에서 선택한 안의 `성립 전제`가 코드 탐색 결과와 맞는가. 전제가 깨졌으면 선택하지 않은 안을 다시 꺼내 비교하자고 지적한다(심각도 높음). 구현 방법이 갈리는 계획인데 비교 없이 `대안 없음`으로 되어 있으면 그것도 지적한다
9. **문서 정합성** — 상단 표의 전체진행률·작업상태, 진행률 바, Phase 제목의 상태/진행률이 실제 체크 표기와 맞는가. 항목 ID가 중복되거나 빠지지 않았는가. `진행 관리 규칙` 블록이 있는가. 소스 코드를 바꾸는 계획인데 마지막 Phase에 `코드 정리 및 리뷰`(`/simplify`, `/code-review medium`)가 없거나 그 뒤에 다른 Phase가 붙어 있지 않은가 (새 Phase를 추가할 때는 이 Phase 앞에 넣고, 이 Phase는 번호를 하나 뒤로 민다. 다른 문서가 참조하지 않는 Phase이므로 ID 불변 규칙의 예외다. 이미 `[~]`·`[V]`가 있으면 밀지 말고 사용자에게 확인한다)

## 처리 절차

1. 대상 계획서를 읽는다.
2. 계획서의 `4. 영향 범위` 및 요구사항 관련 코드를 탐색한다.
   - 먼저 Glob/Grep 몇 번으로 범위를 가늠한다. 다음 중 하나라도 해당하면 Explore agent로 나누어 탐색하고, 아니면 직접 탐색한다. (범위가 작으면 agent를 띄우는 쪽이 오히려 느리다)
     - 계획서가 2개 이상의 모듈/계층(화면, API, DB, 설정 등)에 걸친다
     - 확인할 후보 파일이 많다 (대략 20개 이상)
   - Agent 도구를 `subagent_type: "Explore"`로 **2~3개**, 서로 겹치지 않는 영역으로 나누어 **한 메시지에서 동시에** 실행한다. 프롬프트에 탐색 폭(`medium` 또는 `very thorough`)을 적는다.
   - 각 agent 프롬프트에는 다음을 넣는다.
     - 계획서의 요구사항과 그 영역의 작업항목, `4. 영향 범위`에 이미 적힌 파일
     - 맡은 영역 (다른 영역은 보지 않도록 명시)
     - 요청: 영향 범위에 빠진 호출부·설정·스키마·API 계약·리소스 등을 찾아 `path:line`과 근거로 보고
     - "판단하지 말고 후보와 근거만 보고한다"
   - agent는 코드 위치만 찾는다. 리뷰 판단(지적 사항, 심각도)은 직접 한다. agent는 AskUserQuestion을 쓸 수 없으므로 애매한 점은 결과로 받아 4단계에서 묻는다.
   - 지적 사항의 근거가 되는 파일은 직접 열어 확인한다. agent 결과끼리 어긋나면 해당 파일을 직접 읽어 판단한다.
   - Agent 도구를 쓸 수 없는 환경이면 직접 탐색한다.
3. 위 리뷰 관점으로 지적 사항을 정리하고 심각도(높음/중간/낮음)를 매긴다.
4. 판단이 필요한 지적 사항은 AskUserQuestion으로 반영 여부/방향을 확인한다. (한 번에 최대 4개씩 나누어 묻고, 추천안은 첫 번째 옵션 + `(Recommended)`)
   - 리뷰 관점 9(문서 정합성)의 수치 불일치처럼 답이 하나뿐인 것은 묻지 않고 바로잡는다.
5. 확정된 내용을 계획서에 직접 반영한다.
   - 신규 작업항목은 해당 Phase의 마지막 번호 다음 번호로, 신규 완료 기준은 다음 `DoD-n`으로 `[ ]` 상태로 추가한다.
   - 체크 항목 수가 바뀌므로 표기를 다시 세어 **전체진행률, 진행률 바, Phase별 진행률/상태, 작업상태**를 재계산한다.
   - 이번 리뷰에서 AskUserQuestion으로 받은 답은 질문·선택지·선택 결과를 작업계획서 `2. 결정 사항`에 한 행씩 추가한다. 기존 행은 고치거나 지우지 않는다. (기록 형식은 계획서의 `진행 관리 규칙` 참고) `단계`는 `review`다. 질문의 답이 아니라 사용자가 대화로 직접 준 지시·정정도 같은 표에 `review · 대화 지시`로 남긴다. (형식은 계획서의 `결정 · 이력 기록 규칙`)
   - 설계 방향을 바꿨으면 `설계안 비교`의 선택 결과를 고치고, 바뀌기 전 안은 선택하지 않은 안으로 이유와 함께 옮긴다.
6. 현재 시각을 조회한다. (Bash: `date '+%Y-%m-%d %H:%M:%S'` / PowerShell: `Get-Date -Format 'yyyy-MM-dd HH:mm:ss'`) 상단 표의 `최종 갱신`을 고치고 `8. 작업 이력`에 구분 `리뷰`로 한 행을 남긴다. (예: `1차 리뷰: 지적 5건, 반영 3건, 체크 항목 12 → 14`)
7. 계획서 맨 아래 `## 9. 리뷰 결과` 섹션에 이번 회차를 기록한다. 섹션이 없으면 만들고, 있으면 그 아래에 다음 회차(`### N차`)만 추가한다. 지적 사항이 없어도 `지적 사항 없음`으로 회차를 남긴다.

```markdown
## 9. 리뷰 결과

### 1차 (YYYY-MM-DD HH:MI:SS)

| # | 관점 | 심각도 | 지적 사항 | 조치 |
|---|------|--------|-----------|------|
| 1 | 영향 범위 누락 | 높음 | ... | 작업항목 2.3 추가 |
| 2 | 리스크 | 중간 | ... | 사용자 확인 후 제외 |

- 체크 항목 수: 반영 전 N → 반영 후 M
```

## 완료 보고
- 대상 계획서 경로
- 지적 사항 수(심각도별), 반영/미반영 건수
- 체크 항목 수 변화와 재계산된 진행률
- 구현은 `/workflow:workflow-do @<계획서 경로>`로 시작한다고 안내한다.
- 화면으로 검증할 항목이 있으면 `/workflow:workflow-usecase-plan @<계획서 경로>` 실행을 안내한다.
