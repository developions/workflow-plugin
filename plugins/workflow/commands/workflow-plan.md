# workflow-plan

사용자가 입력한 요구사항을 바탕으로 **작업계획서**를 생성한다.

## 입력

```
$ARGUMENTS
```

입력에 `@경로`가 있으면 `@`를 뗀 경로의 파일(요구사항 문서, 화면 설계서 등)을 직접 읽어 요구사항에 포함한다. (자동 첨부에 기대지 않는다) 1단계의 기준 브랜치 확인보다 먼저 읽는다. 그 질문 본문에 알릴 근거이고, 브랜치를 바꾸면 문서가 달라지거나 없어질 수 있다. (1단계 참고) 읽은 직후 시각을 조회해 `### 요구사항 문서`의 읽은 시점으로 쓴다. (다음 명령에 붙여 조회해도 된다) 문서의 요구 항목은 계획서 `1. 요구사항` 아래 `### 요구사항 문서`에 옮긴다. 경로만 남기면 문서가 바뀌거나 지워졌을 때 계획의 근거를 잃는다. (형식은 `템플릿 작성 지침`의 `요구사항 문서`)

`@경로`가 `ai-work/roadmaps/` 아래 파일이면 로드맵 업무 계획서를 만든다. 아래 `로드맵 업무`가 일반 계획서와 다른 점을 정한다. 이때는 업무 파일만 있고 다른 문장이 없어도 진행한다.

입력이 비어 있으면 계획서를 만들지 않는다. 작업 요구사항을 문장으로 입력해 달라고 요청하고 종료한다. (AskUserQuestion은 선택지형이라 자유 서술을 받는 용도로 쓰지 않는다)

## 절대 규칙

- **애매한 사항은 직접 결정하지 않는다.** 요구사항의 범위, 기술 선택, 우선순위, 대상 화면/모듈, 완료 기준 등 해석이 둘 이상 가능한 사항은 반드시 AskUserQuestion으로 확답을 받은 뒤 계획서에 반영한다. 어느 단계에서 묻는지는 2단계의 분류를 따른다. (DB·API·화면 형식처럼 설계 skill이 관례·기본값으로 정하는 것은 묻지 않는다)
  - 한 번에 최대 4개 질문까지 묶어서 묻고, 더 있으면 여러 번 나누어 묻는다. 추천안이 있으면 첫 번째 옵션에 두고 라벨 끝에 `(Recommended)`를 붙인다.
  - 이 커맨드에서 받은 모든 AskUserQuestion 답(애매한 사항, 설계안 선택, 브랜치 선택 등)을 질문·선택지·선택 결과와 함께 계획서의 `2. 결정 사항`에 기록한다. 사용자가 대화로 직접 준 지시·정정도 기록한다. (요구사항 원문은 `1. 요구사항`에 따로 남긴다) 형식은 템플릿의 `결정 · 이력 기록 규칙`과 `템플릿 작성 지침`의 `결정 사항 기록`을 따른다.
  - 사용자가 지금 정하지 않겠다고 답하면(직접 입력 등) 추측하지 말고 계획서의 해당 자리에 `(미결: 결정 #n)`을, 결정 사항 행 `#n`의 `선택`에 `(미결)`과 사용자 답 원문(예: `(미결) 지금은 정하지 않을게요`)을 남긴다. `workflow-do`가 시작 전에 다시 묻는다. 어느 단계(2·3·4단계)의 질문에서 미뤘든 같다.
    - 표시는 그 답에 기대는 곳마다 붙인다: `1. 요구사항`의 요약, `### 요구사항 문서`의 반영 표시, `현재 동작 → 변경 후 동작` 표, `3. 작업 범위`, 정의 표의 칸과 비고, 작업항목, 완료 기준, 리스크 줄.
    - 괄호 안에 다른 말을 섞지 않고 `(미결: 결정 #n)` 그대로 쓴다. 설명은 괄호 밖에 둔다. (예: `회차를 취소한 뒤의 표시 방식 (미결: 결정 #7)`. `(표시 방식은 미결: 결정 #7)`처럼 쓰면 `workflow-do`·`workflow-status`가 찾지 못한다)
    - 4단계에서 설계 skill을 부르면 미결 사항도 초안과 함께 넘긴다. (`DB·API·화면 설계 skill`의 `미정 사항을 묻는 시점`)
  - AskUserQuestion을 쓸 수 없는 환경(비대화형 실행 등)이면 추측으로 진행하지 말고, 질문 목록을 출력한 뒤 중단한다.
- 이 커맨드는 **브랜치 생성, 계획서 작성, 계획서 커밋까지만** 수행한다. 구현은 `workflow-do`로 진행한다. 커밋은 5단계에서 정한 `커밋 방식`을 따르고(8단계), push는 하지 않는다. (로드맵 업무 계획서면 로드맵 README의 이 업무 행 갱신도 한다. 아래 `로드맵 업무`. 추적하지 않는 요구사항 문서가 있으면 그 문서의 커밋도 한다. 5단계)

## 로드맵 업무
입력의 `@경로`가 `ai-work/roadmaps/` 아래 파일이면 `/workflow:workflow-roadmap`이 만든 로드맵의 업무 하나로 계획서를 만든다. 아래만 다르고 나머지 절차는 일반 계획서와 같다.

- **대상 업무 정하기**
  - 업무 파일(`NN_*.md`)이면 그 업무다. 상단 표 `로드맵`의 README를 함께 읽는다.
  - `README.md`를 지정했으면 `2. 업무 목록`에서 `대기`이면서 `선행`이 모두 `완료`인 업무를 행 순서대로 최대 3개 골라 어느 업무로 만들지 묻는다. (첫 번째에 `(Recommended)`, 마지막에 `중단`. 답은 `plan · 로드맵`으로 기록한다) 그런 업무가 없으면 막고 있는 선행 업무를 알리고 중단한다.
  - 파일이 작업 트리에 없으면(로드맵 브랜치가 아닌 곳에서 실행) 로컬 브랜치마다 `git cat-file -e <브랜치>:<경로>`로 찾아 `<브랜치>로 전환` / `중단`을 묻는다. 전환은 `git switch <브랜치>`로 하고, 실패하면 stash나 강제 전환을 하지 않고 중단한다. 어디에도 없으면 알리고 중단한다.
- **읽기**: 업무 파일 전체와 README의 `2. 업무 목록`(이 업무와 선행 업무의 행), `3. 공통 결정 · 업무 간 약속`을 읽는다. 선행 업무의 계획서(`계획서` 칸)는 `4. 영향 범위`와 정의(`### DB 변경`·`### API 변경`·`### 화면 변경`)만 읽는다. 선행 업무가 만든 것은 1단계에서 실제 코드로 확인한다.
- **시작 전 확인** (AskUserQuestion, 단계 `plan · 로드맵`. 답은 계획서를 쓸 때 `2. 결정 사항`에 기록한다)
  - 이 업무의 `상태`가 `진행`·`완료`이고 `계획서` 칸에 경로가 있다: `기존 계획서로 계속 — 종료 (Recommended)` / `새 계획서 작성` / `중단`. 앞의 것을 고르면 아무것도 고치지 않고 `/workflow:workflow-do @<기존 계획서>`를 안내하고 끝낸다. (이때는 기록할 계획서가 없으므로 결정 사항에 남기지 않는다) `새 계획서 작성`이면 기존 계획서는 그대로 두고, 7단계에서 README의 `계획서` 칸을 새 경로로 바꾼다.
  - `선행` 업무 중 `완료`가 아닌 것이 있다: 질문 본문에 그 업무와 상태를 적는다. 선택지는 `중단 (Recommended)` / `그대로 진행 (선행 업무의 결과는 약속대로 있다고 보고 계획)`이다. 진행하면 그 가정을 `7. 리스크 및 고려사항`에 적는다.
  - 이 업무에 걸린 `(미결)`이 있다: 업무 파일 전체, README `1. 요구사항`(요약과 `### 요구사항 문서`에서 이 업무 번호가 붙은 항목), `3. 공통 결정 · 업무 간 약속`(이 업무 번호가 걸린 줄)에서 찾는다. 인용 줄(`>`로 시작하는 규칙 블록)과 `4. 결정 사항`·`5. 작업 이력` 표 안의 글자는 세지 않는다. 여러 업무에 걸친 사항이라 로드맵에서 정해야 뒤 업무와 어긋나지 않는다. 질문 본문에 그 줄을 적는다. 선택지는 `로드맵에서 먼저 확정 — 종료 (Recommended)` / `이 계획에서 정함 (로드맵은 나중에 고침)`이다. 앞의 것이면 아무것도 고치지 않고 `/workflow:workflow-roadmap @<README> 미결 확정`을 안내하고 끝낸다. (기록할 계획서가 없으므로 결정 사항에 남기지 않는다) 뒤의 것이면 그 사항을 2단계에서 묻고, 아래 `묻는 것`의 약속을 바꾸는 경우처럼 완료 보고에 로드맵 수정 커맨드를 안내한다.
- **요구사항 문서**: 업무 파일의 `## 요구 항목`만 `### 요구사항 문서`에 옮긴다. 문서 경로는 업무 파일 경로다. (`workflow-do`·`workflow-roadmap`·`workflow-status`가 이 경로로 계획서와 업무를 잇는다) 나머지 섹션(`이 업무가 기대는 것`, `다른 업무에 넘길 것`, `정하지 않은 것`)은 옮기지 않고 1~4단계의 근거로 쓴다.
  - 요구 항목의 `(로드맵 결정 #n)`은 로드맵 README `4. 결정 사항`의 번호다. 그대로 옮긴다. 이 계획서에서 `(결정 #n)`은 이 계획서 `2. 결정 사항`의 번호만 가리킨다. 업무 파일에 `(결정 #n)`으로만 적혀 있으면(이전 버전으로 만든 로드맵) 로드맵 번호이므로 `(로드맵 결정 #n)`으로 바꿔 옮긴다. 그대로 두면 `workflow-plan-review`·`workflow-do`가 이 계획서의 다른 결정으로 읽는다.
  - 요구사항 문서 밖에서 로드맵 README의 결정을 근거로 적을 때도 `(로드맵 결정 #n)`으로 쓴다. (현재 동작 표의 `변경 없음 (…)`, `3. 작업 범위`의 제외 사유, `4. 영향 범위`, 작업항목, 리스크 등. 예: `변경 없음 (이미 충족, 로드맵 결정 #2)`) 이 계획서에서 받은 답만 `(결정 #n)`이다.
  - 항목 아래에 일부 이미 충족 줄(`이미 있음: … / 이 업무가 맡는 것: …`)이 있으면 그 줄도 항목과 함께 옮기고, 반영 표시는 항목 줄 끝에 `반영 — <이 업무가 맡는 것> (일부 이미 충족: <근거 path:line>)`으로 붙인다. 이미 있는 부분은 1단계에서 코드로 확인하고 다시 계획하지 않는다.
- **묻는 것**
  - README의 `공통 결정`과 `업무 간 약속`으로 정해진 것은 묻지 않는다. 약속에 이름이 적혀 있으면(코드에 이미 있는 이름, 사용자가 지정한 이름) 그 이름도 정해진 것이다. 다르게 해야 하면(코드가 약속과 다르다, 설계안이 약속을 바꿔야 한다) 2단계나 3단계에서 묻는다. 바꾸기로 하면 계획서 `2. 결정 사항`에 남기고, 로드맵은 이 커맨드에서 고치지 않는다. 완료 보고에 `/workflow:workflow-roadmap @<README> <변경 내용>`으로 로드맵을 고치라고 안내한다.
  - 업무 파일의 `정하지 않은 것`은 이 계획에서 정할 사항이다. 2단계의 분류대로 해당 단계에서 묻는다.
  - 업무 간 약속 중 이 업무가 제공하는 것은 약속에 이름이 없으면 이 계획에서 이름·저장 위치·방식을 정한다. (로드맵에는 보통 제공하는 것만 적혀 있다. 이름이 적혀 있으면 위 규칙대로 그 이름을 쓴다) 정한 이름은 정의 표(테이블·엔드포인트·화면)에 남긴다. 정의 표에 넣을 자리가 없는 것(모듈·함수, 세션 값, 설정 값, 파일 규칙)은 `4. 영향 범위`의 그 파일 줄 끝에 `(로드맵 약속: <제공하는 것> — <정한 이름>)`으로 적는다. (쓰는 업무의 `workflow-plan`이 위 `읽기`대로 이 계획서의 영향 범위와 정의를 읽는다) `6. 완료 기준`에 구현이 약속을 제공하는지 확인하는 기준을 넣는다. (예: `DoD-4 로드맵 약속의 회원 정보와 로그인한 회원 식별값을 다른 모듈이 정의 표의 이름으로 쓸 수 있다 (확인: 테스트 1.3)`)
- **브랜치 · 커밋 방식**: 모든 업무를 로드맵 브랜치에서 진행한다. 1단계 기준 브랜치 확인과 5단계 브랜치 질문을 하지 않는다. 대신 1단계 시작에서 아래를 확인하고, README 상단 표의 `작업 브랜치`·`커밋 방식`을 계획서에 그대로 쓴다.
  - README `작업 브랜치`가 `해당 없음`으로 시작하면 건너뛴다.
  - 현재 브랜치가 README `작업 브랜치`와 같으면 그대로 진행한다.
  - 다르면 묻는다. 질문 본문에 현재 브랜치, 로드맵 브랜치, 미커밋 변경 목록을 적는다. 선택지: `<작업 브랜치>로 전환 (Recommended)` / `현재 브랜치에서 진행 (계획서의 작업 브랜치는 현재 브랜치로 쓴다)` / `중단`. 로드맵 브랜치가 어디에도 없으면 `현재 브랜치에서 진행`을 첫 번째에 두고 추천한다. 전환이 실패하면 중단한다. 답은 `plan · 브랜치`로 기록한다.
  - summary는 5단계처럼 정하되 파일 이름에만 쓴다.
- **로드맵 갱신** (7단계에서 계획서를 쓴 뒤): README의 `로드맵 관리 규칙`대로 이 업무 행의 `계획서` 칸에 계획서 경로를 쓰고 `상태`를 `진행`으로 바꾼다. 상단 표의 작업상태·전체진행률·최종 갱신을 고치고, `5. 작업 이력`에 구분 `업무 진행`으로 `<번호> 진행 — <계획서 경로>`를 남긴다. 시각은 계획서의 `작성일시`와 같은 값을 쓴다.
- **커밋** (8단계): 계획서와 README를 함께 커밋한다. 메시지 본문 끝에 `Plan:` 줄과 함께 `Roadmap: <README 경로>` 줄을 붙인다.
- **완료 보고**: 로드맵 README에 반영한 것(업무 번호, 상태), 로드맵을 고쳐야 하는 결정(있으면 위 안내), 선행 업무를 가정하고 진행했으면 그 사실을 더한다.

## engineering plugin 활용 (설치되어 있을 때만)

engineering plugin이 설치되어 있으면, 아래 경우에 그 skill을 불러 설계 관점을 보강한다.

| skill | 언제 부르나 | 단계 | 계획서에 반영할 곳 |
|-------|-------------|------|--------------------|
| `engineering:system-design` | API 계약, 데이터 모델(DB 스키마), 서비스 경계, 캐시·큐 때문에 설계안이 갈릴 때 | 3단계. 3단계를 건너뛰었으면 서비스 경계·캐시·큐가 바뀔 때만 4단계 | 각 설계안의 요약·변경 파일·리스크, (4단계에서 불렀으면) `4. 영향 범위`, 작업항목 |
| `engineering:architecture` | 라이브러리·프레임워크·저장소·인프라 같은 기술 선택이 설계안을 가를 때 | 3단계 | `설계안 비교` 표의 평가 기준(복잡도, 비용, 확장성, 팀 숙련도)과 트레이드오프 |
| `engineering:testing-strategy` | API, 데이터 처리, 새 모듈처럼 테스트 설계가 필요한 코드 변경일 때 | 4단계 | `6. 완료 기준`, 작업항목의 테스트 |
| `engineering:deploy-checklist` | DB 마이그레이션, feature flag, 하위 호환을 깨는 API 변경이 있을 때 | 4단계 | `7. 리스크 및 고려사항`의 운영 관점(롤백 기준, 스테이징·스모크 확인, 배포 후 볼 지표, 알릴 대상), 필요하면 완료 기준 |

- **DB·API 설계 skill과 나누기**: 마이그레이션 롤백 방법, 배포 순서, 하위 호환 대응처럼 DB·API 정의에 속하는 것은 `workflow:db-design`·`workflow:api-design`이 정한다. `system-design`은 설계안 비교에만, `deploy-checklist`는 배포·운영 관점에만 쓰고 같은 내용을 두 번 쓰지 않는다. 두 skill이 이미 낸 롤백 기준·스테이징 적용 확인·알릴 대상은 그 결과를 쓰고, `deploy-checklist`에서는 그 밖의 것(스모크 확인, 배포 후 볼 지표 등)만 더한다. engineering skill은 두 skill 안에서 부르지 않는다. (DB·API에 대해서는 두 skill이 더 구체적이다)

- **설치 확인**: Skill 도구로 쓸 수 있는 skill 목록에 `engineering:<이름>`이 있을 때만 부른다. 없으면 그 단계를 지금처럼 직접 진행한다. 설치를 권하거나 묻지 않는다.
- **부르는 방법**: 해당 단계에서 Skill 도구로 부른다. 같은 skill은 한 번만 부르고, 얻은 관점을 이후 단계에서 다시 쓴다. Plan agent를 쓸 때는 메인이 skill을 부른 뒤 그 점검 관점을 각 agent 프롬프트에 넣는다.
- **쓰는 범위**: skill에서는 점검 관점과 평가 기준만 가져오고, 결과는 이 계획서의 해당 섹션에 계획서 형식으로 쓴다.
  - skill이 안내하는 별도 문서(설계 문서, ADR, 배포 체크리스트 파일)는 만들지 않는다.
  - skill이 안내하는 외부 도구 연동(knowledge base 검색, project tracker 작업 생성, 알림)은 하지 않는다.
  - 이 커맨드의 규칙(애매한 사항은 AskUserQuestion으로 확인, 브랜치 생성·계획서 작성·계획서 커밋까지만)이 skill 내용보다 우선한다.
- **기록**: 부른 skill은 `8. 작업 이력` 첫 행 내용 끝에 ` · 참고 skill: system-design, testing-strategy`처럼 ` · `로 이어 남기고 완료 보고에 적는다. 부른 skill이 없으면 템플릿 첫 행의 ` · 참고 skill: xxx`를 지운다.

## DB·API·화면 설계 skill

DB 스키마, API, 화면이 바뀌는 계획이면 4단계에서 이 플러그인의 skill로 테이블·엔드포인트·화면 정의를 만든다. engineering plugin 유무와 상관없다. (`engineering:system-design`은 설계안을 비교할 때 쓰는 일반 관점이고, 구체적인 정의는 이 skill이 맡는다)

| skill | 언제 부르나 | 결과를 쓸 곳 |
|-------|-------------|--------------|
| `workflow:db-design` | 테이블·컬럼·제약·인덱스가 바뀌거나 기존 데이터 이관이 필요할 때 | `4. 영향 범위` 아래 `### DB 변경` |
| `workflow:api-design` | 엔드포인트가 추가·삭제되거나 요청·응답·오류 코드·권한이 바뀔 때. 요청 필드의 검증 규칙(길이·형식·범위·허용 값)만 바뀌어도 부른다 (전에 통과하던 요청이 거부되므로 하위 호환을 판단해야 한다) | `4. 영향 범위` 아래 `### API 변경` |
| `workflow:ui-design` | 화면이 추가·삭제되거나 화면 요소, 입력 검증, 사용자에게 보이는 메시지, 이동, 권한별 노출이 바뀔 때. 아래는 부르지 않고 `4. 영향 범위`에 바꿀 파일과 문구만 적는다: 스타일(색·크기·배치)만 바꾼다 / 문구를 하나 고치거나 안내 문구 한 줄을 더한다 (요소·검증·이동은 그대로) / 새 오류 코드의 문구를 기존 오류 문구 매핑(코드→문구 표)에 한 줄 더한다 / 서버 검증만 바뀌고 화면 코드는 그대로다. 부르지 않을 때 문구의 문장 표현은 같은 파일의 기존 문구 말투를 따른다. 화면에 규칙 안내나 클라이언트 검증을 더할지는 2단계에서 묻는다(2단계 표 아래 참고). 클라이언트 검증·입력 요소·메시지 여러 개를 더하기로 하면 부른다 | `4. 영향 범위` 아래 `### 화면 변경` |

- **부르는 방법**: 4단계에서 Skill 도구로 인자 `설계`를 주어 부른다. 여럿이 필요하면 `workflow:db-design` → `workflow:api-design` → `workflow:ui-design` 순서로, 앞 skill의 정의 초안을 가지고 다음 skill을 부른다. (응답 스키마가 테이블 정의에, 화면의 검증·오류 메시지가 API 정의에 의존한다) 각각 한 번만 부른다.
  - 초안 넘기기: skill 인자는 `설계` 하나뿐이고, skill은 "계획서(또는 대화)"의 앞 정의를 먼저 읽는다. 그래서 앞 skill의 초안(`### DB 변경` 또는 `### API 변경` 전체, 결과 형식 그대로)을 대화에 출력한 뒤 다음 skill을 부른다. 요약 한 줄만 출력하지 않는다.
  - 미정 사항을 묻는 시점: 앞 skill의 `미정 사항` 중 다음 skill의 정의가 기대는 것(오류 코드, 검증 규칙, 응답 필드, 컬럼, 조회 범위)은 다음 skill을 부르기 전에 묻고, 답을 반영한 초안을 출력한 뒤 다음 skill을 부른다. 아래 `(기본값)` 점검에서 물을 것으로 고른 것도, 답에 따라 다음 skill의 정의(새 오류 코드, 화면 문구·요소)가 달라지면 같은 시점에 묻는다. 나머지 미정 사항과 `(기본값)` 점검 결과는 마지막 skill이 끝난 뒤 모아서 묻는다.
    - 사용자가 그 사항을 지금 정하지 않으면(`(미결)`) 초안의 그 칸에 `(미결: 결정 #n)`을 남기고, 다음 skill에도 그 값에 기대는 칸(응답 필드의 NULL 여부, 화면 표시 등)을 `(미결: 결정 #n)`으로 두라고 초안과 함께 적어 넘긴다. 2단계나 3단계에서 미결로 남긴 사항도 skill을 부를 때 같은 방법으로 넘긴다. (skill은 대화의 답만 보므로, 넘기지 않으면 미결인 값을 기본값으로 채운다) 7단계에서 그 값에 기대는 곳에도 같은 표시를 붙인다. 붙이는 자리와 형식은 절대 규칙의 미결 항목을 따른다. (`workflow-do`가 시작 전에 한 번에 묻고 모든 자리를 고친다)
    - 그 사항이 DB 스키마·마이그레이션처럼 뒤 작업이 모두 기대는 것에 걸리면(질문할 때는 아직 Phase를 나누기 전이므로 무엇에 걸리는지로 판단한다. 2단계의 업무 규칙 질문도 답에 따라 테이블·컬럼이 달라지면 해당한다), 질문 본문에 "정하지 않으면 `workflow-do`에서 보류할 때 그 항목과 뒤 Phase를 진행할 수 없다"고 적는다. `(미결)`로 남겼으면 완료 보고에도 적는다.
- **skill을 쓸 수 없으면**(Skill 도구로 쓸 수 있는 목록에 없음): `${CLAUDE_PLUGIN_ROOT}/skills/<db-design|api-design|ui-design>/SKILL.md`를 Read 해서 같은 기준으로 직접 진행한다.
- **skill은 기준과 형식만 준다.** 파일을 쓰거나 사용자에게 묻지 않는다. skill을 부른 뒤 이 커맨드의 4단계를 이어서 한다.
  - skill이 돌려준 `미정 사항`은 이 커맨드가 AskUserQuestion으로 확인하고 `2. 결정 사항`에 기록한다. skill이 관례나 기본값으로 정한 것(`따른 관례`에 근거나 `(기본값)`으로 적힌 것)은 절대 규칙의 애매한 사항으로 보지 않고 묻지 않는다.
  - 단, `(기본값)` 중 사용자가 겪는 동작을 정하거나 기능을 범위에서 빼는 것은 묻는다. 예: 입력 요소끼리 연동할지(날짜를 고르면 시작·종료 입력에 채울지), 자동 채움, 목록을 언제 갱신할지, "하지 않음"이 기본값이라 `3. 작업 범위`의 `제외`로 가게 되는 것. skill 결과를 받으면 `(기본값)` 항목을 훑어 이런 것을 골라 4단계 질문(`plan · 상세 설계`)에 넣는다. 형식(이름, 상태 코드, 배치, 표시 형식)을 정한 기본값은 묻지 않는다.
  - 정의는 7단계에서 계획서 `4. 영향 범위` 아래에 skill의 결과 형식대로 쓴다. 섹션 제목은 `### DB 변경`, `### API 변경`, `### 화면 변경` 그대로, 이 순서로 쓴다. (다른 커맨드가 이 제목으로 찾는다) `따른 관례` 줄은 빼지 않는다. `workflow-plan-review`와 `workflow-do`가 점검할 때 관례를 다시 찾지 않고 이 줄을 재사용한다.
  - skill이 돌려준 작업항목·완료 기준·리스크 후보를 계획서에 반영한다. 작업항목은 이 정의를 기준으로 나누고, 마이그레이션 항목에는 `(단독 커밋)`을 붙인다. 테스트를 별도 항목 후보로 냈으면 그 동작을 구현하는 항목에 합친다. (4단계의 `테스트 위치`)
- 3단계(설계안 비교)에서는 부르지 않는다. 상세 정의는 선택한 안에 대해서만 한다.
- **기록**: 부른 skill은 engineering skill과 같이 `8. 작업 이력` 첫 행의 `참고 skill:`에 남기고 완료 보고에 적는다. (예: `… 완료 기준 4개) · 참고 skill: db-design, api-design, testing-strategy`)

## 기존 기능 변경 점검 항목
새 기능 추가가 아니라 이미 있는 기능의 동작을 바꾸는 계획이면(일부라도), 4단계에서 아래 항목을 확인해 계획서에 반영한다.
- **현재 동작**: 바뀌는 동작을 코드에서 직접 찾아 `1. 요구사항` 아래 `현재 동작 → 변경 후 동작` 표에 근거(`path:line`)와 함께 쓴다. 요구사항 문장만 보고 현재 동작을 추측하지 않는다. 기존 동작에 대한 요구 항목 중 이미 충족됐거나 범위에서 뺀 것도 코드에서 확인했으면 `변경 없음 (<이유 또는 결정 #n>)` 행으로 남긴다. (리뷰하는 쪽이 그 항목을 확인했는지 알 수 있다) 범위에서 뺀 새 기능은 이 표에 넣지 않고 `### 요구사항 문서`의 `제외`로만 남긴다. (`템플릿 작성 지침`의 `현재 동작 → 변경 후 동작`) 코드의 실제 동작이 요구사항의 전제와 다르면 AskUserQuestion으로 확인한다. 1단계 탐색 중에 발견한 전제 불일치(예: 요구사항은 관리자를 전제하는데 코드에 권한 개념이 없다)는 4단계까지 미루지 않고 2단계 질문에 넣는다. 범위와 설계안이 달라지기 때문이다.
- **호출부·영향 추적**: 바뀌는 함수·메서드·API·화면·공통 컴포넌트·설정값을 쓰는 곳을 Grep으로 모두 찾는다.
  - 함께 동작이 바뀌는 호출부는 `4. 영향 범위`에 넣는다. 코드를 고쳐야 하면 작업항목으로 다루고, 고칠 코드 없이 동작만 따라 바뀌면 `코드 변경 없음`으로 적고 바뀐 동작을 `6. 완료 기준`에서 확인한다.
  - 영향을 받지만 그대로 두는 호출부는 `7. 리스크 및 고려사항`에 이유와 함께 적는다.
  - 호출부를 바꿀지 그대로 둘지 판단이 갈리면 AskUserQuestion으로 확인한다.
- **기존 테스트**: 바뀌기 전 동작을 검증하는 기존 테스트를 찾는다.
  - 새 동작에 맞게 기대값을 고치거나 지워야 하는 테스트는 그 동작을 바꾸는 작업항목에 테스트 이름과 함께 넣는다. (`workflow-do`가 그 실패를 회귀로 오인하지 않게 한다. 다른 항목으로 나누면 앞 항목을 검증할 때 그 테스트가 실패한다)
  - 바뀌지 않아야 하는 동작을 지키는 테스트는 그대로 두고, 이 테스트가 통과하는 것을 `6. 완료 기준`에 넣는다.
  - 바뀌는 동작을 검증하는 테스트가 없으면 그 동작을 구현하는 작업항목에 테스트 추가를 함께 넣는다. (`workflow-do`가 항목마다 그 테스트로 검증한다) 여러 항목의 결과를 함께 거쳐야 하는 테스트(예: 서비스와 라우트를 모두 거치는 HTTP 테스트)만 마지막 관련 항목에 넣는다.
- 1단계에서 Explore agent를 쓰면 호출부와 기존 테스트 찾기도 agent의 반환 항목에 넣는다. `4. 영향 범위`와 작업항목에 쓸 곳은 직접 열어 확인한다.

## 병렬 그룹
`workflow-do`가 동시에 구현할 수 있는 작업항목을 4단계에서 표시한다. `workflow-do`는 표시된 항목을 `item-implementer` agent에 하나씩 맡겨 동시에 구현하고, 검증과 계획서 갱신은 메인이 한다. 표시가 없으면 지금처럼 순서대로 구현한다. 묶을 것이 없으면 표시하지 않는다. (기본은 순서대로다)

**묶는 조건** — 모두 만족할 때만 묶는다.
- 같은 Phase 안의 항목이다. (Phase가 커밋 단위이기 때문이다)
- 서로의 결과를 쓰지 않는다. 한 항목이 다른 항목이 만드는 클래스·함수·타입·테이블·API를 쓰면 묶지 않는다.
- 고칠 파일이 겹치지 않는다. 새로 만들 파일도 포함한다.
- 아래 공유 파일을 함께 고치지 않는다. 라우터·메뉴 등록, 메시지·다국어 파일, 빌드·의존성 파일(`package.json`, `build.gradle` 등), DI·빈 설정, index·barrel export, 마이그레이션 번호, 공통 상수·enum. 이런 수정은 별도 항목으로 빼서 그룹 뒤에 두면 나머지를 묶을 수 있다.
- 각 항목의 복잡도가 `중` 이상이다. (아래 `복잡도` 기준) `하`인 항목은 파일 수와 관계없이 묶지 않는다. agent는 계획서와 주변 코드를 처음부터 다시 읽느라 작은 항목에도 1~2분이 걸려서, 맥락을 이미 가진 메인이 순서대로 하는 편이 빠르다.
- 아래 항목은 묶지 않는다.
  - `(단독 커밋)` 항목
  - `코드 정리 및 리뷰` Phase
  - `(미결)`이 걸린 항목
  - 구현 중 사용자 확인이 필요할 것 같은 항목 (agent는 사용자에게 묻지 못한다)

**복잡도** — 항목마다 판단한다. 먼저 줄 수를 본다. 테스트를 포함해 대략 50줄 이하면 새 로직이 있어도 다른 기준과 관계없이 `하`다. 그 밖에는 위 등급부터 보고, 하나라도 해당하면 그 등급이다.

| 등급 | 기준 |
|------|------|
| 상 | 중에 더해, 구현에 필요한 관례가 다른 모듈이나 여러 파일에 흩어져 있어 구현하는 쪽이 탐색해야 한다 (메인이 계획 단계에서 그 파일을 열어 봤는지와 관계없다. agent는 처음부터 다시 읽는다) / 테스트를 포함해 대략 300줄 이상이다 |
| 중 | 새 로직(분기·검증·계산·상태 변경)이 있는 함수를 여러 개 만든다 / 정의 표의 여러 행을 구현한다 / 테스트를 포함해 대략 100줄 이상이다 |
| 하 | 값·문구·설정·상수만 바꾼다 / 기존 코드를 거의 그대로 따라 쓴다 / 새 분기·검증·계산이 없다 / 계산·분기가 있는 함수가 1개뿐이고 테스트를 포함해 대략 100줄 미만이다 / (위 문단) 대략 50줄 이하다. 파일 수와 관계없다 |

- 줄 수는 어림값이다. 50줄 이하 판정 말고는 줄 수보다 새 로직과 탐색량을 먼저 본다. (같은 패턴을 10개 파일에 반복하면 줄 수가 많아도 `하`다)
- 등급은 4단계에서 이미 정한 변경 내용(만들 함수, 구현할 정의 행)과 `파일:` 목록을 확인하며 연 파일로 판단한다. 줄 수를 세려고 코드 초안을 쓰거나 파일을 더 읽지 않는다.
- 판단이 경계에 걸리면 낮은 등급으로 본다. (묶지 않는 쪽이 안전하다) 경계란 한 기준의 어림값이 기준선 근처라 맞는지 판단이 서지 않는 경우다(예: 100줄 기준에 90~110줄). 두 등급의 기준에 모두 맞는 것은 경계가 아니고, 위 순서(50줄 이하 → 상 → 중 → 하)로 정한다.
- 같은 Phase에서 묶는 조건을 모두 만족하는 `중` 이상 항목이 하나뿐이면 묶지 않는다. (`상`이어도 짝이 없으면 순서대로 한다)
- 구현 방향이 갈리거나 사용자 확인이 필요할 것 같은 항목은 등급과 관계없이 묶지 않는다.
- 측정 근거: README `병렬 구현 측정`. 항목당 약 200줄(`중`)에서는 속도가 메인과 비슷했고, 메인 컨텍스트가 덜 차는 것이 주된 이점이었다. 속도 이득은 `상`에서 크다.

**표기**
- 그룹마다 Phase 안에서 겹치지 않는 대문자를 정해 항목 끝에 `(병렬 A)`처럼 붙이고, 같은 그룹 항목은 이어서 쓴다. 한 그룹은 2~3개다. 묶을 수 있는 항목이 4개 이상이면 그룹을 나눈다. (`(병렬 A)` 3개, `(병렬 B)` 나머지. `workflow-do`는 그룹 하나씩 실행한다)
- 그룹 항목 바로 아래에 들여쓴 `  - 파일:` 줄로 고칠 파일을 모두 적는다. 그 항목에 넣은 테스트 파일도 적는다. (agent는 이 목록 밖 파일을 만들지 못한다) 체크박스는 붙이지 않는다. (진행률에 세지 않는다) `workflow-do`가 이 줄로 파일이 겹치지 않는지 확인하고, agent가 이 파일만 고친다.
- `파일:` 줄 아래에 `  - 복잡도: 중 — <근거>` 줄을 둔다. 근거에는 새 로직과 어림 줄 수(또는 탐색 범위)를 짧게 쓴다. `workflow-plan-review`가 이 줄로 등급을 점검한다.

```markdown
- [ ] 2.1 회원 조회 API 구현, `MemberQueryServiceTest` 추가 (정의: API 1) (병렬 A)
  - 파일: `src/.../MemberQueryController.java`, `src/.../MemberQueryService.java`, `src/test/.../MemberQueryServiceTest.java`
  - 복잡도: 중 — 조회·권한 검사·응답 변환 3개 함수, 테스트 포함 약 150줄
- [ ] 2.2 회원 수정 API 구현, `MemberUpdateServiceTest` 추가 (정의: API 2) (병렬 A)
  - 파일: `src/.../MemberUpdateController.java`, `src/.../MemberUpdateService.java`, `src/test/.../MemberUpdateServiceTest.java`
  - 복잡도: 중 — 입력 검증·중복 확인·저장 3개 함수, 테스트 포함 약 180줄
- [ ] 2.3 두 API를 라우트·권한 설정에 등록
```

## 처리 절차

### 1. 컨텍스트 파악
- **기준 브랜치 확인 (탐색하기 전에)** — 탐색과 설계안 검증은 작업 브랜치가 갈라져 나올 코드에서 해야 한다. 다른 브랜치의 코드를 보고 계획을 세운 뒤 분기 기준을 바꾸면 계획이 실제 코드와 어긋난다.
  - 로드맵 업무 계획서면 이 확인 대신 `로드맵 업무`의 `브랜치 · 커밋 방식` 확인을 한다.
  - git 저장소가 아니면 건너뛴다. (`git rev-parse --is-inside-work-tree`)
  - 현재 브랜치(`git branch --show-current`)와 미커밋 변경사항(`git status --short`)을 확인한다.
  - 기본 브랜치는 `git symbolic-ref --short refs/remotes/origin/HEAD`(앞의 `origin/`을 뗀다)로 찾는다. 없으면 로컬 브랜치 중 `main` → `master` → `develop` 순서로 처음 있는 것이다. 이 브랜치와 `develop`(있으면)을 기본 브랜치로 본다.
  - 현재 브랜치가 기본 브랜치이거나 출력이 비어 있으면(detached HEAD) 그대로 진행한다.
  - 기본 브랜치가 아니면 어느 브랜치의 코드를 기준으로 계획할지 AskUserQuestion으로 먼저 묻는다. 질문 본문에 현재 브랜치와 미커밋 변경사항 유무를 적는다. 선택지: `현재 브랜치 기준` / `기본 브랜치(<이름>) 기준` (아래 추천안을 첫 번째에 둔다). 다른 브랜치는 사용자가 "Other"로 입력한다.
    - 현재 브랜치가 기본 브랜치와 같은 커밋을 가리키고(`git rev-parse HEAD <기본 브랜치>`의 두 값이 같다) 미커밋 변경이 없으면 묻지 않고 현재 브랜치 기준으로 진행한다. 어느 쪽을 골라도 코드와 새 브랜치의 분기 위치가 같다.
    - 추천: 현재 브랜치가 아직 기본 브랜치에 합쳐지지 않은 커밋(`git log --oneline <기본 브랜치>..HEAD`)을 가지고 있고 요구사항이 그 작업을 이어 가는 것으로 보이면 `현재 브랜치 기준`, 그 밖에는 `기본 브랜치 기준`을 추천한다. 질문 본문에 합쳐지지 않은 커밋 수와 판단 이유를 한 줄로 적는다.
    - `현재 브랜치 기준`을 고르면 합쳐지지 않은 커밋이 새 작업 브랜치에 함께 들어간다. (요구사항과 관계없는 커밋이면 PR에 섞인다) 합쳐지지 않은 커밋이 있으면 질문 본문에 이 사실과 커밋 수를 적는다.
    - `@경로` 문서가 git이 추적하는 파일인데 기본 브랜치에 없거나(`git cat-file -e <기본 브랜치>:<경로>` 실패) 내용이 다르면(`git diff --quiet <기본 브랜치> -- <경로>` 실패), 추천은 위 기준 그대로 두고 질문 본문에 알린다: 문서가 기본 브랜치에 없다(또는 다르다), 계획서에는 문서 항목을 옮겨 두므로 계획은 그대로 할 수 있다, 문서 파일도 작업 브랜치에 두려면 중단하고 문서를 기본 브랜치에 먼저 커밋한 뒤 다시 실행한다. 이때는 미커밋 변경이 없어도 `중단 (문서를 기본 브랜치에 먼저 커밋한 뒤 다시 실행)` 선택지를 더한다. 추적하지 않는 문서는 전환해도 작업 트리에 남으므로 해당하지 않는다. (추적하지 않는 문서는 5단계에서 작업 브랜치에 커밋한다)
    - 미커밋 변경(추적하지 않는 파일 포함)이 있으면 질문 본문에 그 파일 목록(많으면 앞의 5개와 개수)과 함께, 다른 브랜치로 전환하면 충돌이 없는 한 이 변경이 기준 브랜치와 새 작업 브랜치로 그대로 따라온다고 적는다. 선택지에 `중단 (변경을 먼저 커밋·stash한 뒤 다시 실행)`을 더한다. 중단을 고르면 아무것도 바꾸지 않고 종료한다.
  - 현재 브랜치가 아닌 브랜치를 고르면 `git switch <기준 브랜치>`로 전환한 뒤 탐색한다. 전환이 실패하면(미커밋 변경 충돌 등) stash나 강제 전환을 하지 않고, 실패 내용을 알리고 중단한다. 전환했으면 `@경로` 문서를 다시 읽고, `### 요구사항 문서`의 읽은 시점·커밋은 전환한 뒤의 값을 쓴다. 전환한 브랜치에 문서가 없으면 처음 읽은 내용을 쓰고, 머리 줄에 원래 브랜치에서 읽었다는 것을 적는다. (예: `docs/req.md (2026-11-22 10:00:00에 feature/x의 커밋 abc1234에서 읽음, 작업 브랜치에는 없음)`. `workflow-plan-review`가 이 브랜치·커밋으로 바뀐 곳을 찾는다)
  - 미커밋 변경을 가지고 전환했으면 완료 보고에 그 파일들이 원래 브랜치(`<이름>`)가 아니라 작업 트리에 남아 있다는 것을 적는다. (`workflow-do`는 시작할 때 이 파일들을 `시작 전 미커밋 변경`으로 잡아 커밋에서 뺀다)
  - 답은 결정 사항에 `plan · 기준 브랜치`로 기록한다.
- 현재 프로젝트 구조, 관련 소스, CLAUDE.md 등을 필요한 만큼 탐색하여 요구사항과 관련된 파일/모듈을 파악한다.
- 파악 결과 애매한 부분을 목록화한다.
- API 계약, DB 스키마, 화면 추가·동작 변경, 기술 선택, 마이그레이션처럼 `engineering plugin 활용` 표와 `DB·API·화면 설계 skill` 표에 해당하는 변경이 있는지 함께 정리한다.
- 이미 있는 기능의 동작을 바꾸는 요구사항인지 정리한다. 바꾸면 4단계에서 `기존 기능 변경 점검 항목`을 확인한다.

#### 범위가 넓을 때: Explore agent 병렬 탐색
먼저 저장소 크기를 센다. 추적 중인 파일 수(`git ls-files | wc -l`, git 저장소가 아니면 Glob `**/*`에서 의존성·빌드 산출물 폴더를 뺀 수)다.
- **대략 50개 미만**: agent 없이 관련 파일을 직접 읽는다. 이 크기는 직접 읽는 편이 agent를 띄우고 결과를 다시 확인하는 것보다 빠르다.
- **그 이상**: Glob/Grep 몇 번으로 관련 후보 파일을 가늠한다. 아래 중 하나라도 해당하면 Explore agent로 나누어 탐색하고, 아니면 직접 탐색한다. (agent는 띄우는 비용과 결과 전달 과정의 정보 손실이 있어 범위가 작으면 오히려 느리다)
  - 관련 후보 파일이 많다 (대략 20개 이상)
  - 구조를 모르는 큰 저장소다
  - 요구사항이 2개 이상의 모듈/계층(화면, API, DB, 설정 등)에 걸치고, 관련 후보 파일이 대략 10개 이상이다
- 어느 쪽으로 했는지와 센 파일 수를 기억해 두었다가 3단계에서 쓴다. (Plan agent를 쓸지가 이것에 달렸다)

실행 방법:
- Agent 도구를 `subagent_type: "Explore"`로 **2~3개**, 서로 겹치지 않는 영역(예: 화면 / 서버·API / DB·설정·테스트)으로 나누어 **한 메시지에서 동시에** 실행한다. 프롬프트에 탐색 폭(`medium` 또는 `very thorough`)을 적는다.
- 각 agent 프롬프트에는 다음을 넣는다.
  - 원문 요구사항과 그 agent가 맡은 영역 (다른 영역은 보지 않도록 명시)
  - 이미 확인한 내용
  - 반환 형식: 관련 파일 `path:line`, 한 줄 역할, 변경 필요 가능성, 따라야 할 기존 관례, 애매한 점
  - "결정하지 말고 후보와 근거만 보고한다"
- agent는 AskUserQuestion을 쓸 수 없다. 애매한 점은 결과로 받아 2단계에서 직접 묻는다.
- 결과를 받은 뒤:
  - agent가 맡았던 영역을 다시 처음부터 탐색하지 않는다.
  - `4. 영향 범위`에 적을 파일은 직접 열어 확인한다. (Explore는 일부만 읽고 보고하므로 확인이 필요하다)
  - agent 결과끼리 어긋나면 해당 파일을 직접 읽어 판단한다.
- Agent 도구를 쓸 수 없는 환경이면 직접 탐색한다.

### 2. 애매한 사항 확인 (AskUserQuestion)
- 1단계에서 목록화한 애매한 사항을 AskUserQuestion으로 확인한다. 애매한 사항이 없으면 생략한다.
- 애매한 사항을 어느 단계에서 물을지 먼저 나눈다. (Explore agent가 보고한 애매한 점도 같다)

| 종류 | 예 | 묻는 곳 |
|------|----|---------|
| 업무 규칙·범위·우선순위·완료 기준, 사용자가 겪는 동작 | 몇 회 실패 시 잠금, 잠금 중 정답 입력 처리, 누가 해제할 수 있나, 다섯 번째 실패에서 바로 잠김을 알릴지, 문구에 담을 정보(잠김 여부, 해제 시각, 남은 횟수 등) | 2단계 (지금) |
| 구현 방법을 가르는 것 | 별도 테이블 ↔ 기존 테이블 컬럼, 서버 처리 ↔ 클라이언트 처리, 라이브러리 선택 | 3단계 설계안 비교 (전제와 선택지로 다룬다) |
| DB·API·화면의 형식 | 상태 코드(401/423), URL 모양, 오류 코드·컬럼·상수 이름과 위치, 화면 배치, 문구의 문장 표현(담을 정보는 2단계 답을 따른다) | 4단계. `DB·API·화면 설계 skill` 기준을 따른다. skill이 관례나 기본값으로 정하면 묻지 않고, `미정 사항`으로 돌려준 것만 묻는다 |

- 형식 문제라도 사용자가 겪는 동작이 달라지면(예: 상태 코드에 따라 화면이 다른 안내를 보인다) 그 동작을 2단계에서 묻고, 형식은 그 답에 맞춰 4단계에서 정한다.
- 화면이 서버 오류 코드별로 다른 문구를 보이면(코드를 그대로 표시하든, 코드→문구 매핑을 거치든. 1단계에서 호출부를 볼 때 확인한다) 오류 코드를 나누거나 합치는 일이 곧 사용자에게 보일 문구를 정하는 일이다. 이때는 "어떤 경우를 구분해 알릴지"를 2단계에서 묻는다. 코드 이름은 그 답에 맞춰 4단계에서 정한다.
- 서버 검증이나 업무 규칙에 따른 거부(길이·형식 검증, 중복·겹침·기한 초과 거부 등)가 새로 생기거나 바뀌면, 화면에 규칙 안내나 제출 전 검사(클라이언트 검증)를 더할지 2단계에서 묻는다. 답에 따라 4단계에서 `workflow:ui-design`을 부를지 정한다. (`DB·API·화면 설계 skill` 표의 ui-design 행)
- 사용자가 겪는 동작과 공개 계약(API 요청·응답, DB 스키마, 화면)을 바꾸지 않는 구현 세부는 묻지 않는다. 내부 함수 시그니처, 테스트에서 시각·외부 호출을 다루는 방법, 내부 헬퍼의 위치 같은 것이다. 프로젝트 규칙·관례를 따라 직접 정하고, 작업항목이나 `7. 리스크 및 고려사항`에 이유를 적는다.
- 절대 규칙의 "애매한 사항은 직접 결정하지 않는다"는 이 표의 단계에서 묻는다는 뜻이다. 3·4단계로 넘긴 사항을 빠뜨리지 않도록 목록에 남겨 두고, 그 단계에서 묻거나 skill 기본값으로 정해졌는지 확인한다.

### 3. 설계안 비교 (AskUserQuestion)
한 가지 방향으로만 설계하지 않도록, 구현 방법이 실제로 갈리는 경우 서로 다른 안을 나란히 놓고 사용자가 고르게 한다.

- **언제 하는가**: 구현 방법이 실제로 둘 이상으로 갈릴 때만 한다. 구조 변경, 새 모듈·라이브러리 도입, 데이터 모델·API 계약 변경은 방법이 갈리기 쉬운 경우의 예일 뿐 그 자체로 조건이 아니다. (API 계약이 바뀌어도 검증 조건 변경처럼 구현할 방법이 하나뿐이면 건너뛴다) 버그 수정, 문구·설정 변경처럼 방법이 사실상 하나뿐이면 건너뛰고, `설계안 비교`에 `대안 없음: <이유>`를 한 줄 남긴다. 요구에 없는 기능(변경 이력 테이블, 캐시, 알림 등)을 더하는 것은 방법이 갈리는 것으로 보지 않는다. B(구조 개선)를 요구 범위 안의 다른 구조로 세울 수 없으면 방법이 하나뿐인 것이다.
- **안 만들기**
  - 1단계에서 Explore agent를 썼으면(범위가 넓으면) Agent 도구를 `subagent_type: "Plan"`으로 2~3개, **한 메시지에서 동시에** 실행한다. 각 agent에 서로 다른 전제를 준다. 한 모델이 혼자 여러 안을 쓰면 선호하는 안 하나에 나머지가 들러리가 되기 쉬우므로, 전제를 강제로 다르게 준다.
    - A: 프로젝트 규칙·관례(CLAUDE.md, 기존 코드의 방식) 안에서 기존 구조를 최대한 유지하는 최소 변경. 규칙을 어겨서 줄이는 변경(예: 이미 적용된 마이그레이션 파일 수정)은 최소 변경으로 보지 않는다.
    - B: 확장성·구조 개선을 우선하는 설계
    - C: 요구사항에 맞는 다른 축 (예: 다른 라이브러리, 서버 처리 ↔ 클라이언트 처리, 동기 ↔ 비동기). 의미 있는 세 번째 축이 없으면 2개만 만든다.
  - 각 agent 프롬프트에는 원문 요구사항, 확정된 결정 사항, 1단계 탐색 결과(관련 파일 `path:line`), 프로젝트 규칙 요약(CLAUDE.md 등의 구조·마이그레이션·계층·명명 규칙과, 1단계에서 찾은 따라야 할 기존 관례), 맡은 전제를 넣는다. agent는 이 대화를 보지 못하므로 규칙을 넣지 않으면 규칙을 어기는 안을 낸다. 반환 형식: 설계 요약, 변경 파일, 장점, 단점, 리스크, 작업량(상/중/하), 이 안이 성립하는 전제, 이 안이 따른 프로젝트 규칙과 어긋나는 규칙(있으면).
  - 1단계를 직접 탐색했거나 Agent 도구를 쓸 수 없으면 직접 안을 위 전제로 나누어 쓴다. A·B는 항상 쓰고, C는 agent로 만들 때와 같이 의미 있는 세 번째 축이 있을 때 쓴다. (최대 3개) 떠올린 C 축을 쓰지 않았으면 비교표 아래에 `C 없음: <축> — <뺀 이유>`를 한 줄 남긴다. 설계안이 여러 계층에 걸쳐도 관련 파일을 이미 대부분 읽었으면 agent를 띄우지 않는다. (agent는 같은 파일을 처음부터 다시 읽는다)
- **검증**: 각 안이 실제 코드 구조에서 가능한지, 프로젝트 규칙·관례를 지키는지 관련 파일을 직접 열어 확인한다. 이번 실행에서 이미 읽은 파일은 다시 열지 않고 읽은 내용으로 판단한다. agent가 근거로 든 파일 중 아직 읽지 않은 것만 연다.
  - 코드 구조상 성립하지 않는 안은 뺀다.
  - 규칙·관례를 어기는 안은 그 전제(A·B·C) 안에서 규칙을 지키도록 고쳐 다시 확인한다. 고친 안이 다른 안과 같아지거나 고칠 수 없으면 뺀다. 고친 것은 비교표의 그 안 요약에 `(규칙 맞춰 수정: <규칙>)`로 적는다.
  - 검증하다가 그 전제에 더 맞는 안(예: 규칙을 지키면서 더 작은 변경)이 보이면 그 전제의 안을 그것으로 바꾸고 같은 방식으로 적는다. 전제 밖의 새 안을 추가하지는 않는다.
  - 남은 안이 하나뿐이면 그 사실을 기록한다.
- **선택**: AskUserQuestion으로 안을 고르게 한다. 각 선택지의 `preview`에 구조 요약과 변경 파일, 장단점을 넣어 나란히 비교할 수 있게 한다. 추천안은 첫 번째에 두고 `(Recommended)`와 추천 이유를 쓴다. 두 안을 섞는 등 다른 방향은 사용자가 "Other"로 입력한다.
- **기록**: 계획서 `2. 결정 사항` 아래 `### 설계안 비교`에 비교표와 선택 결과를 남긴다. **선택하지 않은 안과 그 이유도 남긴다.** 이후 리뷰나 구현 중 전제가 깨졌을 때 다시 꺼내 쓰는 근거가 된다.
- `engineering:system-design`·`engineering:architecture`를 부를 경우는 `engineering plugin 활용`을 따른다.
- 이 단계의 설계안은 비교할 수 있는 수준까지만 쓴다. API·DB·화면이 바뀌는 안은 바뀌는 테이블·엔드포인트·화면과 하위 호환 영향만 요약한다. 상세 정의는 4단계에서 선택한 안에 대해서만 한다.

### 4. 상세 설계와 남은 사항 확인 (AskUserQuestion)
선택한 안(3단계를 건너뛰었으면 유일한 방법)을 계획서에 쓸 수 있는 수준으로 구체화하고, 그 과정에서 나온 미정 사항을 계획서를 쓰기 전에 모두 확인한다. 구체화할 것이 없는 단순한 작업이면 건너뛴다. 단, 기존 기능의 동작을 바꾸는 계획이면 변경이 한 줄이어도 `기존 기능 변경 점검 항목`(현재 동작, 호출부, 기존 테스트)은 건너뛰지 않는다. (작은 변경일수록 깨지는 기존 테스트를 놓치기 쉽다)

- 변경할 파일과 변경 내용, 작업 순서(Phase 구성)를 정리한다. 작업 항목과 영향 범위는 선택한 안을 기준으로 한다.
  - Phase는 `workflow-do`의 커밋 단위다. 한 Phase가 끝났을 때 테스트·빌드가 통과하는 상태가 되도록 나눈다. (예: DB → API → 화면처럼 의존 순서대로)
  - DB 마이그레이션, 파일 삭제, 기존 데이터 이관처럼 되돌리기 어려운 항목은 작업항목 끝에 `(단독 커밋)`을 붙인다. 실행되면 기존 DB에 테이블·컬럼·데이터를 남기는 코드 변경(마이그레이션 러너에 이력 테이블 도입, 기동 시 테이블을 만드는 부트스트랩 등)도 포함한다. 코드를 되돌려도 DB에 남은 것은 되돌아가지 않기 때문이다. `workflow-do`가 그 항목만 따로 커밋한다.
  - 같은 Phase에서 동시에 구현할 수 있는 항목은 `병렬 그룹` 기준으로 묶고 `(병렬 A)` 표시와 `파일:` 줄을 붙인다. 묶는 조건에 맞는 항목만 묶는다. 고칠 파일을 확정하려면 관련 파일을 직접 확인한다.
  - **테스트 위치**: 새 동작의 테스트 작성과 기존 테스트의 기대값 수정은 그 동작을 구현·변경하는 작업항목에 넣는다. 새 기능이든 기존 기능 변경이든 같다. `workflow-do`는 항목마다 그 항목의 테스트로 검증하므로, 테스트를 따로 떼면 앞 항목을 검증할 수 없다. 여러 항목의 결과를 함께 거쳐야 하는 테스트(서비스와 라우트를 모두 거치는 HTTP 테스트, E2E 등)만 마지막 관련 항목에 넣는다.
  - **정의 표시**: `### DB 변경`·`### API 변경`·`### 화면 변경` 정의를 구현하는 작업항목에는 어느 정의인지 적는다. (아래 `템플릿 작성 지침`의 `(정의: …)`)
- API·DB·화면이 바뀌면 `DB·API·화면 설계 skill`대로 `workflow:db-design`·`workflow:api-design`·`workflow:ui-design`을 불러 테이블·엔드포인트·화면 정의를 정한다. DB·API 정의 때문에 `engineering:system-design`을 따로 부르지 않는다. 3단계를 건너뛰었고 서비스 경계·캐시·큐가 바뀌면 그때만 여기서 부른다.
- 기존 기능의 동작을 바꾸면 `기존 기능 변경 점검 항목`으로 현재 동작, 호출부, 기존 테스트를 확인한다.
- 완료 기준(기준마다 확인 방법)과 각 작업항목의 테스트, 리스크(롤백 방안 등)를 정리한다. `engineering:testing-strategy`·`engineering:deploy-checklist`를 부를 경우는 `engineering plugin 활용`을 따른다.
- 여기서 새로 나온 애매한 사항(설계를 고른 뒤에야 드러나는 세부 사항)을 AskUserQuestion으로 확인한다. 결정 사항의 `단계`는 `plan · 상세 설계`다. 사용자가 지금 정하지 않겠다고 하면 `(미결)`로 남긴다.
- 이 단계를 마치면 계획서 내용에 대해 더 물을 것이 없어야 한다. 7단계는 정리된 내용을 쓰기만 한다.

### 5. git branch 추천 및 생성 (AskUserQuestion)
- 로드맵 업무 계획서면 summary만 정하고 브랜치는 묻지 않고 커밋 방식은 로드맵 README의 값을 쓴다. (`로드맵 업무`의 `브랜치 · 커밋 방식`)
- 먼저 요구사항을 2~5 단어 영문 소문자로 요약한 **summary**를 정한다. (예: `add login page`) 브랜치명에는 kebab-case(`add-login-page`), 6단계 파일명에는 snake_case(`add_login_page`)로 같은 summary를 쓴다.
- `git rev-parse --is-inside-work-tree`로 git 저장소인지 확인한다.
  - git 저장소가 아니면 AskUserQuestion으로 `git init` 수행 여부를 묻는다. 거부하면 계획서의 작업 브랜치를 `해당 없음`으로 기록하고 6단계로 넘어간다.
- 현재 브랜치(`git branch --show-current`), 미커밋 변경사항(`git status --short`), 기존 브랜치 목록(`git branch -a`)을 확인한다.
- 작업 성격에 맞는 브랜치명 후보 2~3개를 만들어 AskUserQuestion으로 추천한다.
  - 기존 브랜치 네이밍 관례가 있으면 그것을 따른다. 없으면 `feature/<summary-kebab-case>`, `fix/<...>`, `refactor/<...>`, `chore/<...>`처럼 작업 유형 prefix를 쓴다.
  - 이미 존재하는 브랜치명은 후보에서 뺀다.
  - "브랜치 생성 안 함(현재 브랜치 유지)" 옵션을 포함한다.
  - 첫 번째 후보에 `(Recommended)`를 붙인다. 현재 브랜치가 기본 브랜치(1단계의 기준)가 아니고 요구사항이 그 브랜치의 작업을 이어 가는 것이면(1단계에서 `현재 브랜치 기준`을 고른 경우 등) `생성 안 함`을 첫 번째에 두고 추천한다.
  - 현재 브랜치가 기본 브랜치이면, `생성 안 함`을 고를 때 계획서가 기본 브랜치에 커밋되고 커밋 방식이 `자동`이어도 이 계획서의 모든 커맨드가 커밋 시점마다 묻는다는 것을 질문 본문에 적는다. 그래도 `생성 안 함`을 고르면 완료 보고의 작업 브랜치 줄에도 적는다.
- 새 브랜치는 현재 위치(1단계에서 정한 기준 브랜치)에서 만든다. 분기 기준을 여기서 다시 묻지 않는다.
- 미커밋 변경사항이 있으면 브랜치 질문의 본문에 그 사실을 적어, 사용자가 알고 고르게 한다. (변경사항은 새 브랜치로 그대로 따라온다)
- 현재 브랜치 출력이 비어 있으면(detached HEAD) 질문 본문에 그 사실을 적는다. 그래도 "생성 안 함"을 고르면 계획서 작업 브랜치를 `해당 없음 (detached HEAD)`으로 기록한다. 이후 커맨드는 브랜치 확인을 건너뛴다.
- 선택된 브랜치를 `git switch -c <branch>`로 생성한다. "생성 안 함"을 선택하면 계획서에는 현재 브랜치명을 기록한다.
- **커밋 방식**은 묻지 않고 `자동`으로 쓴다. 이 계획서로 하는 모든 커맨드가 이 값을 따른다. (`자동`은 작업 브랜치에서 정해진 시점에 묻지 않고 커밋하고, 작업 브랜치가 기본 브랜치일 때만 묻는다. `진행 관리 규칙` 참고) git 저장소가 아니면 `해당 없음`으로 쓴다.
  - 사용자가 인자나 대화로 `확인`(시점마다 묻기)이나 `끝에 한꺼번에`(각 커맨드가 끝날 때만 묻기)를 지시했으면 그 값을 쓰고 결정 사항에 `plan · 대화 지시`로 남긴다.
- **추적하지 않는 요구사항 문서**: `@경로` 문서가 git이 추적하지 않는 파일이면(`git ls-files --error-unmatch -- <경로>` 실패) 작업 브랜치에 커밋한다. 8단계는 계획서만 커밋하고 `workflow-do`도 이 파일을 `시작 전 미커밋 변경`으로 보고 커밋에서 빼므로, 그대로 두면 계획의 근거 문서가 작업 브랜치에 들어가지 않는다. git 저장소가 아니거나 로드맵 업무 계획서면 해당하지 않는다.
  - 커밋 방식이 `자동`이고 작업 브랜치가 기본 브랜치가 아니면 묻지 않고 커밋한다.
  - 작업 브랜치가 기본 브랜치이거나 커밋 방식이 `확인`이면 브랜치를 정한 뒤 AskUserQuestion으로 묻는다. 질문 본문에 문서 경로, 작업 브랜치와, 커밋하지 않으면 문서가 작업 트리에만 남고 작업 브랜치(PR)에는 들어가지 않는다는 것을 적는다. 선택지: `문서를 작업 브랜치에 커밋 (Recommended)` / `커밋하지 않음 (추적하지 않는 채로 둔다)`. 답은 `plan · 요구사항 문서`로 기록한다.
  - 커밋 방식이 `끝에 한꺼번에`이면(기본 브랜치가 아닐 때) 여기서 묻지 않고 8단계의 커밋 질문 하나로 함께 묻는다. 계획서의 머리 줄에는 일단 `git 추적 안 함`을 적어 둔다.
  - 커밋하면 브랜치를 만든 직후, 계획서를 쓰기 전에 그 문서만 `git add -- <문서>` 후 `git commit -- <문서>`로 커밋하고 8단계의 `알리는 줄`로 알린다. 제목은 8단계와 같은 규칙으로 정한다. 프로젝트 형식이 없으면 `docs: <문서 파일명> 요구사항 문서 추가`, 있으면 분류 자리에 문서 변경에 쓰는 값을 쓰고 설명은 `<문서 파일명> 요구사항 문서 추가`로 쓴다. `Plan:` 줄은 붙이지 않는다. 이 커밋을 `### 요구사항 문서` 머리 줄의 커밋으로 쓴다. (계획서보다 먼저 커밋해야 머리 줄에 커밋을 적을 수 있고, `workflow-plan-review`가 그 커밋으로 바뀐 곳을 찾는다) 커밋이 실패하면 우회하지 않고 원인을 알린 뒤 `커밋하지 않음`으로 진행한다.
  - 커밋하지 않으면 머리 줄에 커밋 대신 `git 추적 안 함`을 적고(`템플릿 작성 지침`의 `요구사항 문서`), 완료 보고에 알린다.

### 6. 파일 경로 결정
- 현재 시각을 조회해서 파일 경로, 계획서의 `작성일시`·`최종 갱신`, `8. 작업 이력`의 첫 행에 **같은 값**을 쓴다. (결정 사항의 일시는 답을 받은 시점의 값이다. 아래 `결정 사항 기록` 참고)
  - Bash: `date '+%y%m%d %H%M%S %Y-%m-%d %H:%M:%S'`
  - PowerShell: `Get-Date -Format 'yyMMdd HHmmss yyyy-MM-dd HH:mm:ss'`
  - 출력 순서: `YYMMDD` `HHMISS` `YYYY-MM-DD HH:MI:SS`
- 5단계에서 정한 summary를 snake_case로 쓴다. (예: `add_login_page`)
- 경로: `ai-work/plans/YYMMDD/HHMISS_[summary_snake_case].md` (프로젝트 루트 기준)
- 디렉토리가 없으면 생성한다.

### 7. 작업계획서 작성
4단계까지 정리한 내용을 아래 규칙과 템플릿을 따라 작성한다. 템플릿은 `${CLAUDE_PLUGIN_ROOT}/templates/plan-template.md`를 Read 해서 쓴다. (아래 `작업계획서 템플릿` 참고) 작업 항목은 **검증 가능한 단위**로 쪼개고, 단계(Phase)별로 묶는다. 생성 시점에는 모든 항목이 `[ ]`이다.
- 작성한 뒤 `진행 표시 확인`을 한 번 실행해 체크 항목 수(`N`)와 진행 표시가 맞는지 확인한다.
- 로드맵 업무 계획서면 이어서 `로드맵 업무`의 `로드맵 갱신`을 한다.

### 8. 계획서 커밋
- git 저장소가 아니면 건너뛴다.
- 5단계에서 정한 `커밋 방식`을 따른다.
  - `자동`: 묻지 않고 커밋한 뒤 한 줄로 알린다. (아래 `알리는 줄`) 작업 브랜치가 기본 브랜치(1단계의 기준. 1단계를 건너뛴 로드맵 업무 계획서도 같은 기준으로 찾는다)일 때만 그 사실을 적고 아래처럼 묻는다.
  - `확인`·`끝에 한꺼번에`: AskUserQuestion으로 묻는다. 질문 본문에 커밋 메시지 초안과 작업 브랜치를 적는다. 선택지: `커밋 (Recommended)` / `커밋하지 않음`. 답은 `2. 결정 사항`에 `plan · 커밋`으로 기록한 뒤 커밋한다. (그 행도 같은 커밋에 들어간다)
  - `끝에 한꺼번에`이고 5단계에서 추적하지 않는 요구사항 문서의 커밋을 미뤘으면, 선택지를 `문서와 계획서 커밋 (Recommended)` / `계획서만 커밋` / `커밋하지 않음`으로 하고 질문 본문에 문서 경로와 5단계의 안내를 적는다. 답은 `plan · 커밋`으로 기록한다. 문서도 커밋하면 문서를 5단계의 규칙대로 먼저 따로 커밋하고, 계획서 머리 줄의 `git 추적 안 함`을 그 커밋으로 바꾼 뒤 계획서를 커밋한다.
- 계획서 파일 하나만 `git add -- <계획서>` 후 `git commit -- <계획서>`로 커밋한다. (로드맵 업무 계획서면 로드맵 README도 함께 넣는다) 1단계에서 확인한 다른 미커밋 변경은 넣지 않는다. (`git add -A` 쓰지 않음)
- 메시지: 제목은 프로젝트 규칙(CLAUDE.md 등)의 커밋 형식이 있으면 그것을 따르고, 없으면 `docs(plan): <작업 제목> 작업계획서 작성`으로 쓴다. 프로젝트 형식에 type·모듈 같은 분류 자리가 있으면 그 프로젝트가 문서 변경에 쓰는 값(`docs`, `[docs]` 등)을 쓰고(정해진 값이 없으면 `docs`), 설명은 `<작업 제목> 작업계획서 작성`으로 쓴다. 본문 끝 줄 `Plan: <계획서 경로>`는 프로젝트 형식이 있어도 붙인다. (프로젝트 규칙이 본문 형식을 따로 정해 막는 경우만 뺀다. `git log --grep`으로 계획서의 커밋을 찾는 근거다)
- **알리는 줄**: 커밋하면 `커밋 <해시> <제목>`, 커밋하지 못하면 `커밋 안 함 — <사유>` 한 줄로 알린다. (모든 workflow 커맨드가 같은 형식을 쓴다. 뺀 파일이 있으면 `(제외: <파일>)`, 실행 전 사용자 변경을 함께 넣었으면 `(실행 전 변경 포함: <파일>)`을 붙인다)
- 커밋이 실패하면(훅 실패 등) `--no-verify`로 우회하지 않고 원인을 알린다. `자동`이고 작업 브랜치가 기본 브랜치가 아니면, 계획서에서 고칠 수 있는 문제(훅이 지적한 포맷 등)는 고쳐 한 번 다시 커밋하고, 다시 실패하면 커밋하지 않고 완료 보고에 적는다.
- push는 하지 않는다.

## 상태 표기 · 진행률 규칙

| 표기 | 의미 |
|------|------|
| `[ ]` | 작업항목 (대기) |
| `[~]` | 진행중 |
| `[V]` | 작업완료 |

- **체크 항목** = `5. 작업 항목`의 항목 + `6. 완료 기준`의 항목. 전체진행률의 분모는 이 둘을 합한 수다.
- **전체진행률** = `[V]` 수 ÷ 체크 항목 수 × 100 (소수점 버림). `0% (0/N)`처럼 개수를 함께 쓴다.
- **진행률 바** = 10칸. 10%당 `■` 1칸(버림), 나머지는 `□`
- **작업상태**는 백분율이 아니라 개수로 판단한다.
  - 대기: `[V]`와 `[~]`가 모두 0개
  - 완료: 모든 체크 항목이 `[V]`
  - 진행: 그 외
- Phase 제목에도 같은 규칙으로 그 Phase의 상태와 진행률을 표시한다. (분모는 그 Phase의 작업항목 수)

### 진행 표시 확인
진행률·진행률 바·작업상태·Phase 제목의 상태는 손으로 다시 세지 않고 스크립트로 확인한다.
- Bash 도구로 `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-progress.sh" "<계획서 경로>"`를 실행한다. (PowerShell에서 `bash`를 부르면 WSL bash가 잡힐 수 있으니 Bash 도구를 쓴다)
- 스크립트는 체크 표기를 세어 맞는 값을 계산하고, 적힌 값과 다른 곳만 `적힌 값 → 맞는 값`으로 출력한다. 체크 표기는 그대로 두고 출력된 값으로 고친다. `진행 표시 일치`가 나오면 고칠 곳이 없다.
- `최종 갱신` 시각은 확인하지 않는다. 스크립트를 실행할 수 없으면(`실행 오류` 출력, bash 없음) 위 규칙대로 직접 센다.

## 작업계획서 템플릿

템플릿은 `${CLAUDE_PLUGIN_ROOT}/templates/plan-template.md`에 있다. 7단계에서 이 파일을 Read 해서 그 구조와 문구대로 쓴다. `workflow-do`·`workflow-plan-review`도 예전 형식 계획서를 올릴 때 이 파일을 읽는다.

- 구성: 상단 표(작성일시, 작업 브랜치, 커밋 방식, 작업상태, 전체진행률, 최종 갱신) → `진행률`(진행률 바, `진행 관리 규칙`·`결정 · 이력 기록 규칙` 블록) → `1. 요구사항` → `2. 결정 사항`(아래 `설계안 비교`) → `3. 작업 범위` → `4. 영향 범위` → `5. 작업 항목` → `6. 완료 기준` → `7. 리스크 및 고려사항` → `8. 작업 이력`
### 템플릿 작성 지침
- **작업 브랜치**: 5단계 결과를 쓴다. 새로 만든 브랜치명 / 생성하지 않았으면 현재 브랜치명 / git 저장소가 아니면 `해당 없음`. 로드맵 업무 계획서면 로드맵 README의 값(`현재 브랜치에서 진행`을 골랐으면 현재 브랜치명)
- **커밋 방식**: 5단계 결과를 쓴다. 기본은 `자동`, 사용자가 지시했으면 `확인` / `끝에 한꺼번에`, git 저장소가 아니면 `해당 없음`. 로드맵 업무 계획서면 로드맵 README의 값
- **N**: 체크 항목 수(작업항목 + 완료 기준)
- **항목 ID**: 작업항목은 `Phase번호.순번`(`1.1`), 완료 기준은 `DoD-순번`(`DoD-1`). 리뷰와 usecase 매핑이 이 ID로 항목을 가리킨다.
- **진행 관리 규칙 블록**은 빼거나 줄이지 않고 그대로 넣는다. `workflow-do`가 이 블록을 기준으로 진행 상황을 갱신하고, 커맨드 없이 직접 구현할 때도 규칙이 전달된다.
- **`(단독 커밋)`**: 되돌리기 어려운 작업항목 끝에만 붙인다. (예: `- [ ] 1.2 회원 테이블에 잠금 컬럼 추가 마이그레이션 (단독 커밋)`) 커밋 단위 표시일 뿐 진행 상태 표기가 아니다.
- **`(병렬 A)`**: `병렬 그룹` 기준에 맞는(복잡도 `중` 이상) 항목에만 붙이고, 항목 바로 아래에 `  - 파일:` 줄과 `  - 복잡도:` 줄을 둔다. 템플릿의 병렬 그룹 주석은 지운다. 진행 상태 표기가 아니다.
- **`(정의: …)`**: `### DB 변경`·`### API 변경`·`### 화면 변경` 정의를 구현하는 작업항목은 내용 끝에 구현하는 정의를 적는다. DB는 테이블 이름, API·화면은 정의 표의 번호다. (예: `- [ ] 2.1 잠금 해제 API 추가, 라우트 테스트 추가 (정의: API 3)`, `- [ ] 1.1 login_locks 테이블 마이그레이션 (정의: DB login_locks) (단독 커밋)`) 정의의 일부만 만드는 항목도 적는다. `workflow-do`가 이 표시로 그 항목에서 대조할 정의를 정한다.
- **표시 순서**: 작업항목 줄에 표시가 여럿이면 내용 뒤에 `(미결: 결정 #n)` → `(정의: …)` → `(단독 커밋)` 또는 `(병렬 A)` 순서로 붙인다. (`(단독 커밋)` 항목은 병렬로 묶지 않으므로 둘이 함께 붙지 않는다) 예: `- [ ] 1.1 reservations에 attendee_count 추가 (미결: 결정 #11) (정의: DB reservations) (단독 커밋)`. 완료 기준 줄은 `(미결: 결정 #n)` → `(확인: …)` 순서로 확인 방법을 줄 끝에 둔다.
- **완료 기준의 확인 방법**: 완료 기준 줄 끝에 확인 방법을 붙인다. `workflow-do` 3단계가 이 표시로 기준을 나누고(명령으로 확인 / 화면 확인 / 사람 판단), `workflow-usecase-plan`이 `usecase` 기준을 UC에 매핑한다.
  - `(확인: 테스트 <테스트 이름 또는 그 테스트를 넣은 항목 ID>)` / `(확인: 명령 <명령>)` / `(확인: usecase)` / `(확인: 사용자)`
  - `(확인: 명령 …)`에는 `workflow-do`가 그대로 실행할 명령을 쓴다. 절차 설명(예: `001~003만 적용한 DB에 004 적용`)을 쓰지 않는다. 명령 하나로 확인할 수 없는 절차(이전 마이그레이션까지만 적용한 DB 만들기, 기존 데이터 넣기 등)는 그 준비까지 하는 테스트를 해당 작업항목에 넣고 `(확인: 테스트 <항목 ID>)`로 쓴다.
  - DB가 필요한 기준(마이그레이션 적용 등)은 어느 DB로 확인하는지 명령에 담는다. (예: `(확인: 명령 DB_PATH=tmp/check.db node scripts/migrate.js 를 두 번 — 두 번째도 오류 없음)`. 서버 기동처럼 끝나지 않는 명령은 쓰지 않는다) 적지 않으면 `workflow-do`가 개발 DB에 적용할지 묻게 된다.
- **코드 정리 및 리뷰 Phase**: 소스 코드를 바꾸는 계획이면 항상 마지막 Phase로 넣는다. Phase 번호는 앞 Phase 다음 번호이고, 항목은 템플릿의 두 개(`/simplify` → `/code-review medium`) 그대로 쓴다. 문서·설정만 바꾸는 계획이면 넣지 않는다. 실행은 `workflow-do`가 Skill 도구로 한다.
- **설계안 비교**: 3단계를 건너뛰었으면 표 대신 `대안 없음: <이유>` 한 줄만 쓴다.
- **결정 사항 기록**
  - `단계`에는 질문한 커맨드와 맥락을 쓴다: `plan`(2단계), `plan · 기준 브랜치`, `plan · 설계안`, `plan · 상세 설계`(4단계), `plan · 브랜치`, `plan · 요구사항 문서`(추적하지 않는 문서를 커밋할지. 묻는 경우만), `plan · 커밋`, `review`, `review · 대상`, `review · 형식`, `review · 커밋`, `do · 대상`, `do · 범위`, `do · 형식`, `do · 추가 지시`, `do · 미결 확정`, `do · 준비`, `do · 1.2`·`do · 3.1, 3.2`·`do · DoD-2`(항목 ID), `do · 커밋`, `plan · 로드맵`(로드맵 업무의 시작 전 확인), `usecase-plan`, `usecase-plan · 커밋`, `usecase-do · 준비`, `usecase-do · 02-03`(단계 ID), `usecase-do · 커밋`, `<커맨드> · 브랜치`(작업 브랜치 확인), `<커맨드> · 대화 지시`
  - 시각 조회는 따로 부르지 않고 답을 받은 직후의 다음 명령(git·탐색 명령 등)에 붙여 실행해도 된다. 한 번의 AskUserQuestion으로 받은 답은 한 번 조회한 값을 함께 쓴다. 같은 단계에서 사이에 다른 일(탐색, skill 호출, 파일 작성) 없이 AskUserQuestion을 여러 번 이어서 불렀으면 마지막 답 뒤에 한 번 조회한 값을 모두에 쓴다. 사이에 다른 일을 했으면 호출마다 조회한다.
  - 6단계(시각 조회) 전에 받은 답의 일시는 답을 받은 시점에 Bash `date '+%Y-%m-%d %H:%M:%S'` / PowerShell `Get-Date -Format 'yyyy-MM-dd HH:mm:ss'`로 조회해 둔다.
  - 한 번의 AskUserQuestion에 질문이 여러 개면 질문마다 한 행씩 쓴다.
  - 대화 지시는 `plan · 대화 지시`로 쓴다. 예: `| 4 | ... | plan · 대화 지시 | - | - | 기존 DateUtil 대신 새 유틸을 만들 것 | 작업항목 1.2 반영 |`
  - 계획서 파일이 생기기 전에 받은 답은 기억해 두었다가 작성할 때 모두 기록한다.
- 템플릿의 `(예시)` 행은 지우고 실제로 받은 답으로 채운다.
- 템플릿의 `<!-- -->` 안내 주석(요구사항 문서, 현재 동작 표, DB·API·화면 변경, 작업항목, 병렬 그룹)은 해당 내용을 채웠든 해당이 없든 작성을 마치면 모두 지운다. 계획서에 주석을 남기지 않는다.
- 결정 사항이 없으면 표는 머리글만 두고, 표 아래에 `계획 단계에서 확인한 사항 없음` 한 줄을 쓴다. (행으로 넣지 않는다. 이후 커맨드가 같은 표에 행을 추가하기 때문이다)
- **요구사항 원문**: `1. 요구사항`의 인용 블록에는 사용자가 입력한 문장을 `@경로`까지 고치지 않고 그대로 넣는다.
- **요구사항 문서**: `@경로`로 읽은 문서가 있으면 템플릿의 `### 요구사항 문서` 주석을 풀어 채운다. 없으면 주석째 지운다.
  - 제목 줄 아래에 경로와 읽은 시점을 적는다. git이 추적하는 파일이면 `git log -1 --format=%h -- <경로>`의 커밋도 적는다. (미커밋 변경이 있으면 `(미커밋 변경 포함)`) 추적하지 않는 파일이었으면 5단계의 답에 따라, 커밋했으면 그 커밋을 적고 커밋하지 않았으면 커밋 대신 `git 추적 안 함`을 적는다. (예: `docs/req.md (2026-11-22 10:00:00에 읽음, git 추적 안 함)`. 커밋을 빼기만 하면 `workflow-plan-review`가 예전 형식의 계획서로 읽는다)
  - 로드맵 업무 파일이면 `## 요구 항목` 섹션의 항목만 옮긴다. (`로드맵 업무`의 `요구사항 문서`)
  - 문서의 요구 항목을 문서의 번호·순서대로 옮긴다. 숫자·기한·조건(1시간, 30분, 전원 등)과 주체(누가)는 바꾸지 않는다. 배경·설명 문단은 옮기지 않는다.
  - 항목마다 반영 여부를 붙인다: `반영` / `일부 반영 — <무엇을 뺐는지> (결정 #n)` / `제외 — <이유> (결정 #n)` / `이미 충족 (<근거 path:line>)`. 일부가 이미 있어 나머지만 반영하면 `반영 — <이번에 맡는 부분> (일부 이미 충족: <근거 path:line>)`으로 쓴다. 반영하지만 일부가 정해지지 않았으면 `반영 — <정하지 않은 부분> (미결: 결정 #n)`으로 쓴다. (`workflow-do`가 확정한 뒤 이 표시를 고친다)
  - 요구사항이 여러 문서면 문서마다 이 블록을 둔다.
- **현재 동작 → 변경 후 동작**: 기존 기능의 동작을 바꾸는 계획이면 주석을 풀고 `기존 기능 변경 점검 항목`에서 확인한 내용으로 채운다. 새 기능만 추가하는 계획이면 주석째 지운다. 새 기능과 기존 동작 변경이 섞이면 바뀌는 기존 동작만 행으로 쓴다. (새 기능은 `1. 요구사항` 요약과 정의 표에 둔다. 표는 리뷰가 현재 코드와 대조하는 곳이라 코드에 없는 동작을 넣지 않는다) `근거`에는 현재 동작을 확인한 코드 위치를 쓴다.

## 완료 보고
작성이 끝나면 사용자에게 다음을 보고한다.
- 생성된 계획서 경로
- 작업 브랜치와 커밋 방식
- 1단계에서 미커밋 변경을 가지고 기준 브랜치로 전환했으면 그 파일 목록과 원래 브랜치 이름
- 계획서 커밋 여부 (커밋했으면 `git log -1 --format='%h %s'`)
- 추적하지 않던 요구사항 문서가 있었으면 그 처리: 커밋했으면 그 커밋, 커밋하지 않았으면 문서가 작업 트리에만 있고 작업 브랜치에는 없다는 것과 `workflow-do`의 커밋에도 들어가지 않는다는 것
- Phase 수 / 작업항목 수 / 완료 기준 수, `(단독 커밋)` 항목 (`코드 정리 및 리뷰` Phase와 그 항목도 센다. `8. 작업 이력` 첫 행의 수와 같다)
- 병렬 그룹과 각 항목의 복잡도 (예: `Phase 2 A: 2.1(중), 2.2(상)`. 없으면 `없음`)
- 선택한 설계안과 선택하지 않은 안 (설계안 비교를 건너뛰었으면 그 이유)
- **요구사항에서 줄이거나 뺀 것**: 요구사항(입력 문장, `@경로` 문서) 중 이번 계획에서 일부만 반영하거나 뺀 항목과 이유·결정 번호. 전제 불일치(코드에 없는 기능을 전제함)로 줄인 것, 사용자 답이나 skill 기본값으로 범위에서 빠진 것을 모두 적는다. 있으면 다른 항목보다 앞에 두고, 요구사항 문서를 쓴 사람(요청 부서 등)에게 알려야 한다고 적는다. 없으면 `없음`.
- 사용자 확인으로 확정한 결정 사항 요약
- 참고한 skill (`workflow:db-design`·`workflow:api-design`·`workflow:ui-design`, engineering skill. 부르지 않았으면 생략)
- 로드맵 업무 계획서면 `로드맵 업무`의 `완료 보고`에 적은 것
- 아래 중 하나라도 해당하면 `/workflow:workflow-plan-review @<계획서 경로>` 실행을 권장한다.
  - `코드 정리 및 리뷰` Phase와 그 Phase의 작업항목을 모두 빼고 셌을 때 Phase가 3개 이상이다
  - 같은 방식으로 셌을 때 작업항목이 10개 이상이다
  - `### DB 변경`·`### API 변경`·`### 화면 변경`이 모두 있다
  - 요구사항의 일부를 전제 불일치로 줄이거나 뺐다
- 구현은 `/workflow:workflow-do @<계획서 경로>`로 시작한다고 안내한다.
- 화면으로 검증할 항목이 있으면 `/workflow:workflow-usecase-plan @<계획서 경로>` 실행을 안내한다.
