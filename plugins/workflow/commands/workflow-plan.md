# workflow-plan

사용자가 입력한 요구사항을 바탕으로 **작업계획서**를 생성한다.

## 입력

```
$ARGUMENTS
```

입력이 비어 있으면 계획서를 만들지 않는다. 작업 요구사항을 문장으로 입력해 달라고 요청하고 종료한다. (AskUserQuestion은 선택지형이라 자유 서술을 받는 용도로 쓰지 않는다)

## 절대 규칙

- **애매한 사항은 직접 결정하지 않는다.** 요구사항의 범위, 기술 선택, 우선순위, 대상 화면/모듈, 완료 기준 등 해석이 둘 이상 가능한 사항은 반드시 AskUserQuestion으로 확답을 받은 뒤 계획서에 반영한다.
  - 한 번에 최대 4개 질문까지 묶어서 묻고, 더 있으면 여러 번 나누어 묻는다. 추천안이 있으면 첫 번째 옵션에 두고 라벨 끝에 `(Recommended)`를 붙인다.
  - 확답 받은 내용은 계획서의 `2. 결정 사항`에 기록한다.
  - AskUserQuestion을 쓸 수 없는 환경(비대화형 실행 등)이면 추측으로 진행하지 말고, 질문 목록을 출력한 뒤 중단한다.
- 이 커맨드는 **브랜치 생성과 계획서 작성까지만** 수행한다. 구현은 `workflow-do`로 진행한다.

## 처리 절차

### 1. 컨텍스트 파악
- 현재 프로젝트 구조, 관련 소스, CLAUDE.md 등을 필요한 만큼 탐색하여 요구사항과 관련된 파일/모듈을 파악한다.
- 파악 결과 애매한 부분을 목록화한다.

#### 범위가 넓을 때: Explore agent 병렬 탐색
먼저 Glob/Grep 몇 번으로 범위를 가늠한다. 아래 중 하나라도 해당하면 Explore agent로 나누어 탐색하고, 아니면 직접 탐색한다. (agent는 띄우는 비용과 결과 전달 과정의 정보 손실이 있어 범위가 작으면 오히려 느리다)
- 요구사항이 2개 이상의 모듈/계층(화면, API, DB, 설정 등)에 걸친다
- 관련 후보 파일이 많다 (대략 20개 이상)
- 구조를 모르는 큰 저장소다

실행 방법:
- Agent 도구를 `subagent_type: "Explore"`로 **2~3개**, 서로 겹치지 않는 영역(예: 화면 / 서버·API / DB·설정·테스트)으로 나누어 **한 메시지에서 동시에** 실행한다. 프롬프트에 탐색 폭(`medium` 또는 `very thorough`)을 적는다.
- 각 agent 프롬프트에는 다음을 넣는다.
  - 원문 요구사항과 그 agent가 맡은 영역 (다른 영역은 보지 않도록 명시)
  - 이미 확인한 내용
  - 반환 형식: 관련 파일 `path:line`, 한 줄 역할, 변경 필요 가능성, 따라야 할 기존 관례, 애매한 점
  - "결정하지 말고 후보와 근거만 보고한다"
- agent는 AskUserQuestion을 쓸 수 없다. 애매한 점은 결과로 받아 2단계에서 직접 묻는다.
- 결과를 받은 뒤:
  - agent가 맡았던 영역을 다시 처음부터 탐색하지 않는다.
  - `4. 영향 범위`에 적을 파일은 직접 열어 확인한다. (Explore는 일부만 읽고 보고하므로 확인이 필요하다)
  - agent 결과끼리 어긋나면 해당 파일을 직접 읽어 판단한다.
- Agent 도구를 쓸 수 없는 환경이면 직접 탐색한다.

### 2. 애매한 사항 확인 (AskUserQuestion)
- 1단계에서 목록화한 애매한 사항을 AskUserQuestion으로 확인한다. 애매한 사항이 없으면 생략한다.

### 3. 설계안 비교 (AskUserQuestion)
한 가지 방향으로만 설계하지 않도록, 구현 방법이 실제로 갈리는 경우 서로 다른 안을 나란히 놓고 사용자가 고르게 한다.

- **언제 하는가**: 구조 변경, 새 모듈·라이브러리 도입, 데이터 모델·API 계약 변경처럼 구현 방법이 둘 이상으로 갈릴 때만 한다. 버그 수정, 문구·설정 변경처럼 방법이 사실상 하나뿐이면 건너뛰고, `설계안 비교`에 `대안 없음: <이유>`를 한 줄 남긴다.
- **안 만들기**
  - 범위가 넓으면 Agent 도구를 `subagent_type: "Plan"`으로 2~3개, **한 메시지에서 동시에** 실행한다. 각 agent에 서로 다른 전제를 준다. 한 모델이 혼자 여러 안을 쓰면 선호하는 안 하나에 나머지가 들러리가 되기 쉬우므로, 전제를 강제로 다르게 준다.
    - A: 기존 구조를 최대한 유지하는 최소 변경
    - B: 확장성·구조 개선을 우선하는 설계
    - C: 요구사항에 맞는 다른 축 (예: 다른 라이브러리, 서버 처리 ↔ 클라이언트 처리, 동기 ↔ 비동기). 의미 있는 세 번째 축이 없으면 2개만 만든다.
  - 각 agent 프롬프트에는 원문 요구사항, 확정된 결정 사항, 1단계 탐색 결과(관련 파일 `path:line`), 맡은 전제를 넣는다. 반환 형식: 설계 요약, 변경 파일, 장점, 단점, 리스크, 작업량(상/중/하), 이 안이 성립하는 전제.
  - 범위가 작거나 Agent 도구를 쓸 수 없으면 직접 2개 안을 위 전제로 나누어 쓴다.
- **검증**: 각 안이 실제 코드 구조에서 가능한지 관련 파일을 직접 열어 확인한다. 성립하지 않는 안은 빼고, 남은 안이 하나뿐이면 그 사실을 기록한다.
- **선택**: AskUserQuestion으로 안을 고르게 한다. 각 선택지의 `preview`에 구조 요약과 변경 파일, 장단점을 넣어 나란히 비교할 수 있게 한다. 추천안은 첫 번째에 두고 `(Recommended)`와 추천 이유를 쓴다. 두 안을 섞는 등 다른 방향은 사용자가 "Other"로 입력한다.
- **기록**: 계획서 `2. 결정 사항` 아래 `### 설계안 비교`에 비교표와 선택 결과를 남긴다. **선택하지 않은 안과 그 이유도 남긴다.** 이후 리뷰나 구현 중 전제가 깨졌을 때 다시 꺼내 쓰는 근거가 된다.
- 작업 항목과 영향 범위는 선택한 안을 기준으로 작성한다.

### 4. git branch 추천 및 생성 (AskUserQuestion)
- `git rev-parse --is-inside-work-tree`로 git 저장소인지 확인한다.
  - git 저장소가 아니면 AskUserQuestion으로 `git init` 수행 여부를 묻는다. 거부하면 계획서의 작업 브랜치를 `해당 없음`으로 기록하고 5단계로 넘어간다.
- 현재 브랜치(`git branch --show-current`), 미커밋 변경사항(`git status --short`), 기존 브랜치 목록(`git branch -a`)을 확인한다.
- 작업 성격에 맞는 브랜치명 후보 2~3개를 만들어 AskUserQuestion으로 추천한다.
  - 기존 브랜치 네이밍 관례가 있으면 그것을 따른다. 없으면 `feature/<summary-kebab-case>`, `fix/<...>`, `refactor/<...>`, `chore/<...>`처럼 작업 유형 prefix를 쓴다.
  - 이미 존재하는 브랜치명은 후보에서 뺀다.
  - "브랜치 생성 안 함(현재 브랜치 유지)" 옵션을 포함한다.
- 현재 브랜치가 기본 브랜치(main/master/develop 등)가 아니면, 어느 브랜치에서 분기할지도 같은 AskUserQuestion에 질문으로 넣는다.
- 미커밋 변경사항이 있으면 브랜치를 만들기 전에 사용자에게 알린다. (변경사항은 새 브랜치로 그대로 따라온다)
- 선택된 브랜치를 `git checkout -b <branch> [<분기 기준 브랜치>]`로 생성한다. "생성 안 함"을 선택하면 계획서에는 현재 브랜치명을 기록한다.

### 5. 파일 경로 결정
- 현재 시각을 **한 번만** 조회해서 파일 경로와 계획서의 일시에 같은 값을 쓴다.
  - Bash: `date '+%y%m%d %H%M%S %Y-%m-%d %H:%M:%S'`
  - PowerShell: `Get-Date -Format 'yyMMdd HHmmss yyyy-MM-dd HH:mm:ss'`
  - 출력 순서: `YYMMDD` `HHMISS` `YYYY-MM-DD HH:MI:SS`
- 요구사항을 2~5 단어 영문 소문자 snake_case로 요약한다. (예: `add_login_page`)
- 경로: `ai-work/plans/YYMMDD/HHMISS_[summary_snake_case].md` (프로젝트 루트 기준)
- 디렉토리가 없으면 생성한다.

### 6. 작업계획서 작성
아래 규칙과 템플릿을 따라 작성한다. 작업 항목은 **검증 가능한 단위**로 쪼개고, 단계(Phase)별로 묶는다. 생성 시점에는 모든 항목이 `[ ]`이다.

## 상태 표기 · 진행률 규칙

| 표기 | 의미 |
|------|------|
| `[ ]` | 작업항목 (대기) |
| `[~]` | 진행중 |
| `[V]` | 작업완료 |

- **체크 항목** = `5. 작업 항목`의 항목 + `6. 완료 기준`의 항목. 전체진행률의 분모는 이 둘을 합한 수다.
- **전체진행률** = `[V]` 수 ÷ 체크 항목 수 × 100 (소수점 버림). `0% (0/N)`처럼 개수를 함께 쓴다.
- **진행률 바** = 10칸. 10%당 `■` 1칸(버림), 나머지는 `□`
- **작업상태**는 백분율이 아니라 개수로 판단한다.
  - 대기: `[V]`와 `[~]`가 모두 0개
  - 완료: 모든 체크 항목이 `[V]`
  - 진행: 그 외
- Phase 제목에도 같은 규칙으로 그 Phase의 상태와 진행률을 표시한다. (분모는 그 Phase의 작업항목 수)

## 작업계획서 템플릿

```markdown
# [작업 제목]

| 항목 | 내용 |
|------|------|
| 작성일시 | YYYY-MM-DD HH:MI:SS |
| 작업 브랜치 | `feature/xxx` |
| 작업상태 | 대기 |
| 전체진행률 | 0% (0/N) |
| 최종 갱신 | YYYY-MM-DD HH:MI:SS |

## 진행률

`[□□□□□□□□□□] 0%`

> **진행 관리 규칙** — 이 계획서로 작업하는 사람과 AI는 아래를 지킨다.
> - 표기: `[ ]` 작업항목(대기) · `[~]` 진행중 · `[V]` 작업완료
> - 항목에 착수하면 즉시 `[ ]` → `[~]`, 끝나면 즉시 `[~]` → `[V]`로 바꾼다. 여러 항목을 몰아서 한꺼번에 갱신하지 않는다.
> - 항목 상태를 바꿀 때마다 상단 표의 작업상태·전체진행률·최종 갱신, 진행률 바, 해당 Phase 제목의 상태/진행률을 함께 고친다.
> - 전체진행률 = `[V]` 수 ÷ 체크 항목 수(5. 작업 항목 + 6. 완료 기준) × 100, 소수점 버림. 진행률 바는 10%당 `■` 1칸.
> - 작업상태: 대기(`[V]`·`[~]` 모두 0개) / 완료(모든 항목 `[V]`) / 진행(그 외)
> - 범위나 항목이 바뀌면 `8. 작업 이력`에 한 줄 남긴다. 항목 번호(`1.1`, `DoD-1`)는 다른 문서가 참조하므로 바꾸지 않는다.
```

### 템플릿 작성 지침
- **작업 브랜치**: 4단계 결과를 쓴다. 새로 만든 브랜치명 / 생성하지 않았으면 현재 브랜치명 / git 저장소가 아니면 `해당 없음`
- **N**: 체크 항목 수(작업항목 + 완료 기준)
- **항목 ID**: 작업항목은 `Phase번호.순번`(`1.1`), 완료 기준은 `DoD-순번`(`DoD-1`). 리뷰와 usecase 매핑이 이 ID로 항목을 가리킨다.
- **진행 관리 규칙 블록**은 빼거나 줄이지 않고 그대로 넣는다. `workflow-do`가 이 블록을 기준으로 진행 상황을 갱신하고, 커맨드 없이 직접 구현할 때도 규칙이 전달된다.
- **코드 정리 및 리뷰 Phase**: 소스 코드를 바꾸는 계획이면 항상 마지막 Phase로 넣는다. Phase 번호는 앞 Phase 다음 번호이고, 항목은 템플릿의 두 개(`/simplify` → `/code-review medium`) 그대로 쓴다. 문서·설정만 바꾸는 계획이면 넣지 않는다. 실행은 `workflow-do`가 Skill 도구로 한다.
- **설계안 비교**: 3단계를 건너뛰었으면 표 대신 `대안 없음: <이유>` 한 줄만 쓴다.
- 결정 사항이 없으면 `2. 결정 사항` 표에 `확인이 필요한 사항 없음` 한 줄을 남긴다.

## 완료 보고
작성이 끝나면 사용자에게 다음을 보고한다.
- 생성된 계획서 경로
- 작업 브랜치
- Phase 수 / 작업항목 수 / 완료 기준 수
- 선택한 설계안과 선택하지 않은 안 (설계안 비교를 건너뛰었으면 그 이유)
