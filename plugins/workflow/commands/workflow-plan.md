# workflow-plan

사용자가 입력한 요구사항을 바탕으로 **작업계획서**를 생성한다.

## 입력

```
$ARGUMENTS
```

입력에 `@경로`가 있으면 `@`를 뗀 경로의 파일(요구사항 문서, 화면 설계서 등)을 직접 읽어 요구사항에 포함한다. (자동 첨부에 기대지 않는다)

입력이 비어 있으면 계획서를 만들지 않는다. 작업 요구사항을 문장으로 입력해 달라고 요청하고 종료한다. (AskUserQuestion은 선택지형이라 자유 서술을 받는 용도로 쓰지 않는다)

## 절대 규칙

- **애매한 사항은 직접 결정하지 않는다.** 요구사항의 범위, 기술 선택, 우선순위, 대상 화면/모듈, 완료 기준 등 해석이 둘 이상 가능한 사항은 반드시 AskUserQuestion으로 확답을 받은 뒤 계획서에 반영한다. 어느 단계에서 묻는지는 2단계의 분류를 따른다. (DB·API·화면 형식처럼 설계 skill이 관례·기본값으로 정하는 것은 묻지 않는다)
  - 한 번에 최대 4개 질문까지 묶어서 묻고, 더 있으면 여러 번 나누어 묻는다. 추천안이 있으면 첫 번째 옵션에 두고 라벨 끝에 `(Recommended)`를 붙인다.
  - 이 커맨드에서 받은 모든 AskUserQuestion 답(애매한 사항, 설계안 선택, 브랜치 선택 등)을 질문·선택지·선택 결과와 함께 계획서의 `2. 결정 사항`에 기록한다. 사용자가 대화로 직접 준 지시·정정도 기록한다. (요구사항 원문은 `1. 요구사항`에 따로 남긴다) 형식은 템플릿의 `결정 · 이력 기록 규칙`과 `템플릿 작성 지침`의 `결정 사항 기록`을 따른다.
  - 사용자가 지금 정하지 않겠다고 답하면(직접 입력 등) 추측하지 말고 계획서의 해당 자리와 결정 사항 행의 `선택`에 `(미결)`을 남긴다. `workflow-do`가 시작 전에 다시 묻는다.
  - AskUserQuestion을 쓸 수 없는 환경(비대화형 실행 등)이면 추측으로 진행하지 말고, 질문 목록을 출력한 뒤 중단한다.
- 이 커맨드는 **브랜치 생성, 계획서 작성, 계획서 커밋까지만** 수행한다. 구현은 `workflow-do`로 진행한다. 커밋은 5단계에서 정한 `커밋 방식`을 따르고(8단계), push는 하지 않는다.

## engineering plugin 활용 (설치되어 있을 때만)

engineering plugin이 설치되어 있으면, 아래 경우에 그 skill을 불러 설계 관점을 보강한다.

| skill | 언제 부르나 | 단계 | 계획서에 반영할 곳 |
|-------|-------------|------|--------------------|
| `engineering:system-design` | API 계약, 데이터 모델(DB 스키마), 서비스 경계, 캐시·큐 때문에 설계안이 갈릴 때 | 3단계. 3단계를 건너뛰었으면 서비스 경계·캐시·큐가 바뀔 때만 4단계 | 각 설계안의 요약·변경 파일·리스크, (4단계에서 불렀으면) `4. 영향 범위`, 작업항목 |
| `engineering:architecture` | 라이브러리·프레임워크·저장소·인프라 같은 기술 선택이 설계안을 가를 때 | 3단계 | `설계안 비교` 표의 평가 기준(복잡도, 비용, 확장성, 팀 숙련도)과 트레이드오프 |
| `engineering:testing-strategy` | API, 데이터 처리, 새 모듈처럼 테스트 설계가 필요한 코드 변경일 때 | 4단계 | `6. 완료 기준`, 테스트 작업항목 |
| `engineering:deploy-checklist` | DB 마이그레이션, feature flag, 하위 호환을 깨는 API 변경이 있을 때 | 4단계 | `7. 리스크 및 고려사항`의 운영 관점(롤백 기준, 스테이징·스모크 확인, 배포 후 볼 지표, 알릴 대상), 필요하면 완료 기준 |

- **DB·API 설계 skill과 나누기**: 마이그레이션 롤백 방법, 배포 순서, 하위 호환 대응처럼 DB·API 정의에 속하는 것은 `workflow:db-design`·`workflow:api-design`이 정한다. `system-design`은 설계안 비교에만, `deploy-checklist`는 배포·운영 관점에만 쓰고 같은 내용을 두 번 쓰지 않는다. 두 skill이 이미 낸 롤백 기준·스테이징 적용 확인·알릴 대상은 그 결과를 쓰고, `deploy-checklist`에서는 그 밖의 것(스모크 확인, 배포 후 볼 지표 등)만 더한다. engineering skill은 두 skill 안에서 부르지 않는다. (DB·API에 대해서는 두 skill이 더 구체적이다)

- **설치 확인**: Skill 도구로 쓸 수 있는 skill 목록에 `engineering:<이름>`이 있을 때만 부른다. 없으면 그 단계를 지금처럼 직접 진행한다. 설치를 권하거나 묻지 않는다.
- **부르는 방법**: 해당 단계에서 Skill 도구로 부른다. 같은 skill은 한 번만 부르고, 얻은 관점을 이후 단계에서 다시 쓴다. Plan agent를 쓸 때는 메인이 skill을 부른 뒤 그 점검 관점을 각 agent 프롬프트에 넣는다.
- **쓰는 범위**: skill에서는 점검 관점과 평가 기준만 가져오고, 결과는 이 계획서의 해당 섹션에 계획서 형식으로 쓴다.
  - skill이 안내하는 별도 문서(설계 문서, ADR, 배포 체크리스트 파일)는 만들지 않는다.
  - skill이 안내하는 외부 도구 연동(knowledge base 검색, project tracker 작업 생성, 알림)은 하지 않는다.
  - 이 커맨드의 규칙(애매한 사항은 AskUserQuestion으로 확인, 브랜치 생성·계획서 작성·계획서 커밋까지만)이 skill 내용보다 우선한다.
- **기록**: 부른 skill은 `8. 작업 이력` 첫 행 내용 끝에 ` · 참고 skill: system-design, testing-strategy`처럼 ` · `로 이어 남기고 완료 보고에 적는다. 부른 skill이 없으면 템플릿 첫 행의 ` · 참고 skill: xxx`를 지운다.

## DB·API·화면 설계 skill

DB 스키마, API, 화면이 바뀌는 계획이면 4단계에서 이 플러그인의 skill로 테이블·엔드포인트·화면 정의를 만든다. engineering plugin 유무와 상관없다. (`engineering:system-design`은 설계안을 비교할 때 쓰는 일반 관점이고, 구체적인 정의는 이 skill이 맡는다)

| skill | 언제 부르나 | 결과를 쓸 곳 |
|-------|-------------|--------------|
| `workflow:db-design` | 테이블·컬럼·제약·인덱스가 바뀌거나 기존 데이터 이관이 필요할 때 | `4. 영향 범위` 아래 `### DB 변경` |
| `workflow:api-design` | 엔드포인트가 추가·삭제되거나 요청·응답·오류 코드·권한이 바뀔 때. 요청 필드의 검증 규칙(길이·형식·범위·허용 값)만 바뀌어도 부른다 (전에 통과하던 요청이 거부되므로 하위 호환을 판단해야 한다) | `4. 영향 범위` 아래 `### API 변경` |
| `workflow:ui-design` | 화면이 추가·삭제되거나 화면 요소, 입력 검증, 사용자에게 보이는 메시지, 이동, 권한별 노출이 바뀔 때. 스타일(색·크기·배치)만 바꾸거나 문구 하나만 고치는 정도면 부르지 않는다. 서버 검증만 바뀌고 화면 코드·문구가 그대로면 부르지 않는다. 이때 화면에 규칙 안내나 클라이언트 검증을 더할지는 애매한 사항으로 2단계에서 묻고, 더하기로 하면 부른다 | `4. 영향 범위` 아래 `### 화면 변경` |

- **부르는 방법**: 4단계에서 Skill 도구로 인자 `설계`를 주어 부른다. 여럿이 필요하면 `workflow:db-design` → `workflow:api-design` → `workflow:ui-design` 순서로, 앞 skill의 정의 초안을 가지고 다음 skill을 부른다. (응답 스키마가 테이블 정의에, 화면의 검증·오류 메시지가 API 정의에 의존한다) 각각 한 번만 부른다.
- **skill을 쓸 수 없으면**(Skill 도구로 쓸 수 있는 목록에 없음): `${CLAUDE_PLUGIN_ROOT}/skills/<db-design|api-design|ui-design>/SKILL.md`를 Read 해서 같은 기준으로 직접 진행한다.
- **skill은 기준과 형식만 준다.** 파일을 쓰거나 사용자에게 묻지 않는다. skill을 부른 뒤 이 커맨드의 4단계를 이어서 한다.
  - skill이 돌려준 `미정 사항`은 이 커맨드가 AskUserQuestion으로 확인하고 `2. 결정 사항`에 기록한다. skill이 관례나 기본값으로 정한 것(`따른 관례`에 근거나 `(기본값)`으로 적힌 것)은 절대 규칙의 애매한 사항으로 보지 않고 묻지 않는다.
  - 정의는 7단계에서 계획서 `4. 영향 범위` 아래에 skill의 결과 형식대로 쓴다. 섹션 제목은 `### DB 변경`, `### API 변경`, `### 화면 변경` 그대로, 이 순서로 쓴다. (다른 커맨드가 이 제목으로 찾는다) `따른 관례` 줄은 빼지 않는다. `workflow-plan-review`와 `workflow-do`가 점검할 때 관례를 다시 찾지 않고 이 줄을 재사용한다.
  - skill이 돌려준 작업항목·완료 기준·리스크 후보를 계획서에 반영한다. 작업항목은 이 정의를 기준으로 나누고, 마이그레이션 항목에는 `(단독 커밋)`을 붙인다.
- 3단계(설계안 비교)에서는 부르지 않는다. 상세 정의는 선택한 안에 대해서만 한다.
- **기록**: 부른 skill은 engineering skill과 같이 `8. 작업 이력` 첫 행의 `참고 skill:`에 남기고 완료 보고에 적는다. (예: `… 완료 기준 4개) · 참고 skill: db-design, api-design, testing-strategy`)

## 기존 기능 변경 점검 항목
새 기능 추가가 아니라 이미 있는 기능의 동작을 바꾸는 계획이면(일부라도), 4단계에서 아래 항목을 확인해 계획서에 반영한다.
- **현재 동작**: 바뀌는 동작을 코드에서 직접 찾아 `1. 요구사항` 아래 `현재 동작 → 변경 후 동작` 표에 근거(`path:line`)와 함께 쓴다. 요구사항 문장만 보고 현재 동작을 추측하지 않는다. 코드의 실제 동작이 요구사항의 전제와 다르면 AskUserQuestion으로 확인한다.
- **호출부·영향 추적**: 바뀌는 함수·메서드·API·화면·공통 컴포넌트·설정값을 쓰는 곳을 Grep으로 모두 찾는다.
  - 함께 동작이 바뀌는 호출부는 `4. 영향 범위`에 넣고 작업항목으로 다룬다.
  - 영향을 받지만 그대로 두는 호출부는 `7. 리스크 및 고려사항`에 이유와 함께 적는다.
  - 호출부를 바꿀지 그대로 둘지 판단이 갈리면 AskUserQuestion으로 확인한다.
- **기존 테스트**: 바뀌기 전 동작을 검증하는 기존 테스트를 찾는다.
  - 새 동작에 맞게 기대값을 고치거나 지워야 하는 테스트는 작업항목에 테스트 이름과 함께 명시한다. (`workflow-do`가 그 실패를 회귀로 오인하지 않게 한다)
  - 바뀌지 않아야 하는 동작을 지키는 테스트는 그대로 두고, 이 테스트가 통과하는 것을 `6. 완료 기준`에 넣는다.
  - 바뀌는 동작을 검증하는 테스트가 없으면 테스트 추가 작업항목을 넣는다.
- 1단계에서 Explore agent를 쓰면 호출부와 기존 테스트 찾기도 agent의 반환 항목에 넣는다. `4. 영향 범위`와 작업항목에 쓸 곳은 직접 열어 확인한다.

## 병렬 그룹
`workflow-do`가 동시에 구현할 수 있는 작업항목을 4단계에서 표시한다. `workflow-do`는 표시된 항목을 `item-implementer` agent에 하나씩 맡겨 동시에 구현하고, 검증과 계획서 갱신은 메인이 한다. 표시가 없으면 지금처럼 순서대로 구현한다. 묶을 것이 없으면 표시하지 않는다. (기본은 순서대로다)

**묶는 조건** — 모두 만족할 때만 묶는다.
- 같은 Phase 안의 항목이다. (Phase가 커밋 단위이기 때문이다)
- 서로의 결과를 쓰지 않는다. 한 항목이 다른 항목이 만드는 클래스·함수·타입·테이블·API를 쓰면 묶지 않는다.
- 고칠 파일이 겹치지 않는다. 새로 만들 파일도 포함한다.
- 아래 공유 파일을 함께 고치지 않는다. 라우터·메뉴 등록, 메시지·다국어 파일, 빌드·의존성 파일(`package.json`, `build.gradle` 등), DI·빈 설정, index·barrel export, 마이그레이션 번호, 공통 상수·enum. 이런 수정은 별도 항목으로 빼서 그룹 뒤에 두면 나머지를 묶을 수 있다.
- 각 항목의 복잡도가 `중` 이상이다. (아래 `복잡도` 기준) `하`인 항목은 파일 수와 관계없이 묶지 않는다. agent는 계획서와 주변 코드를 처음부터 다시 읽느라 작은 항목에도 1~2분이 걸려서, 맥락을 이미 가진 메인이 순서대로 하는 편이 빠르다.
- 아래 항목은 묶지 않는다.
  - `(단독 커밋)` 항목
  - `코드 정리 및 리뷰` Phase
  - `(미결)`이 걸린 항목
  - 구현 중 사용자 확인이 필요할 것 같은 항목 (agent는 사용자에게 묻지 못한다)

**복잡도** — 항목마다 판단한다. 하나라도 해당하면 그 등급이다. 위 등급부터 본다.

| 등급 | 기준 |
|------|------|
| 상 | 중에 더해, 구현에 필요한 관례가 다른 모듈이나 여러 파일에 흩어져 있어 구현하는 쪽이 탐색해야 한다 (메인이 계획 단계에서 그 파일을 열어 봤는지와 관계없다. agent는 처음부터 다시 읽는다) / 테스트를 포함해 대략 300줄 이상이다 |
| 중 | 새 로직(분기·검증·계산·상태 변경)이 있는 함수를 여러 개 만든다 / 정의 표의 여러 행을 구현한다 / 테스트를 포함해 대략 100줄 이상이다 |
| 하 | 값·문구·설정·상수만 바꾼다 / 기존 코드를 거의 그대로 따라 쓴다 / 새 분기·검증·계산이 없다 / 계산·분기가 있는 함수가 1개뿐이고 테스트를 포함해 대략 100줄 미만이다 / 대략 50줄 이하다. 파일 수와 관계없다 |

- 줄 수는 어림값이다. 줄 수보다 새 로직과 탐색량을 먼저 본다. (같은 패턴을 10개 파일에 반복하면 줄 수가 많아도 `하`다)
- 등급은 4단계에서 이미 정한 변경 내용(만들 함수, 구현할 정의 행)과 `파일:` 목록을 확인하며 연 파일로 판단한다. 줄 수를 세려고 코드 초안을 쓰거나 파일을 더 읽지 않는다.
- 판단이 경계에 걸리면 낮은 등급으로 본다. (묶지 않는 쪽이 안전하다)
- 같은 Phase에서 묶는 조건을 모두 만족하는 `중` 이상 항목이 하나뿐이면 묶지 않는다. (`상`이어도 짝이 없으면 순서대로 한다)
- 구현 방향이 갈리거나 사용자 확인이 필요할 것 같은 항목은 등급과 관계없이 묶지 않는다.
- 측정 근거: README `병렬 구현 측정`. 항목당 약 200줄(`중`)에서는 속도가 메인과 비슷했고, 메인 컨텍스트가 덜 차는 것이 주된 이점이었다. 속도 이득은 `상`에서 크다.

**표기**
- 그룹마다 Phase 안에서 겹치지 않는 대문자를 정해 항목 끝에 `(병렬 A)`처럼 붙이고, 같은 그룹 항목은 이어서 쓴다. 한 그룹은 2~3개다. 묶을 수 있는 항목이 4개 이상이면 그룹을 나눈다. (`(병렬 A)` 3개, `(병렬 B)` 나머지. `workflow-do`는 그룹 하나씩 실행한다)
- 그룹 항목 바로 아래에 들여쓴 `  - 파일:` 줄로 고칠 파일을 모두 적는다. 체크박스는 붙이지 않는다. (진행률에 세지 않는다) `workflow-do`가 이 줄로 파일이 겹치지 않는지 확인하고, agent가 이 파일만 고친다.
- `파일:` 줄 아래에 `  - 복잡도: 중 — <근거>` 줄을 둔다. 근거에는 새 로직과 어림 줄 수(또는 탐색 범위)를 짧게 쓴다. `workflow-plan-review`가 이 줄로 등급을 점검한다.

```markdown
- [ ] 2.1 회원 조회 API 구현 (병렬 A)
  - 파일: `src/.../MemberQueryController.java`, `src/.../MemberQueryService.java`
  - 복잡도: 중 — 조회·권한 검사·응답 변환 3개 함수, 테스트 포함 약 150줄
- [ ] 2.2 회원 수정 API 구현 (병렬 A)
  - 파일: `src/.../MemberUpdateController.java`, `src/.../MemberUpdateService.java`
  - 복잡도: 중 — 입력 검증·중복 확인·저장 3개 함수, 테스트 포함 약 180줄
- [ ] 2.3 두 API를 라우트·권한 설정에 등록
```

## 처리 절차

### 1. 컨텍스트 파악
- **기준 브랜치 확인 (탐색하기 전에)** — 탐색과 설계안 검증은 작업 브랜치가 갈라져 나올 코드에서 해야 한다. 다른 브랜치의 코드를 보고 계획을 세운 뒤 분기 기준을 바꾸면 계획이 실제 코드와 어긋난다.
  - git 저장소가 아니면 건너뛴다. (`git rev-parse --is-inside-work-tree`)
  - 현재 브랜치(`git branch --show-current`)와 미커밋 변경사항(`git status --short`)을 확인한다.
  - 기본 브랜치는 `git symbolic-ref --short refs/remotes/origin/HEAD`(앞의 `origin/`을 뗀다)로 찾는다. 없으면 로컬 브랜치 중 `main` → `master` → `develop` 순서로 처음 있는 것이다. 이 브랜치와 `develop`(있으면)을 기본 브랜치로 본다.
  - 현재 브랜치가 기본 브랜치이거나 출력이 비어 있으면(detached HEAD) 그대로 진행한다.
  - 기본 브랜치가 아니면 어느 브랜치의 코드를 기준으로 계획할지 AskUserQuestion으로 먼저 묻는다. 질문 본문에 현재 브랜치와 미커밋 변경사항 유무를 적는다. 선택지: `현재 브랜치 기준` / `기본 브랜치(<이름>) 기준`. 다른 브랜치는 사용자가 "Other"로 입력한다.
    - 추천: 현재 브랜치가 아직 기본 브랜치에 합쳐지지 않은 커밋(`git log --oneline <기본 브랜치>..HEAD`)을 가지고 있고 요구사항이 그 작업을 이어 가는 것으로 보이면 `현재 브랜치 기준`, 그 밖에는 `기본 브랜치 기준`을 추천한다. 질문 본문에 합쳐지지 않은 커밋 수와 판단 이유를 한 줄로 적는다.
    - 미커밋 변경(추적하지 않는 파일 포함)이 있으면 질문 본문에 그 파일 목록(많으면 앞의 5개와 개수)과 함께, 다른 브랜치로 전환하면 충돌이 없는 한 이 변경이 기준 브랜치와 새 작업 브랜치로 그대로 따라온다고 적는다. 선택지에 `중단 (변경을 먼저 커밋·stash한 뒤 다시 실행)`을 더한다. 중단을 고르면 아무것도 바꾸지 않고 종료한다.
  - 현재 브랜치가 아닌 브랜치를 고르면 `git switch <기준 브랜치>`로 전환한 뒤 탐색한다. 전환이 실패하면(미커밋 변경 충돌 등) stash나 강제 전환을 하지 않고, 실패 내용을 알리고 중단한다.
  - 미커밋 변경을 가지고 전환했으면 완료 보고에 그 파일들이 원래 브랜치(`<이름>`)가 아니라 작업 트리에 남아 있다는 것을 적는다. (`workflow-do`는 시작할 때 이 파일들을 `시작 전 미커밋 변경`으로 잡아 커밋에서 뺀다)
  - 답은 결정 사항에 `plan · 기준 브랜치`로 기록한다.
- 현재 프로젝트 구조, 관련 소스, CLAUDE.md 등을 필요한 만큼 탐색하여 요구사항과 관련된 파일/모듈을 파악한다.
- 파악 결과 애매한 부분을 목록화한다.
- API 계약, DB 스키마, 화면 추가·동작 변경, 기술 선택, 마이그레이션처럼 `engineering plugin 활용` 표와 `DB·API·화면 설계 skill` 표에 해당하는 변경이 있는지 함께 정리한다.
- 이미 있는 기능의 동작을 바꾸는 요구사항인지 정리한다. 바꾸면 4단계에서 `기존 기능 변경 점검 항목`을 확인한다.

#### 범위가 넓을 때: Explore agent 병렬 탐색
먼저 Glob/Grep 몇 번으로 범위를 가늠한다. 아래 중 하나라도 해당하면 Explore agent로 나누어 탐색하고, 아니면 직접 탐색한다. (agent는 띄우는 비용과 결과 전달 과정의 정보 손실이 있어 범위가 작으면 오히려 느리다)
- 관련 후보 파일이 많다 (대략 20개 이상)
- 구조를 모르는 큰 저장소다
- 요구사항이 2개 이상의 모듈/계층(화면, API, DB, 설정 등)에 걸치고, 관련 후보 파일이 대략 10개 이상이다

가늠하는 동안 관련 파일을 이미 대부분 읽었으면(작은 저장소 등) 위 조건과 관계없이 agent 없이 이어서 직접 진행한다.

실행 방법:
- Agent 도구를 `subagent_type: "Explore"`로 **2~3개**, 서로 겹치지 않는 영역(예: 화면 / 서버·API / DB·설정·테스트)으로 나누어 **한 메시지에서 동시에** 실행한다. 프롬프트에 탐색 폭(`medium` 또는 `very thorough`)을 적는다.
- 각 agent 프롬프트에는 다음을 넣는다.
  - 원문 요구사항과 그 agent가 맡은 영역 (다른 영역은 보지 않도록 명시)
  - 이미 확인한 내용
  - 반환 형식: 관련 파일 `path:line`, 한 줄 역할, 변경 필요 가능성, 따라야 할 기존 관례, 애매한 점
  - "결정하지 말고 후보와 근거만 보고한다"
- agent는 AskUserQuestion을 쓸 수 없다. 애매한 점은 결과로 받아 2단계에서 직접 묻는다.
- 결과를 받은 뒤:
  - agent가 맡았던 영역을 다시 처음부터 탐색하지 않는다.
  - `4. 영향 범위`에 적을 파일은 직접 열어 확인한다. (Explore는 일부만 읽고 보고하므로 확인이 필요하다)
  - agent 결과끼리 어긋나면 해당 파일을 직접 읽어 판단한다.
- Agent 도구를 쓸 수 없는 환경이면 직접 탐색한다.

### 2. 애매한 사항 확인 (AskUserQuestion)
- 1단계에서 목록화한 애매한 사항을 AskUserQuestion으로 확인한다. 애매한 사항이 없으면 생략한다.
- 애매한 사항을 어느 단계에서 물을지 먼저 나눈다. (Explore agent가 보고한 애매한 점도 같다)

| 종류 | 예 | 묻는 곳 |
|------|----|---------|
| 업무 규칙·범위·우선순위·완료 기준, 사용자가 겪는 동작 | 몇 회 실패 시 잠금, 잠금 중 정답 입력 처리, 누가 해제할 수 있나, 다섯 번째 실패에서 바로 잠김을 알릴지, 사용자에게 보일 문구의 내용 | 2단계 (지금) |
| 구현 방법을 가르는 것 | 별도 테이블 ↔ 기존 테이블 컬럼, 서버 처리 ↔ 클라이언트 처리, 라이브러리 선택 | 3단계 설계안 비교 (전제와 선택지로 다룬다) |
| DB·API·화면의 형식 | 상태 코드(401/423), URL 모양, 오류 코드·컬럼·상수 이름과 위치, 화면 배치 | 4단계. `DB·API·화면 설계 skill` 기준을 따른다. skill이 관례나 기본값으로 정하면 묻지 않고, `미정 사항`으로 돌려준 것만 묻는다 |

- 형식 문제라도 사용자가 겪는 동작이 달라지면(예: 상태 코드에 따라 화면이 다른 안내를 보인다) 그 동작을 2단계에서 묻고, 형식은 그 답에 맞춰 4단계에서 정한다.
- 절대 규칙의 "애매한 사항은 직접 결정하지 않는다"는 이 표의 단계에서 묻는다는 뜻이다. 3·4단계로 넘긴 사항을 빠뜨리지 않도록 목록에 남겨 두고, 그 단계에서 묻거나 skill 기본값으로 정해졌는지 확인한다.

### 3. 설계안 비교 (AskUserQuestion)
한 가지 방향으로만 설계하지 않도록, 구현 방법이 실제로 갈리는 경우 서로 다른 안을 나란히 놓고 사용자가 고르게 한다.

- **언제 하는가**: 구조 변경, 새 모듈·라이브러리 도입, 데이터 모델·API 계약 변경처럼 구현 방법이 둘 이상으로 갈릴 때만 한다. 버그 수정, 문구·설정 변경처럼 방법이 사실상 하나뿐이면 건너뛰고, `설계안 비교`에 `대안 없음: <이유>`를 한 줄 남긴다.
- **안 만들기**
  - 1단계에서 Explore agent를 썼으면(범위가 넓으면) Agent 도구를 `subagent_type: "Plan"`으로 2~3개, **한 메시지에서 동시에** 실행한다. 각 agent에 서로 다른 전제를 준다. 한 모델이 혼자 여러 안을 쓰면 선호하는 안 하나에 나머지가 들러리가 되기 쉬우므로, 전제를 강제로 다르게 준다.
    - A: 프로젝트 규칙·관례(CLAUDE.md, 기존 코드의 방식) 안에서 기존 구조를 최대한 유지하는 최소 변경. 규칙을 어겨서 줄이는 변경(예: 이미 적용된 마이그레이션 파일 수정)은 최소 변경으로 보지 않는다.
    - B: 확장성·구조 개선을 우선하는 설계
    - C: 요구사항에 맞는 다른 축 (예: 다른 라이브러리, 서버 처리 ↔ 클라이언트 처리, 동기 ↔ 비동기). 의미 있는 세 번째 축이 없으면 2개만 만든다.
  - 각 agent 프롬프트에는 원문 요구사항, 확정된 결정 사항, 1단계 탐색 결과(관련 파일 `path:line`), 프로젝트 규칙 요약(CLAUDE.md 등의 구조·마이그레이션·계층·명명 규칙과, 1단계에서 찾은 따라야 할 기존 관례), 맡은 전제를 넣는다. agent는 이 대화를 보지 못하므로 규칙을 넣지 않으면 규칙을 어기는 안을 낸다. 반환 형식: 설계 요약, 변경 파일, 장점, 단점, 리스크, 작업량(상/중/하), 이 안이 성립하는 전제, 이 안이 따른 프로젝트 규칙과 어긋나는 규칙(있으면).
  - 1단계를 직접 탐색했거나 Agent 도구를 쓸 수 없으면 직접 2개 안을 위 전제로 나누어 쓴다. 설계안이 여러 계층에 걸쳐도 관련 파일을 이미 대부분 읽었으면 agent를 띄우지 않는다. (agent는 같은 파일을 처음부터 다시 읽는다)
- **검증**: 각 안이 실제 코드 구조에서 가능한지, 프로젝트 규칙·관례를 지키는지 관련 파일을 직접 열어 확인한다.
  - 코드 구조상 성립하지 않는 안은 뺀다.
  - 규칙·관례를 어기는 안은 그 전제(A·B·C) 안에서 규칙을 지키도록 고쳐 다시 확인한다. 고친 안이 다른 안과 같아지거나 고칠 수 없으면 뺀다. 고친 것은 비교표의 그 안 요약에 `(규칙 맞춰 수정: <규칙>)`로 적는다.
  - 검증하다가 그 전제에 더 맞는 안(예: 규칙을 지키면서 더 작은 변경)이 보이면 그 전제의 안을 그것으로 바꾸고 같은 방식으로 적는다. 전제 밖의 새 안을 추가하지는 않는다.
  - 남은 안이 하나뿐이면 그 사실을 기록한다.
- **선택**: AskUserQuestion으로 안을 고르게 한다. 각 선택지의 `preview`에 구조 요약과 변경 파일, 장단점을 넣어 나란히 비교할 수 있게 한다. 추천안은 첫 번째에 두고 `(Recommended)`와 추천 이유를 쓴다. 두 안을 섞는 등 다른 방향은 사용자가 "Other"로 입력한다.
- **기록**: 계획서 `2. 결정 사항` 아래 `### 설계안 비교`에 비교표와 선택 결과를 남긴다. **선택하지 않은 안과 그 이유도 남긴다.** 이후 리뷰나 구현 중 전제가 깨졌을 때 다시 꺼내 쓰는 근거가 된다.
- `engineering:system-design`·`engineering:architecture`를 부를 경우는 `engineering plugin 활용`을 따른다.
- 이 단계의 설계안은 비교할 수 있는 수준까지만 쓴다. API·DB·화면이 바뀌는 안은 바뀌는 테이블·엔드포인트·화면과 하위 호환 영향만 요약한다. 상세 정의는 4단계에서 선택한 안에 대해서만 한다.

### 4. 상세 설계와 남은 사항 확인 (AskUserQuestion)
선택한 안(3단계를 건너뛰었으면 유일한 방법)을 계획서에 쓸 수 있는 수준으로 구체화하고, 그 과정에서 나온 미정 사항을 계획서를 쓰기 전에 모두 확인한다. 구체화할 것이 없는 단순한 작업이면 건너뛴다. 단, 기존 기능의 동작을 바꾸는 계획이면 변경이 한 줄이어도 `기존 기능 변경 점검 항목`(현재 동작, 호출부, 기존 테스트)은 건너뛰지 않는다. (작은 변경일수록 깨지는 기존 테스트를 놓치기 쉽다)

- 변경할 파일과 변경 내용, 작업 순서(Phase 구성)를 정리한다. 작업 항목과 영향 범위는 선택한 안을 기준으로 한다.
  - Phase는 `workflow-do`의 커밋 단위다. 한 Phase가 끝났을 때 테스트·빌드가 통과하는 상태가 되도록 나눈다. (예: DB → API → 화면처럼 의존 순서대로)
  - DB 마이그레이션, 파일 삭제, 기존 데이터 이관처럼 되돌리기 어려운 항목은 작업항목 끝에 `(단독 커밋)`을 붙인다. 실행되면 기존 DB에 테이블·컬럼·데이터를 남기는 코드 변경(마이그레이션 러너에 이력 테이블 도입, 기동 시 테이블을 만드는 부트스트랩 등)도 포함한다. 코드를 되돌려도 DB에 남은 것은 되돌아가지 않기 때문이다. `workflow-do`가 그 항목만 따로 커밋한다.
  - 같은 Phase에서 동시에 구현할 수 있는 항목은 `병렬 그룹` 기준으로 묶고 `(병렬 A)` 표시와 `파일:` 줄을 붙인다. 묶는 조건에 맞는 항목만 묶는다. 고칠 파일을 확정하려면 관련 파일을 직접 확인한다.
- API·DB·화면이 바뀌면 `DB·API·화면 설계 skill`대로 `workflow:db-design`·`workflow:api-design`·`workflow:ui-design`을 불러 테이블·엔드포인트·화면 정의를 정한다. DB·API 정의 때문에 `engineering:system-design`을 따로 부르지 않는다. 3단계를 건너뛰었고 서비스 경계·캐시·큐가 바뀌면 그때만 여기서 부른다.
- 기존 기능의 동작을 바꾸면 `기존 기능 변경 점검 항목`으로 현재 동작, 호출부, 기존 테스트를 확인한다.
- 완료 기준과 테스트 항목, 리스크(롤백 방안 등)를 정리한다. `engineering:testing-strategy`·`engineering:deploy-checklist`를 부를 경우는 `engineering plugin 활용`을 따른다.
- 여기서 새로 나온 애매한 사항(설계를 고른 뒤에야 드러나는 세부 사항)을 AskUserQuestion으로 확인한다. 사용자가 지금 정하지 않겠다고 하면 `(미결)`로 남긴다.
- 이 단계를 마치면 계획서 내용에 대해 더 물을 것이 없어야 한다. 7단계는 정리된 내용을 쓰기만 한다.

### 5. git branch 추천 및 생성 (AskUserQuestion)
- 먼저 요구사항을 2~5 단어 영문 소문자로 요약한 **summary**를 정한다. (예: `add login page`) 브랜치명에는 kebab-case(`add-login-page`), 6단계 파일명에는 snake_case(`add_login_page`)로 같은 summary를 쓴다.
- `git rev-parse --is-inside-work-tree`로 git 저장소인지 확인한다.
  - git 저장소가 아니면 AskUserQuestion으로 `git init` 수행 여부를 묻는다. 거부하면 계획서의 작업 브랜치를 `해당 없음`으로 기록하고 6단계로 넘어간다.
- 현재 브랜치(`git branch --show-current`), 미커밋 변경사항(`git status --short`), 기존 브랜치 목록(`git branch -a`)을 확인한다.
- 작업 성격에 맞는 브랜치명 후보 2~3개를 만들어 AskUserQuestion으로 추천한다.
  - 기존 브랜치 네이밍 관례가 있으면 그것을 따른다. 없으면 `feature/<summary-kebab-case>`, `fix/<...>`, `refactor/<...>`, `chore/<...>`처럼 작업 유형 prefix를 쓴다.
  - 이미 존재하는 브랜치명은 후보에서 뺀다.
  - "브랜치 생성 안 함(현재 브랜치 유지)" 옵션을 포함한다.
- 새 브랜치는 현재 위치(1단계에서 정한 기준 브랜치)에서 만든다. 분기 기준을 여기서 다시 묻지 않는다.
- 미커밋 변경사항이 있으면 브랜치 질문의 본문에 그 사실을 적어, 사용자가 알고 고르게 한다. (변경사항은 새 브랜치로 그대로 따라온다)
- 현재 브랜치 출력이 비어 있으면(detached HEAD) 질문 본문에 그 사실을 적는다. 그래도 "생성 안 함"을 고르면 계획서 작업 브랜치를 `해당 없음 (detached HEAD)`으로 기록한다. 이후 커맨드는 브랜치 확인을 건너뛴다.
- 선택된 브랜치를 `git checkout -b <branch>`로 생성한다. "생성 안 함"을 선택하면 계획서에는 현재 브랜치명을 기록한다.
- **커밋 방식**도 브랜치 질문과 같은 AskUserQuestion에 질문 하나로 함께 묻는다. 이 계획서로 하는 모든 커맨드가 이 값을 따른다. 선택지:
  - `자동 (Recommended)`: 정해진 시점(계획서 작성, 리뷰 반영, Phase 완료 등)에 묻지 않고 커밋한다. 위험한 경우(`진행 관리 규칙`의 예외)에만 묻는다.
  - `확인`: 커밋 시점마다 묻는다.
  - `끝에 한꺼번에`: 각 커맨드가 끝날 때만 묻는다.
  - 답은 계획서 상단 표의 `커밋 방식`에 쓰고 결정 사항에 `plan · 커밋 방식`으로 기록한다. git 저장소가 아니면 묻지 않고 `해당 없음`으로 쓴다.

### 6. 파일 경로 결정
- 현재 시각을 조회해서 파일 경로, 계획서의 `작성일시`·`최종 갱신`, `8. 작업 이력`의 첫 행에 **같은 값**을 쓴다. (결정 사항의 일시는 답을 받은 시점의 값이다. 아래 `결정 사항 기록` 참고)
  - Bash: `date '+%y%m%d %H%M%S %Y-%m-%d %H:%M:%S'`
  - PowerShell: `Get-Date -Format 'yyMMdd HHmmss yyyy-MM-dd HH:mm:ss'`
  - 출력 순서: `YYMMDD` `HHMISS` `YYYY-MM-DD HH:MI:SS`
- 5단계에서 정한 summary를 snake_case로 쓴다. (예: `add_login_page`)
- 경로: `ai-work/plans/YYMMDD/HHMISS_[summary_snake_case].md` (프로젝트 루트 기준)
- 디렉토리가 없으면 생성한다.

### 7. 작업계획서 작성
4단계까지 정리한 내용을 아래 규칙과 템플릿을 따라 작성한다. 템플릿은 `${CLAUDE_PLUGIN_ROOT}/templates/plan-template.md`를 Read 해서 쓴다. (아래 `작업계획서 템플릿` 참고) 작업 항목은 **검증 가능한 단위**로 쪼개고, 단계(Phase)별로 묶는다. 생성 시점에는 모든 항목이 `[ ]`이다.
- 작성한 뒤 `진행 표시 확인`을 한 번 실행해 체크 항목 수(`N`)와 진행 표시가 맞는지 확인한다.

### 8. 계획서 커밋 (AskUserQuestion)
- git 저장소가 아니면 건너뛴다.
- 5단계에서 정한 `커밋 방식`을 따른다.
  - `자동`: 묻지 않고 커밋한 뒤 `커밋 <해시> <제목>` 한 줄로 알린다. 단, 작업 브랜치가 기본 브랜치(main/master/develop 등)이면 그 사실을 적고 아래처럼 묻는다.
  - `확인`·`끝에 한꺼번에`: AskUserQuestion으로 묻는다. 질문 본문에 커밋 메시지 초안과 작업 브랜치를 적는다. 선택지: `커밋 (Recommended)` / `커밋하지 않음`. 답은 `2. 결정 사항`에 `plan · 커밋`으로 기록한 뒤 커밋한다. (그 행도 같은 커밋에 들어간다)
- 계획서 파일 하나만 `git add -- <계획서>` 후 `git commit -- <계획서>`로 커밋한다. 1단계에서 확인한 다른 미커밋 변경은 넣지 않는다. (`git add -A` 쓰지 않음)
- 메시지: 제목은 프로젝트 규칙(CLAUDE.md 등)의 커밋 형식이 있으면 그것을 따르고, 없으면 `docs(plan): <작업 제목> 작업계획서 작성`으로 쓴다. 본문 끝 줄 `Plan: <계획서 경로>`는 프로젝트 형식이 있어도 붙인다. (프로젝트 규칙이 본문 형식을 따로 정해 막는 경우만 뺀다. `git log --grep`으로 계획서의 커밋을 찾는 근거다)
- 커밋이 실패하면(훅 실패 등) `--no-verify`로 우회하지 않고 원인을 알린다.
- push는 하지 않는다.

## 상태 표기 · 진행률 규칙

| 표기 | 의미 |
|------|------|
| `[ ]` | 작업항목 (대기) |
| `[~]` | 진행중 |
| `[V]` | 작업완료 |

- **체크 항목** = `5. 작업 항목`의 항목 + `6. 완료 기준`의 항목. 전체진행률의 분모는 이 둘을 합한 수다.
- **전체진행률** = `[V]` 수 ÷ 체크 항목 수 × 100 (소수점 버림). `0% (0/N)`처럼 개수를 함께 쓴다.
- **진행률 바** = 10칸. 10%당 `■` 1칸(버림), 나머지는 `□`
- **작업상태**는 백분율이 아니라 개수로 판단한다.
  - 대기: `[V]`와 `[~]`가 모두 0개
  - 완료: 모든 체크 항목이 `[V]`
  - 진행: 그 외
- Phase 제목에도 같은 규칙으로 그 Phase의 상태와 진행률을 표시한다. (분모는 그 Phase의 작업항목 수)

### 진행 표시 확인
진행률·진행률 바·작업상태·Phase 제목의 상태는 손으로 다시 세지 않고 스크립트로 확인한다.
- Bash 도구로 `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-progress.sh" "<계획서 경로>"`를 실행한다. (PowerShell에서 `bash`를 부르면 WSL bash가 잡힐 수 있으니 Bash 도구를 쓴다)
- 스크립트는 체크 표기를 세어 맞는 값을 계산하고, 적힌 값과 다른 곳만 `적힌 값 → 맞는 값`으로 출력한다. 체크 표기는 그대로 두고 출력된 값으로 고친다. `진행 표시 일치`가 나오면 고칠 곳이 없다.
- `최종 갱신` 시각은 확인하지 않는다. 스크립트를 실행할 수 없으면(`실행 오류` 출력, bash 없음) 위 규칙대로 직접 센다.

## 작업계획서 템플릿

템플릿은 `${CLAUDE_PLUGIN_ROOT}/templates/plan-template.md`에 있다. 7단계에서 이 파일을 Read 해서 그 구조와 문구대로 쓴다. `workflow-do`·`workflow-plan-review`도 예전 형식 계획서를 올릴 때 이 파일을 읽는다.

- 구성: 상단 표(작성일시, 작업 브랜치, 커밋 방식, 작업상태, 전체진행률, 최종 갱신) → `진행률`(진행률 바, `진행 관리 규칙`·`결정 · 이력 기록 규칙` 블록) → `1. 요구사항` → `2. 결정 사항`(아래 `설계안 비교`) → `3. 작업 범위` → `4. 영향 범위` → `5. 작업 항목` → `6. 완료 기준` → `7. 리스크 및 고려사항` → `8. 작업 이력`
### 템플릿 작성 지침
- **작업 브랜치**: 5단계 결과를 쓴다. 새로 만든 브랜치명 / 생성하지 않았으면 현재 브랜치명 / git 저장소가 아니면 `해당 없음`
- **커밋 방식**: 5단계 결과를 쓴다. `자동` / `확인` / `끝에 한꺼번에` / git 저장소가 아니면 `해당 없음`
- **N**: 체크 항목 수(작업항목 + 완료 기준)
- **항목 ID**: 작업항목은 `Phase번호.순번`(`1.1`), 완료 기준은 `DoD-순번`(`DoD-1`). 리뷰와 usecase 매핑이 이 ID로 항목을 가리킨다.
- **진행 관리 규칙 블록**은 빼거나 줄이지 않고 그대로 넣는다. `workflow-do`가 이 블록을 기준으로 진행 상황을 갱신하고, 커맨드 없이 직접 구현할 때도 규칙이 전달된다.
- **`(단독 커밋)`**: 되돌리기 어려운 작업항목 끝에만 붙인다. (예: `- [ ] 1.2 회원 테이블에 잠금 컬럼 추가 마이그레이션 (단독 커밋)`) 커밋 단위 표시일 뿐 진행 상태 표기가 아니다.
- **`(병렬 A)`**: `병렬 그룹` 기준에 맞는(복잡도 `중` 이상) 항목에만 붙이고, 항목 바로 아래에 `  - 파일:` 줄과 `  - 복잡도:` 줄을 둔다. 템플릿의 병렬 그룹 주석은 지운다. 진행 상태 표기가 아니다.
- **코드 정리 및 리뷰 Phase**: 소스 코드를 바꾸는 계획이면 항상 마지막 Phase로 넣는다. Phase 번호는 앞 Phase 다음 번호이고, 항목은 템플릿의 두 개(`/simplify` → `/code-review medium`) 그대로 쓴다. 문서·설정만 바꾸는 계획이면 넣지 않는다. 실행은 `workflow-do`가 Skill 도구로 한다.
- **설계안 비교**: 3단계를 건너뛰었으면 표 대신 `대안 없음: <이유>` 한 줄만 쓴다.
- **결정 사항 기록**
  - `단계`에는 질문한 커맨드와 맥락을 쓴다: `plan`, `plan · 기준 브랜치`, `plan · 설계안`, `plan · 브랜치`, `plan · 커밋 방식`, `plan · 커밋`, `review`, `review · 커밋`, `do`, `do · 1.2`·`do · DoD-2`(항목 ID), `do · 미결 확정`, `do · 커밋`, `usecase-plan`, `usecase-plan · 커밋`, `usecase-do · 02-03`(단계 ID), `usecase-do · 커밋`, `<커맨드> · 브랜치`(작업 브랜치 확인), `<커맨드> · 대화 지시`
  - 6단계(시각 조회) 전에 받은 답의 일시는 답을 받은 시점에 Bash `date '+%Y-%m-%d %H:%M:%S'` / PowerShell `Get-Date -Format 'yyyy-MM-dd HH:mm:ss'`로 조회해 둔다.
  - 한 번의 AskUserQuestion에 질문이 여러 개면 질문마다 한 행씩 쓴다.
  - 대화 지시는 `plan · 대화 지시`로 쓴다. 예: `| 4 | ... | plan · 대화 지시 | - | - | 기존 DateUtil 대신 새 유틸을 만들 것 | 작업항목 1.2 반영 |`
  - 계획서 파일이 생기기 전에 받은 답은 기억해 두었다가 작성할 때 모두 기록한다.
- 템플릿의 `(예시)` 행은 지우고 실제로 받은 답으로 채운다.
- 템플릿의 `<!-- -->` 안내 주석(현재 동작 표, DB·API·화면 변경, 병렬 그룹)은 해당 내용을 채웠든 해당이 없든 작성을 마치면 모두 지운다. 계획서에 주석을 남기지 않는다.
- 결정 사항이 없으면 표는 머리글만 두고, 표 아래에 `계획 단계에서 확인한 사항 없음` 한 줄을 쓴다. (행으로 넣지 않는다. 이후 커맨드가 같은 표에 행을 추가하기 때문이다)
- **요구사항 원문**: `1. 요구사항`의 인용 블록에는 사용자가 입력한 문장을 고치지 않고 그대로 넣는다. `@경로`로 읽은 문서는 경로만 적는다.
- **현재 동작 → 변경 후 동작**: 기존 기능의 동작을 바꾸는 계획이면 주석을 풀고 `기존 기능 변경 점검 항목`에서 확인한 내용으로 채운다. 새 기능만 추가하는 계획이면 주석째 지운다. `근거`에는 현재 동작을 확인한 코드 위치를 쓴다.

## 완료 보고
작성이 끝나면 사용자에게 다음을 보고한다.
- 생성된 계획서 경로
- 작업 브랜치와 커밋 방식
- 1단계에서 미커밋 변경을 가지고 기준 브랜치로 전환했으면 그 파일 목록과 원래 브랜치 이름
- 계획서 커밋 여부 (커밋했으면 `git log -1 --format='%h %s'`)
- Phase 수 / 작업항목 수 / 완료 기준 수, `(단독 커밋)` 항목
- 병렬 그룹과 각 항목의 복잡도 (예: `Phase 2 A: 2.1(중), 2.2(상)`. 없으면 `없음`)
- 선택한 설계안과 선택하지 않은 안 (설계안 비교를 건너뛰었으면 그 이유)
- 사용자 확인으로 확정한 결정 사항 요약
- 참고한 skill (`workflow:db-design`·`workflow:api-design`·`workflow:ui-design`, engineering skill. 부르지 않았으면 생략)
- 범위가 크거나 복잡하면(예: `코드 정리 및 리뷰` Phase와 그 항목을 빼고 센 Phase가 3개 이상이거나 작업항목이 10개 이상, 여러 모듈에 걸친 변경) `/workflow:workflow-plan-review @<계획서 경로>` 실행을 권장한다.
- 구현은 `/workflow:workflow-do @<계획서 경로>`로 시작한다고 안내한다.
- 화면으로 검증할 항목이 있으면 `/workflow:workflow-usecase-plan @<계획서 경로>` 실행을 안내한다.
