# workflow-plan

사용자가 입력한 요구사항을 바탕으로 **작업계획서**를 생성한다.

## 입력

```
$ARGUMENTS
```

입력이 비어 있으면 AskUserQuestion으로 작업 내용을 먼저 받는다.

## 절대 규칙

- **애매한 사항은 직접 결정하지 않는다.** 요구사항의 범위, 기술 선택, 우선순위, 대상 화면/모듈, 완료 기준 등 해석이 둘 이상 가능한 사항은 반드시 AskUserQuestion으로 확답을 받은 뒤 계획서에 반영한다.
  - 한 번에 최대 4개 질문까지 묶어서 묻는다. 추천안이 있으면 첫 번째 옵션에 두고 라벨 끝에 `(Recommended)`를 붙인다.
  - 확답 받은 내용은 계획서의 `결정 사항` 섹션에 기록한다.
- 이 커맨드는 **계획서 생성까지만** 수행한다. 실제 구현 작업은 사용자가 지시할 때 진행한다.

## 처리 절차

### 1. 컨텍스트 파악
- 현재 프로젝트 구조, 관련 소스, CLAUDE.md 등을 필요한 만큼 탐색하여 요구사항과 관련된 파일/모듈을 파악한다.
- 파악 결과 애매한 부분을 목록화한다.

### 2. 애매한 사항 확인 (AskUserQuestion)
- 1단계에서 목록화한 애매한 사항을 AskUserQuestion으로 확인한다. 애매한 사항이 없으면 생략한다.

### 3. git branch 추천 및 생성 (AskUserQuestion)
- `git rev-parse --is-inside-work-tree`로 git 저장소인지 확인한다.
  - git 저장소가 아니면 AskUserQuestion으로 `git init` 수행 여부를 묻는다. 거부하면 branch 항목은 `해당 없음`으로 기록하고 진행한다.
- 현재 브랜치(`git branch --show-current`)와 미커밋 변경사항(`git status --short`)을 확인한다.
- 작업 성격에 맞는 브랜치명 후보 2~3개를 만들어 AskUserQuestion으로 추천한다.
  - 규칙: `feature/<summary-kebab-case>`, `fix/<...>`, `refactor/<...>`, `chore/<...>` 등 작업 유형 prefix 사용
  - 기존 브랜치 네이밍 관례(`git branch -a`)가 있으면 그것을 우선 따른다.
  - "브랜치 생성 안 함(현재 브랜치 유지)" 옵션도 포함한다.
- 선택된 브랜치를 `git checkout -b <branch>`로 생성한다. 미커밋 변경사항이 있으면 생성 전에 사용자에게 알린다.

### 4. 파일 경로 결정
- Bash로 현재 시각을 구한다: `date +%y%m%d` (YYMMDD), `date +%H%M%S` (HHMISS)
- 요구사항을 2~5 단어 영문 snake_case로 요약한다. (예: `add_login_page`)
- 경로: `ai-work/plans/YYMMDD/HHMISS_[summary_snake_case].md`
- 디렉토리가 없으면 생성한다.

### 5. 작업계획서 작성
아래 템플릿을 따라 작성한다. 작업 항목은 **검증 가능한 단위**로 쪼개고, 단계(Phase)별로 묶는다.

## 상태 표기 규칙

| 표기 | 의미 |
|------|------|
| `[ ]` | 작업항목 (대기) |
| `[~]` | 진행중 |
| `[V]` | 작업완료 |

- **전체진행률** = `[V]` 개수 / 전체 작업항목 수 × 100 (소수점 버림, 정수 %)
- **작업상태**
  - 대기: 진행률 0% 이고 `[~]` 없음
  - 진행: `[~]`가 하나라도 있거나 0% < 진행률 < 100%
  - 완료: 진행률 100%
- Phase별로도 진행률과 상태를 표시한다.

## 작업계획서 템플릿

```markdown
# [작업 제목]

| 항목 | 내용 |
|------|------|
| 작성일시 | YYYY-MM-DD HH:MI:SS |
| 작업 브랜치 | `feature/xxx` (또는 해당 없음) |
| 작업상태 | 대기 |
| 전체진행률 | 0% (0/N) |
| 최종 갱신 | YYYY-MM-DD HH:MI:SS |

## 진행률

`[□□□□□□□□□□] 0%`

> 진행률 바: 10칸 기준, 10%당 ■ 1칸

## 1. 요구사항
- 사용자 원문 요구사항 요약

## 2. 결정 사항
| # | 질문 | 확정 내용 |
|---|------|-----------|
| 1 | ... | ... |

## 3. 작업 범위
- 포함:
- 제외:

## 4. 영향 범위 (관련 파일/모듈)
- `path/to/file` - 변경 내용 요약

## 5. 작업 항목

### Phase 1. [단계명] — 대기 (0%)
- [ ] 1.1 작업 내용
- [ ] 1.2 작업 내용

### Phase 2. [단계명] — 대기 (0%)
- [ ] 2.1 작업 내용

## 6. 완료 기준 (Definition of Done)
- [ ] 기능/테스트/빌드 등 검증 가능한 기준

## 7. 리스크 및 고려사항
- ...

## 8. 작업 이력
| 일시 | 내용 |
|------|------|
| YYYY-MM-DD HH:MI:SS | 작업계획서 생성 |
```

> `6. 완료 기준`의 체크박스도 전체진행률 계산에 포함한다.

## 실시간 갱신 규칙 (이후 작업 수행 시)
계획서 하단 또는 작업 수행 시 다음 규칙을 지킨다.
1. 작업항목 착수 시 즉시 `[ ]` → `[~]` 로 변경하고 작업상태/최종 갱신 시각을 갱신한다.
2. 작업항목 완료 시 즉시 `[~]` → `[V]` 로 변경하고 전체진행률, 진행률 바, Phase 진행률/상태, 작업상태를 재계산한다.
3. 주요 변경은 `8. 작업 이력`에 한 줄 추가한다.

## 완료 보고
작성이 끝나면 사용자에게 다음을 보고한다.
- 생성된 계획서 경로
- 작업 브랜치
- 작업 항목 수 / Phase 수
- 범위가 크거나 복잡하면(예: Phase 3개 이상 또는 작업항목 10개 이상, 여러 모듈에 걸친 변경) `/workflow:workflow-plan-review @<계획서 경로>` 실행을 권장한다.
- UI 검증이 필요한 작업이면 `/workflow:workflow-usecase-plan @<계획서 경로>` 실행을 안내한다.
