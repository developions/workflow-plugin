# workflow-plan

사용자가 입력한 요구사항을 바탕으로 **작업계획서**를 생성한다.

## 입력

```
$ARGUMENTS
```

입력이 비어 있으면 계획서를 만들지 않는다. 작업 요구사항을 문장으로 입력해 달라고 요청하고 종료한다. (AskUserQuestion은 선택지형이라 자유 서술을 받는 용도로 쓰지 않는다)

## 절대 규칙

- **애매한 사항은 직접 결정하지 않는다.** 요구사항의 범위, 기술 선택, 우선순위, 대상 화면/모듈, 완료 기준 등 해석이 둘 이상 가능한 사항은 반드시 AskUserQuestion으로 확답을 받은 뒤 계획서에 반영한다.
  - 한 번에 최대 4개 질문까지 묶어서 묻고, 더 있으면 여러 번 나누어 묻는다. 추천안이 있으면 첫 번째 옵션에 두고 라벨 끝에 `(Recommended)`를 붙인다.
  - 확답 받은 내용은 계획서의 `2. 결정 사항`에 기록한다.
  - AskUserQuestion을 쓸 수 없는 환경(비대화형 실행 등)이면 추측으로 진행하지 말고, 질문 목록을 출력한 뒤 중단한다.
- 이 커맨드는 **브랜치 생성과 계획서 작성까지만** 수행한다. 구현은 사용자가 따로 지시할 때 진행한다.

## 처리 절차

### 1. 컨텍스트 파악
- 현재 프로젝트 구조, 관련 소스, CLAUDE.md 등을 필요한 만큼 탐색하여 요구사항과 관련된 파일/모듈을 파악한다.
- 파악 결과 애매한 부분을 목록화한다.

### 2. 애매한 사항 확인 (AskUserQuestion)
- 1단계에서 목록화한 애매한 사항을 AskUserQuestion으로 확인한다. 애매한 사항이 없으면 생략한다.

### 3. git branch 추천 및 생성 (AskUserQuestion)
- `git rev-parse --is-inside-work-tree`로 git 저장소인지 확인한다.
  - git 저장소가 아니면 AskUserQuestion으로 `git init` 수행 여부를 묻는다. 거부하면 계획서의 작업 브랜치를 `해당 없음`으로 기록하고 4단계로 넘어간다.
- 현재 브랜치(`git branch --show-current`), 미커밋 변경사항(`git status --short`), 기존 브랜치 목록(`git branch -a`)을 확인한다.
- 작업 성격에 맞는 브랜치명 후보 2~3개를 만들어 AskUserQuestion으로 추천한다.
  - 기존 브랜치 네이밍 관례가 있으면 그것을 따른다. 없으면 `feature/<summary-kebab-case>`, `fix/<...>`, `refactor/<...>`, `chore/<...>`처럼 작업 유형 prefix를 쓴다.
  - 이미 존재하는 브랜치명은 후보에서 뺀다.
  - "브랜치 생성 안 함(현재 브랜치 유지)" 옵션을 포함한다.
- 현재 브랜치가 기본 브랜치(main/master/develop 등)가 아니면, 어느 브랜치에서 분기할지도 같은 AskUserQuestion에 질문으로 넣는다.
- 미커밋 변경사항이 있으면 브랜치를 만들기 전에 사용자에게 알린다. (변경사항은 새 브랜치로 그대로 따라온다)
- 선택된 브랜치를 `git checkout -b <branch> [<분기 기준 브랜치>]`로 생성한다. "생성 안 함"을 선택하면 계획서에는 현재 브랜치명을 기록한다.

### 4. 파일 경로 결정
- 현재 시각을 **한 번만** 조회해서 파일 경로와 계획서의 일시에 같은 값을 쓴다.
  - Bash: `date '+%y%m%d %H%M%S %Y-%m-%d %H:%M:%S'`
  - PowerShell: `Get-Date -Format 'yyMMdd HHmmss yyyy-MM-dd HH:mm:ss'`
  - 출력 순서: `YYMMDD` `HHMISS` `YYYY-MM-DD HH:MI:SS`
- 요구사항을 2~5 단어 영문 소문자 snake_case로 요약한다. (예: `add_login_page`)
- 경로: `ai-work/plans/YYMMDD/HHMISS_[summary_snake_case].md` (프로젝트 루트 기준)
- 디렉토리가 없으면 생성한다.

### 5. 작업계획서 작성
아래 규칙과 템플릿을 따라 작성한다. 작업 항목은 **검증 가능한 단위**로 쪼개고, 단계(Phase)별로 묶는다. 생성 시점에는 모든 항목이 `[ ]`이다.

## 상태 표기 · 진행률 규칙

| 표기 | 의미 |
|------|------|
| `[ ]` | 작업항목 (대기) |
| `[~]` | 진행중 |
| `[V]` | 작업완료 |

- **체크 항목** = `5. 작업 항목`의 항목 + `6. 완료 기준`의 항목. 전체진행률의 분모는 이 둘을 합한 수다.
- **전체진행률** = `[V]` 수 ÷ 체크 항목 수 × 100 (소수점 버림). `0% (0/N)`처럼 개수를 함께 쓴다.
- **진행률 바** = 10칸. 10%당 `■` 1칸(버림), 나머지는 `□`
- **작업상태**는 백분율이 아니라 개수로 판단한다.
  - 대기: `[V]`와 `[~]`가 모두 0개
  - 완료: 모든 체크 항목이 `[V]`
  - 진행: 그 외
- Phase 제목에도 같은 규칙으로 그 Phase의 상태와 진행률을 표시한다. (분모는 그 Phase의 작업항목 수)

## 작업계획서 템플릿

```markdown
# [작업 제목]

| 항목 | 내용 |
|------|------|
| 작성일시 | YYYY-MM-DD HH:MI:SS |
| 작업 브랜치 | `feature/xxx` |
| 작업상태 | 대기 |
| 전체진행률 | 0% (0/N) |
| 최종 갱신 | YYYY-MM-DD HH:MI:SS |

## 진행률

`[□□□□□□□□□□] 0%`

> **진행 관리 규칙** — 이 계획서로 작업하는 사람과 AI는 아래를 지킨다.
> - 표기: `[ ]` 작업항목(대기) · `[~]` 진행중 · `[V]` 작업완료
> - 항목에 착수하면 즉시 `[ ]` → `[~]`, 끝나면 즉시 `[~]` → `[V]`로 바꾼다. 여러 항목을 몰아서 한꺼번에 갱신하지 않는다.
> - 항목 상태를 바꿀 때마다 상단 표의 작업상태·전체진행률·최종 갱신, 진행률 바, 해당 Phase 제목의 상태/진행률을 함께 고친다.
> - 전체진행률 = `[V]` 수 ÷ 체크 항목 수(5. 작업 항목 + 6. 완료 기준) × 100, 소수점 버림. 진행률 바는 10%당 `■` 1칸.
> - 작업상태: 대기(`[V]`·`[~]` 모두 0개) / 완료(모든 항목 `[V]`) / 진행(그 외)
> - 범위나 항목이 바뀌면 `8. 작업 이력`에 한 줄 남긴다. 항목 번호(`1.1`, `DoD-1`)는 다른 문서가 참조하므로 바꾸지 않는다.

## 1. 요구사항
- 사용자 원문 요구사항 요약

## 2. 결정 사항
| # | 질문 | 확정 내용 |
|---|------|-----------|
| 1 | ... | ... |

## 3. 작업 범위
- 포함:
- 제외:

## 4. 영향 범위 (관련 파일/모듈)
- `path/to/file` - 변경 내용 요약

## 5. 작업 항목

### Phase 1. [단계명] — 대기 (0%)
- [ ] 1.1 작업 내용
- [ ] 1.2 작업 내용

### Phase 2. [단계명] — 대기 (0%)
- [ ] 2.1 작업 내용

## 6. 완료 기준 (Definition of Done)
- [ ] DoD-1 기능/테스트/빌드 등 검증 가능한 기준

## 7. 리스크 및 고려사항
- ...

## 8. 작업 이력
| 일시 | 내용 |
|------|------|
| YYYY-MM-DD HH:MI:SS | 작업계획서 생성 |
```

### 템플릿 작성 지침
- **작업 브랜치**: 3단계 결과를 쓴다. 새로 만든 브랜치명 / 생성하지 않았으면 현재 브랜치명 / git 저장소가 아니면 `해당 없음`
- **N**: 체크 항목 수(작업항목 + 완료 기준)
- **항목 ID**: 작업항목은 `Phase번호.순번`(`1.1`), 완료 기준은 `DoD-순번`(`DoD-1`). 리뷰와 usecase 매핑이 이 ID로 항목을 가리킨다.
- **진행 관리 규칙 블록**은 빼거나 줄이지 않고 그대로 넣는다. 구현은 이 커맨드가 로드되지 않은 세션에서 이뤄지므로, 실시간 갱신 규칙은 계획서 안에 있어야 전달된다.
- 결정 사항이 없으면 `2. 결정 사항` 표에 `확인이 필요한 사항 없음` 한 줄을 남긴다.

## 완료 보고
작성이 끝나면 사용자에게 다음을 보고한다.
- 생성된 계획서 경로
- 작업 브랜치
- Phase 수 / 작업항목 수 / 완료 기준 수
- 사용자 확인으로 확정한 결정 사항 요약
- 범위가 크거나 복잡하면(예: Phase 3개 이상 또는 작업항목 10개 이상, 여러 모듈에 걸친 변경) `/workflow:workflow-plan-review @<계획서 경로>` 실행을 권장한다.
- 구현을 시작할 때는 `@<계획서 경로>`를 mention하여 지시하면 계획서의 진행 관리 규칙에 따라 진행 상황이 갱신된다고 안내한다.
- 화면으로 검증할 항목이 있으면 `/workflow:workflow-usecase-plan @<계획서 경로>` 실행을 안내한다.
