# workflow-roadmap

계획서 하나에 담기 어려운 큰 작업을 **업무**로 나눈 로드맵을 만들고 고친다. 업무 하나가 업무 파일 하나이고, 업무마다 `/workflow:workflow-plan @<업무 파일>`로 작업계획서를 만든다.

로드맵은 요구사항과 업무 순서만 다룬다. 설계(설계안 비교, DB·API·화면 정의, 작업항목)는 업무마다 `workflow-plan`이 실제 코드를 보고 한다. 앞 업무를 구현한 뒤에 뒤 업무를 계획해야 계획이 코드와 맞기 때문이다.

## 입력

```
$ARGUMENTS
```

입력으로 세 가지 모드 중 하나를 정한다. `@`를 뗀 경로의 파일을 직접 읽는다. (자동 첨부에 기대지 않는다)

| 입력 | 모드 |
|------|------|
| `ai-work/roadmaps/` 아래 파일(README.md 또는 업무 파일) + 다른 텍스트 | **수정** — 텍스트를 수정 지시로 본다 |
| `ai-work/roadmaps/` 아래 파일만 | **현황** |
| 그 밖의 문장, 또는 `@<요구사항 문서>` | **생성** |
| 비어 있음 | 아래 `빈 입력`대로 로드맵을 골라 **현황**. 없으면 로드맵으로 나눌 요구사항을 문장으로 입력해 달라고 하고 종료한다 |

- **빈 입력**: 로드맵은 로드맵 브랜치에만 있을 수 있으므로 작업 트리와 로컬 브랜치를 함께 찾는다.
  - 작업 트리: `ai-work/roadmaps/*/README.md`. git 저장소이면 로컬 브랜치에서도 `git grep -e '^| 작업상태 |' $(git for-each-ref --format='%(refname:short)' refs/heads) -- 'ai-work/roadmaps/*/README.md'`로 찾는다. (결과는 `<브랜치>:<경로>:<줄>`) 같은 로드맵이 여러 곳에 있으면 작업 트리의 것, 없으면 README `작업 브랜치`와 같은 브랜치의 것을 쓴다.
  - 작업상태가 `완료`가 아닌 것만 후보로 하고, 디렉토리 이름의 `YYMMDD`가 최근인 순(같으면 README `최종 갱신`이 최근인 순)으로 최대 3개를 AskUserQuestion으로 묻는다. 선택지마다 `<제목> (<디렉토리 이름>, <있는 곳: 작업 트리 또는 브랜치>)`로 쓰고 첫 번째에 `(Recommended)`, 마지막에 `중단`을 둔다. 후보가 하나뿐이어도 묻는다.
  - 다른 브랜치에만 있는 로드맵은 선택지 끝에 `— <브랜치>로 전환`을 적는다. 이 선택이 전환 답을 겸하므로, 고르면 다시 묻지 않고 그 브랜치로 전환한다. (전환 방법과 실패할 때는 아래 브랜치 전환 규칙과 같다) 이런 선택지가 있으면 질문 본문에 미커밋 변경 목록(`git status --short`, 많으면 앞의 5개와 개수)을 적고, 전환하면 충돌이 없는 한 그 변경이 그 브랜치로 따라온다고 적는다.
  - 같은 로드맵이 여러 브랜치에 있는데 README `작업 브랜치`와 같은 브랜치가 없어 전환할 곳을 하나로 정할 수 없을 때만, 선택지에는 `여러 브랜치`로 적고 고른 뒤 아래 브랜치 전환 규칙대로 묻는다.

- 업무 파일을 지정했으면 그 파일 상단 표의 `로드맵` README를 대상으로 한다. 수정 지시가 대상을 밝히지 않으면 그 업무에 대한 지시로 본다.
- 로드맵 파일이 작업 트리에 없으면 다른 브랜치에만 있는 것이다. (`빈 입력`에서 전환할 브랜치까지 고른 경우는 묻지 않고 전환만 한다) git 저장소이면 로컬 브랜치마다 `git cat-file -e <브랜치>:<경로>`로 찾아 어느 브랜치로 전환할지 묻는다. (선택지: 찾은 브랜치마다 `<브랜치>로 전환` — 로드맵 `작업 브랜치`와 같은 것에 `(Recommended)` / `중단`) 전환은 `git switch <브랜치>`로 하고, 실패하면(미커밋 변경 충돌 등) stash나 강제 전환을 하지 않고 중단한다. 어디에도 없으면 알리고 중단한다.
- 생성 모드의 `@<요구사항 문서>`는 `workflow-plan`과 같이 직접 읽어 요구 항목을 README `### 요구사항 문서`에 옮긴다. (아래 `작성 지침`)

## 절대 규칙

- **애매한 사항은 직접 결정하지 않는다.** 범위, 업무 분할, 순서, 여러 업무에 걸치는 업무 규칙처럼 해석이 둘 이상인 것은 AskUserQuestion으로 확답을 받는다. 한 번에 최대 4개, 추천안은 첫 번째 옵션 + `(Recommended)`.
  - AskUserQuestion을 쓸 수 없는 환경(비대화형 실행 등)이면 추측으로 진행하지 말고, 질문 목록을 출력한 뒤 중단한다.
- **설계하지 않는다.** 기술 선택, 설계안 비교, DB·API·화면 정의, 작업항목은 정하지 않는다. 업무 계획서를 만들 때 `workflow-plan`이 한다.
  - 업무 간 약속에는 **무엇을 제공하는지**(예: 회원 정보, 로그인한 회원 식별값, 관리자 전용 기능 접근 막기)만 쓴다. 이름(테이블·컬럼·엔드포인트·세션 값·모듈)은 코드에 이미 있는 것과 사용자가 요구사항이나 지시로 지정한 것만 쓴다. 사용자가 지정한 이름에는 `(사용자 지정, 결정 #n)`을 붙인다. 이름이 적힌 약속은 업무 계획서가 그 이름을 따른다. 새로 만들 것의 이름·저장 위치·방식(예: 어느 테이블에 둘지, 세션인지 토큰인지)은 제공하는 업무의 계획서가 정하고, 쓰는 업무의 `workflow-plan`이 선행 계획서와 코드에서 읽는다.
  - 공통 결정에도 업무 규칙(누가 무엇을 할 수 있는지, 범위, 수량·기간 기준)만 쓴다. 기술 방식은 사용자가 요구사항에 적은 것만 옮긴다.
  - 한 업무 안에서 끝나는 업무 규칙(잠금 횟수, 화면 문구 등)은 묻지 않고 그 업무 파일의 `정하지 않은 것`에 남긴다.
  - 사용자가 요구사항에 기술 스택이나 규칙을 이미 적었으면 `공통 결정`에 옮긴다. 새로 정하지는 않는다.
- 받은 답은 README `4. 결정 사항`에 기록한다. 사용자가 대화로 직접 준 지시·정정과 인자로 준 수정 지시도 `roadmap · 대화 지시`로 남긴다. 형식은 README의 `결정 · 이력 기록 규칙`을 따른다. `단계` 값: `roadmap`, `roadmap · 기준 브랜치`, `roadmap · 분할`, `roadmap · 브랜치`, `roadmap · 수정`, `roadmap · 미결 확정`, `roadmap · 커밋`, `roadmap · 대화 지시`
  - `일시`는 답을 받은 시점이다. 답을 받으면 바로 시각을 조회해 둔다. (Bash `date '+%Y-%m-%d %H:%M:%S'` / PowerShell `Get-Date -Format 'yyyy-MM-dd HH:mm:ss'`. 다음 명령에 붙여 조회해도 된다) 파일이 생기기 전에 받은 답은 기억해 두었다가 작성할 때 기록한다.
- **로드맵 파일(README, 업무 파일)만 만들고 고친다.** 작업계획서·usecase 계획서·소스는 고치지 않는다.
- 업무 `상태`와 `계획서` 칸은 `workflow-plan`(진행)·`workflow-do`·`workflow-usecase-do`(완료)가 README의 `로드맵 관리 규칙`대로 바꾼다. 이 커맨드는 현황 모드에서 계획서와 어긋난 상태를 바로잡을 때와, 수정 모드에서 업무를 취소·병합할 때만 바꾼다.
- 커밋은 README 상단 표의 `커밋 방식`을 따르고, push는 하지 않는다. (아래 `커밋`)

## 업무 나누기 기준

- **크기**: 업무 하나가 작업계획서 하나에 들어가야 한다. Phase 2~4개, 작업항목 대략 15개 이하(`코드 정리 및 리뷰` Phase 제외)가 기준이다. 넘을 것 같으면 나눈다.
- **기능 단위로 나눈다.** 업무마다 따로 완료하고 검증(테스트, usecase)할 수 있어야 한다. 계층별(DB 전부 → API 전부 → 화면 전부)로 나누지 않는다. 계층별로 나누면 마지막 업무가 끝날 때까지 검증할 수 있는 기능이 없다.
- **첫 업무는 뼈대다.** 프로젝트가 아직 없거나, 여러 업무가 함께 쓰는 기반(빌드, DB 연결, 공통 오류 처리, 인증 기반)이 없으면 그것을 첫 업무로 둔다.
  - 그 업무의 요구 항목에 "프로젝트 공통 규칙(구조, 명명, 오류 응답 형식, 공통 컬럼 등)을 CLAUDE.md에 정리한다"를 넣는다. 뒤 업무의 `workflow-plan`은 CLAUDE.md의 규칙과 관례를 따라 설계한다.
- **만드는 업무를 쓰는 업무보다 앞에 둔다.** 다른 업무가 쓰는 테이블·API·세션 값·공통 컴포넌트를 만드는 업무는 그것을 쓰는 업무보다 앞 행에 두고, 쓰는 업무의 `선행`에 적는다. 그 내용은 `업무 간 약속`에 쓴다.
- **요구 항목은 빠짐없이 배정한다.** 요구사항(입력 문장, 요구사항 문서)의 모든 항목이 어느 업무에든 들어가거나, 결정을 거쳐 `제외`되어야 한다.
- **업무가 2개 미만이면 로드맵이 필요 없다.** AskUserQuestion으로 `workflow-plan으로 진행 — 로드맵을 만들지 않고 종료 (Recommended)` / `그래도 로드맵 작성`을 묻는다. 앞의 것을 고르면 `/workflow:workflow-plan <요구사항>`을 안내하고 파일을 만들지 않고 끝낸다.

## 처리 절차 — 생성

### 1. 컨텍스트 파악
- **기준 브랜치 확인 (둘러보기 전에)** — 로드맵 브랜치가 갈라져 나올 코드를 보고 업무를 나눈다.
  - git 저장소가 아니면 건너뛴다. (`git rev-parse --is-inside-work-tree`)
  - 현재 브랜치(`git branch --show-current`)와 미커밋 변경(`git status --short`)을 확인한다. 기본 브랜치는 `git symbolic-ref --short refs/remotes/origin/HEAD`(앞의 `origin/`을 뗀다)로 찾고, 없으면 로컬 브랜치 중 `main` → `master` → `develop` 순서로 처음 있는 것이다. 이 브랜치와 `develop`(있으면)을 기본 브랜치로 본다. (`workflow-plan` 1단계와 같은 기준. 4단계 질문과 아래 `커밋`의 기본 브랜치도 이것이다)
  - 현재 브랜치가 기본 브랜치이거나 detached HEAD이거나, 기본 브랜치와 같은 커밋을 가리키고 미커밋 변경이 없으면 묻지 않고 진행한다.
  - 그 밖이면 `현재 브랜치 기준` / `기본 브랜치(<이름>) 기준`을 묻는다. 현재 브랜치에 기본 브랜치에 합쳐지지 않은 커밋(`git log --oneline <기본 브랜치>..HEAD`)이 있고 요구사항이 그 작업을 이어 가는 것으로 보이면 `현재 브랜치 기준`을, 아니면 `기본 브랜치 기준`을 추천하고, 추천하는 것을 첫 번째에 둔다.
  - 미커밋 변경이 있으면 질문 본문에 목록과 함께, 전환하거나 새 브랜치를 만들면 충돌이 없는 한 그 변경이 로드맵 브랜치로 따라온다고 적고 `중단 — 미커밋 변경을 먼저 커밋하거나 정리`를 더한다. 이때 `기본 브랜치 기준`을 추천할 상황이면(요구사항이 현재 작업과 무관하므로 따라오는 변경은 다른 작업의 것이다) `중단`을 첫 번째에 두고 추천한다. 순서는 `중단` → `기본 브랜치 기준` → `현재 브랜치 기준`이다. 그 밖이면 추천안 → 다른 기준 → `중단` 순서다.
  - 기본 브랜치를 고르면 `git switch <기본 브랜치>`로 전환한다. 실패하면 중단한다. 답은 `roadmap · 기준 브랜치`로 기록한다.
- **프로젝트 둘러보기** — 업무 경계를 정할 만큼만 본다. 자세한 탐색은 업무 계획서를 만들 때 한다.
  - 추적 중인 파일 수(`git ls-files | wc -l`), 최상위 디렉토리 구조, CLAUDE.md, README, 빌드 파일(`package.json`, `build.gradle` 등)을 본다.
  - 이미 있는 기능과 모듈을 파악한다. 요구사항 중 이미 있는 기능은 `이미 충족` 후보다. 후보마다 근거(path)와, 요구 항목 중 코드에서 찾지 못한 부분(예: API는 있는데 화면이 없다)을 적어 둔다. 2단계에서 확인받기 전에는 `이미 충족`으로 표시하지 않는다.
  - 구조를 모르는 큰 저장소(대략 파일 500개 이상)이면 Agent 도구를 `subagent_type: "Explore"`로 하나 실행해, 모듈 목록과 각 모듈의 역할·주요 진입점만 받는다. (`medium`) 그 밖에는 직접 본다.

### 2. 애매한 사항 확인 (AskUserQuestion)
- 여러 업무에 걸치는 것만 묻는다: 이번 범위에 넣을 것과 다음으로 미룰 것, 우선순위, 사용자 구분·권한 체계처럼 여러 업무가 따르는 업무 규칙, 요구사항 사이의 충돌.
- 한 업무 안에서 끝나는 것은 묻지 않고 그 업무 파일의 `정하지 않은 것`에 남긴다. (절대 규칙의 `설계하지 않는다`)
- **이미 충족 후보**도 여기서 확인받는다. 질문 본문에 요구 항목, 근거 path, 찾지 못한 부분을 적는다.
  - 찾지 못한 부분이 없으면: `이미 충족으로 표시 (Recommended)` / `업무에 배정`
  - 찾지 못한 부분이 있으면: `찾지 못한 부분만 업무에 배정 (Recommended)` / `이미 충족으로 표시` / `전부 업무에 배정`
- 답은 `roadmap`으로 기록한다. 여러 업무가 따르는 답은 `3. 공통 결정`에 결정 번호와 함께 쓴다.
- **답을 미루면 `(미결)`로 남긴다.** 사용자가 지금 정하지 않겠다고 답하면(직접 입력 등) 추측해서 채우지 않는다. 결정 사항 행의 `선택`에는 답 원문을, `비고`에는 `미결로 남김 — <위치>`를 쓴다. (결정 행에는 괄호 표시를 붙이지 않는다. 미결 표시는 아래 자리에만 둔다)
  - 그 사항이 들어갈 자리에 `(미결)`을 붙인다: 공통 결정 줄(따르는 업무 번호와 함께), 업무 간 약속 행의 `내용`, 그 사항에 기대는 업무 파일의 줄(`요구 항목`·`이 업무가 기대는 것` 등).
  - 범위(이번에 넣을지 미룰지)를 미뤘으면 그 항목도 맡을 업무에 배정하고, 그 업무 파일의 요구 항목 줄과 `### 요구사항 문서`의 배정 표시(있으면, 예: `— 04 (미결)`)에 붙인다. 업무에 배정돼야 그 업무의 `workflow-plan`이 미결을 찾아 로드맵에서 먼저 확정하라고 안내한다. 나중에 빼기로 하면 수정 모드가 그 업무를 취소하거나 항목을 `제외`로 바꾼다.
  - 미결은 수정 모드에서 묻는다. (`처리 절차 — 수정` 4번)

### 3. 업무 분할 확인 (AskUserQuestion)
- `업무 나누기 기준`대로 분할안을 만든다. 나누는 축이 실제로 갈리면(예: 기능별 / 사용자 유형별) 2개까지 만든다.
- 질문 하나로 고르게 한다. 각 선택지의 `preview`에 업무 목록(번호, 업무, 선행, 담을 요구 항목 요약)과 업무 간 약속을 넣는다. 추천안은 첫 번째에 두고 `(Recommended)`를 붙인다. 업무를 더하거나 빼는 등 다른 분할은 사용자가 "Other"로 입력한다.
  - 분할안이 하나뿐이면(AskUserQuestion은 선택지가 2개 이상이어야 한다) `<분할안> (Recommended)` / `업무를 더 크게 묶기` 또는 `업무를 더 잘게 나누기`(업무 나누기 기준의 크기에 더 가까운 쪽) 중 하나를 둔다. 두 번째를 고르면 그 방향으로 다시 만든 분할안을 보여 주고 확인받는다.
- 답은 `roadmap · 분할`로 기록한다. "Other"로 고쳐 달라고 하면 반영한 분할안을 다시 보여 주고 확인받는다.

### 4. 브랜치 · 커밋 방식 (AskUserQuestion)
- 로드맵을 2~5 단어 영문 소문자로 요약한 **summary**를 정한다. (예: `order service v1`) 브랜치명에는 kebab-case, 디렉토리 이름에는 snake_case로 쓴다.
- git 저장소가 아니면 `git init` 수행 여부를 묻는다. 거부하면 `작업 브랜치`·`커밋 방식`을 `해당 없음`으로 쓰고 5단계로 간다.
- 현재 브랜치, 미커밋 변경, 기존 브랜치 목록(`git branch -a`)을 확인하고, 브랜치명 후보 2~3개를 만든다. 기존 브랜치의 이름 관례가 있으면 따르고, 없으면 `feature/<summary-kebab-case>`를 쓴다. 이미 있는 이름은 뺀다. `브랜치 생성 안 함 (현재 브랜치 유지)`도 선택지에 넣는다.
  - 이 브랜치가 **로드맵 브랜치**다. 모든 업무 계획서가 이 브랜치에서 진행된다. 질문 본문에 이것을 적는다.
  - 현재 브랜치가 기본 브랜치인데 `생성 안 함`을 고르면 모든 업무가 기본 브랜치에 커밋되고, 커밋 방식이 `자동`이어도 모든 커맨드가 커밋 시점마다 묻는다. 질문 본문에 이것을 적고, 첫 번째 브랜치명 후보에 `(Recommended)`를 붙인다. 이때 `생성 안 함`을 고르면 완료 보고의 작업 브랜치 줄에도 커밋마다 묻게 된다는 것을 적는다.
  - 미커밋 변경이 있으면 질문 본문에 적는다. (새 브랜치로 따라온다) 따라온 파일은 완료 보고에도 적는다. 로드맵 커밋에는 넣지 않는다.
- **커밋 방식**은 묻지 않고 `자동`으로 쓴다. (작업 브랜치에서 정해진 시점에 묻지 않고 커밋하고, 작업 브랜치가 기본 브랜치일 때만 묻는다) 이 값은 로드맵 파일의 커밋뿐 아니라 업무 계획서가 그대로 이어받는다. 사용자가 인자나 대화로 `확인`(시점마다 묻기)이나 `끝에 한꺼번에`(각 커맨드가 끝날 때만 묻기)를 지시했으면 그 값을 쓰고 `roadmap · 대화 지시`로 남긴다.
- 고른 브랜치는 `git switch -c <branch>`로 만든다. `생성 안 함`이면 현재 브랜치명을 쓴다. 답은 `roadmap · 브랜치`로 기록한다.

### 5. 경로 · 시각
- 현재 시각을 조회한다. (Bash `date '+%y%m%d %Y-%m-%d %H:%M:%S'` / PowerShell `Get-Date -Format 'yyMMdd yyyy-MM-dd HH:mm:ss'`) README의 `작성일시`·`최종 갱신`과 `5. 작업 이력` 첫 행에 같은 값을 쓴다.
- 디렉토리: `ai-work/roadmaps/YYMMDD_<summary_snake_case>/` (프로젝트 루트 기준). 이미 있으면 끝에 `_2`, `_3`을 붙인다.
- 업무 파일: `NN_<업무 summary snake_case>.md` (예: `01_scaffold.md`, `02_login.md`). 업무 summary는 1~3 단어 영문 소문자다.

## 처리 절차 — 수정

1. **브랜치**: 현재 브랜치에서 고치고 커밋한다. 현재 브랜치가 README `작업 브랜치`와 다르면 묻지 않고 진행하되, 완료 보고와 `5. 작업 이력` 행에 현재 브랜치를 적는다. (로드맵 브랜치로 합칠 때 함께 들어간다)
2. **읽기**: README 전체와 지시에 걸린 업무 파일을 읽는다. 규칙 블록이 템플릿(`${CLAUDE_PLUGIN_ROOT}/templates/roadmap-template.md`)과 다르고 템플릿 줄이 빠지기만 했으면 묻지 않고 템플릿 블록으로 바꾸고 `5. 작업 이력`에 `변경 — 규칙 블록 갱신`을 남긴다.
3. **지시 해석**: 지시를 아래 중 하나 이상으로 나눈다. 해석이 둘 이상이면 묻는다.
   - 업무 추가 / 분할 / 병합 / 취소 / 순서·선행 변경
   - 업무 파일의 요구 항목·기대는 것·넘길 것·정하지 않은 것 수정
   - 공통 결정·업무 간 약속 수정, 범위(포함·제외) 변경
   - 작업 브랜치·커밋 방식 변경
4. **영향 확인** — 다음에 해당하면 AskUserQuestion으로 묻는다. 질문 본문에 걸리는 업무와 그 상태, 계획서 경로를 적는다. 답은 `roadmap · 수정`으로 기록한다.
   - 대상 업무가 `진행`·`완료`다: 분할·병합·취소는 하지 않는다(규칙 블록). 선택지는 `새 업무로 추가` / `업무 파일만 고치고 계획서에는 workflow-do로 반영` / `하지 않음`이다. 요구 항목을 고치거나 더하는 지시면 `업무 파일만 고치고…`를, 그 밖(새 기능을 붙이는 지시)이면 `새 업무로 추가`를 추천해 첫 번째에 둔다.
   - 업무 간 약속·공통 결정을 바꾸는데, 그것을 쓰거나 제공하는 업무가 `진행`·`완료`다: 바꾼 뒤 그 계획서마다 `/workflow:workflow-do @<계획서> 업무 파일 반영: <변경 요약>`으로 반영해야 한다는 것을 적고, `변경 (Recommended)` / `하지 않음`을 묻는다.
   - 한 업무의 요구 항목을 고치는데 그 내용을 다른 업무도 따라야 한다(예: 01에 넣는 CLAUDE.md 공통 규칙, 여러 업무가 쓰는 값의 규칙): 그 내용을 `3. 공통 결정`에도 쓰고(따르는 업무 번호와 함께), 따르는 업무 중 `진행`·`완료`인 것을 위 경우처럼 걸리는 업무로 본다. 질문 본문과 완료 보고의 반영 안내에 그 업무의 계획서도 넣는다.
   - 위 두 경우 모두, 따르거나 쓰거나 제공하는 업무의 업무 파일도 5번에서 함께 고친다. (`업무 파일 동기화`)
   - 선행을 바꿔 `진행`·`완료` 업무가 아직 `완료`가 아닌 업무를 선행으로 갖게 된다: 순서가 이미 어긋났다는 것을 적고 그대로 바꿀지 묻는다.
   - `(미결)`로 남은 사항이 있으면 이번에 함께 묻는다. 답은 `roadmap · 미결 확정`으로 기록하고, 본문의 `(미결)`을 확정 내용으로 바꾼다.
5. **고치기**: README의 `로드맵 관리 규칙`대로 번호·취소·병합·분할 표기를 하고, 새 업무 파일은 템플릿으로 만든다. 취소·병합한 업무 파일은 지우지 않는다. 업무 목록이 바뀌면 상단 표의 작업상태·전체진행률·최종 갱신을 다시 계산한다. `5. 작업 이력`에 구분 `변경`으로 바꾼 것을 한 행에 요약한다. (예: `업무 05 추가(정산 엑셀), 03 요구 항목 2건 수정 — 계획서 반영 필요`)
   - 새로 생긴 요구 항목도 `업무 나누기 기준`의 빠짐없이 배정하기를 지킨다.
   - **업무 파일 동기화**: `3. 공통 결정`·`업무 간 약속`을 더하거나 바꾸면, 그것을 따르거나 쓰는 업무 파일의 `이 업무가 기대는 것`과 제공하는 업무 파일의 `다른 업무에 넘길 것`을 같은 내용으로 고친다. (공통 결정은 `- 공통 결정: <내용> (로드맵 결정 #n)`으로 쓴다. n은 그 결정을 기록한 `4. 결정 사항` 행 번호다) 업무 상태와 관계없이 고친다. 업무 파일이 바뀌어야 현황 모드·`workflow-status`가 `진행`·`완료` 업무를 `반영 필요`로 잡는다. 그 업무 파일의 `정하지 않은 것`에 새 결정으로 정해진 줄이 있으면(예: 공통 결정 "비밀번호는 해시로만 저장"과 `정하지 않은 것`의 "비밀번호 저장 방법") 그 줄을 지우거나 남은 부분만 남긴다.
   - **취소·병합 뒷정리**: 업무를 취소하거나 병합하면 같은 수정에서 아래를 함께 고친다.
     - `3. 공통 결정` 줄 끝과 `업무 간 약속`의 `쓰는 업무`에서 그 번호를 뺀다. (병합이면 남는 업무 번호로 바꾼다) 다른 업무 파일의 `이 업무가 기대는 것`·`다른 업무에 넘길 것`에서도 그 번호를 빼거나 바꾼다. (위 `업무 파일 동기화`)
     - 따르는 업무가 하나도 남지 않는 공통 결정과, `쓰는 업무`가 하나도 남지 않는 약속은 줄을 지운다.
     - 단, 지울 약속에 사용자가 지정한 이름(`(사용자 지정, 결정 #n)`)이 있으면 바로 지우지 않는다. 약속 줄과 함께 지우면 그 이름이 결정 표에만 남아, 제공하는 업무의 계획서가 다른 이름을 정할 수 있다. 제공하는 업무가 `취소`가 아니고 그것을 여전히 만들면(그 업무의 요구 항목이나 남는 약속에 들어 있다) AskUserQuestion으로 이름을 어디에 남길지 묻는다. 선택지: `<남는 약속 행>에 이름을 옮김`(같은 업무가 제공하고 같은 것을 가리키는 약속 행이 남을 때만 넣는다. 예: 승인 상태 값을 04는 안 쓰게 됐지만 05가 쓴다) / `제공하는 업무 파일의 요구 항목에 이름을 남김` / `약속과 함께 지움`. 앞에서부터 처음 해당하는 것을 추천해 첫 번째에 둔다. 제공하는 업무가 그것을 더는 만들지 않으면 묻지 않고 지운다. 옮기거나 남긴 이름에는 `(사용자 지정, 결정 #n)`을 그대로 붙이고(업무 파일에는 `(사용자 지정, 로드맵 결정 #n)`), 약속 행으로 옮겼으면 `업무 파일 동기화`도 한다. (`roadmap · 수정`)
     - 따르는 업무가 하나만 남는 공통 결정은 "여러 업무가 따르는 결정만"이라는 기준에 맞지 않는다. 남는 업무에 아직 필요한지 AskUserQuestion으로 묻는다. 선택지: `그 업무 파일 요구 항목으로 옮김` / `지움 (취소된 업무에만 필요했음)` / `공통 결정에 그대로 둠`. 남는 업무의 요구 항목이 그 결정에 기대면 앞의 것을, 아니면 두 번째를 추천해 첫 번째에 둔다. 지우면 남는 업무 파일에서 그 결정에서 온 요구 항목도 같은 질문에서 뺄지 함께 묻는다. (`roadmap · 수정`)
     - 약속의 `제공`이 취소된 업무면 그 행을 쓰는 업무가 남았는지 확인한다. 남았으면 다른 업무가 제공할지, 쓰는 업무도 바꿀지 AskUserQuestion으로 묻는다. (`roadmap · 수정`)
     - 취소한 업무가 맡은 요구 항목은 범위에서 빠진 것이다. `### 요구사항 문서`가 있으면 그 항목을 `— 제외 — <사유> (결정 #n)`으로 바꾸고, 없으면 `1. 요구사항` 요약에서 그 줄 끝에 `— 제외 — <사유> (결정 #n)`을 붙인다. (병합이면 남는 업무 번호로 바꾼다)
     - 사유는 지시에 있으면 그대로, 없으면 `사용자 지시`로 쓴다.
   - **결정 번호**: 인자나 대화로 받은 지시로 바꾼 곳은 그 지시를 기록한 `roadmap · 대화 지시` 행 번호를 `(결정 #n)`으로 쓴다. 업무 파일에 쓸 때는 `(로드맵 결정 #n)`이다. (`작성 지침`의 `업무 파일`) 이번 수정에서 고치는 업무 파일에 옛 표기 `(결정 #n)`이 남아 있으면(이전 버전으로 만든 로드맵) 같은 수정에서 모두 `(로드맵 결정 #n)`으로 바꾼다. 업무 파일 안의 결정 번호는 모두 로드맵 번호다. 한 파일에 두 표기가 섞이지 않게 한다. 이번 수정에서 고치지 않는 업무 파일은 표기만 바꾸려고 건드리지 않는다. (건드리면 `진행`·`완료` 업무가 `반영 필요`로 잡힌다)
6. **커밋**: 아래 `커밋`대로 한다.

## 처리 절차 — 현황

1. README를 읽는다. 작업 트리에 없으면 입력의 방법으로 찾는다.
2. **업무마다 계획서 상태를 확인한다.**
   - `계획서` 칸에 경로가 있으면 그 계획서의 작업상태를 읽는다. 작업 트리에 있으면 Bash 도구로 `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-progress.sh" "<계획서 경로>"`를 실행해 실제 개수로 정한 작업상태·전체진행률을 쓴다. 없으면 로컬 브랜치에서 `git grep -n -e '^| 작업상태 |' -e '^| 전체진행률 |' <브랜치...> -- <계획서 경로>`로 적힌 값을 읽고 `(적힌 값)`을 붙인다.
   - `계획서` 칸이 비었는데 `대기`가 아니거나, `대기`인데 그 업무 파일로 만든 계획서가 있을 수 있다. 계획서 `### 요구사항 문서`에 업무 파일 경로가 적힌 계획서를 `git grep --untracked -l -F '<업무 파일 경로>' -- 'ai-work/plans/**.md'`로 찾는다. (`--untracked`는 `--` 앞에 둔다. 뒤에 두면 경로로 읽혀 미추적 계획서를 조용히 놓친다)
   - 찾은 계획서마다 `git status --short -- <계획서 경로>`로 커밋 여부를 확인해 둔다. (`??` 미추적, ` M` 등 미커밋 변경)
   - **반영 필요**: `진행`·`완료` 업무는 계획서 `### 요구사항 문서` 제목 아래의 `커밋 <해시>`(계획서를 만들 때 읽은 업무 파일 커밋)를 읽고, `git log --oneline <해시>..HEAD -- <업무 파일 경로>`가 비어 있지 않으면 계획서를 만든 뒤 업무 파일이 바뀐 것이다. 그 업무를 `반영 필요`로 표시한다. 커밋 표기가 없거나 업무 파일에 미커밋 변경이 있으면 판정하지 않고 `반영 확인 못 함`으로 적는다.
3. **어긋난 곳을 바로잡는다.** README `상태`·`계획서` 칸이 2번 결과와 다르면 `로드맵 관리 규칙`대로 고친다.
   - 상태 대응: 계획서 작업상태 `대기`·`진행`은 README `진행`, `완료`는 README `완료`다. (계획서를 막 만든 업무는 계획서가 `대기`여도 README는 `진행`이 맞다) 계획서가 없으면 `대기`다.
   - 커밋된 계획서끼리 어긋난 것은 답이 하나뿐이므로 묻지 않는다.
   - 찾은 계획서가 미추적이거나 미커밋 변경이 있으면 묻지 않고 바로잡지 않는다. AskUserQuestion으로 묻는다. 질문 본문에 계획서 경로, 커밋 상태, 제목·작업상태, `### 요구사항 문서`의 항목이 업무 파일 `## 요구 항목`과 같은지를 적는다. 선택지: `README에 연결 (계획서는 이 커맨드에서 커밋하지 않음)` / `연결하지 않음`. 요구 항목이 같으면 앞의 것을, 다르면 뒤의 것을 추천해 첫 번째에 둔다. (결정 번호 표기 `(결정 #n)`·`(로드맵 결정 #n)`의 차이와 계획서 쪽 반영 표시(`— 반영` 등)는 빼고 비교한다) 답은 `roadmap · 수정`으로 기록한다. 연결했으면 완료 보고에 계획서가 커밋되지 않았다는 것을 적는다.
   - 바꾼 업무마다 `5. 작업 이력`에 구분 `업무 진행` 또는 `업무 완료`로 `<번호> 완료 — <계획서 경로> (상태 바로잡음)`처럼 남긴다. (`로드맵 관리 규칙`의 상태 변경 기록) 그리고 아래 `커밋`대로 커밋한다. 고칠 곳이 없으면 파일을 고치지 않는다.
   - `반영 필요`는 README를 고치지 않는다. (계획서를 고쳐야 풀린다)
   - 같은 업무 파일로 만든 계획서가 둘 이상이면 고치지 않고 알린다. (`workflow-plan`에서 `새 계획서 작성`을 고른 경우 `계획서` 칸의 것이 기준이다)
4. **다음 커맨드를 정한다.** 위에서부터 처음 해당하는 것 하나다.
   - `반영 필요` 업무가 있다: 행 순서로 첫 업무의 `/workflow:workflow-do @<계획서> 업무 파일 반영: <요약>`. (`git diff <해시> -- <업무 파일>`로 바뀐 내용을 한 줄로 요약한다. `업무 파일 반영:`은 고정 문구다. `workflow-do`가 이 문구로 업무 파일 반영 지시를 알아본다. 요약은 사용자가 읽을 안내이고, `workflow-do`는 같은 diff를 직접 다시 읽어 요약에 없는 변경까지 맞춰 본다) 그 업무의 `선행`에 `완료`가 아닌 업무가 있으면 커맨드 뒤에 `(반영까지만 — 구현은 선행 <번호> 다음)`을 붙인다. `workflow-do`는 반영을 마친 뒤 구현 전에 선행을 확인해 묻는다.
   - `진행` 업무 중 `선행`이 모두 `완료`인 것(`선행`이 `-`인 것 포함)이 있다: 표의 행 순서로 첫 업무의 계획서의 다음 커맨드. (`진행` 업무가 여럿일 수 있다. 선행이 끝나기 전에 계획서만 먼저 쓴 업무를 고르면 선행보다 먼저 구현하게 된다) 작업항목이 남았으면 `/workflow:workflow-do @<계획서>`다. 작업항목은 끝났는데 완료 기준이 남았으면, 남은 기준이 `(확인: usecase)`이면 `/workflow:workflow-usecase-plan @<계획서>`(그 계획서의 usecase 문서가 이미 있으면 `/workflow:workflow-usecase-do @<usecase>`), 아니면 `/workflow:workflow-do @<계획서>`다.
     - 그 계획서의 작업상태가 `대기`이고 Phase 3개 이상 또는 작업항목 10개 이상이며 리뷰 이력(`8. 작업 이력`의 `리뷰` 행)이 없으면, 커맨드 앞에 `/workflow:workflow-plan-review @<계획서> 권장 →`을 붙인다. (`workflow-status`와 같은 기준이다. 같은 상태에서 두 커맨드가 다른 안내를 내지 않게 한다)
   - `대기` 업무 중 `선행`이 모두 `완료`인 것이 있다: 표의 행 순서로 첫 업무의 `/workflow:workflow-plan @<업무 파일 경로>`
   - `진행`·`대기` 업무가 남았는데 모두 선행이 끝나지 않았다: 막고 있는 선행 업무를 알린다.
   - 모두 `완료`·`취소`다: 없음 (완료)
5. 출력한다.

```markdown
로드맵: `ai-work/roadmaps/261123_order_service_v1/README.md` 주문 관리 서비스 1차
작업 브랜치: `feature/order-service-v1` (현재) · 진행 40% (2/5)

| # | 업무 | 선행 | 상태 | 계획서 진행률 |
|---|------|------|------|---------------|
| 01 | 프로젝트 생성·스캐폴드 | - | 완료 | 100% |
| 02 | 로그인 | 01 | 진행 | 60% (6/10) |
| 03 | 회원 관리 | 02 | 대기 | - |

다음: `/workflow:workflow-do @ai-work/plans/261125/091500_login.md`
```

- `반영 필요`·`반영 확인 못 함` 업무는 `상태` 칸 값 뒤에 붙여 쓰고(예: `완료 · 반영 필요`), 표 아래에 바뀐 업무 파일 커밋(`git log --oneline <해시>..HEAD -- <업무 파일>`)을 적는다.
- `(미결)`이 남아 있으면 표 아래에 건수와 위치를 적고, `/workflow:workflow-roadmap @<README> 미결 확정`으로 정할 수 있다고 안내한다.

## 작성 지침

- **상단 표**: `작업 브랜치`·`커밋 방식`은 생성 4단계 결과다. git 저장소가 아니면 둘 다 `해당 없음`이다.
- **규칙 블록**(`로드맵 관리 규칙`, `결정 · 이력 기록 규칙`)은 빼거나 줄이지 않고 템플릿 그대로 넣는다. `workflow-plan`·`workflow-do`·`workflow-usecase-do`가 이 블록대로 업무 상태를 갱신한다.
- **요구사항 원문**: `1. 요구사항`의 인용 블록에는 입력 문장을 `@경로`까지 고치지 않고 그대로 넣는다.
- **요구사항 문서**: `@경로`로 읽은 문서가 있으면 템플릿 주석을 풀어 채운다. 없으면 주석째 지운다.
  - 제목 아래에 경로와 읽은 시점, git이 추적하는 파일이면 `git log -1 --format=%h -- <경로>`의 커밋을 적는다.
  - 문서의 요구 항목을 번호·순서대로 옮긴다. 숫자·기한·조건과 주체는 바꾸지 않는다. 배경·설명 문단은 옮기지 않는다.
  - 항목마다 맡은 업무 번호(`— 01, 02`)를 붙인다. 맡은 업무가 없으면 `— 제외 — <이유> (결정 #n)` 또는 `— 이미 충족 (<근거 path>, 결정 #n)`이다. 일부만 충족해 나머지를 업무에 배정했으면 `— 03 (일부 이미 충족: <근거 path>, 결정 #n)`이다. `이미 충족`은 2단계에서 확인받은 것만 쓴다.
- **업무 목록**: 진행할 순서대로 행을 둔다. `파일`은 README 기준 상대 경로(파일 이름), `선행`은 업무 번호(여럿이면 `01, 02`, 없으면 `-`)다.
- **공통 결정**: 여러 업무가 따르는 결정만 쓴다. 줄 끝에 결정 번호와 따르는 업무를 쓴다. 없으면 `없음`.
- **업무 간 약속**: 한 업무가 만들고 다른 업무가 쓰는 것만 쓴다. 내용은 제공하는 것이고, 이름은 코드에 이미 있는 것과 사용자가 지정한 것(`(사용자 지정, 결정 #n)`)만 쓴다. (절대 규칙의 `설계하지 않는다`) 없으면 표 대신 `없음`.
- **업무 파일**
  - 제목은 `# <번호> <업무 이름>`이고, 상단 표 `로드맵`에는 README의 프로젝트 루트 기준 경로를 쓴다.
  - **결정 번호**: 업무 파일 안에서는 README `4. 결정 사항`의 번호를 `(로드맵 결정 #n)`으로 쓴다. (README 안에서는 `(결정 #n)`이다) `workflow-plan`이 `요구 항목`을 계획서로 그대로 옮기는데, 계획서에는 자기 결정 표가 따로 있어 `(결정 #n)`으로 쓰면 계획서의 다른 결정을 가리키게 된다. README에서 `(결정 #n)`이 붙은 줄을 업무 파일로 옮길 때(일부 이미 충족, 사용자 지정 이름, 지시로 바꾼 곳)도 이렇게 바꿔 쓴다.
  - `요구 항목`: 그 업무가 맡은 요구 항목을 구체적으로 쓴다. 요구사항 문서에서 왔으면 원문 그대로 옮기고 `(문서 3)`처럼 출처를 붙인다. 입력 문장에서 왔으면 업무에 해당하는 부분을 뜻을 바꾸지 않고 나누어 쓴다.
    - 일부 이미 충족한 항목은 원문 다음 줄에 `  - 이미 있음: <근거 path와 있는 부분> / 이 업무가 맡는 것: <찾지 못한 부분> (로드맵 결정 #n)`을 붙인다. 원문만 두면 `workflow-plan`이 이미 있는 부분까지 다시 계획한다.
  - `이 업무가 기대는 것`·`다른 업무에 넘길 것`: `업무 간 약속`과 같은 내용을 그 업무 쪽에서 쓴다. 없으면 `없음`.
  - `정하지 않은 것`: 2단계에서 업무 안의 일이라 묻지 않은 것. 없으면 `없음`.
- 템플릿의 `(예시)` 행과 `<!-- -->` 주석은 모두 지운다.
- 결정 사항이 없으면 표는 머리글만 두고, 표 아래에 `확인한 사항 없음` 한 줄을 쓴다.
- `5. 작업 이력` 첫 행: `로드맵 생성 (업무 N개, 업무 간 약속 N개)`

## 커밋

- git 저장소가 아니거나 README `커밋 방식`이 `해당 없음`이면 건너뛴다.
- `자동`: 묻지 않고 커밋한 뒤 `커밋 <해시> <제목>` 한 줄로 알린다. 커밋할 파일에 이 실행 전부터 미커밋 변경이 있었어도 묻지 않고 함께 커밋하고, 알리는 줄에 `(실행 전 변경 포함: <파일>)`을 붙인다. (알리는 줄은 모든 workflow 커맨드가 같은 형식이다. 커밋하지 못하면 `커밋 안 함 — <사유>`) 현재 브랜치가 기본 브랜치일 때만 그 사유를 적고 아래처럼 묻는다.
- `확인`·`끝에 한꺼번에`: AskUserQuestion으로 묻는다. 질문 본문에 커밋할 파일과 메시지 초안을 적는다. 선택지: `커밋 (Recommended)` / `커밋하지 않음`. 답은 `roadmap · 커밋`으로 기록한 뒤 커밋한다. (그 행도 같은 커밋에 들어간다)
- 이번 실행에서 만들거나 고친 로드맵 파일만 `git add -- <경로...>` 후 `git commit -- <경로...>`로 커밋한다. (`git add -A` 쓰지 않음)
- 메시지: 제목은 프로젝트 규칙(CLAUDE.md 등)의 커밋 형식이 있으면 그것을 따르고, 분류 자리에는 그 프로젝트가 문서 변경에 쓰는 값(정해진 값이 없으면 `docs`)을 쓴다. 없으면 `docs(roadmap): <로드맵 제목> 로드맵 작성` / `docs(roadmap): <로드맵 제목> 로드맵 수정 — <요약>` / `docs(roadmap): 업무 상태 바로잡음`으로 쓴다. 본문 끝 줄 `Roadmap: <README 경로>`는 프로젝트 형식이 있어도 붙인다. (프로젝트 규칙이 본문 형식을 막는 경우만 뺀다)
- 커밋이 실패하면(훅 실패 등) `--no-verify`로 우회하지 않고 원인을 알린다. 이번에 스테이징한 파일은 `git restore --staged -- <경로...>`로 스테이징을 되돌린다. (작업 트리는 그대로다) `자동`이고 현재 브랜치가 기본 브랜치가 아니면, 로드맵 파일에서 고칠 수 있는 문제(훅이 지적한 포맷 등)는 고쳐 한 번 다시 커밋하고, 다시 실패하면 커밋하지 않고 완료 보고에 원인과, 원인을 고친 뒤 직접 커밋하는 명령(`git add -- <파일...> && git commit -m "<제목>" -- <파일...>`)을 적는다. push는 하지 않는다.
