# workflow-usecase-plan

`workflow-plan`으로 생성한 작업계획서를 mention으로 받아, **Playwright MCP로 실행 가능한 usecase 계획서**를 생성한다.

## 입력

```
$ARGUMENTS
```

- mention(`@경로`) 또는 경로로 지정된 작업계획서를 기준으로 한다. `@`를 뗀 경로의 파일을 직접 읽는다. (자동 첨부에 기대지 않는다)
- 지정이 없으면 `ai-work/plans/` 하위 최신 계획서를 찾아 AskUserQuestion으로 대상이 맞는지 확인한다.
  - git 저장소이면 작업 트리와 함께 로컬·원격 브랜치(`git for-each-ref --format='%(refname:short)' refs/heads refs/remotes`)마다 `git ls-tree -r --name-only <ref> -- ai-work/plans`로도 찾는다. 처리 절차 1처럼 로컬 브랜치와 그 원격 추적 브랜치는 하나로 세고 `<원격>/HEAD`는 뺀다. 계획서는 작업 브랜치에만 커밋되므로, 다른 브랜치(main 등)에서 실행하면 작업 트리에 없는 경우가 많다. 다른 사람이 push한 작업 브랜치는 원격에만 있기도 하다.
  - 고른 계획서가 작업 트리에 없으면 그 선택지에 계획서가 있는 브랜치를 함께 적는다. (예: `<경로와 제목> — feature/xxx로 전환`) 이때 질문 본문에 미커밋 변경 목록(`git status --short`, 많으면 앞의 5개와 개수)을 적고, 전환하면 충돌이 없는 한 그 변경이 그 브랜치로 따라온다고 적는다. (이 선택이 전환 답을 겸하므로, 따로 하는 브랜치 질문의 안내를 여기서 한다)
    - 그 계획서가 한 브랜치에만 있으면, 이 선택지를 고른 것을 전환 답으로 보고 처리 절차 1의 `작업계획서가 작업 트리에 없을 때`의 브랜치 질문은 하지 않는다. 그 절의 전환 방법대로 전환한다. (같은 답을 두 번 묻지 않는다)
    - 여러 브랜치에 있으면 대상으로 정한 뒤 처리 절차 1의 `작업계획서가 작업 트리에 없을 때`로 이어 간다.
  - 하나도 없으면 `/workflow:workflow-plan`으로 계획서를 먼저 만들라고 알리고 중단한다.
- 경로 외 추가 텍스트는 usecase 작성 시 추가 요청사항으로 반영한다.

## 절대 규칙

- **애매한 사항은 직접 결정하지 않는다.** 다음과 같은 정보가 계획서/코드에서 확정되지 않으면 AskUserQuestion으로 확인한다.
  - 실행 환경 설정 파일(아래 `실행 환경 설정`)이 없거나 값이 빠졌을 때: web·api URL, 서버 기동 방법과 health URL, 공통 로그인 절차
  - 사용할 계정 역할(권한) 등 사전 조건
  - 테스트 데이터, 해상도, 포함할 시나리오 범위(정상/예외/권한)
  - 구현된 화면·API 소스가 계획서의 `화면 변경`·`API 변경` 정의와 다를 때 어느 쪽으로 쓸지 (처리 절차 2의 `소스가 정의와 다를 때`)
  - 계획서에 화면으로 검증할 항목이 없을 때 계속 진행할지 여부
  - AskUserQuestion을 쓸 수 없는 환경(비대화형 실행 등)이면 추측으로 진행하지 말고, 질문 목록을 출력한 뒤 중단한다.
- 이 커맨드에서 AskUserQuestion으로 받은 답은 질문·선택지·선택 결과를 **원본 작업계획서** `2. 결정 사항`에 한 행씩 추가한다. `단계`는 `usecase-plan`이다. 질문의 답이 아니라 사용자가 대화로 직접 준 지시·정정도 같은 표에 `usecase-plan · 대화 지시`로 남긴다. (형식은 계획서의 `결정 · 이력 기록 규칙`) `일시`는 답을 받은 시점이다. 기존 행은 고치거나 지우지 않는다.
  - 원본 계획서의 표가 예전 형식(결정 사항 3열, 작업 이력 2열 등)이면 형식을 올리지 말고, 그 표의 머리글에 맞춰 행을 쓴다. 형식 올리기는 `workflow-plan-review`나 `workflow-do`가 한다.
  - 원본 계획서에 결정 사항 표가 없으면 usecase 계획서 `5. 작업 이력`에 `결정: <질문> → <선택> (선택지: …)` 한 칸 형식으로 남긴다.
  - 사용자가 답으로 계정 아이디·비밀번호를 알려 주면 결정 사항의 `선택`에는 `(입력됨, 기록 안 함)`으로 쓴다. 그 값은 어느 문서에도 쓰지 않고, 완료 보고에서 `accounts.yaml`에 직접 넣으라고 안내한다.
- 계정 아이디·비밀번호는 usecase 문서와 공용 설정 파일 어디에도 쓰지 않는다. 문서에는 계정 역할(예: `admin`)과 자리표시자(`{account.id}`, `{account.password}`)만 쓴다. 이 커맨드는 `accounts.yaml`을 읽지 않는다.
  - 계정은 실행 전부터 그 환경에 있는 로그인 계정을 말한다. UC가 화면에서 스스로 만들고 쓰는 일회용 테스트 데이터(테스트 중에 등록하는 회원의 이메일·비밀번호 등)는 계정이 아니라 테스트 데이터다. 값을 지어 `1. 사전 조건`의 테스트 데이터에 적고 단계에 그대로 쓴다. (예: `uc-lock-01@example.com`) 실제 사람이 쓰는 값으로 보이는 것은 쓰지 않는다. 이런 데이터 때문에 계정 역할을 만들지 않는다.
- URL·포트·서버 기동 명령·로그인 절차는 usecase 문서에 다시 적지 않는다. 실행 환경 설정 파일에 한 번만 두고, 문서에는 환경 이름과 web 기준 경로(`/login`)만 쓴다.
- usecase의 각 단계는 Playwright MCP 도구로 **그대로 실행 가능한 수준**으로 구체적으로 쓴다. ("확인한다" 같은 모호한 표현 대신 무엇을, 어떤 값으로 확인하는지 명시)
- 이 커맨드는 **계획서 작성까지만** 수행한다. 브라우저를 실행하지 않는다. 커밋은 원본 작업계획서의 `커밋 방식`을 따르고(처리 절차 7), push는 하지 않는다.

## 실행 환경 설정

테스트 실행 환경은 프로젝트의 `ai-work/usecase-env/`에 둔다. usecase 문서를 만들 때마다 URL·계정을 다시 묻지 않기 위해서다.

| 파일 | git | 내용 | 누가 만드나 |
|------|-----|------|-------------|
| `environment.yaml` | 커밋 | 환경별 web·api URL, 서비스 기동 명령과 health URL, 공통 로그인 절차, 계정 역할(이름과 설명만) | 이 커맨드 (처음 한 번) |
| `environment.local.yaml` | 제외 | 개인 PC에서만 다른 값 (포트 등). 공용 파일과 같은 키로 쓴 값만 덮어쓴다 | 사용자 (필요할 때만) |
| `accounts.yaml` | 제외 | 환경·역할별 실제 아이디·비밀번호. **테스트 전용 계정만** 쓴다 | `workflow-usecase-do`가 뼈대를 만들고 사용자가 채움 |

- 병합 규칙: `environment.local.yaml`의 값이 같은 키의 공용 값을 덮어쓴다. 목록(`services`, `login.steps`)은 항목별로 합치지 않고 통째로 바꾼다.
- 같은 이름의 개인 파일을 쓰는 다른 플러그인과 섞이지 않도록 이 플러그인의 작업 폴더(`ai-work/`) 아래에 둔다.

### environment.yaml 형식
```yaml
# workflow-usecase-plan / workflow-usecase-do 가 쓰는 테스트 실행 환경 (공용, 커밋한다)
# 비밀값은 쓰지 않는다. 계정 실제 값은 accounts.yaml(커밋 금지)에 둔다.
# 개인 PC에서만 다른 값은 environment.local.yaml(커밋 금지)에 같은 키로 덮어쓴다.
default: local

environments:
  local:
    web: http://localhost:8080        # 화면 기준 URL. usecase의 navigate 경로는 이 URL 기준이다
    api: http://localhost:8080        # API 기준 URL (network 단계 확인용)
    services:                         # usecase의 "필요 서비스" 이름과 같아야 한다
      - name: app
        health: http://localhost:8080/actuator/health   # 전용 health URL이 없으면 200을 돌려주는 화면 URL을 쓴다 (예: http://localhost:8080/login). 생략하면 web URL로 확인한다
        start: ./gradlew bootRun      # 저장소 루트 기준. Claude가 띄우면 안 되는 서비스는 start를 생략한다
  # dev:                              # 공용 서버는 start 없이 health만 적는다
  #   web: https://dev.example.com
  #   api: https://dev.example.com
  #   services:
  #     - name: app
  #       health: https://dev.example.com/actuator/health

# 공통 로그인 절차. usecase의 login 단계가 이 절차를 그 역할의 계정으로 실행한다.
# 형식: "액션 | 대상 | 값 / 기대결과" (usecase 단계 표기와 같다)
# 로그인해야 볼 수 있는 화면이 없으면 enabled: false (로그인 화면이 없거나, 있어도 다른 화면이 로그인을 요구하지 않는 경우). 이때 steps는 생략해도 된다
# 접근 가능한 이름이 없는 입력은 'type | textbox css=input[name="email"] | {account.id}'처럼 쓴다
login:
  enabled: true
  steps:
    - 'navigate | /login | -'
    - 'type | textbox "아이디" | {account.id}'
    - 'type | textbox "비밀번호" | {account.password}'
    - 'click | button "로그인" | -'
    - 'wait | text "로그아웃" | 나타남'

# 계정 역할. 실제 값은 accounts.yaml에 같은 역할 키로 둔다.
accounts:
  admin: 관리자
  user: 일반 사용자
```

### 처음 만들기
`environment.yaml`이 없을 때만 한다.
1. 코드(설정 파일, README, `application.yml`, `package.json` 등)에서 web·api URL, 기동 명령, health URL, 로그인 화면 요소를 찾는다.
2. 찾지 못했거나 후보가 여럿인 값을 3단계 질문에 넣어 확인한다. 다음은 묻지 않고 정한다.
   - 전용 health 엔드포인트가 없으면 소스에서 확인한, 로그인 없이 200을 돌려주는 화면 URL(로그인 화면, 정적 첫 화면 등)을 `health`에 쓰고 주석에 `전용 health 없음`을 적는다. 그런 화면을 찾지 못했을 때만 묻는다.
   - `login.enabled`: 로그인해야 볼 수 있는 화면이 소스에 없으면(로그인 화면이 없거나, 있어도 세션·인증 검사가 없어 다른 화면이 로그인을 요구하지 않으면) `false`로 쓰고 주석에 근거(`path:line`)를 적는다. `steps`는 생략한다. 로그인 화면 자체는 UC에서 `navigate`·`type`·`click`으로 풀어 써서 검증한다.
3. 위 형식으로 `environment.yaml`을 만든다. 확인하지 못한 값은 `# TODO 확인 필요` 주석을 붙인다.
4. 두 개인 파일이 git에서 무시되는지 `git check-ignore -q ai-work/usecase-env/accounts.yaml`(`environment.local.yaml`도 같은 방법)로 확인한다. 무시되지 않으면(종료 코드 1) `ai-work/usecase-env/.gitignore`(이 커맨드 전용 무시 파일)에 아래 두 줄을 추가한다. (없으면 만든다) 저장소 루트의 `.gitignore`는 고치지 않는다. 루트 `.gitignore`는 사용자가 고쳐 둔 채인 경우가 많아, 섞이면 무시 줄을 커밋할 수 없기 때문이다. 이 전용 파일은 이번에 만들거나 줄을 더했거나, 이전 실행이 커밋하지 못하고 남긴 상태(미추적이거나 수정됨)이면 7단계 커밋에 넣는다. (7단계 스테이징)
   ```
   environment.local.yaml
   accounts.yaml
   ```
- 이미 있으면 URL·기동 방법·로그인 절차는 묻지 않는다. 이 usecase에 필요한 계정 역할이나 서비스가 `environment.yaml`에 없을 때만 3단계에서 확인하고 추가한다. (역할은 이름과 설명만 쓴다)

## 처리 절차

1. 대상 작업계획서를 읽고 요구사항, 작업항목, 완료 기준, 영향 범위(`API 변경`·`화면 변경` 정의 표가 있으면 포함)를 파악한다.
   - **작업 브랜치 확인** — 작업계획서의 `작업 브랜치`에서 실행되도록, 코드를 보거나 문서를 고치기 전에 먼저 한다.
     - **작업계획서가 작업 트리에 없을 때** — 아래 확인보다 먼저 본다. `workflow-plan`은 작업 브랜치에서 계획서를 만들고 커밋하므로, 다른 브랜치(main 등)에서 실행하면 흔히 생긴다.
       - git 저장소가 아니면 경로를 확인하라고 알리고 중단한다.
       - 로컬·원격 브랜치(`git for-each-ref --format='%(refname:short)' refs/heads refs/remotes`)마다 `git cat-file -e <브랜치>:<경로>`로 그 경로에 작업계획서가 있는 브랜치를 찾는다. 로컬 브랜치와 그 원격 추적 브랜치는 하나로 센다. `<원격>/HEAD`(short 이름이 `origin`처럼 원격 이름만 나오는 ref)는 다른 브랜치를 가리키는 별칭이라 뺀다. 어느 브랜치에도 없으면 경로를 확인하라고 알리고 중단한다.
       - 찾은 브랜치마다 사본의 상단 표 `작업 브랜치`를 `git show <브랜치>:<경로>`로 읽고, 어느 브랜치로 전환할지 AskUserQuestion으로 묻는다. 질문 본문에 작업계획서가 현재 브랜치에 없다는 것, 찾은 브랜치와 각 사본의 `작업 브랜치`, 미커밋 변경사항(`git status --short`) 유무를 적는다. 선택지는 `중단`을 포함해 4개까지다. (넘으면 최근 커밋 순으로 고른다)
         - `<브랜치>로 전환`: 찾은 브랜치마다 하나. 사본의 `작업 브랜치`가 그 브랜치와 같은 것에 `(Recommended)`를 붙인다. 그런 브랜치가 없고 찾은 브랜치가 하나면 그 브랜치에 붙인다. (작업 브랜치 이름을 바꾼 경우 등이다. 전환한 뒤 아래 `다르면` 질문으로 이어진다)
         - `중단`
       - 전환은 로컬에 있으면 `git switch <브랜치>`, 원격에만 있으면 `git switch --track <원격>/<브랜치>`로 한다. 실패하면 아래 `전환이 실패하면`대로 한다. 전환한 뒤 작업 트리의 작업계획서를 읽고 아래 확인을 이어 간다. 답은 `usecase-plan · 브랜치`로 기록한다.
     - git 저장소가 아니거나 `작업 브랜치`가 `해당 없음`으로 시작하면(`해당 없음 (detached HEAD)` 포함) 건너뛴다.
     - 현재 브랜치(`git branch --show-current`)가 `작업 브랜치`와 같으면 그대로 진행한다. 출력이 비어 있으면(detached HEAD) 다른 것으로 본다.
     - 다르면 AskUserQuestion으로 묻는다. 질문 본문에 현재 브랜치, 작업 브랜치, 미커밋 변경사항(`git status --short`) 유무를 적는다. 선택지:
       - `작업 브랜치로 전환 (Recommended)`: 로컬에 있으면 `git switch <작업 브랜치>`, 원격에만 있으면 `git switch --track <원격>/<작업 브랜치>`. 어디에도 없으면 이 선택지를 `현재 위치에서 작업 브랜치를 새로 만들어 전환`(`git switch -c <작업 브랜치>`)으로 바꾸고 추천을 붙이지 않는다. 대신 `중단`을 추천한다. (작업 브랜치 이름을 바꿨거나 브랜치를 지운 경우다. 계획서의 작업 브랜치를 지금 브랜치로 고치는 일은 이 커맨드가 하지 않는다)
       - `중단`
       - 작업 브랜치 자체를 바꾸려면 `workflow-do`나 `workflow-plan-review`에서 한다고 안내한다. (두 커맨드는 이 경우 `현재 브랜치에서 진행`을 추천한다)
     - 전환이 실패하면(미커밋 변경 충돌 등) stash나 강제 전환을 하지 않는다. 실패 내용을 알리고 중단한다.
     - 전환했으면 작업계획서를 다시 읽는다. (브랜치마다 내용이 다를 수 있다)
     - 답은 작업계획서 `2. 결정 사항`에 `usecase-plan · 브랜치`로 기록한다.
   - **실행 전 미커밋 변경 확인** — git 저장소이면 브랜치 확인 직후, 이 커맨드가 파일을 고치기 전에 7단계의 `git status --short` 확인을 해 두고 결과를 적어 둔다. (7단계 커밋에서 쓴다)
   - 취소선 줄(취소·병합된 항목)은 검증 대상이 아니다. 매핑에 취소된 ID를 쓰지 않고, 병합된 항목은 남은 ID로 매핑한다.
   - `(미결)`이 붙은 항목은 여기서 확정하지 않는다. (계획서 본문을 고치는 일은 `workflow-do`·`workflow-plan-review`가 한다) 미결인 내용(표시할지 여부, 문구 등)은 대상이나 기대결과를 지어 UC로 쓰지 않는다. 그 항목에 이미 확정된 부분이 있으면 그 부분만 UC로 쓰고, 없으면 UC를 만들지 않는다. 어느 쪽이든 그 항목 ID는 매핑에 넣지 않고 완료 보고에 알린다. (확정된 뒤 이 커맨드를 다시 실행해 기존 문서 갱신으로 UC를 더한다. 지어 쓴 UC는 실행할 때마다 멈추고 문서가 `완료`가 되지 못한다)
   - `ai-work/usecase-env/environment.yaml`을 읽는다. (`environment.local.yaml`·`accounts.yaml`은 읽지 않는다) 없으면 `실행 환경 설정`의 `처음 만들기`를 따른다. 있으면 어느 환경으로 쓸지(`default` 값이 기본) 정하고, 환경이 여러 개면 3단계에서 확인한다.
   - `ai-work/usecases`에서 `원본 작업계획서`가 이 계획서인 usecase 계획서가 이미 있는지 찾는다. 있으면 새로 쓸지 기존 문서를 갱신할지 **먼저** 묻는다. (다른 질문은 이 답에 따라 달라지므로 같은 묶음에 넣지 않는다. 아래 `기존 문서 갱신` 참고) 답은 `usecase-plan`으로 기록한다.
     - 그런 문서가 여럿이면 `작성일시`가 가장 늦은 문서를 갱신 대상으로 하고, 질문 본문에 나머지 문서 경로를 적는다.
     - 선택지: `기존 문서 갱신 (Recommended)` / `새로 작성`. 기존 문서가 예전 형식이거나, 실행 이력이 있는데(`4. 실행 결과`에 행이 있음) 기존 단계를 지우거나 순서를 바꿔야 하면 `새로 작성`에 `(Recommended)`를 붙인다.
     - `새로 작성`을 골라도 기존 문서는 지우거나 고치지 않는다. 새 문서 `5. 작업 이력` 첫 행에 `이전 문서: <경로>`를 덧붙이고 완료 보고에 알린다.
     - 커맨드 인자로 받은 추가 요청 시나리오는 기존 UC와 대조한다. 이미 같은 것을 확인하는 단계가 있으면 그 UC·단계를 질문 본문에 적고 `별도 UC로 추가` / `추가하지 않음`을 묻는다. (말없이 같은 검증을 두 번 넣지 않는다)
2. 관련 화면 소스(라우트, 템플릿/컴포넌트, 폼 필드, 버튼 라벨, API 엔드포인트)를 탐색하여 실제 URL 경로와 화면 요소(라벨/텍스트/role)를 확인한다.
   - 아직 구현되지 않은 화면은 계획서 내용을 기준으로 쓰되 대상 칸에 `(가정)`을 붙인다. 작업계획서에 `화면 변경` 표가 있으면 경로, 요소(`role "이름"`), 문구, 이동 경로를 그 표에서 그대로 가져온다. (추측해서 이름을 짓지 않는다)
   - 화면이 구현돼 있으면 소스에서 확인한 이름을 쓰고 `(가정)`을 붙이지 않는다.
   - `network` 단계의 엔드포인트와 기대 응답은 작업계획서의 `API 변경` 표를 기준으로 쓴다.
   - **소스가 정의와 다를 때** — 구현된 화면·API 소스가 작업계획서의 `화면 변경`·`API 변경` 표와 다르면(요소 이름, 문구, 경로, 응답 코드 등) 어느 쪽으로 쓸지 직접 정하지 않고 3단계에서 묻는다. 소스대로 쓰면 구현 버그가 기대결과가 되어, 실행하면 통과로 굳기 때문이다.
     - 질문 본문에 다른 곳마다 정의 표의 값과 소스의 값(`path:line`)을 적는다. 다른 곳이 여럿이면 한 질문에 모은다. (곳마다 다르게 하려는 답은 직접 입력으로 받는다) 선택지:
       - `정의대로 쓴다 (Recommended)`: 대상·기대결과를 정의 표대로 쓴다. 구현된 화면이므로 `(가정)`은 붙이지 않는다. 구현이 그대로면 `workflow-usecase-do`에서 그 단계가 실패로 드러난다.
       - `소스대로 쓴다`: 정의 표가 낡은 경우다. 소스에서 확인한 값으로 쓴다. 계획서는 이 커맨드가 고치지 않으므로, 완료 보고에 `workflow-do`나 `workflow-plan-review`로 정의 표를 고치라고 안내한다.
     - 어느 쪽이든 usecase 계획서 `5. 작업 이력`에 `정의와 다른 곳: <단계 ID> <정의 값> ↔ <소스 값> — 정의대로(또는 소스대로) (결정 #n)`를 한 행 남기고 완료 보고에 적는다. (계획서의 정의 표는 고치지 않는다)
   - `화면 변경` 표의 메시지·상태·권한별 노출 행은 예외·권한 시나리오 UC의 근거가 된다. 표에 있는 오류 문구와 권한별 노출은 UC로 다루거나, 다루지 않으면 완료 보고에 적는다.
   - 먼저 Glob/Grep 몇 번으로 범위를 가늠한다. 검증할 화면이 여러 개이거나(대략 3개 이상) 화면 소스와 API 소스가 다른 모듈에 있으면 Explore agent로 나누어 탐색하고, 아니면 직접 탐색한다. (범위가 작으면 agent를 띄우는 쪽이 오히려 느리다)
   - Agent 도구를 `subagent_type: "Explore"`로 **2~3개**, 서로 겹치지 않게(예: 화면별, 또는 화면 / API) 나누어 **한 메시지에서 동시에** 실행한다. 프롬프트에 탐색 폭(`medium` 또는 `very thorough`)을 적는다.
   - 각 agent 프롬프트에는 다음을 넣는다.
     - 맡은 화면과 관련 작업항목 (다른 화면은 보지 않도록 명시)
     - 요청: URL 경로, 폼 필드·버튼의 라벨/텍스트/role, 호출하는 API 엔드포인트와 메서드를 `path:line`과 함께 보고
     - 소스에서 확인하지 못한 요소는 "미확인"으로 표시
   - agent는 AskUserQuestion을 쓸 수 없으므로 애매한 점은 결과로 받아 3단계에서 묻는다.
   - usecase 단계의 대상으로 쓸 라벨/텍스트는 해당 소스를 직접 열어 확인한다. 확인하지 못한 요소에는 `(가정)`을 붙인다.
   - Agent 도구를 쓸 수 없는 환경이면 직접 탐색한다.
3. 애매한 사항을 AskUserQuestion으로 확인한다. 답을 받을 때마다(AskUserQuestion 한 번마다) 현재 시각을 조회해 두었다가 결정 사항 행의 `일시`에 쓴다. (Bash: `date '+%Y-%m-%d %H:%M:%S'` / PowerShell: `Get-Date -Format 'yyyy-MM-dd HH:mm:ss'`)
4. 파일 경로 결정
   - 기존 문서를 갱신하기로 했으면 이 단계와 5단계를 건너뛰고 `기존 문서 갱신`을 따른다.
   - 현재 시각을 조회해서 파일 경로, 문서의 `작성일시`·`최종 갱신`, `5. 작업 이력`의 첫 행에 같은 값을 쓴다.
     - Bash: `date '+%y%m%d %H%M%S %Y-%m-%d %H:%M:%S'`
     - PowerShell: `Get-Date -Format 'yyMMdd HHmmss yyyy-MM-dd HH:mm:ss'`
   - 경로: `ai-work/usecases/YYMMDD/HHMISS_[summary_snake_case].md` (프로젝트 루트 기준. summary는 원본 계획서 파일명의 summary를 우선 재사용)
   - 디렉토리가 없으면 생성한다.
5. 아래 규칙과 템플릿으로 usecase 계획서를 작성한다. 생성 시점에는 모든 단계가 `[ ]`이다. 작성한 뒤 `진행 표시 확인`을 한 번 실행해 전체 단계 수(`N`)와 진행 표시가 맞는지 확인한다.
6. 원본 작업계획서를 갱신한다.
   - `8. 작업 이력` 표가 있으면 구분 `usecase`로 usecase 계획서 생성(또는 갱신) 이력과 경로를 한 행 추가한다.
   - `8. 작업 이력` 표가 있든 없든, 원본 작업계획서의 `진행 관리 규칙`에 1.5.0 전 커밋 예외 줄(``> - `자동`이어도 다음 경우에는 커밋 전에 묻는다:``로 시작하는 줄)이 있으면, 그 줄만 템플릿(`${CLAUDE_PLUGIN_ROOT}/templates/plan-template.md`)의 같은 자리 줄(``> - `자동`은 작업 브랜치에서``로 시작하는 줄)로 바꾸고 `8. 작업 이력`에 구분 `계획 변경`으로 `규칙 블록의 커밋 예외 줄 갱신 (1.5.0 — 작업 브랜치에서는 예외도 묻지 않음)`을 남긴다. 7단계 커밋은 새 줄대로 하므로, 계획서에 남은 예전 줄과 동작이 어긋나지 않게 한다. `8. 작업 이력` 표가 없으면 이력 대신 완료 보고에 적는다. 규칙 블록의 다른 줄은 고치지 않는다. (블록 전체 갱신은 `workflow-do`·`workflow-plan-review`가 한다)
7. 커밋한다. git 저장소가 아니거나 원본 작업계획서의 `커밋 방식`이 `해당 없음`이면 건너뛴다. 이 단계의 기본 브랜치는 `git symbolic-ref --short refs/remotes/origin/HEAD`(앞의 `origin/`을 뗀다)가 가리키는 브랜치(없으면 로컬 브랜치 중 `main` → `master` → `develop` 순서로 처음 있는 것)와, 있으면 `develop`이다. (`workflow-plan` 1단계와 같은 기준)
   - 커밋할 수 있는 파일에 이 커맨드 실행 전부터 미커밋 변경이 있었는지는 1단계 브랜치 확인 직후에 해 둔 `git status --short -- <원본 작업계획서> ai-work/usecase-env/environment.yaml ai-work/usecase-env/.gitignore` 결과로 본다. (1단계의 `실행 전 미커밋 변경 확인`. 같은 원본의 기존 usecase 계획서가 있으면 그 파일도 넣는다. 이 커맨드가 고친 파일은 파일 단위로 스테이징되므로, 사용자가 고쳐 둔 내용도 함께 들어간다)
     - 이 결과에서 git이 추적하지 않거나 새로 추가만 된(`??`·`A `) usecase 계획서, `environment.yaml`, 전용 무시 파일은 앞선 실행(이 커맨드나 `workflow-usecase-do`)이 만들고 커밋하지 못한 것이다. (이전 실행분. 커밋 훅 실패, 기본 브랜치에서 `커밋하지 않음` 등) 사용자 변경으로 보지 않고 이번에 만든 파일처럼 넣는다. 빼면 그 파일은 어느 커맨드도 다시 커밋하지 않아, 커밋된 usecase 계획서가 작업 트리에만 있는 설정에 기댄다.
     - 추적 중인 파일의 수정(`M`)만 실행 전 사용자 변경 후보다. 원본 작업계획서는 diff에 workflow 커맨드가 남긴 `8. 작업 이력` 행이 있으면 그 행들이 가리키는 변경을 이전 실행분으로 보고, 나머지가 있을 때만 사용자 변경으로 본다. (`workflow-do` 준비 2번과 같은 방법)
   - 원본 작업계획서 상단 표의 `커밋 방식`을 따른다. 값이 없거나 원본 계획서를 읽을 수 없으면 `확인`으로 본다.
     - `자동`: 묻지 않고 커밋한 뒤 `커밋 <해시> <제목>` 한 줄로 알린다. 스테이징할 파일에 실행 전부터 미커밋 변경이 있었어도 묻지 않고 아래 질문의 추천대로 처리한다. 추적 중인 `environment.yaml`의 사용자 변경이면 그 파일은 빼고 커밋하고, 그 밖의 파일(원본 작업계획서, 기존 usecase 계획서, `ai-work/usecase-env/.gitignore`)과 이전 실행분은 함께 커밋한다. 알리는 줄은 모든 workflow 커맨드가 같은 형식이다: `커밋 <해시> <제목>`에 해당하는 것을 `(제외: <파일>)`·`(실행 전 변경 포함: <파일>)`(사용자 변경)·`(이전 실행분 포함: <파일>)`로 붙인다. (커밋하지 못하면 `커밋 안 함 — <사유>`) 완료 보고에도 적는다. 작업 브랜치가 기본 브랜치일 때만 질문 본문 첫 줄에 그 사유(`작업 브랜치가 기본 브랜치(<이름>)라 커밋마다 확인합니다`)를 적고 아래 `확인`과 같은 질문·선택지·기록으로 묻는다.
     - `확인`·`끝에 한꺼번에`: AskUserQuestion으로 묻는다.
   - 질문: 선택지는 커밋 메시지 초안을 보여 주고 `커밋 (Recommended)` / `커밋하지 않음`
     - 스테이징할 파일에 실행 전부터 미커밋 변경이 있었으면 질문 본문에 그 파일과, 그 변경도 함께 커밋된다는 것을 적는다. (파일 단위로 스테이징하기 때문이다) 그 파일이 추적 중인 `environment.yaml`이고 사용자 변경이면 `environment.yaml은 빼고 커밋 (Recommended)`을 첫 번째에 둔다. 이전 실행분은 질문 본문에 이전 실행이 커밋하지 못하고 남긴 것이라고 적고 함께 넣는다. (이번에 고친 내용은 작업 트리에 남아 그대로 적용된다)
     - 답은 원본 작업계획서 `2. 결정 사항`에 `usecase-plan · 커밋`으로 기록한 뒤 커밋한다. (그 행도 같은 커밋에 들어간다)
   - `environment.yaml`을 빼고 커밋했는데 이번에 그 파일에 역할·서비스를 더했으면, 커밋한 usecase 계획서가 커밋되지 않은 설정에 기댄다. 완료 보고에 더한 역할·서비스와, 다른 사람이 이 브랜치로 실행하려면 그 파일을 확인해 직접 커밋해야 한다는 것을 적는다.
   - 이번 실행에서 만들거나 고친 usecase 계획서, 원본 작업계획서, `ai-work/usecase-env/environment.yaml`, 그리고 `ai-work/usecase-env/.gitignore`만 스테이징한다. 전용 무시 파일은 이번에 고치지 않았어도 미추적이거나 수정 상태이면 넣는다. (이전 실행이 커밋하지 못하고 남긴 무시 줄이다. 그대로 두면 `check-ignore`가 작업 트리의 파일로 통과해 어느 커맨드도 다시 커밋하지 않는다) (`git add -A` 쓰지 않음) `environment.local.yaml`·`accounts.yaml`은 절대 넣지 않는다.
   - 메시지: 제목은 프로젝트 규칙(CLAUDE.md 등)의 커밋 형식이 있으면 그것을 따르고, 없으면 `docs(usecase): <작업 제목> usecase 계획서 작성`(기존 문서 갱신이면 `갱신`)으로 쓴다. 프로젝트 형식에 type·모듈 같은 분류 자리가 있으면 그 프로젝트가 문서 변경에 쓰는 값(`docs`, `[docs]` 등)을 쓰고(정해진 값이 없으면 `docs`), 설명은 위 기본 제목의 설명 부분을 쓴다. 본문 끝 줄 `Plan: <원본 작업계획서 경로>`는 프로젝트 형식이 있어도 붙인다. (프로젝트 규칙이 본문 형식을 따로 정해 막는 경우만 뺀다)
   - 커밋이 실패하면(훅 실패 등) `--no-verify`로 우회하지 않고 원인을 알린다. 이번에 스테이징한 파일은 `git restore --staged -- <경로...>`로 스테이징을 되돌린다. (작업 트리는 그대로다. 남겨 두면 다음 실행에서 뺀다고 알린 파일이 함께 커밋될 수 있다) `자동`이고 작업 브랜치가 기본 브랜치가 아니면, 문서에서 고칠 수 있는 문제(훅이 지적한 포맷 등)는 고쳐 한 번 다시 커밋하고, 다시 실패하면 커밋하지 않는다.
     - 커밋하지 못했으면 완료 보고에 원인과, 원인을 고친 뒤 직접 커밋하는 명령(`git add -- <파일...> && git commit -m "<제목>" -- <파일...>`, 이번에 스테이징하려던 파일 그대로)을 적는다. 이 커맨드를 다시 실행해도 된다. (다시 실행하면 남은 파일을 이전 실행분으로 함께 커밋한다)
   - push는 하지 않는다.

## 상태 표기 · 진행률 규칙

| 표기 | 의미 |
|------|------|
| `[ ]` | 작업항목 (대기 / 미실행) |
| `[~]` | 진행중 |
| `[V]` | 작업완료 (검증 통과) |
| `[X]` | 실패 (`workflow-usecase-do` 실행 시에만 기록) |

- **전체진행률** = `[V]` 단계 수 ÷ 전체 단계 수 × 100 (소수점 버림). `0% (0/N)`처럼 개수를 함께 쓴다.
- **진행률 바** = 10칸. 10%당 `■` 1칸(버림), 나머지는 `□`
- **작업상태**는 백분율이 아니라 개수로 판단한다.
  - 대기: `[V]`·`[~]`·`[X]`가 모두 0개
  - 완료: 모든 단계가 `[V]`
  - 진행: 그 외
- UC 제목에도 같은 규칙으로 그 UC의 상태와 진행률을 표시한다. (분모는 그 UC의 단계 수)
- **진행 표시 확인**: 진행률·진행률 바·작업상태·UC 제목의 상태는 손으로 다시 세지 않는다. Bash 도구로 `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-progress.sh" "<usecase 계획서 경로>"`를 실행한다. 스크립트가 적힌 값과 다른 곳만 `적힌 값 → 맞는 값`으로 출력하면 체크 표기는 그대로 두고 그 값으로 고친다. (`진행 표시 일치`면 고칠 곳 없음) 스크립트를 실행할 수 없으면 위 규칙대로 직접 센다.

## Playwright MCP 액션 표기

각 단계는 `액션` + `대상` + `값 / 기대결과`로 쓴다. 액션은 Playwright MCP 도구 하나에 대응한다.

| 액션 | MCP 도구 | 표기 예 |
|------|----------|---------|
| login | (공통 로그인 절차) | 대상 계정 역할 `admin`. `environment.yaml`의 `login.steps`를 그 역할의 계정으로 실행 |
| navigate | browser_navigate | 대상 `/login` (환경의 web URL 기준 경로) |
| back | browser_navigate_back | 대상 `-` |
| click | browser_click | 대상 button "로그인" |
| hover | browser_hover | 대상 menuitem "설정" |
| type | browser_type | 대상 textbox "아이디", 값 `testuser` |
| fill_form | browser_fill_form | 값 `아이디=testuser, 이름=홍길동` (여러 필드 일괄 입력) |
| select | browser_select_option | 대상 combobox "구분", 값 `전체` |
| press | browser_press_key | 값 `Enter` |
| wait | browser_wait_for | 대상 text "저장되었습니다" 나타남/사라짐 (최대 30초) |
| dialog | browser_handle_dialog | 값 `accept` 또는 `dismiss`. dialog를 띄우는 단계 **바로 다음**에 둔다 |
| upload | browser_file_upload | 값 파일 경로. 파일 선택창을 여는 click **바로 다음**에 둔다 |
| assert | browser_find / browser_snapshot / browser_evaluate | 대상 text "홍길동", 기대결과 `표시됨` |
| network | browser_network_requests | 대상 `POST /api/xxx`, 기대결과 `응답 200` |
| console | browser_console_messages | 기대결과 `error 없음` |
| screenshot | browser_take_screenshot | 값 `01-06.png` (파일명만 쓴다) |

- 대상은 가능한 한 **role + 접근 가능한 이름(라벨/텍스트)** 으로 지정한다. (예: button "저장", textbox "이메일")
  - 접근 가능한 이름이 없는 요소(`<label>`·`placeholder`·`aria-label`이 없는 input 등)는 이름을 지어 쓰지 않고 role 뒤에 `css=<선택자>`를 쓴다. (예: `textbox css=input[name="email"]`) 선택자는 소스에서 확인한 것만 쓰고, `id`·`name` 속성처럼 그 요소 하나만 가리키는 것으로 고른다. `fill_form`은 이름으로 필드를 가리키므로 이런 입력에는 `type`을 쓴다.
  - 같은 이름의 요소가 여러 개면(목록 행마다 있는 버튼 등) 범위를 앞에 쓴다: `<범위> 안의 <요소>`. (예: `row "홍길동" 안의 button "삭제"`) 범위는 그 행에만 있는 텍스트로 가리킨다.
  - `dialog` 단계의 대상에는 확인 창 문구를 쓴다. (예: `확인 창 "삭제할까요?"`) 문구를 모르면 `-`.
- 로그인이 필요한 UC는 첫 단계를 `login`으로 쓴다. 로그인 화면 자체를 검증하는 UC가 아니면 로그인 단계를 풀어 쓰지 않는다. `login.enabled`가 `false`이면 `login` 단계를 쓰지 않는다.
- 계정 값은 `{account.id}`, `{account.password}`로만 쓴다. 로그인 화면을 직접 검증하는 UC에서 `type` 값으로 쓸 때도 같다.
  - 자리표시자는 값 칸뿐 아니라 대상·기대결과 칸에도 쓸 수 있다. (예: `row "{account.id}" 안의 button "잠금 해제"`, `text "{account.id}"` 사라짐) 실행할 때 그 UC의 계정 역할 값으로 바뀐다.
  - UC의 계정 역할이 아닌 다른 역할의 계정이 필요하면 `{account.<역할>.id}`·`{account.<역할>.password}`로 쓴다. (예: 관리자로 로그인해 일반 사용자 `{account.user.id}`를 검색)
  - 계정을 쓰지 않는 UC는 `계정 역할`을 `없음`으로 쓴다. 모든 UC가 그러면 `1. 사전 조건`의 계정 역할도 `없음`이다. (`workflow-usecase-do`가 `accounts.yaml`을 요구하지 않는다)
  - `화면 변경` 표의 문구에 실행할 때마다 달라지는 부분이 있으면(시각, 건수 등) `{…}`를 쓰지 않고 `<…>`로 형식을 적는다. (예: `계정이 잠겼습니다. <YYYY-MM-DD HH:MM> 이후에 다시 시도하세요.`) `{…}`는 자리표시자에만 쓴다.
- 경로가 아니라 전체 URL이 필요하면(값으로 URL을 입력, 기대결과에 URL 비교 등) `{web}`·`{api}`를 쓴다. 실행할 때 환경의 web·api URL로 바뀐다. 실제 호스트·포트는 쓰지 않는다.
- 표에 없는 동작(드래그, 탭 전환 등)은 해당 Playwright MCP 도구 이름에서 `browser_`를 뺀 것을 액션으로 쓴다. (예: `drag`, `tabs`)
- `network` 단계의 기대결과는 다음 중 하나로 쓴다: `응답 200` / `요청 없음` / `요청 N건, 모두 응답 401` / `요청 N건, 마지막 응답 423`. 건수는 그 화면에 들어온(마지막 `navigate`) 뒤의 요청을 센다. 화면에 응답이 드러나는 변화(문구, 목록 갱신)가 있으면 `network` 앞에 그것을 기다리는 `wait` 단계를 둔다. (없으면 실행할 때 잠깐 기다렸다가 한 번 더 조회한다)
- 같은 동작을 여러 번 해야 하면(예: 5회 연속 로그인 실패) 횟수만큼 행을 쓰고 값 칸에 `(n번째)`를 적는다. 한 행에 `5회 반복`처럼 쓰지 않는다. (행 하나가 도구 호출 하나다)
- 단계 ID는 `UC번호-순번`(`01-01`)으로 문서 전체에서 유일하게 매긴다. 실행 중 행 단위로 상태를 고치므로 같은 내용의 행이 여러 UC에 있어도 구분되어야 한다.
- 스크린샷 파일명은 `단계ID.png`로 쓴다. 저장 디렉토리는 실행할 때 정해진다. (템플릿의 표기 규칙 참고)
- 데이터 삭제·결제·메일 발송처럼 되돌리기 어려운 효과를 일으키는 단계는 `값 / 기대결과` 칸 끝에 `(되돌리기 어려움)`을 붙인다. 효과가 실제로 생기는 단계에 붙인다. (확인 창이 있으면 `dialog accept` 단계, 없으면 그 `click` 단계) `workflow-usecase-do`가 실행 전에 이 단계들을 모아 한 번에 실행 여부를 묻는다. 표시가 빠지면 실행 중에 그 단계에서 멈추고 묻게 된다.
  - 표시한 `dialog` 단계는 확인 창을 띄우는 단계(click 등) **바로 다음**에 둔다. 실행하지 않기로 하면 `workflow-usecase-do`가 창을 띄우는 앞 단계부터 실행하지 않는다. (창을 띄워 둔 채 끝내지 않기 위해서다)
- UC는 되도록 다른 UC에 기대지 않게 쓴다. (필요한 데이터를 그 UC 안에서 만들고 정리한다) 앞 UC가 남긴 상태(등록한 데이터, 잠금 등)를 이어 써야 하면 그 UC의 `선행:` 줄에 선행 UC와 필요한 상태를 쓴다. (예: `UC-01 (테스트 회원이 잠긴 상태, 잠근 지 30분 이내)`) 선행으로 쓸 수 있는 것은 문서에서 앞에 나오는 UC뿐이다. (`workflow-usecase-do`는 문서에 나온 순서대로 실행한다) 기대는 UC가 없으면 `없음`으로 쓴다. `workflow-usecase-do`는 이 줄을 보고, 일부 UC만 실행할 때 선행 UC를 함께 실행할지 묻고, 선행 UC가 통과하지 못하면 뒤 UC를 건너뛸지 묻는다.

### 템플릿 작성 지침
- **N**: 전체 단계 수(모든 UC의 단계 합)
- **작업 브랜치**: 원본 작업계획서의 값을 그대로 옮긴다.
- **2. 작업계획서 매핑**: 원본 계획서의 항목 ID(`1.2`, `DoD-1`)로 쓴다. 실행 후 통과 여부를 원본 계획서에 반영할 때 이 표를 쓴다. (`workflow-usecase-do`는 한 항목에 매핑된 UC가 모두 통과하면 그 항목을 `[V]`로 바꾸자고 제안한다)
  - 칸에는 ID만 `, `로 이어 쓴다. 설명이나 괄호를 넣지 않는다. 가리킬 항목이 없는 UC(추가 요청으로 넣은 시나리오 등)는 `-`로 쓴다.
  - 그 항목에 매핑된 UC가 모두 통과하면 항목 전체가 확인됐다고 할 수 있을 때만 매핑한다. UC들이 항목의 일부만 확인하면(나머지는 테스트·명령으로 확인하는 기준 등) 매핑하지 않고 완료 보고에 `일부만 확인: <ID> — <UC>`로 알린다.
  - 완료 기준은 줄 끝 표시가 `(확인: usecase)`인 것을 매핑한다. `(확인: 테스트 …)`·`(확인: 명령 …)`·`(확인: 사용자)`인 기준은 UC가 같은 내용을 화면으로 확인해도 매핑하지 않는다. (그 기준은 `workflow-do`가 적힌 방법으로 확인한다) 표시가 없는 예전 계획서는 화면으로 전부 확인할 수 있는 기준만 매핑한다.
- **표기 규칙 블록**은 빼지 않고 그대로 넣는다.
- **환경**: `environment.yaml`의 환경 이름을 쓴다. (기본은 `default` 값)
- **예시**: 템플릿의 UC-01 단계와 `UC-01 | 1.2, DoD-1` 매핑은 예시다. 실제 시나리오와 항목 ID로 바꾼다.
- **선행**: UC마다 쓴다. 앞 UC의 상태를 이어 쓰면 `UC-01 (필요한 상태)`, 아니면 `없음`. (`Playwright MCP 액션 표기`의 선행 규칙)
- **테스트 데이터**(`1. 사전 조건`): 실행을 시작할 때 있어야 하는 상태와, 다시 실행하려면 무엇을 되돌려야 하는지를 쓴다. (예: `UC-06이 끝에서 테스트 회원을 삭제한다. 삭제되지 않았으면 서버를 다시 띄운 뒤 실행한다`)

## 기존 문서 갱신
같은 원본 계획서의 usecase 계획서가 이미 있고 갱신하기로 했을 때만 적용한다. `workflow-usecase-do`가 그대로 실행할 수 있도록 다음 범위 안에서만 고친다.
- **실행 이력이 없는 문서**(`4. 실행 결과`에 행이 없고 모든 단계가 `[ ]`)는 아래 제한 없이 고쳐도 된다. UC·단계를 지우거나 번호를 다시 매겨도 된다. (단계 ID를 참조하는 증적과 실패 기록이 아직 없다) 바꾼 내용은 `5. 작업 이력`에 남긴다.
- 새 UC는 기존 마지막 UC 다음 번호를 쓰고, 단계 ID도 그 번호로 새로 매긴다. 문서 안의 위치는 실행 순서에 맞게 정한다. 기존 UC가 남긴 상태를 이어 쓰거나 뒤 UC가 그 상태를 없애면(삭제 UC 등) 그 사이에 넣는다. (`workflow-usecase-do`는 번호가 아니라 문서에 나온 순서대로 실행한다) 넣을 자리가 없어 상태를 새로 만들어야 하면 맨 뒤에 둔다.
- 기존 UC에 단계를 더할 때는 그 UC의 마지막 단계 다음 순번으로 끝에 붙인다. 중간에 끼워 넣지 않는다.
- `1. 사전 조건`(필요 서비스, 계정 역할, 테스트 데이터)과 UC의 목적·기대 결과 요약은 바뀐 UC 구성에 맞게 고친다. (`workflow-usecase-do`가 필요 서비스와 계정 역할을 이 문서에서 읽는다)
- `2. 작업계획서 매핑`을 원본 계획서의 현재 ID에 맞게 고친다. (취소된 ID는 빼고, 병합된 항목은 남은 ID로)
- `(가정)`이 붙은 대상은 소스에서 확인되고 정의 표와 같으면 실제 이름으로 바꾸고 `(가정)`을 뗀다. 소스가 정의 표와 다르면 처리 절차 2의 `소스가 정의와 다를 때`대로 묻는다. (`정의대로`면 정의 값을 둔 채 `(가정)`만 떼고, `소스대로`면 소스 값으로 바꾼다)
- UC의 `선행:` 줄은 추가하거나 고칠 수 있다. 새 UC가 기존 UC의 상태를 이어 쓰면 새 UC에 `선행:` 줄을 쓴다.
- `[V]`가 아닌 단계는 대상·값·기대결과를 고칠 수 있다. `[V]` 단계는 고치지 않는다.
- 단계를 지우거나 번호를 바꾸지 않는다. 증적 파일명과 `6. 실패 상세`가 단계 ID를 참조한다.
- `4. 실행 결과`와 `6. 실패 상세`는 그대로 둔다.
- 상단 표의 전체진행률·작업상태, 진행률 바, UC 제목의 상태/진행률은 `진행 표시 확인`으로 바로잡고, `최종 갱신`을 고친다.
- `5. 작업 이력`에 갱신 내용을 한 행 남긴다. (예: `갱신: UC-03 추가, 매핑 2건 수정, (가정) 4건 해소`) `최종 갱신`과 이 행의 일시는 갱신을 시작할 때 조회한 현재 시각이다. (Bash: `date '+%Y-%m-%d %H:%M:%S'`)
- 기존 문서가 예전 형식(상단 표에 `Base URL` 행, 계정을 `${환경변수}`·`(실행 시 입력)`으로 표기)이면 그 형식은 그대로 둔다. (`workflow-usecase-do`가 예전 형식도 실행한다) 새 형식으로 바꾸려면 새 문서로 작성하자고 권한다.
- 기존 단계를 없애야 하는 등 이 범위를 넘는 변경이 필요하면 새 문서로 작성하자고 권하고 사용자에게 확인한다.

## 완료 보고
- 생성된 usecase 계획서 경로
- UC 수, 전체 단계 수
- 사용할 환경, 필요 서비스, 계정 역할
- 실행 환경 설정 파일을 새로 만들었거나 고쳤으면 그 내용(`# TODO 확인 필요` 항목 포함)과 전용 무시 파일(`ai-work/usecase-env/.gitignore`) 추가 여부. 각자 `accounts.yaml`(포트 등이 다르면 `environment.local.yaml`도)을 채워야 한다는 점과, 테스트 전용 계정만 쓰라는 점
- 새로 작성했는지 기존 문서를 갱신했는지 (갱신했으면 바뀐 내용)
- `(가정)`으로 쓴 요소가 있으면 그 목록과, 구현 후 실제 화면 기준으로 고쳐야 한다는 점
- 원본 계획서의 `(미결)` 때문에 UC로 쓰지 않은 항목(확정된 부분만 쓴 항목 포함)과, 확정된 뒤 이 커맨드를 다시 실행해 기존 문서 갱신으로 더하라는 안내
- 화면으로 검증해야 하는데 UC가 없는 작업항목·완료 기준, UC가 일부만 확인해 매핑하지 않은 항목
- 답으로 받은 계정 값이 있으면 `accounts.yaml`의 어느 역할 키에 넣어야 하는지 (값은 적지 않는다)
- 지어 쓴 일회용 테스트 데이터가 있으면 그 값과 어느 UC가 만들고 지우는지
- 브랜치를 전환했으면 그 사실과 지금 브랜치 (미커밋 변경이 따라왔으면 그것도)
- 구현된 API·화면이 작업계획서의 `API 변경`·`화면 변경` 표와 다른 곳과 어느 쪽으로 썼는지. `정의대로` 썼으면 구현을 고치기 전에는 실행 때 그 단계가 실패한다는 점, `소스대로` 썼으면 `workflow-do`나 `workflow-plan-review`로 정의 표를 고치라는 안내
- UC 사이 선행 관계가 있으면 그 목록과, 일부 UC만 실행하면 선행 UC를 함께 실행할지 묻게 된다는 점
- `화면 변경` 표에 있는데 UC로 다루지 않은 메시지·권한별 노출
- 커밋 여부 (커밋했으면 커밋한 파일, 하지 않았으면 미커밋으로 남은 문서)
- 실행 방법: 구현이 끝나고 서버가 기동된 상태에서 `/workflow:workflow-usecase-do @<usecase 경로>`
