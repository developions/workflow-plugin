# workflow-status

로드맵, 작업계획서, usecase 계획서의 **진행 현황**을 보여 주고, 계획서마다 다음에 실행할 커맨드를 안내한다.

## 입력

```
$ARGUMENTS
```

- 비어 있으면: 완료되지 않은 로드맵·계획서(작업상태가 `완료`가 아님)와 현재 브랜치의 계획서를 보여 준다.
- `all`: 완료된 로드맵·계획서까지 모두 보여 준다.
- `@경로` 또는 경로: 그 계획서 하나를 자세히 보여 준다. (아래 `상세 보기`) `@`를 뗀 경로의 파일을 직접 읽는다.
  - 로드맵 README(`ai-work/roadmaps/*/README.md`)면 그 로드맵의 업무 행 전체(번호, 업무, 선행, 상태, 계획서와 그 진행률), 남은 `(미결)`, `5. 작업 이력` 마지막 3행, 다음 커맨드를 보여 준다.

## 절대 규칙

- **읽기 전용이다.** 파일을 만들거나 고치지 않는다. 브랜치를 바꾸지 않고, 커밋·stash 등 git 상태를 바꾸는 명령을 쓰지 않는다. 진행 표시가 틀린 계획서를 찾아도 고치지 않고 알리기만 한다.
- 다른 브랜치의 계획서는 작업 트리에 없다. (`workflow-plan`은 작업 브랜치에서 계획서를 만들고 커밋한다) 브랜치를 바꾸지 말고 `git grep`·`git show <브랜치>:<경로>`로 읽는다.
- 계획서 전체를 읽지 않는다. 아래 명령으로 필요한 줄만 뽑는다. (`상세 보기`는 예외)
- 사용자에게 묻지 않는다. 그래서 결정 사항을 기록하지 않는다.

## 처리 절차

### 1. 계획서 찾기
- git 저장소가 아니면 작업 트리의 `ai-work/plans/**/*.md`, `ai-work/usecases/**/*.md`만 본다. (`*_evidence/` 아래는 제외)
- git 저장소이면 현재 브랜치(`git branch --show-current`)와 브랜치 목록(`git for-each-ref --format='%(refname:short)' refs/heads refs/remotes`)을 구한다. 원격 추적 브랜치는 같은 이름의 로컬 브랜치가 없는 것만 남긴다. (로컬 브랜치와 그 원격 추적 브랜치는 하나로 세고 로컬 쪽을 읽는다) `<원격>/HEAD`(short 이름이 `origin`처럼 원격 이름만 나오는 ref)는 다른 브랜치를 가리키는 별칭이라 뺀다. 다른 커맨드가 계획서를 찾는 범위(로컬·원격 브랜치)와 같다.
- 그 브랜치 전체에서 상단 표의 필요한 줄만 한 번에 뽑는다. 출력은 `<브랜치>:<경로>:<줄번호>:<내용>`이다.
  ```bash
  git -c core.quotepath=false grep -n --no-color -e '^# ' -e '^| 작업 브랜치 |' -e '^| 작업상태 |' -e '^| 전체진행률 |' -e '^| 최종 갱신 |' -e '^| 원본 작업계획서 |' <브랜치...> -- 'ai-work/plans/**.md' 'ai-work/usecases/**.md'
  ```
  - 미커밋 변경은 작업 트리에만 있다. 현재 브랜치의 계획서는 같은 명령을 브랜치 이름 없이 `--untracked`를 붙여 실행해 작업 트리 기준으로 다시 읽는다. (`--untracked`가 없으면 커밋하지 않은 새 계획서를 놓친다)
  - 제목은 줄번호 1의 `# ` 줄만 쓴다. (본문의 `# ` 줄도 걸린다)
- 같은 경로의 계획서가 여러 브랜치에 있으면(분기 전 계획서를 이어받은 경우), 계획서의 `작업 브랜치` 값과 같은 브랜치의 사본을 기준으로 한다. 같은 브랜치가 없으면 가장 최근 커밋의 사본을 쓰고 `(사본)`이라고 적는다.
- 원격 추적 브랜치에서만 찾은 계획서는 작업 브랜치 칸에 `(원격)`을 붙인다. 원격 추적 브랜치는 마지막 `git fetch` 때의 내용이고, 이 커맨드는 fetch하지 않는다. (읽기 전용) 원격 계획서가 있으면 표 아래에 `원격 브랜치는 마지막 fetch 기준`이라고 한 줄 적는다.
- **로드맵**(`/workflow:workflow-roadmap`이 만든 `ai-work/roadmaps/*/README.md`)도 같은 방법으로 찾는다. 위 명령의 pathspec에 `'ai-work/roadmaps/*/README.md'`를 더하고, `-e '^## '`와 `-e '^| [0-9]'`를 더해 업무 행을 함께 뽑는다.
  - 업무 행은 `## 2. 업무 목록` 섹션(그 제목부터 다음 `## ` 제목 전까지)의 표 행이다. 다른 섹션의 `| 1 |` 같은 결정 사항 행은 쓰지 않는다.
  - 업무 행의 칸: `# | 업무 | 파일 | 선행 | 상태 | 계획서`
  - 같은 로드맵이 여러 브랜치에 있으면 README `작업 브랜치`와 같은 브랜치의 사본을 기준으로 한다. (계획서와 같은 규칙)

### 2. 계획서마다 상태 모으기
- **진행 표시**: 작업 트리에 있는 파일은 Bash 도구로 `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-progress.sh" "<경로>"`를 실행해 실제 개수와 진행률을 쓴다. 스크립트가 불일치를 내면 `진행 표시 불일치`라고 표시만 하고 고치지 않는다. 다른 브랜치의 계획서는 상단 표에 적힌 값을 쓰고 `(적힌 값)`을 붙인다. 스크립트를 실행할 수 없으면 적힌 값을 쓴다.
- **진행중 항목**: `[~]` 줄 (`git grep -n -e '^\s*- \[~\]'`, usecase는 `-e '^| \[~\] |'`)
- **미결**: `(미결)`이 붙은 줄 수 (`git grep -n -E -e '\(미결\)' --and --not -e '^[[:space:]]*>' --and --not -e '~~'`). 인용 블록(상단 규칙 블록의 설명 문구, `1. 요구사항` 원문)과 취소선 줄은 세지 않는다. (규칙 블록에 `(미결)` 설명이 있어 그대로 세면 모든 계획서가 미결 1건이 된다) `workflow-do`가 시작할 때 묻는다.
  - `## 2. 결정 사항` 섹션 안의 줄은 결정 행이라 따로 판정한다. 섹션 범위는 `git grep -n -e '^## '`의 줄 번호로 정한다. (그 제목부터 다음 `## ` 제목 전까지) 결정 행은 고치지 않고 새 행으로 확정하므로, 그 행의 번호 `n`을 가리키는 `#n 확정`·`#n 변경`·`#n 정정` 행이 같은 섹션에 있으면 세지 않는다. 다만 마지막으로 가리키는 행의 `선택`이 여전히 미정이면 센다. (`workflow-do` 준비 3번의 미결 판정과 같다)
  - 세지 않으면 확정된 결정이 계속 미결로 남아, 아래 다음 커맨드가 `workflow-do`로 잘못 나온다.
- **실패**: usecase 계획서의 `[X]` 단계 수 (`git grep -c -e '^| \[X\] |'`)
- **마지막 이력**: 작업계획서 `8. 작업 이력` 표의 마지막 행. 상세 보기에서만 읽는다.
- **usecase 연결**: usecase 계획서의 `원본 작업계획서` 값으로 작업계획서와 짝을 짓는다.

### 3. 다음 커맨드 정하기
위에서부터 처음 해당하는 것 하나를 쓴다.

| 상태 | 다음 커맨드 |
|------|-------------|
| 작업계획서에 `[~]` 항목이 있다 (중단된 작업) | `/workflow:workflow-do @<계획서>` (이어서 진행) |
| `(미결)`이 있거나 `[ ]` 작업항목이 남았다 | `/workflow:workflow-do @<계획서>` |
| 작업항목은 모두 `[V]`인데 완료 기준이 남았고, 연결된 usecase가 없다 | 화면 검증이 필요한 기준이면 `/workflow:workflow-usecase-plan @<계획서>`, 아니면 `/workflow:workflow-do @<계획서>` (완료 기준 확인) |
| 연결된 usecase에 `[X]`·`[ ]`·`[~]` 단계가 있다 | `/workflow:workflow-usecase-do @<usecase>` (실패가 있으면 먼저 `/workflow:workflow-do @<계획서> <수정 지시>`) |
| 모든 항목이 `[V]` | 없음 (완료) |

- 계획서의 작업 브랜치가 현재 브랜치와 다르면 다음 커맨드 앞에 `git switch <작업 브랜치>` 후 실행하라고 적는다. (커맨드도 시작할 때 브랜치 전환을 묻는다) 원격에서만 찾은 계획서는 `git switch --track <원격>/<작업 브랜치>` 후 실행하라고 적는다.
- 작업상태가 `대기`이고 Phase 3개 이상 또는 작업항목 10개 이상이면 `/workflow:workflow-plan-review`도 함께 권한다. (리뷰 이력(`리뷰` 행)이 이미 있으면 권하지 않는다)

### 4. 로드맵마다 상태 모으기
- **업무 상태**: 업무 행의 `상태`를 쓴다. `계획서` 칸의 계획서를 2번에서 읽었으면 그 작업상태와 비교해, 계획서가 `완료`인데 업무가 `진행`이거나 그 반대면 `상태 불일치`로 표시만 한다. 계획서 `대기`·`진행`은 업무 `진행`과 맞는 것이다. (`/workflow:workflow-roadmap @<README>`가 바로잡는다)
- **반영 필요**: 작업 트리에 있는 로드맵이면, `진행`·`완료` 업무의 계획서 `### 요구사항 문서` 제목 아래 `커밋 <해시>`를 읽어 `git log --oneline <해시>..HEAD -- <업무 파일>`이 비어 있지 않을 때 `반영 필요`로 표시한다. (`workflow-roadmap` 현황 모드와 같은 판정. 다른 브랜치의 로드맵이거나 커밋 표기가 없으면 판정하지 않는다) 이 업무의 다음은 `/workflow:workflow-roadmap @<README>`가 안내하는 반영 커맨드다.
- **진행률**: README 상단 표의 `전체진행률`을 쓴다. 업무 행으로 센 값(`완료` 수 ÷ `취소`를 뺀 수)과 다르면 센 값을 쓰고 `진행 표시 불일치`를 표시한다.
- **다음**: 위에서부터 처음 해당하는 것 하나다.
  - `반영 필요` 업무가 있다: `업무 <번호> 반영 필요 — /workflow:workflow-roadmap @<README>` (현황 모드가 반영 커맨드를 만든다)
  - `진행` 업무가 있다: `업무 <번호> — 아래 계획서 표`. (그 계획서의 다음 커맨드는 계획서 표에 있다)
  - `대기` 업무 중 `선행`이 모두 `완료`인 것이 있다: 행 순서로 첫 업무의 `/workflow:workflow-plan @<업무 파일 경로>` (업무 파일 경로는 README 디렉토리 + `파일` 칸)
  - `대기` 업무가 남았는데 선행이 끝나지 않았다: `선행 <번호> 대기 중`
  - 모두 `완료`·`취소`: 없음 (완료)
- 로드맵 `작업 브랜치`가 현재 브랜치와 다르면 다음 커맨드 앞에 `git switch <작업 브랜치>` 후 실행하라고 적는다.
- 계획서 표에서 로드맵 업무의 계획서(업무 행 `계획서` 칸에 있는 계획서)는 계획서 칸 제목 뒤에 `· 로드맵 <번호>`를 붙인다.

## 출력 형식

```markdown
현재 브랜치: `feature/order-service-v1`

| 로드맵 | 작업 브랜치 | 상태 | 진행률 | 업무 (완료/진행/대기) | 다음 |
|--------|-------------|------|--------|------------------------|------|
| `261123_order_service_v1` 주문 관리 서비스 1차 | `feature/order-service-v1` (현재) | 진행 | 20% (1/5) | 1 / 1 / 3 | 업무 02 — 아래 계획서 표 |

| 계획서 | 작업 브랜치 | 상태 | 진행률 | 진행중 | 미결 | usecase | 다음 |
|--------|-------------|------|--------|--------|------|---------|------|
| `261121/153000_add_login_page` 로그인 페이지 | `feature/add-login` (현재) | 진행 | 40% (4/10) | 2.1 | 1 | 실패 1 / 미실행 2 | `/workflow:workflow-do @ai-work/plans/261121/153000_add_login_page.md` |
| `261120/100000_fix_export` 엑셀 다운로드 오류 | `fix/export` | 대기 | 0% (0/6) (적힌 값) | - | 0 | 없음 | `git switch fix/export` 후 `/workflow:workflow-do @...` |
```

- 로드맵이 없으면 로드맵 표는 쓰지 않는다. 로드맵 칸은 `ai-work/roadmaps/`를 뗀 디렉토리 이름과 제목을 쓴다.
- 계획서 칸은 `ai-work/plans/`를 뗀 경로(확장자 제외)와 제목을 쓴다. 다음 칸에는 전체 경로를 쓴다.
- 진행 표시 불일치, `(사본)`처럼 알릴 것이 있으면 표 아래에 한 줄씩 적는다.
- 보여 줄 계획서가 없으면 `진행 중인 작업계획서 없음`과 `/workflow:workflow-plan <요구사항>`으로 시작한다는 안내만 쓴다. (진행 중인 로드맵이 있으면 로드맵 표와 그 다음 커맨드는 그대로 쓴다) 큰 작업이면 `/workflow:workflow-roadmap <요구사항>`으로 업무를 나눌 수 있다고 한 줄 덧붙인다.
- 기본 보기에서 완료된 계획서를 뺐으면 표 아래에 `완료 N건은 /workflow:workflow-status all로 볼 수 있다`를 쓴다.

## 상세 보기

경로를 지정했을 때만 한다. 그 계획서가 작업 트리에 없으면 1번의 방법으로 다른 브랜치에서 찾아 `git show <브랜치>:<경로>`로 읽는다. 그래도 없으면 `git log --all --format=%h -1 -- <경로>`와 `git branch -a --contains <커밋>`으로 있는 브랜치를 알린다.

- 위 표의 한 행
- Phase별 상태/진행률 (Phase 제목 줄)
- `[~]` 항목과 `[ ]` 항목 (항목 ID와 내용. 많으면 Phase마다 앞의 3개만)
- `(미결)`이 붙은 곳 (섹션과 내용. 위 `미결`과 같이 인용 블록과 취소선 줄은 뺀다)
- 남은 완료 기준
- `8. 작업 이력`의 마지막 3행
- 연결된 usecase 계획서마다: 경로, 진행률, `[X]` 단계 ID, `4. 실행 결과`의 마지막 행
- 다음 커맨드
