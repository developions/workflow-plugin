# workflow-usecase-do

`workflow-usecase-plan`으로 생성한 usecase 계획서를 **Playwright MCP**로 실행하고, 각 단계 결과를 계획서에 실시간으로 체크한다.

## 입력

```
$ARGUMENTS
```

- mention(`@경로`) 또는 경로로 지정된 usecase 계획서를 실행한다. `@`를 뗀 경로의 파일을 직접 읽는다. (자동 첨부에 기대지 않는다)
- 지정이 없으면 `ai-work/usecases/` 하위 최신 계획서를 찾아 AskUserQuestion으로 대상이 맞는지 확인한다.
- `UC-01,UC-03`처럼 UC ID가 주어지면 해당 UC만 실행한다. 없으면 전체 실행한다.

## 절대 규칙

- 브라우저 조작은 **Playwright MCP 도구로만** 한다. (`browser_navigate`, `browser_navigate_back`, `browser_snapshot`, `browser_find`, `browser_click`, `browser_hover`, `browser_type`, `browser_fill_form`, `browser_select_option`, `browser_press_key`, `browser_wait_for`, `browser_handle_dialog`, `browser_file_upload`, `browser_take_screenshot`, `browser_network_requests`, `browser_console_messages`, `browser_evaluate`, `browser_resize`, `browser_close` 등)
  - 실제 도구 이름 앞에는 설치 방식에 따라 `mcp__plugin_playwright_playwright__` 같은 prefix가 붙는다. 이 문서는 뒷부분 이름만 쓴다.
  - Playwright MCP 도구를 쓸 수 없으면(미설치, 연결 실패) 다른 브라우저 도구나 스크립트로 대체하지 말고, 그 사실을 알리고 중단한다.
- **이 커맨드는 검증만 한다.** 실패 원인이 코드에 있어 보여도 애플리케이션 소스를 고치지 않고 결과로 보고한다. 문서 커밋은 원본 작업계획서의 `커밋 방식`을 따르고(종료 처리 8), push는 하지 않는다.
- **애매한 사항은 직접 결정하지 않는다.** 다음 경우 AskUserQuestion으로 확인한다.
  - 사전 조건(서버 기동, 계정 정보 등)이 충족되지 않았을 때
  - 계획서의 대상에 해당하는 요소 후보가 여러 개이거나 이름이 달라 특정이 어려울 때
  - 실제 화면 동작이 기대결과와 다른데 그것이 버그인지 계획서 오류인지 판단이 필요할 때
  - 데이터 삭제/결제/메일 발송 등 되돌리기 어려운 동작을 실행해야 할 때
  - AskUserQuestion을 쓸 수 없는 환경(비대화형 실행 등)이면 해당 단계를 `[X]`로 기록하고 사유를 남긴 뒤 다음 UC로 넘어간다. 되돌리기 어려운 동작은 실행하지 않는다.
- AskUserQuestion으로 받은 답은 질문·선택지·선택 결과를 **원본 작업계획서** `2. 결정 사항`에 한 행씩 추가한다. `단계`는 `usecase-do`이고, 특정 단계에서 물었으면 `usecase-do · 02-03`처럼 단계 ID를 붙인다. 질문의 답이 아니라 사용자가 대화로 직접 준 지시·정정도 같은 표에 `usecase-do · 대화 지시`로 남긴다. (형식은 계획서의 `결정 · 이력 기록 규칙`) `일시`는 답을 받은 시점이다. 기존 행은 고치거나 지우지 않는다. 입력받은 계정 값은 `(입력됨, 기록 안 함)`으로 쓴다.
  - 원본 계획서의 표가 예전 형식(결정 사항 3열, 작업 이력 2열 등)이면 형식을 올리지 말고, 그 표의 머리글에 맞춰 행을 쓴다. 형식 올리기는 `workflow-plan-review`나 `workflow-do`가 한다.
  - 원본 계획서에 결정 사항 표가 없으면 usecase 계획서 `5. 작업 이력`에 `결정: <질문> → <선택> (선택지: …)` 한 칸 형식으로 남긴다.
- 계정 비밀번호 등 민감 정보의 실제 값은 계획서, 실행 결과, 보고, 파일명에 남기지 않는다.
  - `ai-work/usecase-env/accounts.yaml`은 값을 도구 인자에 넣기 위해서만 읽는다. 내용을 화면에 보여 주거나 요약하지 않는다.
  - 비밀번호를 대화창으로 입력받지 않는다. 값이 없으면 사용자가 `accounts.yaml`을 직접 채우게 한다.

## 상태 표기 · 진행률 규칙

계획서 안의 `표기 규칙` 블록과 같다.

| 표기 | 의미 |
|------|------|
| `[ ]` | 작업항목 (대기 / 미실행) |
| `[~]` | 진행중 |
| `[V]` | 작업완료 (검증 통과) |
| `[X]` | 실패 (기대결과 불일치 또는 실행 오류) |

- **전체진행률** = `[V]` 단계 수 ÷ 전체 단계 수 × 100 (소수점 버림). `[X]`는 분자에 넣지 않는다. 일부 UC만 실행해도 분모는 문서의 전체 단계 수다.
- **진행률 바** = 10칸. 10%당 `■` 1칸(버림), 나머지는 `□`
- **작업상태**는 백분율이 아니라 개수로 판단한다: 대기(`[V]`·`[~]`·`[X]` 모두 0개) / 완료(모든 단계 `[V]`) / 진행(그 외)
  - 실행이 끝났는데 완료가 아니면 `진행 (실패 N건, 미실행 M건)`처럼 사유를 덧붙인다. 실패나 미실행이 남아 있으면 `완료`라고 쓰지 않는다.
- UC 제목의 상태/진행률도 같은 규칙으로 갱신한다. (분모는 그 UC의 단계 수)

## 처리 절차

### 1. 준비
1. usecase 계획서를 읽고 환경(예전 형식은 Base URL), 사전 조건, 실행 대상 UC를 확인한다.
   - **작업 브랜치 확인** — 원본 작업계획서의 `작업 브랜치`가 기준이다. (원본 계획서를 읽을 수 없을 때만 usecase 계획서의 값을 쓴다)
     - usecase 계획서의 `작업 브랜치`가 원본 계획서와 다르면 원본 계획서 값으로 고치고 `5. 작업 이력`에 남긴다.
     - git 저장소가 아니거나 `작업 브랜치`가 `해당 없음`이면 건너뛴다.
     - 현재 브랜치(`git branch --show-current`)가 작업 브랜치와 다르면(출력이 비어 있는 detached HEAD 포함) 서버가 다른 코드로 떠 있을 수 있다. 브랜치를 직접 바꾸지 않고 AskUserQuestion으로 묻는다. 선택지:
       - `중단 (Recommended)`: 작업 브랜치로 바꾸고 서버를 다시 띄운 뒤 재실행하도록 안내한다.
       - `현재 브랜치로 계속`: `4. 실행 결과` 비고에 `브랜치 불일치: <현재 브랜치>`를 적는다. 이 실행 결과로는 원본 계획서 항목을 `[V]`로 반영하지 않는다.
     - 답은 원본 작업계획서 `2. 결정 사항`에 `usecase-do · 브랜치`로 기록한다.
2. Playwright MCP 도구를 쓸 수 있는지 확인한다. 쓸 수 없으면 중단한다.
3. 실행 환경과 계정을 준비한다. usecase 계획서 상단 표에 `환경` 행이 있으면 새 형식, `Base URL` 행이 있으면 예전 형식이다.
   - **새 형식**
     - `ai-work/usecase-env/environment.yaml`을 읽고, `environment.local.yaml`이 있으면 같은 키의 값을 덮어쓴다. 목록(`services`, `login.steps`)은 통째로 바꾼다. `environment.yaml`이 없으면 `/workflow:workflow-usecase-plan`으로 먼저 만들라고 알리고 중단한다.
     - 문서의 `환경` 값에 해당하는 환경의 `web`·`api`·`services`를 쓴다. 그 환경이 없으면 AskUserQuestion으로 어느 환경을 쓸지 묻는다.
     - 두 개인 파일(`environment.local.yaml`, `accounts.yaml`)이 git에서 무시되는지 `git check-ignore -q <파일>`로 확인한다. 무시되지 않으면 `ai-work/`가 있는 디렉토리의 `.gitignore`에 그 경로를 추가한다. (5번의 증적 제외 줄과 같이 "검증만 한다" 규칙의 예외다)
     - 계정: 실행 대상 UC의 `계정 역할`(UC에 없으면 `1. 사전 조건`의 계정 역할)과 `login` 단계의 역할을 모은다. `accounts.yaml`에서 `<환경>.<역할>.id`·`password`가 채워졌는지 확인한다.
       - 파일이 없으면 위 git 무시 확인을 마친 뒤, 필요한 역할 키와 `<채워 넣기>`만 있는 뼈대를 만든다. 파일 첫 줄에 `# 커밋 금지. 테스트 전용 계정만 쓴다.` 주석을 넣는다.
       - 비어 있거나 `<채워 넣기>`인 값이 있으면 AskUserQuestion으로 묻는다. 질문 본문에 채울 파일 경로와 역할 키(값은 쓰지 않는다)를 적는다. 선택지: `accounts.yaml을 채웠음, 계속 (Recommended)` / `중단`. 계속을 골랐는데도 비어 있으면 다시 묻지 않고 중단한다.
   - **예전 형식**
     - `${환경변수명}`은 셸에서 조회한다. (Bash: `printenv 이름` / PowerShell: `$env:이름`) 값이 비어 있으면 어떻게 할지 AskUserQuestion으로 확인한다.
     - `(실행 시 입력)`은 실행 전에 사용자에게 값을 묻는다.
     - 완료 보고에 새 형식(실행 환경 설정 파일)으로 다시 작성하기를 권한다.
4. 실행 시각을 조회한다. 이 값은 증적 디렉토리 이름, `4. 실행 결과` 행, 처음 고치는 `최종 갱신`에 쓴다. 그 밖에는 AskUserQuestion으로 답을 받을 때마다(결정 사항 `일시`)와 UC가 끝날 때마다(`최종 갱신`) 다시 조회한다.
   - Bash: `date '+%y%m%d_%H%M%S %Y-%m-%d %H:%M:%S'`
   - PowerShell: `Get-Date -Format 'yyMMdd_HHmmss yyyy-MM-dd HH:mm:ss'`
5. 증적 디렉토리를 만든다. usecase 파일 경로에서 `.md`를 뺀 뒤 `_evidence/<실행 YYMMDD_HHMISS>/`를 붙인 경로다.
   - 예: `ai-work/usecases/261121/153000_add_login_page.md` → `ai-work/usecases/261121/153000_add_login_page_evidence/261122_101500/`
   - 증적은 git에 올리지 않는다. git 저장소이면 디렉토리를 만든 뒤 `git check-ignore -q <증적 디렉토리>`로 확인하고, 무시되지 않는 상태(종료 코드 1)이면 `ai-work/`가 있는 디렉토리의 `.gitignore`에 `ai-work/**/*_evidence/` 한 줄을 추가한다. (`.gitignore`가 없으면 만든다. 이 한 줄 추가는 "검증만 한다" 규칙의 예외다)
   - 계획서와 usecase 문서는 제외하지 않는다.
6. 이전 실행 흔적을 초기화한다. (재실행 대비)
   - 실행 대상 UC의 모든 단계를 `[ ]`로 되돌리고, 이전 실행에서 덧붙인 `→ 실제: ...`를 지운다.
   - 실행 대상이 아닌 UC는 그대로 둔다. 다만 `[~]`가 남아 있으면(중단된 실행의 흔적) `[ ]`로 되돌린다.
   - 이전 실행의 기록(`4. 실행 결과`, `6. 실패 상세`, 증적 디렉토리)은 지우지 않는다.
7. 표기를 다시 세어 진행률을 고치고, 상단 표의 작업상태를 `진행`으로, `최종 갱신`을 실행 시각으로 바꾼다.
8. 서버가 떠 있는지 확인한다.
   - **새 형식**: 문서의 `필요 서비스`마다 `health` URL을 Bash `curl -s -o /dev/null -w '%{http_code}' --max-time 5 <health URL>`로 확인한다. 응답 코드가 `000`이거나 5xx이면 떠 있지 않은 것으로 본다.
     - 떠 있지 않은 서비스에 `start`가 있으면 AskUserQuestion으로 묻는다. 선택지: `기동 (Recommended)` / `직접 띄운 뒤 계속` / `중단`. `start`가 없으면 뒤의 두 개만 둔다.
     - `기동`을 고르면 저장소 루트에서 `start` 명령을 백그라운드로 실행하고, `health`가 응답할 때까지 최대 3분 기다린다. 응답이 없으면 실행 출력의 마지막 부분을 보여 주고 어떻게 할지 묻는다.
     - 직접 기동한 서버는 실행이 끝나도 끄지 않고 완료 보고에 알린다.
     - 모두 떠 있으면 `browser_navigate`로 환경의 `web` URL에 접속되는지 확인한다.
   - **예전 형식**: `browser_navigate`로 Base URL에 접속되는지 확인한다. 접속되지 않으면 AskUserQuestion으로 서버 기동 방법/대기 여부를 확인한다.
9. 계획서에 해상도가 있으면 `browser_resize`로 맞춘다.

### 2. 단계 실행 (UC 순서대로, 단계 순서대로)
각 단계마다 다음을 **반드시 순서대로** 수행한다.

1. 계획서의 해당 단계 상태를 `[ ]` → `[~]`로 바꾼다. (도구를 실행하기 전에 파일을 먼저 고친다)
2. 대상 요소를 찾는다. 직전 도구 응답에 최신 화면 구조가 들어 있으면 그것을 쓰고, 없으면 `browser_find` 또는 `browser_snapshot`으로 대상(role + 이름)의 ref를 얻는다. ref는 도구의 `target` 인자로 넘긴다.
3. 액션에 대응하는 Playwright MCP 도구를 실행한다.
   - `navigate`: 대상이 `/`로 시작하면 환경의 `web` URL(예전 형식은 Base URL) 뒤에 붙인다.
   - `login`: `login.steps`를 순서대로 실행한다. 각 하위 단계는 같은 규칙(요소 찾기 → 도구 실행 → 확인)으로 하고, `{account.id}`·`{account.password}`는 대상 역할의 `accounts.yaml` 값으로 바꿔 **도구 인자에만** 넣는다.
     - 계획서에는 `login` 단계 한 행의 결과만 기록한다. 하위 단계가 실패하면 그 행을 `[X]`로 하고 `→ 실제:`에 실패한 하위 단계(예: `click button "로그인" — 요소 없음`)를 적는다. 입력한 값은 적지 않는다.
     - `login.enabled`가 `false`이거나 `login`이 없으면 계획서 오류로 보고 AskUserQuestion으로 어떻게 할지 묻는다.
   - 다른 단계의 값에 `{account.id}`·`{account.password}`가 있으면 그 UC의 계정 역할 값으로 바꿔 도구 인자에만 넣는다. `{web}`·`{api}`는 환경의 URL로 바꾼다.
   - `screenshot`: `filename`에 `<증적 디렉토리>/<파일명>`을 프로젝트 루트 기준 상대경로로 넘긴다. Playwright MCP는 상대경로를 자기 작업 루트 기준으로 해석하므로, 첫 스크린샷 뒤에 파일이 증적 디렉토리에 생겼는지 확인한다. 없으면 절대경로로 다시 저장하고 이후에도 절대경로를 쓴다.
   - `upload`: 파일 경로를 절대경로로 바꿔 넘긴다.
   - `wait`: 대기 시간은 최대 30초다.
   - `network`: `filter`로 URL을 좁혀 조회한다. 요청 뒤에 페이지가 이동했으면 `all: true`로 조회한다.
4. 기대결과를 검증한다. (화면 텍스트, URL, network 응답, console 오류 등)
5. 결과를 기록한다.
   - 통과: `[~]` → `[V]`
   - 실패: `[~]` → `[X]`. 그 행의 `값 / 기대결과` 칸 뒤에 `→ 실제: ...`를 덧붙이고(화면 문구의 `|`는 `\|`로 쓴다), `browser_take_screenshot`으로 `<증적 디렉토리>/<단계ID>_fail.png`를 남긴다.
6. 같은 수정에서 상단 표의 전체진행률, 진행률 바, 해당 UC 제목의 상태/진행률을 함께 고친다. `최종 갱신` 시각은 UC가 끝날 때마다 고친다. (단계마다 시각을 조회하지 않는다)

실패 처리 규칙:
- 대상 요소를 못 찾으면 `browser_wait_for`로 짧게 기다린 뒤 한 번 더 찾는다.
  - 그래도 없으면 `[X]`로 기록한다.
  - 이름만 조금 다른 요소가 있거나 후보가 여러 개여서 계획서 쪽 오류로 보이면 AskUserQuestion으로 어느 요소를 쓸지 확인한다. 확인받은 요소로 진행했으면 계획서의 대상 칸을 실제 이름으로 고친다.
- `(가정)`이 붙은 대상이 실제 화면의 요소와 정확히 일치하면 `(가정)`을 뗀다. 일치하지 않으면 위 규칙대로 확인한다.
- 한 단계가 실패하면 같은 UC의 이후 단계가 의미가 있는지 판단한다. 선행 조건이 깨져 의미가 없으면 남은 단계를 `[ ]`(미실행)로 두고 다음 UC로 넘어간다. 판단이 애매하면 AskUserQuestion으로 확인한다.

### 3. 종료 처리
1. 각 UC가 끝날 때 `browser_console_messages`를 `level: error`, `all: true`로 조회한다. 직전 조회 이후 새로 생긴 error가 있으면 `4. 실행 결과`의 비고에 `UC-02 console error 1건`처럼 적는다. 계획서에 `console` 단계가 없으면 이것만으로 단계를 실패 처리하지 않는다.
2. 전체 실행이 끝나면 `browser_close`로 브라우저를 닫는다.
3. 표기를 다시 세어 전체진행률과 작업상태를 확정한다. (완료가 아니면 `진행 (실패 N건, 미실행 M건)`)
4. `4. 실행 결과` 표에 한 행을 추가한다. 통과/실패/미실행은 이번 실행 대상 UC의 단계 수다.

```markdown
| YYYY-MM-DD HH:MI:SS | 전체 (또는 UC-01,UC-03) | N | N | N | `..._evidence/YYMMDD_HHMISS/` / 실패: 02-03, UC-02 console error 1건 |
```

5. 실패한 단계가 있으면 `## 6. 실패 상세` 섹션에 이번 실행을 기록한다. 섹션이 없으면 `5. 작업 이력` 아래에 만들고, 있으면 그 섹션 끝에 이번 실행(`### 실행일시`)만 추가한다.

```markdown
## 6. 실패 상세

### YYYY-MM-DD HH:MI:SS 실행
| 단계 | 기대결과 | 실제결과 | 추정 원인 | 증적 |
|------|----------|----------|-----------|------|
| 02-03 | ... | ... | ... | `02-03_fail.png` |
```

6. `5. 작업 이력`에 실행 이력을 한 행 추가한다.
   - 내용: 실행 대상, 통과/실패/미실행 단계 수, 실행 중 고친 대상 이름 수, 해소한 `(가정)` 수, 증적 경로
   - 예: `실행: 전체 / 통과 12, 실패 1, 미실행 2 / 대상 수정 1건, (가정) 해소 3건 / 153000_add_login_page_evidence/261122_101500/`
7. 원본 작업계획서에 반영한다. (상단 표의 `원본 작업계획서`)
   - `2. 작업계획서 매핑`에서 이번에 통과한 UC(모든 단계가 `[V]`)가 가리키는 항목 ID를 찾는다.
   - 그 항목을 검증하는 UC가 **모두** 통과했고 원본 계획서에서 아직 `[V]`가 아닌 항목만 고른다.
   - 매핑된 ID가 원본 계획서에서 취소·병합됐거나, 없거나, `(미결)`이면 `[V]`로 제안하지 않는다. 매핑을 직접 고치지도 않는다. (매핑은 `workflow-usecase-plan`의 기존 문서 갱신이 맡는다) 완료 보고에 알린다.
   - 브랜치 불일치로 계속한 실행이면 이 반영을 건너뛰고 `usecase` 요약 행에 그 사실만 남긴다.
   - 고른 항목을 `[V]`로 바꿀지 AskUserQuestion으로 확인한다.
   - 반영할 때는 원본 계획서의 `진행 관리 규칙`대로 진행률과 작업상태를 다시 계산하고, 바꾼 항목마다 `8. 작업 이력`에 구분 `항목`으로 한 행을 남긴다. (예: `DoD-1 확인 — UC-01 통과 (<usecase 경로>)`)
   - 원본 계획서에서 이미 `[V]`인 항목을 검증하는 UC가 실패했으면(회귀) 그 항목의 상태는 바꾸지 않는다. 완료 보고와 아래 `usecase` 행에 적는다.
   - 반영 여부와 상관없이 `8. 작업 이력`에 구분 `usecase`로 이번 실행을 요약한 한 행을 남긴다. (예: `usecase-do: 전체 / 통과 UC 3, 실패 UC 1 (회귀: 2.1) / <usecase 경로>`)
8. 커밋한다. git 저장소가 아니거나 원본 작업계획서의 `커밋 방식`이 `해당 없음`이면 건너뛴다. (이 커밋은 "검증만 한다" 규칙의 예외다. 애플리케이션 소스는 커밋 대상이 아니다)
   - 1단계 브랜치 확인 직후 `git status --short -- <usecase 계획서> <원본 작업계획서>`로 두 문서에 실행 전부터 미커밋 변경이 있었는지 확인해 둔다.
   - 원본 작업계획서 상단 표의 `커밋 방식`을 따른다. 값이 없거나 원본 계획서를 읽을 수 없으면 `확인`으로 본다.
     - `자동`: 묻지 않고 커밋한 뒤 `커밋 <해시> <제목>` 한 줄로 알린다. 단, 브랜치 불일치로 계속한 실행이거나, 작업 브랜치가 기본 브랜치이거나, 두 문서에 실행 전부터 미커밋 변경이 있었으면 그 사유를 적고 아래처럼 묻는다.
     - `확인`·`끝에 한꺼번에`: AskUserQuestion으로 묻는다.
   - 질문: 선택지는 커밋 메시지 초안을 보여 주고 커밋 / 커밋하지 않음. 평소에는 커밋을 첫 번째에 두고 `(Recommended)`를 붙인다.
     - 브랜치 불일치로 계속한 실행이면 질문 본문에 현재 브랜치가 작업 브랜치와 다르다는 것을 적고, `커밋하지 않음`을 첫 번째에 두고 `(Recommended)`를 붙인다.
     - 두 문서에 실행 전부터 미커밋 변경이 있었으면 질문 본문에 그 변경도 함께 커밋된다는 것을 적는다. (파일 단위로 스테이징하기 때문이다)
     - 답은 원본 작업계획서 `2. 결정 사항`에 `usecase-do`로 기록한 뒤 커밋한다.
   - usecase 계획서, 이번 실행에서 고친 원본 작업계획서, 이번 실행에서 줄을 추가한 `.gitignore`만 스테이징한다. (`git add -A` 쓰지 않음) 증적 디렉토리, 애플리케이션 소스, `environment.local.yaml`, `accounts.yaml`은 넣지 않는다.
   - push는 하지 않는다.

## 완료 보고
- 실행한 usecase 계획서 경로와 실행 대상
- UC별 결과 (통과/실패/미실행)
- 전체진행률과 작업상태
- 실패 항목 요약과 추정 원인, 증적 경로
- 실행 중 계획서 내용을 고친 것(대상 요소 이름 등)이 있으면 그 목록
- `.gitignore`에 증적 제외 줄이나 개인 설정 파일 줄을 추가했으면 그 사실
- 사용한 환경(새 형식이면 환경 이름, 예전 형식이면 Base URL), `accounts.yaml` 뼈대를 만들었으면 그 사실
- 직접 기동한 서버가 있으면 그 서비스 이름과 명령 (실행 중으로 남아 있다)
- 커밋 여부 (커밋했으면 커밋한 파일, 하지 않았으면 미커밋으로 남은 문서)
- 원본 계획서에 반영한 항목, 회귀(이미 `[V]`인 항목의 UC 실패), 매핑 ID가 취소·병합·미결이라 반영하지 못한 항목 (있으면 `/workflow:workflow-usecase-plan`으로 기존 문서 갱신을 권한다)
- 실패가 있으면 수정 방법을 안내한다: `/workflow:workflow-do @<원본 계획서> <수정 지시>`로 고친 뒤(계획에 없는 수정이면 새 작업항목으로 추가된다) `/workflow:workflow-usecase-do @<usecase 경로> UC-xx`로 실패한 UC만 재실행한다.
