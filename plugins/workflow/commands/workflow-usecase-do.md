# workflow-usecase-do

`workflow-usecase-plan`으로 생성한 usecase 계획서를 **Playwright MCP**로 실행하고, 각 단계 결과를 계획서에 실시간으로 체크한다.

## 입력

```
$ARGUMENTS
```

- mention(`@경로`) 또는 경로로 지정된 usecase 계획서를 실행한다. `@`를 뗀 경로의 파일을 직접 읽는다. (자동 첨부에 기대지 않는다)
- 지정이 없으면 `ai-work/usecases/` 하위 최신 계획서를 찾아 AskUserQuestion으로 대상이 맞는지 확인한다.
- `UC-01,UC-03`처럼 UC ID가 주어지면 해당 UC만 실행한다. 없으면 전체 실행한다.

## 절대 규칙

- 브라우저 조작은 **Playwright MCP 도구로만** 한다. (`browser_navigate`, `browser_navigate_back`, `browser_snapshot`, `browser_find`, `browser_click`, `browser_hover`, `browser_type`, `browser_fill_form`, `browser_select_option`, `browser_press_key`, `browser_wait_for`, `browser_handle_dialog`, `browser_file_upload`, `browser_take_screenshot`, `browser_network_requests`, `browser_console_messages`, `browser_evaluate`, `browser_resize`, `browser_close` 등)
  - 실제 도구 이름 앞에는 설치 방식에 따라 `mcp__plugin_playwright_playwright__` 같은 prefix가 붙는다. 이 문서는 뒷부분 이름만 쓴다.
  - Playwright MCP 도구를 쓸 수 없으면(미설치, 연결 실패) 다른 브라우저 도구나 스크립트로 대체하지 말고, 그 사실을 알리고 중단한다.
- **이 커맨드는 검증만 한다.** 실패 원인이 코드에 있어 보여도 애플리케이션 소스를 고치지 않고 결과로 보고한다. 문서 커밋은 원본 작업계획서의 `커밋 방식`을 따르고(종료 처리 8), push는 하지 않는다.
- **애매한 사항은 직접 결정하지 않는다.** 다음 경우 AskUserQuestion으로 확인한다.
  - 사전 조건(서버 기동, 계정 정보 등)이 충족되지 않았을 때
  - 계획서의 대상에 해당하는 요소 후보가 여러 개이거나 이름이 달라 특정이 어려울 때
  - 실제 화면 동작이 기대결과와 다른데 그것이 버그인지 계획서 오류인지 판단이 필요할 때
  - 데이터 삭제/결제/메일 발송 등 되돌리기 어려운 동작을 실행해야 할 때
  - AskUserQuestion을 쓸 수 없는 환경(비대화형 실행 등)이면 해당 단계를 `[X]`로 기록하고 사유를 남긴 뒤 다음 UC로 넘어간다. 되돌리기 어려운 동작은 실행하지 않는다.
- AskUserQuestion으로 받은 답은 질문·선택지·선택 결과를 **원본 작업계획서** `2. 결정 사항`에 한 행씩 추가한다. `단계`는 `usecase-do`이고, 특정 단계에서 물었으면 `usecase-do · 02-03`처럼 단계 ID를 붙인다. 질문의 답이 아니라 사용자가 대화로 직접 준 지시·정정도 같은 표에 `usecase-do · 대화 지시`로 남긴다. (형식은 계획서의 `결정 · 이력 기록 규칙`) `일시`는 답을 받은 시점이다. 기존 행은 고치거나 지우지 않는다. 입력받은 계정 값은 `(입력됨, 기록 안 함)`으로 쓴다.
  - 원본 계획서의 표가 예전 형식(결정 사항 3열, 작업 이력 2열 등)이면 형식을 올리지 말고, 그 표의 머리글에 맞춰 행을 쓴다. 형식 올리기는 `workflow-plan-review`나 `workflow-do`가 한다.
  - 원본 계획서에 결정 사항 표가 없으면 usecase 계획서 `5. 작업 이력`에 `결정: <질문> → <선택> (선택지: …)` 한 칸 형식으로 남긴다.
- 계정 비밀번호 등 민감 정보의 실제 값은 계획서, 실행 결과, 보고, 파일명에 남기지 않는다.
  - `ai-work/usecase-env/accounts.yaml`은 값을 도구 인자에 넣기 위해서만 읽는다. 내용을 화면에 보여 주거나 요약하지 않는다.
  - 비밀번호를 대화창으로 입력받지 않는다. 값이 없으면 사용자가 `accounts.yaml`을 직접 채우게 한다.

## 상태 표기 · 진행률 규칙

계획서 안의 `표기 규칙` 블록과 같다.

| 표기 | 의미 |
|------|------|
| `[ ]` | 작업항목 (대기 / 미실행) |
| `[~]` | 진행중 |
| `[V]` | 작업완료 (검증 통과) |
| `[X]` | 실패 (기대결과 불일치 또는 실행 오류) |

- **전체진행률** = `[V]` 단계 수 ÷ 전체 단계 수 × 100 (소수점 버림). `[X]`는 분자에 넣지 않는다. 일부 UC만 실행해도 분모는 문서의 전체 단계 수다.
- **진행률 바** = 10칸. 10%당 `■` 1칸(버림), 나머지는 `□`
- **작업상태**는 백분율이 아니라 개수로 판단한다: 대기(`[V]`·`[~]`·`[X]` 모두 0개) / 완료(모든 단계 `[V]`) / 진행(그 외)
  - 실행이 끝났는데 완료가 아니면 `진행 (실패 N건, 미실행 M건)`처럼 사유를 덧붙인다. 실패나 미실행이 남아 있으면 `완료`라고 쓰지 않는다.
- UC 제목의 상태/진행률도 같은 규칙으로 갱신한다. (분모는 그 UC의 단계 수)
- **진행 표시 확인**: Bash 도구로 `bash "${CLAUDE_PLUGIN_ROOT}/scripts/plan-progress.sh" --fix "<계획서 경로>"`를 실행한다. 스크립트가 체크 표기를 세어 진행률·진행률 바·UC(작업계획서는 Phase) 제목의 상태 중 다른 곳을 직접 고치고, 고친 곳을 `적힌 값 → 맞는 값`으로 출력한다. (`진행 표시 일치`면 고친 곳 없음) usecase 계획서와 원본 작업계획서 모두에 쓴다.
  - usecase 계획서의 작업상태는 스크립트가 고치지 않고 출력만 한다. 사유(`(실패 N건, 미실행 M건)`)를 붙여 직접 고친다. 원본 작업계획서의 작업상태는 스크립트가 고친다.
  - 스크립트가 파일을 고쳤으면, 다음에 Edit 도구로 그 파일을 고치기 전에 Read로 몇 줄(`limit`)만 다시 읽는다. (Edit 도구는 밖에서 바뀐 파일을 다시 읽어야 고칠 수 있다)
  - 스크립트를 실행할 수 없으면 위 규칙대로 직접 센다.

## 처리 절차

### 1. 준비
1. usecase 계획서를 읽고 환경(예전 형식은 Base URL), 사전 조건, 실행 대상 UC를 확인한다.
   - **작업 브랜치 확인** — 원본 작업계획서의 `작업 브랜치`가 기준이다. (원본 계획서를 읽을 수 없을 때만 usecase 계획서의 값을 쓴다)
     - usecase 계획서의 `작업 브랜치`가 원본 계획서와 다르면 원본 계획서 값으로 고치고 `5. 작업 이력`에 남긴다. 이 수정은 아래 현재 브랜치 확인을 마친 뒤(`중단`이 아닐 때) 한다.
     - git 저장소가 아니거나 `작업 브랜치`가 `해당 없음`으로 시작하면(`해당 없음 (detached HEAD)` 포함) 건너뛴다.
     - 현재 브랜치(`git branch --show-current`)가 작업 브랜치와 다르면(출력이 비어 있는 detached HEAD 포함) 서버가 다른 코드로 떠 있을 수 있다. 브랜치를 직접 바꾸지 않고 AskUserQuestion으로 묻는다. 선택지:
       - `중단 (Recommended)`: 작업 브랜치로 바꾸고 서버를 다시 띄운 뒤 재실행하도록 안내한다.
       - `현재 브랜치로 계속`: `4. 실행 결과` 비고에 `브랜치 불일치: <현재 브랜치>`를 적는다. 이 실행 결과로는 원본 계획서 항목을 `[V]`로 반영하지 않는다.
     - 답은 원본 작업계획서 `2. 결정 사항`에 `usecase-do · 브랜치`로 기록한다. `중단`이면 기록하지 않고 문서를 고치지 않은 채 끝낸다. (작업 브랜치가 아닌 곳에서 기록하면 그 행이 엉뚱한 브랜치에 미커밋으로 남는다)
   - **준비 중 중단** — 준비(1~9번)의 다른 질문(선행 UC, `accounts.yaml`, 서버 기동 등)에서 `중단`을 고르거나 준비 중에 멈추면, 그때까지 이 커맨드가 고친 문서(원본 작업계획서의 결정 행, usecase 계획서, 전용 무시 파일)를 종료 처리 8의 규칙대로 커밋하고 끝낸다.
     - 커밋 전에 종료 처리 7의 1.5.0 전 커밋 예외 줄 교체를 한다. (원본 작업계획서를 고쳤을 때만. 예전 줄은 "미커밋 변경이 섞이면 묻는다"인데 커밋은 새 규칙대로 묻지 않으므로, 줄과 동작이 어긋나지 않게 한다) 종료 처리 7의 다른 일(반영, `usecase` 요약 행)은 하지 않는다.
     - 스테이징 대상은 종료 처리 8과 같다. 이번에 고친 문서와, 이번에 고치지 않았어도 미추적이거나 수정 상태인 전용 무시 파일이다. 고친 문서가 하나도 없으면 커밋하지 않는다. (전용 무시 파일만 남아 있으면 다음 실행의 종료 처리 8이 커밋한다)
     - 제목은 종료 처리 8의 형식에서 설명을 `usecase 실행 준비 중단 기록 (<사유>)`로 쓴다. (커밋하지 않고 끝내면 다음 실행이 그 기록을 실행 전 변경으로 잘못 알린다)
   - **실행 전 미커밋 변경 확인** — git 저장소이면 이 커맨드가 문서를 하나라도 고치기 전에(위 브랜치 확인에서 usecase 계획서의 `작업 브랜치`를 고치는 것보다도 먼저) `git status --short -- <usecase 계획서> <원본 작업계획서> ai-work/usecase-env/.gitignore ai-work/usecases/.gitignore`(원본 계획서가 로드맵 업무 계획서면 그 로드맵 README도)를 실행해 결과를 적어 둔다. 종료 처리 8에서 커밋할 수 있는 파일 전부다. 종료 처리 8의 커밋에서 쓴다. (이 커맨드가 더하는 무시 줄은 루트 `.gitignore`가 아니라 전용 무시 파일에만 쓴다. 아래 준비 4·7번)
   - **선행 UC** — UC ID가 주어져 일부만 실행할 때, 실행 대상 UC의 `선행:` 줄을 읽는다. (줄이 없거나 `없음`이면 건너뛴다) 선행 UC(그 UC의 선행까지 거슬러 올라가 모두)가 실행 대상에 없으면 AskUserQuestion으로 묻는다. 질문 본문에 UC마다 선행 UC와 필요한 상태, `1. 사전 조건`의 테스트 데이터 설명을 적는다. 선택지:
     - `선행 UC도 함께 실행 (Recommended)`: 선행 UC를 실행 대상에 넣는다. (실행은 문서에 나온 UC 순서대로다. 아래 되돌리기 어려운 단계와 계정 역할도 넣은 UC까지 포함해 모은다)
     - `지정한 UC만 실행`: 필요한 상태가 이미 만들어져 있을 때다. `4. 실행 결과` 비고에 `선행 <UC ID> 실행 안 함`을 적는다.
     - `중단`
     - 답은 `usecase-do · 준비`로 기록한다. AskUserQuestion을 쓸 수 없으면 선행 UC를 함께 실행한다.
   - **되돌리기 어려운 단계** — 실행 대상 UC에서 `값 / 기대결과` 칸에 `(되돌리기 어려움)`이 붙은 단계를 모아, 실행할지 실행 전에 한 번에 묻는다. 실행 중에 단계마다 멈추고 agent를 다시 띄우지 않기 위해서다.
     - AskUserQuestion으로 묻는다. 질문 본문에 실행 환경 이름과 각 단계가 일으키는 효과(삭제·발송 등)를 적는다. 테스트 데이터인지는 실행 환경을 아는 사용자가 판단하므로 추천은 붙이지 않는다.
       - 표시된 단계가 2개 이상이면 `multiSelect: true`로 묻고, 선택지는 단계마다 `<단계 ID> <액션> <대상> 실행`이다. 4개가 넘으면 질문을 나누되, 한 질문에 단계가 하나만 남지 않게 나눈다. (예: 5개면 3개 + 2개)
       - 표시된 단계가 1개면 `multiSelect` 없이 `<단계 ID> <액션> <대상> 실행` / `실행하지 않음` 두 선택지로 묻는다. (선택지는 2개 이상이어야 한다)
       - 대상이 `-`인 `dialog` 단계는 선택지에 확인 창을 띄우는 앞 단계의 액션·대상을 적는다. (예: `06-15 삭제 확인 창 accept (06-14 click button "삭제") 실행`)
     - 고른 단계는 `실행 승인된 단계`, 고르지 않은 단계는 `실행하지 않을 단계`로 2단계에 넘긴다. 답은 원본 작업계획서 `2. 결정 사항`에 `usecase-do · 준비`로, `선택`에 고른 단계 ID를 쓴다. (하나도 고르지 않았으면 `없음`)
     - 표시가 없는데 실행하다가 되돌리기 어려운 동작으로 보이는 단계는 지금처럼 그 단계에서 멈추고 묻는다. (usecase-runner의 `확인 필요`)
     - AskUserQuestion을 쓸 수 없으면 표시된 단계는 모두 `실행하지 않을 단계`로 넘긴다.
2. Playwright MCP 도구를 쓸 수 있는지 확인한다. 도구가 이름만 보이고 아직 불러오지 않은(deferred) 상태면 ToolSearch로 불러온 뒤 판단한다. (예: `select:<prefix>browser_navigate,<prefix>browser_resize,<prefix>browser_close,…`처럼 메인이 쓸 도구를 한 번에. 직접 실행이면 단계에 쓰이는 도구도 함께) 불러와도 쓸 수 없으면 중단한다.
3. 실행 환경과 계정을 준비한다. usecase 계획서 상단 표에 `환경` 행이 있으면 새 형식, `Base URL` 행이 있으면 예전 형식이다.
   - **새 형식**
     - `ai-work/usecase-env/environment.yaml`을 읽고, `environment.local.yaml`이 있으면 같은 키의 값을 덮어쓴다. 목록(`services`, `login.steps`)은 통째로 바꾼다. `environment.yaml`이 없으면 `/workflow:workflow-usecase-plan`으로 먼저 만들라고 알리고 중단한다.
     - 문서의 `환경` 값에 해당하는 환경의 `web`·`api`·`services`를 쓴다. 그 환경이 없으면 AskUserQuestion으로 어느 환경을 쓸지 묻는다.
     - 두 개인 파일(`environment.local.yaml`, `accounts.yaml`)이 git에서 무시되는지 `git check-ignore -q <파일>`로 확인한다. 무시되지 않으면 `ai-work/usecase-env/.gitignore`(전용 무시 파일, 없으면 만든다)에 그 파일 이름(`environment.local.yaml`, `accounts.yaml`)을 추가한다. 저장소 루트의 `.gitignore`는 고치지 않는다. (7번의 증적 제외 줄과 같이 "검증만 한다" 규칙의 예외다)
     - 계정: 실행 대상 UC의 `계정 역할`(UC에 없으면 `1. 사전 조건`의 계정 역할), `login` 단계의 역할, 단계에 쓰인 `{account.<역할>.id}`·`{account.<역할>.password}`의 역할을 모은다. `없음`·`-`는 역할이 아니다. 모은 역할이 하나도 없으면 `accounts.yaml` 확인을 건너뛴다. 있으면 `accounts.yaml`에서 `<환경>.<역할>.id`·`password`가 채워졌는지 확인한다.
       - 파일이 없으면 위 git 무시 확인을 마친 뒤, 필요한 역할 키와 `<채워 넣기>`만 있는 뼈대를 만든다. 파일 첫 줄에 `# 커밋 금지. 테스트 전용 계정만 쓴다.` 주석을 넣고, 역할 키마다 `environment.yaml`의 `accounts`에 적힌 그 역할의 설명을 주석으로 옮긴다.
       - 비어 있거나 `<채워 넣기>`인 값이 있으면 AskUserQuestion으로 묻는다. 질문 본문에 채울 파일 경로와 역할 키(값은 쓰지 않는다)를 적는다. 선택지: `accounts.yaml을 채웠음, 계속 (Recommended)` / `중단`. 계속을 골랐는데도 비어 있으면 다시 묻지 않고 중단한다. 답은 `usecase-do · 준비`로 기록한다.
   - **예전 형식**
     - `${환경변수명}`은 셸에서 조회한다. (Bash: `printenv 이름` / PowerShell: `$env:이름`) 값이 비어 있으면 어떻게 할지 AskUserQuestion으로 확인한다.
     - `(실행 시 입력)`은 실행 전에 사용자에게 값을 묻는다.
     - 완료 보고에 새 형식(실행 환경 설정 파일)으로 다시 작성하기를 권한다.
4. 실행 시각을 조회한다. 이 값은 증적 디렉토리 이름, `4. 실행 결과` 행, 처음 고치는 `최종 갱신`에 쓴다. 그 밖에는 AskUserQuestion으로 답을 받을 때마다(결정 사항 `일시`)와 UC가 끝날 때마다(`최종 갱신`) 다시 조회한다.
   - Bash: `date '+%y%m%d_%H%M%S %Y-%m-%d %H:%M:%S'`
   - PowerShell: `Get-Date -Format 'yyMMdd_HHmmss yyyy-MM-dd HH:mm:ss'`
5. 서버가 떠 있는지 확인한다. (여기서 중단할 수 있으므로, 증적 디렉토리를 만들고 usecase 계획서를 고치는 7~9번보다 먼저 한다)
   - **새 형식**: 문서의 `필요 서비스`마다 `health` URL을 Bash `curl -s -o /dev/null -w '%{http_code}' --max-time 5 <health URL>`로 확인한다. 응답 코드가 `000`이거나 5xx이면 떠 있지 않은 것으로 본다. 서비스에 `health`가 없으면 환경의 `web` URL로 같은 확인을 한다.
     - 떠 있지 않은 서비스에 `start`가 있으면 AskUserQuestion으로 묻는다. 선택지: `기동 (Recommended)` / `직접 띄운 뒤 계속` / `중단`. `start`가 없으면 뒤의 두 개만 둔다. 답은 `usecase-do · 준비`로 기록한다.
     - `기동`을 고르면 저장소 루트에서 `start` 명령을 백그라운드로 실행하고, `health`가 응답할 때까지 최대 3분 기다린다. 응답이 없으면 실행 출력의 마지막 부분을 보여 주고 어떻게 할지 묻는다.
     - 직접 기동한 서버는 실행이 끝나도 끄지 않고 완료 보고에 알린다.
     - 모두 떠 있으면 `browser_navigate`로 환경의 `web` URL에 접속되는지 확인한다. 서버가 응답하면 접속된 것이다. (루트 경로에 화면이 없어 404 페이지가 떠도 된다. 연결 거부·시간 초과일 때만 접속 실패로 본다) 접속을 확인한 뒤 `browser_console_messages`(`level: error`, `all: true`)로 지금까지의 error 수를 조회해 둔다. 첫 UC의 console error를 셀 때 이 값을 빼는 기준이다. (접속 확인의 404 등이 첫 UC 몫으로 세지지 않게 한다)
   - **예전 형식**: `browser_navigate`로 Base URL에 접속되는지 확인한다. 접속되지 않으면 AskUserQuestion으로 서버 기동 방법/대기 여부를 확인한다.
6. 계획서에 해상도가 있으면 `browser_resize`로 맞춘다.
7. 증적 디렉토리를 만든다. usecase 파일 경로에서 `.md`를 뺀 뒤 `_evidence/<실행 YYMMDD_HHMISS>/`를 붙인 경로다.
   - 예: `ai-work/usecases/261121/153000_add_login_page.md` → `ai-work/usecases/261121/153000_add_login_page_evidence/261122_101500/`
   - 증적은 git에 올리지 않는다. git 저장소이면 디렉토리를 만든 뒤 `git check-ignore -q <증적 디렉토리>`로 확인하고, 무시되지 않는 상태(종료 코드 1)이면 `ai-work/usecases/.gitignore`(전용 무시 파일, 없으면 만든다)에 `*_evidence/` 한 줄을 추가한다. 저장소 루트의 `.gitignore`는 고치지 않는다. (사용자가 고쳐 둔 루트 `.gitignore`와 섞이면 무시 줄을 커밋할 수 없기 때문이다. 이 한 줄 추가는 "검증만 한다" 규칙의 예외다)
   - 계획서와 usecase 문서는 제외하지 않는다.
8. 이전 실행 흔적을 초기화한다. (재실행 대비)
   - 실행 대상 UC의 모든 단계를 `[ ]`로 되돌리고, 이전 실행에서 덧붙인 `→ 실제: ...`를 지운다.
   - 실행 대상이 아닌 UC는 그대로 둔다. 다만 `[~]`가 남아 있으면(중단된 실행의 흔적) `[ ]`로 되돌린다.
   - 이전 실행의 기록(`4. 실행 결과`, `6. 실패 상세`, 증적 디렉토리)은 지우지 않는다.
9. `진행 표시 확인`으로 진행률·진행률 바·UC 제목을 고치고, 상단 표의 작업상태를 `진행`으로, `최종 갱신`을 실행 시각으로 바꾼다. (아직 `[~]`가 없어 스크립트가 작업상태를 `대기`로 낼 수 있다. 이 지적만은 따르지 않는다)

### 2. 단계 실행 (문서에 나온 UC 순서대로, 단계 순서대로)
UC는 번호 순서가 아니라 `3. Usecase`에 나온 순서대로 실행한다. (기존 문서 갱신으로 넣은 UC는 번호가 뒤여도 문서에서는 앞에 있을 수 있다) 단계 실행 규칙(요소 찾기, 액션별 도구, 결과 기록, 실패 처리)은 `${CLAUDE_PLUGIN_ROOT}/agents/usecase-runner.md`의 `단계 실행`·`실패 처리`·`UC를 마칠 때`에 있다. 실행 방법은 둘 중 하나다.

- **agent에 맡기기** (추천): 다음을 모두 만족하면 UC마다 `usecase-runner` agent에 맡긴다. Playwright 응답(화면 구조)이 메인 대화에 쌓이지 않아 UC가 많아도 컨텍스트가 덜 찬다.
  - 실행 대상 UC가 2개 이상이다. (1개면 agent를 띄우는 비용이 더 크고, 실패한 UC만 다시 돌릴 때는 질문이 많다)
  - 새 형식 문서다. (예전 형식의 `(실행 시 입력)` 값을 agent에 넘기지 않기 위해서다)
  - Agent 도구에 이 플러그인의 `usecase-runner` agent가 있다. (목록에 표시된 이름, 보통 `workflow:usecase-runner`)
- **직접 실행**: 위에 해당하지 않으면 `${CLAUDE_PLUGIN_ROOT}/agents/usecase-runner.md`를 Read 해서 `단계 실행`·`실패 처리`·`UC를 마칠 때`를 메인에서 그대로 따른다. agent 입력의 스크린샷 경로 방식은 첫 UC에서 `미확인`으로 시작하고, 정해진 값을 이후 UC에 쓴다. (아래 `프롬프트`와 같다) agent의 `확인 필요`에 해당하는 경우는 그 자리에서 AskUserQuestion으로 묻는다. 추천·선택지와 답에 따른 처리는 아래 `확인 필요`와 같다. (agent를 새로 실행하는 대신 메인이 그 단계부터 이어 간다) 준비 1번에서 정한 `실행하지 않을 단계`는 `단계 실행`의 `실행하지 않을 단계` 규칙대로 다룬다. (`입력`·`돌려줄 것`·agent 전용 절대 규칙은 쓰지 않는다)
- **선행 UC가 통과하지 못했을 때** (두 방법 공통): UC가 끝났는데 통과가 아니고(`[X]`나 `[ ]`가 남음), 남은 실행 대상 중에 그 UC를 `선행:`으로 쓰는 UC가 있으면, 그 UC들을 실행하기 전에 AskUserQuestion으로 한 번 묻는다. 질문 본문에 선행 UC의 실패·미실행 단계와 그 UC에 딸린 UC를 적는다. 선택지는 `건너뜀` / `그래도 실행`이다.
  - 추천: 선행 UC가 남겨야 할 상태를 만드는 단계가 실패했거나 실행되지 않았으면 `건너뜀`에, 상태는 만들어졌고 확인 단계만 실패했으면 `그래도 실행`에 `(Recommended)`를 붙인다. 판단이 서지 않으면 `건너뜀`에 붙인다.
  - `건너뜀`: 딸린 UC(그 UC를 선행으로 쓰는 UC까지 모두)를 실행하지 않고 `[ ]`로 둔다. `4. 실행 결과` 비고에 `UC-03 선행 UC-01 미통과로 실행 안 함`처럼 적는다.
  - 답은 원본 작업계획서 `2. 결정 사항`에 `usecase-do · <선행 UC ID>`로 기록한다. AskUserQuestion을 쓸 수 없으면 건너뛴다.

#### agent에 맡길 때
- **한 번에 하나만 실행한다.** 브라우저가 하나이므로 UC를 동시에 실행하지 않는다. Agent 도구를 포그라운드로 실행하고, 결과를 받은 뒤 다음 UC로 간다. agent가 실행되는 동안 메인은 usecase 계획서와 브라우저를 건드리지 않는다.
- **프롬프트**에는 agent 파일의 `입력` 항목을 넣는다: usecase 계획서 경로, UC ID, 시작 단계, 환경 이름, `web`·`api` URL, 합친 `login` 절차, `accounts.yaml` 경로와 계정 역할, 증적 디렉토리(상대·절대), 스크린샷 경로 방식(첫 UC는 `미확인`, 이후는 앞 UC 결과의 값), 이 UC에 대한 사용자 지시, 실행 승인된 단계와 실행하지 않을 단계(준비 1번). **계정 값은 넣지 않는다.**
- **결과 처리**
  - `통과`·`실패`: 결과의 실패 표와 console error를 모아 둔다. (3. 종료 처리에서 `6. 실패 상세`와 `4. 실행 결과` 비고에 쓴다) console error는 앞 UC 결과와 비교해 새로 생긴 것만 그 UC의 것으로 센다. 결과에 `실행하지 않음: <단계 ID>`가 있으면 `4. 실행 결과` 비고에 `<단계 ID> 사용자 확인으로 실행 안 함`을 적는다.
  - `확인 필요`: 질문을 AskUserQuestion으로 묻는다. (추천안 첫 번째, 답은 원본 작업계획서 `2. 결정 사항`에 `usecase-do · <단계 ID>`로 기록) 답에 따라 다음 중 하나를 한다.
    - **추천은 메인이 정한다.** agent는 원본 작업계획서의 정의 표를 보지 않으므로 agent가 붙인 추천을 그대로 쓰지 않는다. 대상 이름이나 화면 동작이 usecase 계획서와 다르면 원본 계획서의 `### 화면 변경`·`### API 변경` 정의와 대조한다.
      - 실제 화면이 정의와 같으면 usecase 문서 쪽 오류다. `대상(또는 기대결과)을 실제대로 고치고 계속`을 추천한다.
      - 실제 화면이 정의와 다르면 구현 버그다. 실패로 기록하는 쪽을 추천한다. (이름만 고치고 계속하면 버그가 통과로 바뀐다) agent의 근거로 보아 그 단계의 동작은 수행됐고 문구·표시만 달라 뒤 단계의 선행 조건이 그대로면 `실패로 기록하고 다음 단계부터 계속`을, 선행 조건이 깨졌거나 알 수 없으면 `실패로 기록하고 이 UC를 끝냄`을 추천한다.
      - 정의에 없는 요소·동작이면 추천 없이 묻고, 질문 본문에 정의에 없다는 것을 적는다. 선택지에 `미실행으로 두고 이 UC를 끝냄`을 넣는다. (원본 계획서에서 아직 `(미결)`인 내용을 다루는 단계처럼 지금 정할 수 없는 경우다)
      - 되돌리기 어려운 동작이면 `실행하지 않음`을 추천한다.
    - 선택지는 상황에 맞는 것을 4개까지 고른다: `<고칠 내용>대로 고치고 계속` / `실패로 기록하고 다음 단계부터 계속` / `실패로 기록하고 이 UC를 끝냄` / `미실행으로 두고 이 UC를 끝냄`(되돌리기 어려운 동작이면 `실행` / `실행하지 않음`). agent가 실패 뒤 계속할지를 물은 경우(멈춘 단계가 이미 `[X]`)는 실패로 기록하는 두 선택지만 낸다.
    - 지시대로 계속: 같은 UC를 `시작 단계`를 결과의 `재개 단계`로 하고 지시(또는 실행 승인)를 넣어 agent를 **새로** 실행한다. 되돌리기 어려운 동작의 실행을 승인받았으면 멈춘 단계와 그 확인 창 `dialog` 단계를 `실행 승인된 단계`로 넘긴다.
    - 실패로 기록: 메인이 멈춘 단계를 `[X]`(`→ 실제:`에 사유)로 바꾸고, `browser_take_screenshot`으로 `<증적 디렉토리>/<단계ID>_fail.png`를 남긴다. (agent가 돌려준 뒤라 메인이 브라우저를 써도 된다. agent가 이미 `[X]`로 기록한 단계는 그대로 둔다)
      - 다음 단계부터 계속: 같은 UC를 `시작 단계`를 그다음 단계로 해서 agent를 **새로** 실행한다.
      - 이 UC를 끝냄: 남은 단계를 `[ ]`(미실행)로 두고, 아래 `메인이 UC를 끝낼 때`를 한 뒤 다음 UC로 간다.
    - 미실행으로 두고 끝냄 · 실행하지 않음: 메인이 그 단계와 남은 단계를 `[ ]`(미실행)로 되돌리고, `4. 실행 결과` 비고에 `<단계 ID> 사용자 확인으로 실행 안 함`을 적는다. 확인 창이 열려 있으면(agent가 `상황`에 적는다) `browser_handle_dialog`를 `accept: false`로 닫는다. `accept`로 닫지 않는다. `메인이 UC를 끝낼 때`를 한 뒤 다음 UC로 간다.
    - **메인이 UC를 끝낼 때**: agent가 `UC를 마칠 때`를 하지 않았으므로, 메인이 `browser_console_messages`를 `level: error`, `all: true`로 조회해 그 수를 이 UC의 결과로 둔다. (`(기대한 응답)` 표시는 usecase-runner `UC를 마칠 때` 1번과 같이 한다) (하지 않으면 이 UC의 error가 다음 UC의 것으로 세어진다) 진행 표시는 다음 UC의 agent나 종료 처리 3이 고친다.
  - `실행 불가`: agent는 파일을 고치지 않았다. 사유를 알리고, 이 UC부터 남은 UC를 **직접 실행**으로 바꿔 진행한다.
  - 결과 형식이 아니거나 agent가 중간에 실패했으면, 계획서에서 그 UC의 `[~]` 단계를 확인해 그 단계부터 직접 실행으로 이어 간다.

### 3. 종료 처리
1. 각 UC가 끝날 때의 console error(직접 실행은 `UC를 마칠 때`에서 `browser_console_messages`를 `level: error`, `all: true`로 조회하고, agent는 결과로 돌려준다)를 앞 UC 때(첫 UC는 준비 5번 접속 확인 뒤 조회해 둔 값)와 비교한다. 직전 조회 이후 새로 생긴 error가 있으면 `4. 실행 결과`의 비고에 `UC-02 console error 1건`처럼 적는다. 새로 생긴 error 중 `(기대한 응답)`이 붙은 것(usecase-runner `UC를 마칠 때` 1번. UC가 일부러 받은 4xx 응답)은 세지 않고 `UC-02 console error 1건 (기대한 응답 6건 제외)`처럼 따로 적는다. 기대한 응답만 있으면 `UC-02 기대한 응답 6건 외 console error 없음`으로 적는다. 계획서에 `console` 단계가 없으면 이것만으로 단계를 실패 처리하지 않는다.
2. 전체 실행이 끝나면 `browser_close`로 브라우저를 닫는다.
3. `진행 표시 확인`으로 전체진행률·진행률 바·UC 제목·작업상태를 확정한다. 완료가 아니면 작업상태를 `진행 (실패 N건, 미실행 M건)`으로 쓴다. (N은 `[X]` 수, M은 `[ ]` 수. 스크립트 출력의 개수를 쓴다)
4. `4. 실행 결과` 표에 한 행을 추가한다. 통과/실패/미실행은 이번 실행 대상 UC의 단계 수다.

```markdown
| YYYY-MM-DD HH:MI:SS | 전체 (또는 UC-01,UC-03) | N | N | N | `..._evidence/YYMMDD_HHMISS/` / 실패: 02-03, UC-02 console error 1건 |
```

5. 실패한 단계가 있으면 `## 6. 실패 상세` 섹션에 이번 실행을 기록한다. 섹션이 없으면 `5. 작업 이력` 아래에 만들고, 있으면 그 섹션 끝에 이번 실행(`### 실행일시`)만 추가한다.

```markdown
## 6. 실패 상세

### YYYY-MM-DD HH:MI:SS 실행
| 단계 | 기대결과 | 실제결과 | 추정 원인 | 증적 |
|------|----------|----------|-----------|------|
| 02-03 | ... | ... | ... | `02-03_fail.png` |
```

6. `5. 작업 이력`에 실행 이력을 한 행 추가한다.
   - 내용: 실행 대상, 통과/실패/미실행 단계 수, 실행 중 고친 대상 이름 수, 해소한 `(가정)` 수, 증적 경로
   - 예: `실행: 전체 / 통과 12, 실패 1, 미실행 2 / 대상 수정 1건, (가정) 해소 3건 / 153000_add_login_page_evidence/261122_101500/`
7. 원본 작업계획서에 반영한다. (상단 표의 `원본 작업계획서`)
   - `2. 작업계획서 매핑`에서 이번에 통과한 UC(모든 단계가 `[V]`)가 가리키는 항목 ID를 찾는다. 매핑 칸에서 ID(`1.2`, `DoD-1`)만 읽는다. `-`와 괄호 안 설명은 항목이 아니다.
   - 그 항목을 검증하는 UC가 **모두** 통과 상태이고 원본 계획서에서 아직 `[V]`가 아닌 항목만 고른다. 통과 상태는 usecase 계획서의 지금 표기로 본다. (이번 실행 대상이 아닌 UC도 모든 단계가 `[V]`면 통과 상태다)
   - 고른 항목이 이번 실행 대상이 아닌 UC의 통과(이전 실행 결과)에 기대면, 그 통과가 지금 코드에서도 맞는지 확인한다. 그 UC마다 마지막 실행일시(`4. 실행 결과`에서 `대상`이 `전체`이거나 그 UC를 포함한 마지막 행)를 찾고, git 저장소이면 `ai-work/`가 있는 디렉토리에서 `git log --since='<실행일시>' --format='%h %s' -- . ':(exclude)ai-work' ':(exclude).gitignore'`로 그 뒤에 애플리케이션 소스를 바꾼 커밋이 있는지 본다. (`ai-work/`와 `.gitignore`는 이 커맨드가 스스로 커밋하므로 뺀다) 커밋이 있으면 그 통과는 고치기 전 코드의 결과다.
   - 매핑된 ID가 원본 계획서에서 취소·병합됐거나, 없거나, `(미결)`이면 `[V]`로 제안하지 않는다. 매핑을 직접 고치지도 않는다. (매핑은 `workflow-usecase-plan`의 기존 문서 갱신이 맡는다) 완료 보고에 알린다.
   - 브랜치 불일치로 계속한 실행이면 이 반영을 건너뛰고 `usecase` 요약 행에 그 사실만 남긴다.
   - 고른 항목을 `[V]`로 바꿀지 AskUserQuestion으로 확인한다. 질문 본문에 항목마다 검증한 UC와 그 UC가 통과한 실행일시를 적는다. 답은 `usecase-do · 반영`으로 기록한다.
     - 검증 UC가 모두 이번 실행에서 통과한 항목, 이전 실행에 기대지만 그 뒤 소스 커밋이 없는 항목: `[V]`로 반영 (Recommended) / `반영하지 않음`
     - 이전 실행에 기대고 그 뒤 소스 커밋이 있는 항목: 위 항목과 따로 묻는다. 질문 본문에 그 커밋(해시·제목, 많으면 3개와 개수)을 적고 `반영하지 않음 (Recommended)` / `[V]`로 반영. 반영하지 않으면 완료 보고에 그 UC들을 다시 실행(`UC-xx,UC-yy` 또는 전체)하면 반영된다고 안내한다.
   - 반영할 때는 항목을 `[V]`로 바꾼 뒤 원본 계획서에 `진행 표시 확인`을 실행해 진행률과 작업상태를 고치고, 바꾼 항목마다 `8. 작업 이력`에 구분 `항목`으로 한 행을 남긴다. (예: `DoD-1 확인 — UC-01 통과 (<usecase 경로>)`)
   - 원본 계획서에서 이미 `[V]`인 항목을 검증하는 UC가 실패했으면(회귀) 그 항목의 상태는 바꾸지 않는다. 완료 보고와 아래 `usecase` 행에 적는다.
   - 반영 여부와 상관없이 `8. 작업 이력`에 구분 `usecase`로 이번 실행을 요약한 한 행을 남긴다. (예: `usecase-do: 전체 / 통과 UC 3, 실패 UC 1 (회귀: 2.1) / <usecase 경로>`)
   - 원본 계획서의 `진행 관리 규칙`에 1.5.0 전 커밋 예외 줄이 있으면 `workflow-usecase-plan` 6단계와 같이 그 줄만 템플릿 줄로 바꾸고 이력을 남긴다. (`8. 작업 이력` 표가 없으면 완료 보고에 적는다)
   - 반영으로 원본 계획서의 작업상태가 `완료`가 됐고, 원본 계획서 `### 요구사항 문서`의 경로가 `ai-work/roadmaps/` 아래 업무 파일이면 로드맵 README도 갱신한다. 그 업무 파일 상단 표의 `로드맵` README에서 `계획서` 칸이 원본 계획서인 행을 README의 `로드맵 관리 규칙`대로 `완료`로 바꾸고, 상단 표와 `5. 작업 이력`(구분 `업무 완료`)을 고친다. README가 작업 트리에 없거나 그런 행이 없으면 고치지 않고 완료 보고에 적는다.
8. 커밋한다. git 저장소가 아니거나 원본 작업계획서의 `커밋 방식`이 `해당 없음`이면 건너뛴다. (이 커밋은 "검증만 한다" 규칙의 예외다. 애플리케이션 소스는 커밋 대상이 아니다) 이 단계의 기본 브랜치는 `git symbolic-ref --short refs/remotes/origin/HEAD`(앞의 `origin/`을 뗀다)가 가리키는 브랜치(없으면 로컬 브랜치 중 `main` → `master` → `develop` 순서로 처음 있는 것)와, 있으면 `develop`이다. (`workflow-plan` 1단계와 같은 기준)
   - 커밋할 수 있는 파일에 실행 전부터 미커밋 변경이 있었는지는 준비 1의 `실행 전 미커밋 변경 확인` 결과로 본다. (파일 단위로 스테이징되므로, 사용자가 고쳐 둔 내용도 함께 들어간다)
   - Playwright MCP는 작업 루트에 `.playwright-mcp/`(화면 구조·console 로그 파일)를 만든다. `git status --short`에 `.playwright-mcp/`가 미추적으로 보이면 `git rev-parse --git-path info/exclude`가 가리키는 파일(이 PC에서만 쓰는 git 무시 목록, 커밋되지 않는다)에 `/<저장소 루트 기준 경로>/` 한 줄(루트에 있으면 `/.playwright-mcp/`)을 추가한다. Playwright MCP를 쓰는 PC마다 생기는 도구 파일이라 커밋할 무시 줄이 아니다. (증적 제외 줄과 같은 예외다. 지우지는 않는다)
   - 원본 작업계획서 상단 표의 `커밋 방식`을 따른다. 값이 없거나 원본 계획서를 읽을 수 없으면 `확인`으로 본다.
     - `자동`: 묻지 않고 커밋한 뒤 `커밋 <해시> <제목>` 한 줄로 알린다. 스테이징할 파일에 실행 전부터 미커밋 변경이 있었어도 묻지 않고 아래 질문의 추천대로 처리한다. 그 파일(usecase 계획서, 원본 작업계획서, 로드맵 README, 전용 무시 파일)을 함께 커밋한다. 알리는 줄은 모든 workflow 커맨드가 같은 형식이다: `커밋 <해시> <제목>`에 해당하는 것을 `(실행 전 변경 포함: <파일>)`(사용자 변경)·`(이전 실행분 포함: <파일>)`로 붙인다. (아래 스테이징 줄의 구분) (커밋하지 못하면 `커밋 안 함 — <사유>`) 완료 보고에도 적는다. 브랜치 불일치로 계속한 실행이거나 작업 브랜치가 기본 브랜치일 때만 질문 본문 첫 줄에 그 사유(`작업 브랜치가 기본 브랜치(<이름>)라 커밋마다 확인합니다`)를 적고 아래 `확인`과 같은 질문·선택지·기록으로 묻는다.
     - `확인`·`끝에 한꺼번에`: AskUserQuestion으로 묻는다.
   - 질문: 선택지는 커밋 메시지 초안을 보여 주고 커밋 / 커밋하지 않음. 평소에는 커밋을 첫 번째에 두고 `(Recommended)`를 붙인다.
     - 브랜치 불일치로 계속한 실행이면 질문 본문에 현재 브랜치가 작업 브랜치와 다르다는 것을 적고, `커밋하지 않음`을 첫 번째에 두고 `(Recommended)`를 붙인다.
     - 스테이징할 파일에 실행 전부터 미커밋 변경이 있었으면 질문 본문에 그 파일과, 그 변경도 함께 커밋된다는 것을 적는다. (파일 단위로 스테이징하기 때문이다) 선택지와 추천은 바꾸지 않는다. (브랜치 불일치이면 위 줄대로 `커밋하지 않음`이 추천이다)
     - 답은 원본 작업계획서 `2. 결정 사항`에 `usecase-do · 커밋`으로 기록한 뒤 커밋한다. (그 행도 같은 커밋에 들어간다) 물어서 커밋했어도 커밋한 뒤 `자동`과 같은 알리는 줄로 알린다. (`커밋하지 않음`이면 `커밋 안 함 — 사용자 선택`)
   - usecase 계획서, 이번 실행에서 고친 원본 작업계획서, 7번에서 고친 로드맵 README, 전용 무시 파일(`ai-work/usecase-env/.gitignore`, `ai-work/usecases/.gitignore`) 중 이번 실행에서 만들거나 줄을 추가한 것과, 이번에 고치지 않았어도 미추적이거나 수정 상태인 것만 스테이징한다. (뒤의 것은 이전 실행이 커밋하지 못하고 남긴 무시 줄이다. 그대로 두면 `check-ignore`가 작업 트리의 파일로 통과해 어느 커맨드도 다시 커밋하지 않는다) 준비 1에서 미커밋 변경이 있던 파일이면 알리는 줄에 넣는다. 미추적이거나 새로 추가만 된(`??`·`A `) 전용 무시 파일·usecase 계획서는 앞선 실행이 만들고 커밋하지 못한 것이므로 `(이전 실행분 포함: <파일>)`에, 원본 작업계획서는 diff가 workflow 커맨드가 남긴 기록(`8. 작업 이력` 행, 단계가 workflow 커맨드인 결정 사항 행과 그 답으로 고친 곳)뿐이면 `(이전 실행분 포함: …)`에, 그 밖의 변경이 있으면 `(실행 전 변경 포함: <파일>)`에 넣는다. 둘 다 있으면 두 표시를 함께 붙인다. 앞선 실행이 사용자 변경을 적어 둔 행(`리뷰 전 미커밋 변경 있음 — …` 등)이 `사용자 변경`으로 적은 변경은 사용자 변경이다. (`workflow-do` 준비 2번과 같은 방법. 사용자 변경이 함께 커밋됐다는 것이 이전 실행분에 묻히지 않게 한다) (`git add -A` 쓰지 않음) 증적 디렉토리, 애플리케이션 소스, `environment.local.yaml`, `accounts.yaml`은 넣지 않는다.
   - 메시지: 제목은 프로젝트 규칙(CLAUDE.md 등)의 커밋 형식이 있으면 그것을 따르고, 없으면 `docs(usecase): usecase 실행 결과 (통과 N, 실패 N, 미실행 N)`으로 쓴다. 프로젝트 형식에 type·모듈 같은 분류 자리가 있으면 그 프로젝트가 문서 변경에 쓰는 값(`docs`, `[docs]` 등)을 쓰고(정해진 값이 없으면 `docs`), 설명은 위 기본 제목의 설명 부분을 쓴다. 본문 끝 줄 `Plan: <원본 작업계획서 경로>`는 프로젝트 형식이 있어도 붙인다. (프로젝트 규칙이 본문 형식을 따로 정해 막는 경우만 뺀다)
   - 커밋이 실패하면(훅 실패 등) `--no-verify`로 우회하지 않고 원인을 알린다. 이번에 스테이징한 파일은 `git restore --staged -- <경로...>`로 스테이징을 되돌린다. (작업 트리는 그대로다) `자동`이고 작업 브랜치가 기본 브랜치가 아니면, 문서에서 고칠 수 있는 문제(훅이 지적한 포맷 등)는 고쳐 한 번 다시 커밋하고, 다시 실패하면 커밋하지 않고 완료 보고에 원인과, 원인을 고친 뒤 직접 커밋하는 명령(`git add -- <파일...> && git commit -m "<제목>" -- <파일...>`)을 적는다.
   - push는 하지 않는다.

## 완료 보고
- 실행한 usecase 계획서 경로와 실행 대상
- 실행 방법 (`usecase-runner` agent / 직접 실행). agent가 `실행 불가`여서 직접 실행으로 바꿨으면 그 사유
- UC별 결과 (통과/실패/미실행)
- 전체진행률과 작업상태
- 실패 항목 요약과 추정 원인, 증적 경로
- 실행 중 계획서 내용을 고친 것(대상 요소 이름 등)이 있으면 그 목록
- 전용 무시 파일에 증적 제외 줄·개인 설정 파일 줄을, `.git/info/exclude`에 `.playwright-mcp/` 줄을 추가했으면 그 사실
- 사용한 환경(새 형식이면 환경 이름, 예전 형식이면 Base URL), `accounts.yaml` 뼈대를 만들었으면 그 사실
- 직접 기동한 서버가 있으면 그 서비스 이름과 명령 (실행 중으로 남아 있다)
- 커밋 여부 (커밋했으면 커밋한 파일, 하지 않았으면 미커밋으로 남은 문서)
- 로드맵 README를 `완료`로 갱신했으면 그 업무 번호와 `/workflow:workflow-roadmap @<README>`로 다음 업무를 확인하라는 안내
- 원본 계획서에 반영한 항목, 회귀(이미 `[V]`인 항목의 UC 실패), 매핑 ID가 취소·병합·미결이라 반영하지 못한 항목 (있으면 `/workflow:workflow-usecase-plan`으로 기존 문서 갱신을 권한다)
- 실패가 있으면 수정 방법을 안내한다: `/workflow:workflow-do @<원본 계획서> <수정 지시>`로 고친 뒤(계획에 없는 수정이면 새 작업항목으로 추가된다) `/workflow:workflow-usecase-do @<usecase 경로> UC-xx`로 실패한 UC만 재실행한다. 이때 함께 알린다.
  - 그 UC에 `선행:`이 있으면 선행 UC도 함께 실행해야 할 수 있다. (재실행 때 묻는다) `1. 사전 조건`의 테스트 데이터에 적힌 대로 다시 실행하기 전 상태를 먼저 맞춘다.
  - 소스를 고치면 이전 실행에서 통과한 UC의 결과만으로는 원본 계획서 항목 반영을 추천하지 않는다. 여러 UC가 검증하는 항목은 그 UC들을 함께 재실행한다.
