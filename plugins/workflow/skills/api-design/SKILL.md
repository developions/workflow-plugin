# api-design

API 변경을 **설계**하거나 **점검**할 때 쓰는 기준과 결과 형식이다.

## 입력

```
$ARGUMENTS
```

- 모드: `설계`(기본), `점검 계획`, `점검 구현`. 인자가 없으면 `설계`, `점검`만 있으면 `점검 계획`으로 본다.
  - `점검 계획`: 계획서의 정의를 요구사항·현재 코드와 대조한다. (`workflow-plan-review`가 쓴다)
  - `점검 구현`: 구현 결과를 계획서의 정의와 대조한다. (`workflow-do`가 쓴다)
- `@경로`나 경로가 있으면 그 작업계획서를 대상으로 한다. 이미 대화에서 읽은 계획서면 다시 읽지 않는다.
- 커맨드가 이 파일을 Skill 도구 대신 직접 읽은 경우(위 입력 칸이 치환되지 않은 글자 그대로 보인다) 모드는 그 커맨드가 Skill 도구에 넘기려던 인자다.

## 이 skill의 범위

이 skill은 절차가 아니라 **기준**이다. 불러온 쪽(커맨드나 사용자 요청)의 흐름 안에서 쓴다.

- 파일을 만들거나 고치지 않는다. 브랜치·커밋을 다루지 않는다. 완료 보고를 하지 않는다.
- 실제 서버에 요청을 보내지 않는다.
- **커맨드가 불렀을 때**: 사용자에게 직접 묻지 않는다. 정해지지 않은 것은 `미정 사항`으로 모아 돌려준다. 질문, 결정 사항 기록, 계획서 작성은 부른 커맨드가 한다.
- **커맨드 없이 불렸을 때**(대화에 진행 중인 workflow 커맨드가 없음): 결과를 대화에 보여 주기만 한다. 미정 사항은 결과 끝에 목록으로 보여 준다.

## 1. 기존 관례 찾기 (설계 모드)

새로 정하기 전에 현재 프로젝트가 어떻게 하고 있는지 먼저 찾는다. 찾은 관례는 근거(`path:line`)와 함께 결과의 `따른 관례`에 적는다. 점검 모드는 이 단계를 하지 않고 계획서의 `따른 관례`를 재사용한다. (3번 참고) 설계 모드라도 계획서에 이 정의의 `따른 관례`가 이미 있으면(정의를 다시 쓸 때) 처음부터 찾지 않고, 점검 모드처럼 근거 위치만 열어 확인하고 재사용한다. 새 설계에 필요한데 그 줄에 없는 관례(예: 처음 만드는 목록 API의 페이지네이션)만 아래대로 찾는다.

**어디서 찾나**
- 컨트롤러·라우터·핸들러, 공통 응답 클래스, 전역 예외 처리기(`@ControllerAdvice`, 오류 미들웨어 등)
- API 문서(OpenAPI·Swagger 설정과 어노테이션, `.http` 파일, Postman 컬렉션)
- API를 부르는 쪽(프런트엔드 API 모듈, 다른 서비스의 클라이언트)

**무엇을 찾나**
- URL: 접두어와 버전(`/api/v1`), 자원 이름(단수/복수, kebab-case 등), 행위를 나타내는 방식
- 메서드 사용: 수정에 `PUT`/`PATCH` 중 무엇을 쓰는지, 삭제 방식
- 요청·응답: 필드 네이밍(camelCase 등), 공통 응답 형식(`{code, message, data}` 등), 날짜·시각 형식과 타임존, 빈 값 표현(`null` / 생략 / 빈 배열)
- 성공 상태 코드: 생성 시 `200`/`201`, 본문 없는 응답의 `204`
- 오류: 오류 응답 형식, 오류 코드 체계, 검증 오류의 필드별 메시지 형식
- 목록: 페이지네이션(page/size, offset/limit, cursor)과 응답 메타, 정렬·필터 파라미터 표기
- 인증·권한: 방식(세션, JWT 등), 권한 검사 위치(어노테이션, 필터, 서비스)
- 입력 검증 방식(Bean Validation, 스키마 검증 라이브러리 등)
- API 문서를 코드와 함께 고치는지

관례가 서로 다르면 가장 최근 코드와 다수를 따른다. 관례를 찾지 못하면 그 프레임워크에서 흔히 쓰는 기본값을 제안하고 그대로 쓴다. 두 경우 모두 `따른 관례`에 근거(관례를 찾지 못했으면 `(기본값)`)와 함께 적는다. 이것만으로는 묻지 않는다. 묻는 기준은 `4. 결과 형식`의 `미정 사항`을 따른다.

## 2. 설계 모드

계획서(또는 대화)에 `### DB 변경` 정의가 있으면 **먼저 읽는다.** 응답 필드의 타입·NULL 여부·길이를 컬럼 정의와 맞춘다. DB도 바뀌는데 정의가 아직 없으면 `workflow:db-design`을 먼저 하도록 부른 쪽에 알린다.

요구사항(과 선택한 설계안)에서 아래 순서로 정한다. 변경과 관계있는 단계만 한다. (예: 기존 엔드포인트 응답에 필드 하나 추가면 4·8·10만)

1. **엔드포인트 목록**: 메서드, URL, 설명, 신규/변경/삭제 구분
2. **인증·권한**: 누가 부를 수 있는가. 본인 데이터만 다루는지, 역할 제한이 있는지, 검사 위치
3. **요청**: path·query·body 필드별 타입, 필수 여부, 검증 규칙(길이, 범위, 형식, 허용 값)
4. **응답**: 성공 상태 코드와 응답 스키마. 민감한 필드(비밀번호, 내부 식별자, 개인정보)가 나가지 않는지
5. **오류**: 상태 코드, 오류 코드, 발생 조건. 최소한 검증 실패, 인증 없음, 권한 없음, 대상 없음, 업무 규칙 위반(충돌)을 다룬다
6. **목록 API**: 페이지네이션, 정렬, 필터, 최대 건수
7. **멱등성·동시성**: 같은 요청이 두 번 와도 안전한가(재시도, 중복 클릭). 동시에 수정할 때 처리(낙관적 잠금 등)
8. **하위 호환** (기존 API를 바꿀 때)
   - 호환되는 변경: 응답 필드 추가, 선택 요청 필드 추가
   - 호환되지 않는 변경: 필드 삭제·이름 변경·타입 변경, 필수 요청 필드 추가, URL·메서드·상태 코드·오류 코드 변경
   - 조건부: 요청 검증 강화(길이·형식·범위·허용 값이 좁아져 전에 통과하던 요청이 기존 오류 코드나 새 오류 코드로 거부됨), 새 상태 코드·오류 코드 추가. 판단은 호출부마다 한다.
     - 호환: 호출부가 이제 거부될 요청을 보내지 않는다(같은 검증을 이미 하는 등) / 거부 응답을 다른 오류와 같은 방식으로 사용자에게 보여 준다(기존 코드든 새 코드든)
     - 호환되지 않음: 호출부가 그 응답을 처리하지 못한다(특정 코드만 분기, 성공을 전제로 다음 동작을 함) / 바로 업데이트되지 않는 클라이언트(앱, 외부 시스템)가 이제 거부될 요청을 자동으로 보낸다
     - 판단한 근거(호출부 위치)를 `하위 호환` 칸이나 비고에 적는다
     - 저장소 밖 호출부(다른 서비스, 앱, 외부 시스템)를 확인할 수 없으면 저장소 안 호출부로 판단하고 `(외부 호출부 미확인)`을 붙인다. 이 표시는 리스크 후보로도 돌려준다
   - 호환되지 않거나 조건부이면 그 API를 부르는 곳을 모두 찾아 적고, 새 버전 추가 / 병행 기간 / 동시 배포 중 어떻게 할지 정한다
   - 호환되지 않는 변경이면 부르는 쪽(다른 팀, 외부 클라이언트, 앱처럼 바로 업데이트되지 않는 클라이언트)에 언제 어떻게 알릴지 정한다
9. **성능**: 응답 크기, N+1 조회, 무거운 조회의 캐시·비동기 필요 여부
10. **영향받는 코드**: 컨트롤러·서비스·DTO, 호출부(프런트엔드, 다른 서비스), API 문서, 테스트

**돌려줄 것**
- `### API 변경` 초안 (아래 결과 형식)
- 미정 사항 목록
- 작업항목 후보: 엔드포인트 단위로 나누고, 호출부 수정·API 문서 갱신·테스트도 항목으로 낸다. 부르는 쪽이 다른 서비스·팀이거나 하위 호환이 중요하면 계약 테스트(consumer contract test)도 항목으로 낸다.
- 완료 기준 후보(엔드포인트별 정상·오류 응답 확인)와 리스크(하위 호환, 배포 순서, 부르는 쪽 알림)

## 3. 점검 모드

**관례는 처음부터 다시 찾지 않는다.** 계획서 `### API 변경`의 `따른 관례`를 기준으로 쓰고, 적힌 근거 위치를 열어 아직 그대로인지만 확인한다. `따른 관례`가 없거나(예전 계획서) 근거가 바뀌었거나 사라진 항목만 1번대로 찾는다. 계획 점검에서 `따른 관례`가 실제 코드와 다르면 그것도 지적한다.

대상은 인자로 정한다.
- **계획 점검**(`점검 계획`): 계획서의 `### API 변경`을 요구사항·현재 코드와 대조한다. 아래 표에서 `구현 일치`를 뺀 모든 행을 본다.
- **구현 점검**(`점검 구현`): 구현된 컨트롤러·DTO·예외 처리를 계획서의 `### API 변경`과 대조한다. `관례`와 `구현 일치` 행만 본다. 부른 쪽이 작업항목을 알려 주면 그 항목이 다루는 정의만 보고, 아직 구현하지 않은 정의는 지적하지 않는다.

| 점검 | 볼 것 |
|------|-------|
| 정의 누락 | API가 바뀌는 계획인데 `### API 변경`이 없다. 요구사항에 필요한 엔드포인트가 표에 없다 |
| 관례 | URL, 필드 네이밍, 응답 형식, 상태 코드, 페이지네이션이 `따른 관례`와 다르다 |
| 요청·응답 | 필수 여부·검증 규칙이 없다. 응답 필드가 `### DB 변경`의 컬럼과 맞지 않는다. 민감한 필드가 나간다 |
| 오류 | 오류 코드와 조건이 없다. 검증 실패·권한 없음·대상 없음 중 빠진 것이 있다 |
| 인증·권한 | 권한이 정해지지 않았다. 본인 데이터 확인이 빠졌다 |
| 하위 호환 | 호환되지 않는 변경인데 호출부와 대응 방법, 부르는 쪽 알림이 없다. 요청 검증 강화나 새 상태·오류 코드 추가를 근거(호출부 위치) 없이 `호환`으로 적었다 |
| 멱등성·동시성 | 중복 요청·동시 수정에 대한 처리가 없다 |
| 검증 가능성 | URL·메서드·상태 코드가 구체적이지 않아 usecase의 `network` 단계 기대값으로 쓸 수 없다 |
| 작업항목 연결 | 표의 엔드포인트 중 작업항목이 다루지 않는 것이 있다. 호출부·문서 수정 항목이 없다 |
| 구현 일치 (구현 점검) | URL·메서드·인증·권한·요청/응답 필드·검증 규칙·상태 코드·오류 코드가 표와 다르다. 표에 없는 엔드포인트가 있다 |

**돌려줄 것**: 지적 목록과 미정 사항. 지적이 없으면 `지적 없음`.

```markdown
| # | 점검 | 심각도 | 지적 | 근거 | 제안 |
|---|------|--------|------|------|------|
| 1 | 오류 | 중간 | 잠긴 계정으로 로그인할 때의 오류 코드가 없다 | `### API 변경` 1번 | `423 ACCOUNT_LOCKED` 추가 |
```

심각도: 높음(보안 문제, 기존 호출부가 깨짐) / 중간(오류 처리·검증 누락) / 낮음(관례·표기)

## 4. 결과 형식

### `### API 변경` (계획서 `4. 영향 범위` 아래 하위 섹션)

섹션 제목은 `### API 변경` 그대로 쓴다. 다른 커맨드가 이 제목으로 찾는다.

**변경 규모에 맞게 쓴다.** 아래 예시는 가장 큰 경우의 형식이다.
- 해당 없는 표·줄은 빼고, 빈 표를 남기지 않는다.
- 신규 엔드포인트는 요청·응답·오류 표를 모두 쓴다. 기존 엔드포인트 변경은 바뀐 필드·코드만 표에 쓴다.
- `sequenceDiagram`은 여러 호출·서비스에 걸친 흐름일 때만 넣는다.
- `따른 관례`는 줄이지 않는다. 이 설계에 쓴 관례를 근거(`path:line`, 기본값이면 `(기본값)`)와 함께 모두 적는다. 찾아봤지만 없는 것은 `<항목> 없음 (찾은 범위)`로 적는다. (예: `API 문서 없음 (OpenAPI·.http 파일 없음)`) 점검 모드가 이 줄을 재사용한다.

```markdown
### API 변경

- 따른 관례: 접두어 `/api/v1`, 공통 응답 `{code, message, data}`, 오류는 `GlobalExceptionHandler` (`GlobalExceptionHandler.java:20`)

| # | 구분 | 메서드 | URL | 설명 | 인증·권한 | 하위 호환 |
|---|------|--------|-----|------|-----------|-----------|
| 1 | 변경 | POST | `/api/v1/auth/login` | 로그인 (실패 횟수 제한 추가) | 없음 | 조건부 → 비호환 (423 추가, `auth.ts:31`이 처리 못 함) |
| 2 | 신규 | POST | `/api/v1/admin/members/{id}/unlock` | 계정 잠금 해제 | ADMIN | - |

#### 1. POST `/api/v1/auth/login`

**요청**
| 위치 | 필드 | 타입 | 필수 | 검증 | 설명 |
|------|------|------|------|------|------|
| body | loginId | string | Y | 4~20자 | 아이디 |
| body | password | string | Y | 8~64자 | 비밀번호 |

**응답 (200)**
| 필드 | 타입 | NULL | 설명 |
|------|------|------|------|
| data.accessToken | string | N | 접근 토큰 |

**오류**
| 상태 | 오류 코드 | 조건 |
|------|-----------|------|
| 400 | VALIDATION_ERROR | 필수 값 누락, 형식 오류 |
| 401 | LOGIN_FAILED | 아이디 또는 비밀번호 불일치 (남은 횟수 포함) |
| 423 | ACCOUNT_LOCKED | 5회 실패로 잠긴 계정 |

- 비고: 멱등하지 않음(실패 횟수 증가). 기존 클라이언트는 423을 모르므로 호출부 `auth.ts:31` 수정 필요
```

- 호출 순서가 중요하면(인증 흐름, 여러 서비스 호출) Mermaid `sequenceDiagram`을 함께 넣는다.
- 변경된 엔드포인트는 바뀐 필드·코드에 `(추가)`, `(변경: 이전 → 이후)`, `(삭제)`를 붙인다.

### 미정 사항

코드·요구사항·관례(또는 기본값)로 정할 수 없고, 아래 중 하나에 해당하는 것만 넣는다. 필드 이름·URL 표기처럼 관례나 기본값으로 정할 수 있는 것은 넣지 않는다.
- 되돌리기 어렵다: 이미 쓰이는 API의 URL·필드·상태 코드·오류 코드 변경 (하위 호환이 깨지는 것)
- 업무 규칙이다: 누가 부를 수 있는가(권한), 중복 요청을 어떻게 처리할지, 목록 최대 건수·조회 기간 상한
  - 최대 건수·기간 상한은 외부 호출부가 있거나 사용자 입력이 조회 범위를 정할 때만 넣는다. 저장소 안 화면만 고정된 범위(하루, 한 페이지 등)로 부르는 API의 방어용 상한은 그 범위에 맞춰 기본값으로 정한다.
- 다른 팀·시스템에 영향을 준다: 다른 팀·외부 클라이언트가 부르는 API
- 관례가 없어서 이 계획이 프로젝트 전체의 형식(공통 응답 형식, 오류 형식, 페이지네이션 방식)을 처음 정하게 된다: 한 질문으로 묶는다

부른 커맨드가 그대로 질문으로 바꿀 수 있게 쓴다. 추천안을 첫 번째에 둔다.
이 목록은 계획서에 옮겨 쓰지 않는다. 답을 받은 것은 정의에 반영하고, 사용자가 보류한 것만 부른 커맨드가 정의의 해당 자리에 `(미결)`로 남긴다. (`workflow-do`가 계획서의 `미정`·`(미결)` 표시를 찾아 다시 묻기 때문이다)

```markdown
- [POST /api/v1/auth/login 오류] 잠긴 계정의 상태 코드가 정해지지 않았다 — 후보: 423(추천, 잠김을 구분) / 401(기존 클라이언트 수정 불필요)
```

## 5. 이어서 할 일

- 커맨드가 불렀으면, 위 결과를 가지고 **그 커맨드의 다음 절차로 돌아가 계속한다.** 이 skill로 작업이 끝나는 것이 아니다.
- 커맨드 없이 불렸으면 결과와 미정 사항을 대화에 보여 준다. 계획서에 반영하려면 `/workflow:workflow-plan`이나 `/workflow:workflow-plan-review`를 쓰라고 안내한다.
