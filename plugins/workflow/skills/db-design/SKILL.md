# db-design

DB 스키마 변경을 **설계**하거나 **점검**할 때 쓰는 기준과 결과 형식이다.

## 입력

```
$ARGUMENTS
```

- 모드: `설계`(기본) 또는 `점검`. 인자가 없으면 `설계`로 본다.
- `@경로`나 경로가 있으면 그 작업계획서를 대상으로 한다. 이미 대화에서 읽은 계획서면 다시 읽지 않는다.
- 커맨드가 이 파일을 Skill 도구 대신 직접 읽은 경우(위 입력 칸이 치환되지 않은 글자 그대로 보인다) 모드는 부른 커맨드가 정한다: `workflow-plan`은 `설계`, `workflow-plan-review`는 `점검`(계획 점검), `workflow-do`는 `점검`(구현 점검).

## 이 skill의 범위

이 skill은 절차가 아니라 **기준**이다. 불러온 쪽(커맨드나 사용자 요청)의 흐름 안에서 쓴다.

- 파일을 만들거나 고치지 않는다. 브랜치·커밋을 다루지 않는다. 완료 보고를 하지 않는다.
- 실제 DB에 접속하거나 마이그레이션을 실행하지 않는다.
- **커맨드가 불렀을 때**: 사용자에게 직접 묻지 않는다. 정해지지 않은 것은 `미정 사항`으로 모아 돌려준다. 질문, 결정 사항 기록, 계획서 작성은 부른 커맨드가 한다.
- **커맨드 없이 불렸을 때**(대화에 진행 중인 workflow 커맨드가 없음): 결과를 대화에 보여 주기만 한다. 미정 사항은 결과 끝에 목록으로 보여 준다.

## 1. 기존 관례 찾기 (설계 모드)

새로 정하기 전에 현재 프로젝트가 어떻게 하고 있는지 먼저 찾는다. 찾은 관례는 근거(`path:line`)와 함께 결과의 `따른 관례`에 적는다. 점검 모드는 이 단계를 하지 않고 계획서의 `따른 관례`를 재사용한다. (3번 참고)

**어디서 찾나**
- 마이그레이션: Flyway(`db/migration/V*__*.sql`), Liquibase(changelog), Prisma(`schema.prisma`, `migrations/`), Alembic(`versions/`), Django(`migrations/`), Rails(`db/migrate`), TypeORM·Knex(`migrations/`)
- DDL 파일(`schema.sql` 등), ORM 엔티티·모델(JPA `@Entity`, MyBatis mapper XML 등)
- DB 접속 설정(DBMS 종류와 버전)

**무엇을 찾나**
- DBMS 종류·버전, 마이그레이션 도구와 파일 이름·번호 규칙, 롤백 스크립트를 두는지
- 네이밍: 테이블(단수/복수, 접두어), 컬럼(snake_case 등), 인덱스·제약 이름
- PK 전략: 자동 증가 / 시퀀스 / UUID, 컬럼 이름과 타입
- 공통 컬럼: 생성·수정 일시, 생성·수정자, 삭제 표시(soft delete), 버전(낙관적 잠금)
- 타입 관례: 날짜·시각 타입과 타임존, 참/거짓 표현(`Y/N`, `TINYINT(1)`, `BOOLEAN`), 금액, 문자열 길이, 코드값(enum / 코드 테이블 / 문자열)
- FK 제약을 실제로 거는지(논리적 참조만 하는 프로젝트도 있다), 삭제 시 동작
- 문자셋·정렬 규칙

관례가 서로 다르면 가장 최근 마이그레이션과 다수를 따른다. 관례를 찾지 못하면 그 DBMS·ORM에서 흔히 쓰는 기본값을 제안하고 그대로 쓴다. 두 경우 모두 `따른 관례`에 근거(관례를 찾지 못했으면 `(기본값)`)와 함께 적는다. 이것만으로는 묻지 않는다. 묻는 기준은 `4. 결과 형식`의 `미정 사항`을 따른다.

## 2. 설계 모드

요구사항(과 선택한 설계안)에서 아래 순서로 정한다. 변경과 관계있는 단계만 한다. (예: 기존 테이블에 컬럼 하나 추가면 1·3·6·7만)

1. **데이터와 조회 패턴**: 무엇을 저장하는가. 어떤 조건으로 조회·정렬·집계하는가. 예상 건수와 증가 속도는. (인덱스와 타입 결정의 근거다)
2. **테이블**: 기존 테이블을 바꿀지 새 테이블을 만들지 정한다. 기존 테이블에 컬럼을 계속 붙이는 것보다 생명주기가 다른 데이터는 새 테이블이 낫다.
3. **컬럼**: 이름, 타입, NULL 허용, 기본값, 설명. 1번에서 찾은 관례(공통 컬럼 포함)를 따른다.
4. **제약**: PK, FK(참조 대상과 삭제 시 동작), UNIQUE(업무상 중복 불가 조건), CHECK
5. **인덱스**: 1번의 조회 패턴마다 필요한 인덱스를 도출한다.
   - WHERE·JOIN·ORDER BY에 쓰는 컬럼, 복합 인덱스의 컬럼 순서(선택도가 높고 등치 조건인 컬럼 먼저)
   - 기존 인덱스로 이미 되는지, 중복 인덱스가 아닌지
   - 쓰기가 많은 테이블에 인덱스를 늘리는 비용
6. **마이그레이션**
   - 파일 이름·번호(관례), 실행 순서
   - 롤백 방법: 롤백 SQL 또는 되돌릴 수 없는 이유(컬럼 삭제, 데이터 변환 등)
   - 기존 데이터: 기존 행에 넣을 값, 이관(백필) 방법과 건수가 많을 때 나누어 처리할지
   - NOT NULL 컬럼 추가: 기본값을 주거나, `NULL 허용으로 추가 → 값 채우기 → NOT NULL 변경` 순서로 나눈다
   - 운영 중 잠금: 큰 테이블의 `ALTER`, 인덱스 생성이 쓰기를 막는지와 온라인 옵션
   - 배포 순서: 스키마와 코드가 동시에 바뀌지 않아도 동작하는가. 컬럼 삭제·이름 변경·타입 변경은 `새 구조 추가 → 코드 전환 → 옛 구조 제거`로 나눈다
   - 적용 확인: 운영과 데이터 규모가 비슷한 환경(스테이징 등)에 먼저 적용해 소요 시간과 잠금을 확인할지
   - 롤백 기준: 적용 후 어떤 상황이면 롤백할지 (마이그레이션 실패, 이관 건수 불일치, 관련 기능의 오류 증가 등)
7. **영향받는 코드**: 엔티티·모델, 매퍼·쿼리, 리포지토리, 테스트 데이터(fixture·seed), 이 테이블을 읽는 배치·리포트

**돌려줄 것**
- `### DB 변경` 초안 (아래 결과 형식)
- 미정 사항 목록
- 작업항목 후보: 마이그레이션은 다른 항목과 나누고 `(단독 커밋)`을 붙이도록 표시한다. 이관·롤백 검증도 항목으로 낸다.
- 완료 기준 후보(마이그레이션 적용·롤백 확인, 기존 데이터 건수 대조 등)와 리스크(잠금, 되돌릴 수 없는 변경, 배포 순서, 스테이징 먼저 적용, 롤백 기준)

## 3. 점검 모드

**관례는 처음부터 다시 찾지 않는다.** 계획서 `### DB 변경`의 `따른 관례`를 기준으로 쓰고, 적힌 근거 위치를 열어 아직 그대로인지만 확인한다. `따른 관례`가 없거나(예전 계획서) 근거가 바뀌었거나 사라진 항목만 1번대로 찾는다. 계획 점검에서 `따른 관례`가 실제 코드와 다르면 그것도 지적한다.

대상은 둘 중 하나다. 부른 쪽이 정한다.
- **계획 점검**: 계획서의 `### DB 변경`을 요구사항·현재 스키마와 대조한다.
- **구현 점검**: 구현된 마이그레이션·엔티티를 계획서의 `### DB 변경`과 대조한다.

| 점검 | 볼 것 |
|------|-------|
| 정의 누락 | DB가 바뀌는 계획인데 `### DB 변경`이 없다. 요구사항에 필요한 테이블·컬럼이 표에 없다 |
| 관례 | 네이밍, PK, 공통 컬럼, 타입 표현이 1번에서 찾은 관례와 다르다 |
| 제약 | PK·FK·UNIQUE가 빠졌다. NULL 허용과 기본값이 업무 규칙과 맞지 않는다 |
| 인덱스 | 조회 패턴에 맞는 인덱스가 없다. 기존 인덱스와 중복된다. 근거 없는 인덱스가 있다 |
| 마이그레이션 | 롤백 방법이 없다. 기존 데이터 처리가 없다. NOT NULL 추가·큰 테이블 변경의 잠금 대책이 없다. 배포 순서가 코드와 맞지 않는다 |
| 작업항목 연결 | 표의 변경 중 작업항목이 다루지 않는 것이 있다. 마이그레이션 항목에 `(단독 커밋)`이 없다 |
| 구현 일치 (구현 점검) | 마이그레이션·엔티티의 테이블·컬럼·타입·NULL·기본값·제약·인덱스가 표와 다르다. 표에 없는 스키마 변경이 있다 |

**돌려줄 것**: 지적 목록과 미정 사항. 지적이 없으면 `지적 없음`.

```markdown
| # | 점검 | 심각도 | 지적 | 근거 | 제안 |
|---|------|--------|------|------|------|
| 1 | 인덱스 | 중간 | `login_attempt`를 `member_id`로 조회하는데 인덱스가 없다 | `LoginService.java:42` | `idx_login_attempt_member_id` 추가 |
```

심각도: 높음(데이터 손실·운영 장애 위험, 되돌릴 수 없음) / 중간(성능·정합성 문제) / 낮음(관례·표기)

## 4. 결과 형식

### `### DB 변경` (계획서 `4. 영향 범위` 아래 하위 섹션)

섹션 제목은 `### DB 변경` 그대로 쓴다. 다른 커맨드가 이 제목으로 찾는다.

**변경 규모에 맞게 쓴다.** 아래 예시는 가장 큰 경우의 형식이다.
- 해당 없는 표·줄은 빼고, 빈 표를 남기지 않는다.
- 기존 테이블에 컬럼 몇 개를 추가·변경하는 정도면 `따른 관례` 줄, 그 테이블의 변경 표, 마이그레이션 표만 쓴다. DBMS 줄과 인덱스 표는 바뀌는 것이 있을 때만 쓴다.
- `erDiagram`은 새 테이블이 둘 이상이고 서로 관계가 있을 때만 넣는다.
- `따른 관례`는 줄이지 않는다. 이 설계에 쓴 관례를 근거(`path:line`, 기본값이면 `(기본값)`)와 함께 모두 적는다. 점검 모드가 이 줄을 재사용한다.

```markdown
### DB 변경

- DBMS / 마이그레이션 도구: MySQL 8 / Flyway (`src/main/resources/db/migration`)
- 따른 관례: snake_case, PK `id BIGINT AUTO_INCREMENT`, 공통 컬럼 `created_at`·`updated_at` (`V12__create_member.sql:3`)

#### 테이블 `login_attempt` (신규)
| 컬럼 | 타입 | NULL | 기본값 | 제약 | 설명 |
|------|------|------|--------|------|------|
| id | BIGINT | N | AUTO_INCREMENT | PK | |
| member_id | BIGINT | N | - | FK → member.id (삭제 시 CASCADE) | 회원 |
| failed_at | DATETIME | N | CURRENT_TIMESTAMP | | 실패 시각 |

| 인덱스 | 컬럼 | 종류 | 근거 (조회 패턴) |
|--------|------|------|------------------|
| idx_login_attempt_member_failed | member_id, failed_at | 일반 | 회원별 최근 실패 조회 |

#### 테이블 `member` (변경)
| 변경 | 컬럼 | 타입 | NULL | 기본값 | 제약 | 설명 |
|------|------|------|------|--------|------|------|
| 추가 | locked_at | DATETIME | Y | NULL | | 잠금 시각. NULL이면 잠기지 않음 |

#### 마이그레이션
| 순서 | 파일 | 내용 | 롤백 | 기존 데이터 | 잠금·배포 주의 |
|------|------|------|------|-------------|----------------|
| 1 | `V13__add_member_locked_at.sql` | member.locked_at 추가 | `ALTER TABLE member DROP COLUMN locked_at` | 기존 행은 NULL | NULL 허용 추가라 잠금 짧음. 코드보다 먼저 배포 |
```

- 테이블이 둘 이상이고 관계가 있으면 Mermaid `erDiagram`을 함께 넣는다.
- 변경 종류는 `추가` / `변경` / `삭제`로 쓴다. `변경`은 설명에 `이전 → 이후`를 적는다.

### 미정 사항

코드·요구사항·관례(또는 기본값)로 정할 수 없고, 아래 중 하나에 해당하는 것만 넣는다. 네이밍·타입 길이처럼 관례나 기본값으로 정할 수 있는 것은 넣지 않는다.
- 되돌리기 어렵다: 기존 테이블·컬럼의 삭제·이름 변경·타입 변경, 기존 데이터 변경·이관
- 업무 규칙이다: 중복 허용 여부(UNIQUE), 함께 삭제할지(FK 삭제 시 동작), 보관 기간, 필수 여부
- 다른 팀·시스템에 영향을 준다: 이 테이블을 읽는 배치·리포트·다른 서비스
- 관례가 없어서 이 계획이 프로젝트 전체의 형식(PK 전략, 공통 컬럼)을 처음 정하게 된다: 한 질문으로 묶는다

부른 커맨드가 그대로 질문으로 바꿀 수 있게 쓴다. 추천안을 첫 번째에 둔다.
이 목록은 계획서에 옮겨 쓰지 않는다. 답을 받은 것은 정의에 반영하고, 사용자가 보류한 것만 부른 커맨드가 정의의 해당 자리에 `(미결)`로 남긴다. (`workflow-do`가 계획서의 `미정`·`(미결)` 표시를 찾아 다시 묻기 때문이다)

```markdown
- [member.locked_at] 잠금 해제 방식이 정해지지 않았다 — 후보: 시간 경과 후 자동 해제(추천, 운영 부담 없음) / 관리자 수동 해제
```

## 5. 이어서 할 일

- 커맨드가 불렀으면, 위 결과를 가지고 **그 커맨드의 다음 절차로 돌아가 계속한다.** 이 skill로 작업이 끝나는 것이 아니다.
- 커맨드 없이 불렸으면 결과와 미정 사항을 대화에 보여 준다. 계획서에 반영하려면 `/workflow:workflow-plan`이나 `/workflow:workflow-plan-review`를 쓰라고 안내한다.
