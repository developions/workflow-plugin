# ui-design

화면 변경을 **설계**하거나 **점검**할 때 쓰는 기준과 결과 형식이다. 시각 디자인(색, 크기, 배치)은 다루지 않는다. 사용자가 무엇을 보고, 무엇을 입력·클릭하고, 그 결과 무엇이 나타나는지를 usecase로 검증할 수 있는 수준으로 정한다.

## 입력

```
$ARGUMENTS
```

- 모드: `설계`(기본), `점검 계획`, `점검 구현`. 인자가 없으면 `설계`, `점검`만 있으면 `점검 계획`으로 본다.
  - `점검 계획`: 계획서의 정의를 요구사항·현재 화면 코드와 대조한다. (`workflow-plan-review`가 쓴다)
  - `점검 구현`: 구현 결과를 계획서의 정의와 대조한다. (`workflow-do`가 쓴다)
- `@경로`나 경로가 있으면 그 작업계획서를 대상으로 한다. 이미 대화에서 읽은 계획서면 다시 읽지 않는다.
- 커맨드가 이 파일을 Skill 도구 대신 직접 읽은 경우(위 입력 칸이 치환되지 않은 글자 그대로 보인다) 모드는 그 커맨드가 Skill 도구에 넘기려던 인자다.

## 이 skill의 범위

이 skill은 절차가 아니라 **기준**이다. 불러온 쪽(커맨드나 사용자 요청)의 흐름 안에서 쓴다.

- 파일을 만들거나 고치지 않는다. 브랜치·커밋을 다루지 않는다. 완료 보고를 하지 않는다.
- 브라우저를 열거나 서버에 요청을 보내지 않는다. (화면 실행 검증은 `workflow-usecase-do`가 한다)
- **커맨드가 불렀을 때**: 사용자에게 직접 묻지 않는다. 정해지지 않은 것은 `미정 사항`으로 모아 돌려준다. 질문, 결정 사항 기록, 계획서 작성은 부른 커맨드가 한다.
- **커맨드 없이 불렸을 때**(대화에 진행 중인 workflow 커맨드가 없음): 결과를 대화에 보여 주기만 한다. 미정 사항은 결과 끝에 목록으로 보여 준다.
- 요구사항에 화면 설계서·시안(이미지, 링크)이 있으면 그것을 기준으로 삼고 근거로 적는다. 시안이 정하지 않은 동작(검증, 메시지, 상태)만 이 기준으로 채운다.

## 1. 기존 관례 찾기 (설계 모드)

새로 정하기 전에 현재 프로젝트가 어떻게 하고 있는지 먼저 찾는다. 찾은 관례는 근거(`path:line`)와 함께 결과의 `따른 관례`에 적는다. 점검 모드는 이 단계를 하지 않고 계획서의 `따른 관례`를 재사용한다. (3번 참고) 설계 모드라도 계획서에 이 정의의 `따른 관례`가 이미 있으면(정의를 다시 쓸 때) 처음부터 찾지 않고, 점검 모드처럼 근거 위치만 열어 확인하고 재사용한다. 새 설계에 필요한데 그 줄에 없는 관례(예: 처음 만드는 목록 화면의 빈 목록 표시)만 아래대로 찾는다.

**어디서 찾나**
- 라우팅: 라우터 설정(`routes.tsx`, `router/index.js` 등), 파일 기반 라우트(`pages/`, `app/`), 서버 템플릿 컨트롤러 매핑
- 비슷한 기존 화면: 같은 종류(목록, 상세, 등록 폼, 모달)의 가장 최근 화면
- 공통 컴포넌트·디자인 시스템(버튼, 입력, 모달, 토스트, 테이블), 레이아웃·메뉴 설정
- 폼과 검증 라이브러리, 메시지·다국어 리소스(`locales/`, `messages*.properties` 등)
- 권한별 노출 처리(권한 컴포넌트, 디렉티브, 서버 템플릿 조건), API 호출 모듈

**무엇을 찾나**
- 화면 기술(React, Vue, Thymeleaf, JSP 등)과 라우트 경로 규칙(kebab-case, 복수형, 상세 경로 `/{id}`)
- 화면 종류별 구성: 목록(검색 조건, 페이지네이션, 정렬), 등록·수정(페이지 / 모달), 삭제 확인 방식
- 입력 검증: 어디서 검증하는지(입력 중 / 제출 시 / 서버 응답), 오류 표시 위치(필드 아래, 상단 요약, 토스트)
- 메시지: 문구를 리소스 키로 두는지 하드코딩하는지, 문구 어조(`~하세요` / `~해 주세요`)
- 결과 알림: 성공·실패를 토스트 / alert / 화면 이동 중 무엇으로 알리는지, 확인 창(dialog) 방식과 어떤 동작에 확인 창을 띄우는지(삭제만 / 모든 변경 등)
- 상태 표시: 로딩(스피너, 스켈레톤, 버튼 비활성), 빈 목록, 오류(재시도)
- 권한: 권한 없는 요소를 숨기는지 비활성화하는지, 권한 없는 경로 접근 시 처리
- 요소 이름: 버튼·입력에 보이는 라벨이 있는지, 아이콘만 있는 버튼의 `aria-label` (usecase가 role과 이름으로 요소를 찾는다)

관례가 서로 다르면 가장 최근 화면과 다수를 따른다. 관례를 찾지 못하면 그 화면 기술에서 흔히 쓰는 기본값을 제안하고 그대로 쓴다. 두 경우 모두 `따른 관례`에 근거(관례를 찾지 못했으면 `(기본값)`)와 함께 적는다. 이것만으로는 묻지 않는다. 묻는 기준은 `4. 결과 형식`의 `미정 사항`을 따른다.

## 2. 설계 모드

계획서(또는 대화)에 `### API 변경` 정의가 있으면 **먼저 읽는다.** 화면이 부르는 API, 입력 검증 규칙, 오류 코드별 메시지를 그 정의와 맞춘다. API도 바뀌는데 정의가 아직 없으면 `workflow:api-design`을 먼저 하도록 부른 쪽에 알린다. (DB·API·화면이 함께 바뀌면 db → api → ui 순서다)

요구사항(과 선택한 설계안)에서 아래 순서로 정한다. 변경과 관계있는 단계만 한다. (예: 기존 화면에 버튼 하나와 확인 메시지 추가면 2·5·9만)

1. **화면 목록**: 경로, 화면 이름, 신규/변경/삭제, 진입 경로(메뉴, 버튼, 링크), 접근 권한
2. **요소**: 사용자가 보고 조작하는 요소를 `role "이름"`으로 적는다. (예: `button "저장"`, `textbox "이메일"`, `combobox "구분"`, `link "상세"`, `columnheader "가입일"`) 이름은 화면에 보이는 라벨·텍스트 그대로 쓴다. 보이는 라벨이 없는 요소(아이콘 버튼 등)는 접근 가능한 이름(`aria-label`)을 정한다.
   - role과 이름은 usecase가 쓰는 Playwright 접근성 스냅샷 기준이다. `password`·`email`·`text` 입력은 `textbox`, `number` 입력은 `spinbutton`이다. `<label>`이 없으면 `placeholder`가 이름이 된다. (예: `<input type="password" placeholder="비밀번호">` → `textbox "비밀번호"`)
   - role이 없는 요소(클릭 처리만 붙은 `div`·`span` 등)는 스냅샷에서 `generic`이라 role로 찾을 수 없다. 기존 요소는 `text "보이는 텍스트"`로 적는다. 새로 만드는 요소는 `button`·`link`처럼 role이 있는 요소로 정한다.
3. **입력 검증**: 필드마다 필수 여부, 형식·길이·범위, 검증 시점, 오류 문구와 표시 위치. API의 요청 검증 규칙과 맞춘다. (화면만 느슨하거나 화면만 엄격하지 않게)
4. **동작·이동**: 요소를 조작하면 무엇이 일어나는가. 부르는 API(`### API 변경`의 번호), 성공 시 결과(이동할 경로, 갱신되는 목록, 성공 문구), 실패 시 결과(오류 코드별 문구). 되돌리기 어려운 동작(삭제, 발송, 결제)은 확인 창 문구와 버튼 이름을 정한다.
5. **메시지**: 사용자에게 보이는 문구를 상황별로 모은다. (성공, 실패, 확인, 안내) 문구는 화면에 나올 그대로 쓴다. 다국어 리소스를 쓰는 프로젝트면 리소스 키도 적는다.
6. **상태**: 로딩 중, 빈 목록, 조회 실패, 처리 중(중복 클릭 방지)에 무엇이 보이는가
7. **권한별 노출**: 역할마다 보이는 요소·숨는 요소·비활성 요소. 권한 없이 경로에 직접 들어오면 어떻게 되는가. API의 권한과 맞춘다. (화면에서 숨겨도 API 권한 검사는 따로 있어야 한다)
8. **기존 화면 변경 시 영향**: 같은 공통 컴포넌트·메뉴·리소스를 쓰는 다른 화면, 경로가 바뀌면 그 경로로 들어오는 링크·북마크·외부 링크
9. **영향받는 코드**: 라우트, 화면·컴포넌트, 메뉴 설정, 메시지 리소스, API 호출 모듈, 화면 테스트

**돌려줄 것**
- `### 화면 변경` 초안 (아래 결과 형식)
- 미정 사항 목록
- 작업항목 후보: 화면 단위로 나누고, 라우트·메뉴 등록, 메시지 리소스, 권한별 노출, 화면 테스트도 항목으로 낸다.
- 완료 기준 후보: 화면별 정상 흐름과 주요 오류 메시지 확인. 화면 확인 기준이므로 `workflow-usecase-plan` → `workflow-usecase-do`로 검증한다고 표시한다.
- 리스크 후보: 공통 컴포넌트 변경의 다른 화면 영향, 경로 변경, 권한 노출과 API 권한 불일치

## 3. 점검 모드

**관례는 처음부터 다시 찾지 않는다.** 계획서 `### 화면 변경`의 `따른 관례`를 기준으로 쓰고, 적힌 근거 위치를 열어 아직 그대로인지만 확인한다. `따른 관례`가 없거나(예전 계획서) 근거가 바뀌었거나 사라진 항목만 1번대로 찾는다. 계획 점검에서 `따른 관례`가 실제 코드와 다르면 그것도 지적한다.

대상은 인자로 정한다.
- **계획 점검**(`점검 계획`): 계획서의 `### 화면 변경`을 요구사항·현재 화면 코드·`### API 변경`과 대조한다. 아래 표에서 `구현 일치`를 뺀 모든 행을 본다.
- **구현 점검**(`점검 구현`): 구현된 라우트·화면·메시지 리소스를 계획서의 `### 화면 변경`과 대조한다. `관례`와 `구현 일치` 행만 본다. 부른 쪽이 작업항목을 알려 주면 그 항목이 다루는 정의만 보고, 아직 구현하지 않은 정의는 지적하지 않는다. 화면을 실제로 띄워 보는 검증은 하지 않는다. (usecase가 한다)

| 점검 | 볼 것 |
|------|-------|
| 정의 누락 | 화면이 바뀌는 계획인데 `### 화면 변경`이 없다. 요구사항에 필요한 화면·요소·메시지가 표에 없다 |
| 관례 | 경로, 검증 표시, 결과 알림, 메시지 관리, 권한 노출 방식이 `따른 관례`와 다르다 |
| 요소 식별 | 요소가 `role "이름"`이 아니다. (role이 없는 기존 요소의 `text "..."`는 괜찮다. 새로 만드는 요소가 role 없는 `div`면 지적한다) 같은 화면에 같은 role·이름이 둘 이상 있어 구분할 수 없다. 아이콘 버튼에 접근 가능한 이름이 없다 |
| 입력 검증 | 필수·형식 규칙이나 오류 문구가 없다. API 요청 검증 규칙과 다르다 |
| 동작·메시지 | 조작 결과(이동, 문구)가 없다. API 오류 코드에 대응하는 문구가 없다. 되돌리기 어려운 동작에 확인 창이 없다 |
| 상태 | 로딩·빈 목록·조회 실패·중복 클릭 처리가 빠졌다 |
| 권한 | 역할별 노출이 정해지지 않았다. API 권한과 다르다. 권한 없는 직접 접근 처리가 없다 |
| API 연결 | 화면이 부르는 API가 `### API 변경`이나 기존 코드에 없다 |
| 검증 가능성 | 요소 이름·문구·이동 경로가 구체적이지 않아 usecase의 대상·기대결과로 쓸 수 없다 |
| 작업항목 연결 | 표의 화면·요소 중 작업항목이 다루지 않는 것이 있다. 메뉴·리소스·권한 처리 항목이 없다 |
| 구현 일치 (구현 점검) | 경로·요소 이름·검증 규칙·문구·이동·권한 노출이 표와 다르다. 표에 없는 화면이나 요소가 생겼다 |

**돌려줄 것**: 지적 목록과 미정 사항. 지적이 없으면 `지적 없음`.

```markdown
| # | 점검 | 심각도 | 지적 | 근거 | 제안 |
|---|------|--------|------|------|------|
| 1 | 동작·메시지 | 중간 | 423 ACCOUNT_LOCKED 응답일 때 보여 줄 문구가 없다 | `### API 변경` 1번 | `alert "계정이 잠겼습니다. 30분 뒤 다시 시도하세요."` 추가 |
```

심각도: 높음(권한 없는 사용자에게 기능이 노출됨, 되돌리기 어려운 동작에 확인 없음, 기존 화면이 깨짐) / 중간(검증·메시지·상태 누락, usecase로 검증할 수 없음) / 낮음(관례·표기)

## 4. 결과 형식

### `### 화면 변경` (계획서 `4. 영향 범위` 아래 하위 섹션)

섹션 제목은 `### 화면 변경` 그대로 쓴다. 다른 커맨드가 이 제목으로 찾는다. `### DB 변경`·`### API 변경`이 있으면 그 뒤에 둔다.

**변경 규모에 맞게 쓴다.** 아래 예시는 가장 큰 경우의 형식이다.
- 해당 없는 표·줄은 빼고, 빈 표를 남기지 않는다.
- 신규 화면은 요소·메시지 표를 모두 쓴다. 기존 화면 변경은 바뀐 요소·문구만 쓰고 `(추가)`, `(변경: 이전 → 이후)`, `(삭제)`를 붙인다.
- 화면 사이 이동이 여러 단계로 얽힐 때만 Mermaid `flowchart`를 넣는다.
- `따른 관례`는 줄이지 않는다. 이 설계에 쓴 관례를 근거(`path:line`, 기본값이면 `(기본값)`)와 함께 모두 적는다. 찾아봤지만 없는 것은 `<항목> 없음 (찾은 범위)`로 적는다. (예: `다국어 리소스 없음 (문구는 JS에 직접 씀)`) 점검 모드가 이 줄을 재사용한다.
- 요소 이름과 문구는 화면에 나올 그대로 쓴다. `workflow-usecase-plan`이 이 값을 usecase 단계의 대상·기대결과로 그대로 옮긴다.


### 미정 사항

코드·요구사항·시안·관례(또는 기본값)로 정할 수 없고, 아래 중 하나에 해당하는 것만 넣는다. 오류 표시 위치·로딩 표시처럼 관례나 기본값으로 정할 수 있는 것은 넣지 않는다.
- 되돌리기 어렵다: 이미 쓰이는 화면 경로의 변경·삭제(북마크, 외부 링크, 메일 속 링크), 화면 삭제
- 업무 규칙이다: 누가 보고 쓸 수 있는가(권한별 노출), 되돌리기 어려운 동작(삭제, 발송, 결제, 취소)에 확인을 받을지, 정책·법적 의미가 있는 문구(약관, 개인정보, 결제 안내)
  - 확인 창: 프로젝트에 확인 창 관례가 있으면(어떤 동작에 확인을 받는지, `1. 기존 관례 찾기`) 따르고 넣지 않는다. 되돌리기 쉬운 동작(잠금 해제, 숨김 해제 등)은 확인 창 없이가 기본값이다. 관례가 없는데 되돌리기 어려운 동작일 때만 넣는다.
- 다른 팀·화면에 영향을 준다: 공통 컴포넌트·디자인 시스템·공통 메뉴 변경
- 관례가 없어서 이 계획이 프로젝트 전체의 형식(결과 알림 방식, 검증 표시 방식)을 처음 정하게 된다: 한 질문으로 묶는다
- 요구사항이 화면 구성 자체를 정하지 않았다: 같은 기능을 페이지 / 모달 / 기존 화면의 탭 중 어디에 둘지처럼 사용자가 보는 흐름이 달라지는 선택
- 요구사항이나 부른 쪽의 결정이 정하지 않은 사용자 동작이다: 입력 요소끼리 연동할지(한 입력을 고르면 다른 입력을 채우거나 제한할지), 자동 채움, 목록·표시를 언제 갱신할지처럼 정하는 방식에 따라 사용자가 하는 일이 달라지는 것. "하지 않음"을 기본값으로 정하면 기능이 범위에서 빠지므로 기본값으로 정하지 않는다

부른 커맨드가 그대로 질문으로 바꿀 수 있게 쓴다. 추천안을 첫 번째에 둔다.
이 목록은 계획서에 옮겨 쓰지 않는다. 답을 받은 것은 정의에 반영하고, 사용자가 보류한 것만 부른 커맨드가 정의의 해당 자리에 `(미결)`로 남긴다. (`workflow-do`가 계획서의 `미정`·`(미결)` 표시를 찾아 다시 묻기 때문이다)

```markdown
- [주문 상세 "주문 취소"] 취소는 되돌릴 수 없는데 프로젝트에 확인 창 관례가 없다 — 후보: 확인 창(추천, 실수로 누른 경우 방지) / 바로 취소
```

## 5. 이어서 할 일

- 커맨드가 불렀으면, 위 결과를 가지고 **그 커맨드의 다음 절차로 돌아가 계속한다.** 이 skill로 작업이 끝나는 것이 아니다.
- 커맨드 없이 불렸으면 결과와 미정 사항을 대화에 보여 준다. 계획서에 반영하려면 `/workflow:workflow-plan`이나 `/workflow:workflow-plan-review`를 쓰라고 안내한다.
